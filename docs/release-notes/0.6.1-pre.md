# satd 0.6.1

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.6.1 is a patch release on the 0.6 line, cut from the `release/0.6`
branch. It carries fixes for 0.6.0.

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- **A refused watch add is reported to the client.** The streaming server used
  to drop a watch add it refused without telling the client; it now answers
  with a `WatchAddRejected` event. See
  [below](#a-refused-watch-add-is-reported-to-the-client).
- **An interrupted `-reindex` continues where it stopped.** A full reindex
  that is stopped, killed or loses power continues on the next start, any
  start, from the height it had flushed, instead of starting over. See
  [below](#an-interrupted--reindex-continues-where-it-stopped).
- **A stop signal stops a rebuild cleanly.** SIGTERM or SIGINT during
  `-reindex`, `-reindex-chainstate` or `-upgradechainstate` now stops the
  replay at the last block it connected, flushed, and satd exits 0, including as PID 1
  of a container with no init. See
  [below](#a-stop-signal-during-a-rebuild-stops-it-cleanly).

- **Sigops are counted as Bitcoin Core counts them.** satd's counter scored
  some P2SH and P2WSH scripts lower than Core for the block sigop limit,
  mempool policy and block templates. See
  [below](#sigops-are-counted-as-bitcoin-core-counts-them).
- **Header sync continues from a peer's last header.** A node whose best
  header chain was on a competing branch could stop syncing headers from a
  peer whose chain forked below it. See
  [below](#header-sync-continues-from-a-peers-last-header).
- **Electrum desktop no longer reconnects in a loop.** The scripthash status
  now hashes the history in the order `get_history` returns it, so an address
  with a pending transaction shows it. See
  [below](#electrum-status-hashes-follow-history-order).
- **A full mempool checks scripts before it evicts.** An incoming
  transaction's scripts are checked before anything is evicted for it, and
  eviction no longer scales with the size of the pool. See
  [below](#a-full-mempool-checks-scripts-before-it-evicts).
- **Blocks that fail to connect from storage are marked invalid.** The IBD
  connector no longer retries a failing stored block and restarts sync onto
  it. See
  [below](#blocks-that-fail-to-connect-from-storage-are-marked-invalid).
## Streaming Consumption API

### A refused watch add is reported to the client

The streaming docs said an over-quota watch add was rejected with
`RESOURCE_EXHAUSTED` on gRPC or `429` on WebSocket. The server sent neither: an
incremental `Add*` it refused was logged on the node and dropped, and the client
was never told. A wallet that hit its quota could believe it was watching an
address and miss a payment to it.

The server now answers every incremental add it does not register with one
`WatchAddRejected` event on the `Watch` stream (`watch_add_rejected` on
WebSocket). It names the kind of add, the reason, the numbers behind it and the
refused items; none of those items is watched. An add that registers still gets
no event.

| Reason | When |
|---|---|
| `QUOTA_EXCEEDED` | the items do not fit the token's watch quota; carries the units required, held and allowed |
| `RATE_LIMITED` | the token's per-add rate limit is spent; carries a retry-after hint |
| `CAP_EXCEEDED` | a per-connection cap: 16 silent-payment targets, 256 descriptors, or `streamwsmaxsubscriptions` |
| `PERMISSION_DENIED` | the token lacks `stream:watch` |
| `MALFORMED` | the message cannot be applied as a whole, such as an invalid descriptor |

Both SDKs decode the event (Rust `Event::WatchAddRejected`, Go
`*WatchAddRejected`). `ResilientWatch` re-sends a rate-limited add itself once the
limit allows, within its backoff budget. Any other refusal, or a rate limit past
the budget, drops the refused items from its mirror, so a reconnect no longer
re-sends adds the server refused; a refused descriptor slide falls back to the
window the server kept.

Two adds that grow nothing are no longer refused. A silent-payment add that only
updates the labels of targets already watched is applied without spending a
per-add rate token, and on WebSocket an add that only re-asserts items already
watched is no longer shed when the connection is at `streamwsmaxsubscriptions`.

The event is an additive schema change (`NodeEvent` tag 32): an older SDK ignores
it, and an older server never sends it.

## Consensus and validation

### Sigops are counted as Bitcoin Core counts them

satd now counts signature operations exactly as Bitcoin Core does: for the
block sigop limit, the mempool's per-transaction sigop cost, block templates,
`getblocktemplate`'s `sigops` field, and the policy rules that read
`tx.sigops_cost`. Earlier versions used rust-bitcoin's counter, which counted
some P2SH redeem scripts and P2WSH witness scripts lower than Core does: an
`OP_CHECKMULTISIG` that follows another signature opcode.

Parents admitted through `submitpackage` without a fee check now carry their
real sigop cost and prevout data, so block templates count their sigops and
streaming spend matchers see their spends (#937).

### The Rust script engine has Core's OP_SUCCESS set

The Rust script engine now treats `OP_LEFT`, `OP_RIGHT`, `OP_INVERT`,
`OP_AND`, `OP_OR` and `OP_XOR` (0x80, 0x81, 0x83–0x86) as `OP_SUCCESSx` in
tapscript, as Bitcoin Core does. Before, it failed a tapscript leaf containing
one of them, where Core accepts the leaf. This affected `-consensus=rust`,
`-consensus=cpp-shadow` and `satd-chainstate-repair`, where the Rust engine's
verdict is used. The default `rust-shadow` mode decided with
libbitcoinconsensus and logged a shadow mismatch.

The Rust engine now also runs the taproot rows of Core's script tests and
Core's taproot script-asset vectors, and exempts pay-to-anchor spends from the
upgradable-witness-program policy check as Core does (#933).

### A block body that fails its own checks is not marked invalid

Blocks that fail the context-free block checks (Core's `CheckBlock`: merkle
root, size, coinbase position, legacy sigop limit) are no longer marked
invalid, as in Bitcoin Core: such a body may simply not be the block its header
names. An empty block body is now checked against the header's merkle root
first. Before, a body that did not match its header could, in some arrival
orders, leave a valid block marked invalid until `reconsiderblock` was run.

A block that extends the tip without its header having arrived first, and then
fails validation, is now recorded as invalid, so a second copy is refused
without being validated or stored again (#936).

### Signet commitments, median-time-past and malformed nBits

On signet, satd now rebuilds the signed coinbase commitment exactly as Bitcoin
Core does, so blocks whose witness commitment contains an empty
`OP_PUSHDATA1/2/4`, or ends in a push that does not parse, are judged as Core
judges them.

If the block index is missing a block inside a median-time-past window, satd
now stops connecting with a storage error instead of computing the median from
fewer blocks, and does not mark the block invalid. The work of a block with
malformed `nBits` is now zero, as in Core (#948).

## Chain, sync and reindex

### Every block that reaches the tip is reported

satd connects a block it already holds once its parent becomes the tip, through
a drain that runs every half second. Two things leave a block there: a block
that arrived before its parent, and the stored blocks an initial-sync batch can
leave behind when it ends. The drain connected the block and told nothing that
watches for new blocks:

- `-blocknotify` did not run for it;
- it was not announced to peers;
- Electrum `blockchain.headers.subscribe` and scripthash subscribers, Esplora's
  `/blocks/sse`, the streaming API and the ZMQ `hashblock` topic never saw it,
  so a wallet learned of a confirmation in that block only at the next one.

The drain now emits the same `BlockConnected` event as every other connect that
extends the tip, after the mempool has dropped the block's transactions (#900).
The connector used during initial sync still emits none, as before.

### satd stops on a chainstate read error

satd now stops, as Bitcoin Core does, when its chainstate database cannot read
a coin: an I/O error, a checksum mismatch, or a coin record that does not
decode. It logs `Error reading from database, shutting down`. Before, satd
treated such a coin as spent. If a valid block spent that coin, satd refused
the block and recorded it as invalid, and that record survived restarts.

After such a stop, the next start replays the blocks after the last flush. If
the error comes back, check the disk and rebuild with `-reindex-chainstate`
(#945).

### Header sync continues from a peer's last header

After a full batch of headers, satd now asks the peer for more starting from
the last header that peer sent, as Bitcoin Core does. Before, a node whose
best header chain was on a competing branch could stop asking a peer whose
chain forked below it for headers, and so fail to sync to the chain with the
most work.

The first block of a difficulty period is now found on the block's own
branch, so a block on a branch that forked before the period starts is judged
against that branch. Headers and blocks must also claim a target within the
network's proof-of-work limit, which on signet bounds the work behind each
header (#954).

### Blocks that fail to connect from storage are marked invalid

When a block failed validation while being connected from storage, during
initial sync or while catching up, satd did not record it as invalid. The IBD
connector retried the same block and restarted sync onto it until a better
chain appeared. satd now marks such a block invalid, as Bitcoin Core does, and
moves on.

After any block fails to connect, the header tip `getblockchaininfo` reports
in `headers` now leaves that block's branch. A chain with more work made of
blocks below the failed one is now activated at once, instead of when the next
block arrives (#957).

### A block submitted before its parent connects with it

A block passed to `submitblock` before its parent's block was stored to wait
for the parent, but its header did not become the best header. When the
parent arrived and connected, nothing connected the child: it stayed
`valid-headers` in `getchaintips`, and `headers` in `getblockchaininfo` did
not count it, until another block or header arrived. satd now indexes the
header of a block it stores, as Bitcoin Core does for every block it accepts,
so the child is the best header as soon as it is stored and connects within
half a second of its parent. Peers announce headers before blocks, so P2P
sync was not affected; pools and test harnesses that submit blocks out of
order were (#922).

## Initial block download

### A block stuck with a slow peer is asked of another again

satd downloads blocks from many peers at once and connects them in height
order. When the block it needs next has been with one peer for 15 seconds, the
network loop's periodic pass takes it back and asks another peer. That pass also
notices peers that have stopped delivering, and gives idle peers work.

In 0.6.0 that pass hardly ran during initial sync. The loop takes arriving
blocks off its queue in batches, and a change in 0.6.0 let a full queue put the
pass off until the queue had room, which during initial sync it never has. The
block the sync needed next could wait up to a minute on one slow peer while tens
of thousands of later blocks sat downloaded behind it.

The pass now runs every half second however busy the queue is, at most one
batch late (#909). We timed two-minute fresh mainnet syncs on a disk with slow
flushes (about 9 ms each), nine with 0.6.0 and six with this fix:

- 0.6.0 never released a stuck block, and five of its nine runs waited more than
  50 seconds on a single block.
- With the fix the pass ran about every 0.7 seconds and released a stuck block
  15 to 25 times per run. No run waited more than 28 seconds on one block.

A wait can still pass 15 seconds when the next peer asked is slow too.

The rate at which a node stores blocks during initial sync is unchanged. That is
set by the disk, which this release does not change (#539).

### The download window no longer stalls

Initial sync no longer stalls when the `-maxahead` window is full while the
next block is not being downloaded. Blocks sent again for heights that are
already connected no longer count against the window, and a peer that is still
owed blocks only counts as active when it delivers blocks it was asked for.

A local disk or database write failure while storing a downloaded block no
longer raises the sending peer's ban score. When following the tip, satd asks
one peer for each missing block instead of all of them. Block downloads,
including the AssumeUTXO background download, now go only to peers that
advertise block service, as in Bitcoin Core (#953).

## P2P

### Blocks that arrive before their parent are kept within bounds

A block received before its parent is now kept only if the node asked for it,
and only within fixed bounds: valid proof of work, at most 4 MB, at most 4
blocks per peer and 32 MB in all, for at most 5 minutes. Other such blocks are
dropped and the sender is asked for headers, which is how the node learns of
the missing parent. A peer's `ping` is no longer held while one of its blocks
waits for a parent (#941).

### Core's message limits and a per-peer send budget

satd now applies Bitcoin Core's limits to single P2P messages. A message over
4,000,000 bytes ends the connection, and an `inv` or `getdata` with more than
50,000 entries, `headers` with more than 2000 or `addr`/`addrv2` with more than
1000 counts as misbehaviour.

Blocks a peer asks for with `getdata` are now served as the peer reads them,
with about 1 MB queued per peer, as with Core's default `-maxsendbuffer`. A
peer whose connection has taken no data for 20 minutes is disconnected, and
`disconnectnode` and bans now take effect on a peer that has stopped reading.
A peer's user agent is limited to 256 bytes and sanitized before it is logged
or reported in `getpeerinfo`. BIP 157 filter requests that Core refuses (an
unknown filter type, an unknown stop hash, a bad range, or any request while
filters are not served) now disconnect the peer instead of being ignored
(#939).

### Misbehaving peers are handled as Core handles them

Peers with the `noban` permission and manual connections (`addnode`,
`-addnode`, `-connect`) are never disconnected or banned for misbehaviour. A
peer on a local address, and every peer that connects through the node's Tor
hidden service, is disconnected but its address is not banned.

Before, one such peer's misbehaviour could ban 127.0.0.1 for `-bantime` (24
hours by default, kept across restarts), which refused every onion and local
P2P client without `noban` for that time. `getpeerinfo` now reports peers that
came in through the hidden service with `network: "onion"` (#944).

### Address rate limits and outbound dial accounting

satd now rate-limits the addresses each peer announces as Bitcoin Core does:
one to start, then one every 10 seconds. Peers with the `addr` permission and
answers to the node's own `getaddr` are exempt. `getpeerinfo` reports
`addr_processed` and `addr_rate_limited`.

Outbound dials in flight now count against the automatic outbound limit, so a
reconnect pass no longer starts more dials than there are free slots. Manual
connections are outside that limit, as in Core: `addnode onetry` works on a
node with all its automatic peers connected (and answers null for a peer
already connected), added nodes are limited to 8 at a time and retried at
least once a minute, and bans stop automatic dials, onion hosts included, but
not manual ones. `setban` of an onion host now disconnects that peer (#952).

## Mempool

### A full mempool checks scripts before it evicts

When the mempool is full, an incoming transaction's scripts are now checked
before anything is evicted to make room for it, and eviction never removes the
incoming transaction's own parent. Eviction now takes time in proportion to
what it removes rather than to the size of the pool, so admitting into a full
pool no longer holds the mempool lock for long.

Lowering `maxmempool` with a config reload now trims the pool to the new size
at once; before, the node refused new transactions until the pool drained
below the new limit. The orphan pool's internal queue no longer grows with
every orphan ever received (#942).

### Mempool RPCs match Bitcoin Core

`getmempoolentry` and `getrawmempool true` report `vsize` rounded up, the
entry's real `height`, only direct parents in `depends`, `bip125-replaceable`
inherited from a signalling ancestor, and ancestor and descendant fees that
include `prioritisetransaction` deltas. `getmempoolinfo` gains `total_fee`,
reports `bytes` as total vsize and `usage` as estimated memory, and reports
`loaded: true` only once the saved mempool has finished loading. `gettxout`
now honours `include_mempool` (default true). `sendrawtransaction` refuses a
negative, unreadable or ≥ 1 BTC/kvB `maxfeerate` or `maxburnamount` instead of
silently dropping the limit, and answers `-27` for an already-confirmed
transaction without needing `-txindex`.

A restart now keeps mempool entry times, so `-mempoolexpiry` keeps counting,
re-admits transactions that met the fee floor through
`prioritisetransaction`, and loads a large mempool in linear time.
Descendants of a transaction that conflicts with a new block now leave the
mempool with it, and confirmed transactions' priority deltas are cleared
(#946).

### A restart keeps the whole mempool

A clean restart could drop most of the saved mempool. satd re-admitted the
transactions in `mempool.dat` in order of entry time, which has one-second
resolution, and the file was written in no particular order, so a child that
entered in the same second as its parent was often tried first, refused for
missing inputs, and took every descendant behind it along. Each restart made
it worse, as the transactions it did re-admit then shared even fewer seconds.
satd now writes the file parents first, as Bitcoin Core does, and on load
puts every transaction after any parent in the same file, so a `mempool.dat`
saved by 0.6.0 also reloads in full. The file format is unchanged (#949).

## Electrum and Esplora

### Electrum status hashes follow history order

The scripthash status satd announces, on `blockchain.scripthash.subscribe` and
in notifications, now hashes the history in the order `get_history` returns
it, as the Electrum protocol defines. Before, an address with both confirmed
and unconfirmed transactions got a status that never matched its history, so
Electrum desktop dropped the connection again and again and did not show the
pending transaction until it confirmed.

`get_history` and `get_mempool` now list mempool transactions with height 0
before those with -1, and order transactions within a block by their position
in it. A subscription no longer gets its own status pushed back at the next
block (#938).

### Esplora paging, empty witnesses and fee estimates

`/address/:addr/txs` and `/scripthash/:hash/txs` now honour mempool.space's
`?after_txid=` cursor, so explorers that page with "load more" get the next
page instead of the first one again; an unknown cursor answers 422
`after_txid not found`. A script's mempool transactions are listed in the
order the node admitted them. `/block/:hash/txs/:start_index` answers 404
`start index out of range` at or past the end of the block, and 400 for a
start that is not a multiple of 25, instead of an empty page. Legacy inputs no
longer carry an empty `witness` array.

`/fee-estimates` now leaves out the targets the node has no estimate for, and
answers `{}` during initial sync or right after startup instead of reporting
1 sat/vB for every target (#943).

### Long address histories no longer hold up other requests

Electrum and Esplora requests that read a long address history now run on a
blocking thread pool instead of the API runtime's worker threads, so one slow
request no longer stalls other Electrum connections, Esplora, events gRPC or
`/metrics`. `--electrumrequesttimeout` now takes effect (a request past it is
answered with an error and its connection closed), and Esplora's address
routes answer 503 at `--esplorarequesttimeout`.

Paging an address with `/txs/chain/:last_seen_txid` or `?after_txid=` reads
only the requested page instead of the whole history, and status
notifications for subscribed addresses are computed off the threads that
connect blocks, once per batch of queued blocks. satd now logs at startup when
fewer Electrum connections than `--electrummaxconns` can fill the server-wide
`--addrindexsubscriptions` registry; see the Electrum chapter's "Subscription
limits" in the Operator Manual (#947).

## Indexes

### Indexes do not serve during or after an unfinished backfill

The address, spend and compact block filter indexes no longer serve while a
`backfillindex` run is in progress or after one stopped part-way, as the
silent-payment index already did, and `NODE_COMPACT_FILTERS` is withdrawn for
that time. Electrum and Esplora subscription statuses refused during a
backfill are pushed once it ends.

A reorg during a backfill can no longer delete rows the active chain wrote,
which could drop an entry from an address history, report a spent output as
unspent, or break the filter header chain. A read during a chainstate flush no
longer misses the newest blocks' index rows; it waits for the flush. A block
whose outputs are all unspendable and which spends nothing no longer loses its
filter and height rows when it replaces another block in a reorg (#958).

## Observability

### No warning for every block early in initial sync

Early in initial sync, 0.6.0 logged `Connector stuck waiting for block data` at
WARN for nearly every block: 112 of the first 624 log lines on a fresh mainnet
sync, and 490 of 508 in a fresh Umbrel install. Blocks arrive out of order from
many peers and the connector takes them in height order, so it waits a second
or two on some block all through a healthy sync. The warning fired on the first
moment of every such wait.

It now fires once the connector has waited 20 seconds on the same block, then
once a minute while the wait goes on, and it carries `waited_secs`, how long the
wait has lasted. That is longer than the scheduler takes to give up on a slow
peer and ask another for the block (15 seconds), so a wait that long means the
sync is held up and not merely handling a slow peer. The warning still carries
the scheduler's view of that block (#904).

## Operator

### An interrupted `-reindex` continues where it stopped

0.6.0 refused to start after an interrupted full `-reindex` until it was
given `--reindex` again, and then replayed the chain from genesis. A mainnet
replay takes days, so on an app-store box every stop, reboot or settings
change during it threw the work away, and a package that passes `--reindex`
once, as StartOS's migration from Bitcoin Core does, left a node that would not
start at all. Start9's review of the StartOS package found it.

Now any start that finds an unfinished full reindex continues it, whatever the
flags. satd scans the block files again and plans the chain to replay as
before, then checks each block the interrupted run had replayed against them:
its index entry must have the header the files hold, at the file position the
scan found it, at its planned height, with the chainwork its ancestors add up
to. It then connects the rest. Nothing is downloaded and no block file is
written. The replay flushes at least every 1000 blocks, so a kill costs at
most that much replay plus the scan, and a stop signal only the scan.

A reindex that cannot be continued runs again from genesis, still on any
start: one whose wipe may not have finished, one satd 0.6.0 started (0.6.0 did
not record whether its wipe had finished), one at another chainstate schema,
and one whose replayed blocks no longer match the block files. In that last
case satd says so and exits without changing anything, and the next start
runs the reindex from genesis. An interrupted `-reindex-chainstate` is not
continued yet: its flags restart it from genesis, as in 0.6.0 (#508).

### The `-reindex` scan reads block headers only

A full `-reindex` first scans the block files and plans the chain to replay
from the block headers. It read each `blk*.dat` file whole to get them, so on
mainnet the scan read the entire chain, about 700 GB, before the first block
connected, and a reindex continued after a stop read it all again on every
start.

The scan now reads each record's length and the block header after it, then
seeks to the next record. A block larger than 4 KiB costs one 4 KiB read;
smaller blocks share reads. The records it finds, and so the chain it plans,
are the same (#916).

### A full `-reindex` writes nothing to the block files

A full `-reindex` empties the database before it scans the block files, and
satd then wrote the genesis block again, to the end of the last block file, as
it does on a new datadir. Every reindex left one duplicate genesis record
behind, and on a node switched from Bitcoin Core it went into one of Core's
files. satd now indexes the genesis record that `blk00000.dat` begins with,
where satd and Core both write it, and writes genesis only when the files do
not begin with it (#931).

### A stop signal during a rebuild stops it cleanly

The block replays of `-reindex`, `-reindex-chainstate` and
`-upgradechainstate` run inside startup, and satd registered its SIGTERM and
SIGINT handlers only once startup had finished. Until then a stop signal had
its default effect. A process that is PID 1 of its PID namespace, as satd is
in a container started without an init, ignores such a signal, so `docker
stop` waited out its whole grace period and then killed the replay. Anywhere
else the signal killed the replay at once, part-way through a batch. Start9's
review of the StartOS package found it: on StartOS, a stop, reboot or settings
change during a reindex ran out the package's stop timeout and killed the
replay.

satd now registers both signals as it starts. During a replay a stop request
is left to the replay, which checks for one between block files while it
scans them, and before and during each block it connects. It abandons the
block it is connecting, which writes nothing until it is complete, flushes
what it had connected, keeps the rebuild marker, and exits 0. On a slow disk a
single block's coin lookups can take seconds, so the stop does not wait for
them. If that takes longer
than `-maxshutdownsecs` (30 s by default), satd exits without waiting, and
loses what the replay connected since its last flush. Anywhere else in startup
a stop signal ends satd at once, as before, and now as PID 1 too.

A shutdown after startup now also logs each wait before it starts: for the
block connector to finish the block in hand, and for the UTXO cache flush,
each with its share of `-maxshutdownsecs`. A stop that runs long says in its
last log line what it is waiting on.

### The StartOS service log shows satd's progress

StartOS starts every service with `RUST_LOG=warn,start_core=debug` in its
environment, and satd takes its log filter from `RUST_LOG`. Under the StartOS
package, satd's log therefore carried warnings only: no sync progress, none of
the reindex phases or stop messages above. The package now runs satd with
`RUST_LOG=info`, satd's default everywhere else.

## Configuration

### `bitcoin.conf` comments, trace logs and the Tor cookie

satd now reads `bitcoin.conf` comments as Bitcoin Core does: a `#` anywhere on
a line starts a comment, so a line such as `txindex=1  # keep it` is no longer
misread, and an `rpcpassword` line containing `#` is refused at startup with
Core's error. sat-cli reads the file the same way.

`-loglevel=trace` no longer writes RPC request headers (including the
`Authorization` credentials) or RPC parameters to the log. With Tor control
enabled, satd reads at most 33 bytes from the cookie file the control port
names and refuses anything that is not a regular file, so a misbehaving
control port cannot make startup hang or run out of memory (#940).

## RPC

### `getrawaddrman` keeps each address in its own bucket

satd does not store addresses by slot. `getrawaddrman` reports a bucket and
position for each one, derived with Core's formulas. When two addresses derived
the same slot, the second moved to the next free slot of the whole table, and
from a bucket's last position that is the first position of the next bucket, one
Core's formulas would never give that address. For one /16 with 32 tried
addresses, about one key in a hundred put an address in another bucket, and some
of those reported the group in nine buckets, where Core's formula allows eight.

The second address now takes the next free position in its own bucket, as Core
keeps every address in the bucket its formula gives. Only a full bucket sends it
on to the next one with room. Core's table never needs that, since it evicts
instead.

### Number formatting, `submitblock` and `getblockfilter` match Core

Difficulty, network hash rate and verification progress are now printed with
Core's 16 significant digits, and `getnetworkinfo` fee floors and PSBT fees as
8-decimal amounts. `submitblock` answers `duplicate-invalid` for a block
already marked invalid, fills in a missing coinbase witness reserved value as
Core does, and throws -22 for undecodable hex and -25 for internal errors
instead of returning them as reject reasons. `getblockfilter` uses Core's
error codes and messages, `getnetworkhashps -1` uses the 144-block interval on
regtest, and a failed RPC password is now logged and answered after a 250 ms
pause, as in Core (#955).

## Upgrade notes

- Drop-in upgrade from 0.6.0 for the changes so far: no reindex. The only
  configuration change is for an `rpcpassword` containing `#` (below).
- A client that treated silence after a watch add as success should handle
  `WatchAddRejected`; one built on a 0.6.0 SDK keeps working and ignores the
  event.
- A full `-reindex` that 0.6.0 left unfinished runs again from genesis on the
  first 0.6.1 start, with or without `--reindex`. Reindexes 0.6.1 starts are
  continued.
- `bitcoin.conf`: a `#` anywhere on a line now starts a comment, as in Core.
  An `rpcpassword` containing `#` is refused at startup; change the password,
  or use `-rpcauth` (#940).
- satd now stops, as Core does, when it cannot read a coin from the
  chainstate. A restart replays the blocks after the last flush; if the stop
  recurs, check the disk and run `-reindex-chainstate` (#945).
- `gettxout` includes the mempool by default (`include_mempool=true`).
  `getmempoolinfo.bytes` is total vsize, not serialized size
  (`satd_mempool_bytes` and the `-maxmempool` budget still count serialized
  bytes), and `loaded` is false until the saved mempool has finished loading.
  `sendrawtransaction` refuses a negative, unreadable or ≥ 1 BTC/kvB
  `maxfeerate` or `maxburnamount` instead of ignoring it (#946).
- `submitblock` throws error -22 for undecodable hex and -25 for an internal
  error instead of returning a reject string. Difficulty, network hash rate
  and verification progress are printed with 16 significant digits, and fee
  fields in `getnetworkinfo` and PSBT RPCs with 8 decimals; clients that
  compared these as strings may see different text (#955).
- Esplora `/fee-estimates` omits targets the node has no estimate for and
  answers `{}` during initial sync. `/block/:hash/txs/:start_index` answers 404
  past the end of the block and 400 for a start that is not a multiple of 25
  (#943).
- The address, spend and compact block filter indexes do not serve during a
  `backfillindex` run, or after one that stopped part-way until a re-run
  completes; `NODE_COMPACT_FILTERS` is withdrawn meanwhile. A redundant run on
  a complete index also stops serving until it completes (#958).
- Misbehaving `noban` and manual peers are never disconnected or banned. Peers
  on local addresses and peers that come in through the onion service are
  disconnected but not banned (#944).

## About this release

satd is free software under the [MIT License](../../LICENSE).

- **Stability & compatibility** — Tier 1 surfaces (Bitcoin Core-compatible
  JSON-RPC wire shape, CLI flag names/defaults, `bitcoin.conf` keys, on-disk
  layout, Electrum/Esplora surfaces) are governed by
  [`STABILITY_POLICY.md`](../../STABILITY_POLICY.md). satd follows
  [semantic versioning](https://semver.org/spec/v2.0.0.html); while in the
  `0.x` pre-1.0 line, deprecations may be accelerated (see the policy).
- **Security & disclosure** — report vulnerabilities per
  [`SECURITY.md`](../../SECURITY.md). Consensus-affecting bugs are treated as
  P0 with same-day acknowledgement.
- **Verifying this release** — tarballs are signed with minisign, container
  images with cosign (keyless OIDC), and git tags with SSH signatures (no GPG).
  The key matrix and verification steps are in
  [`SECURITY.md`](../../SECURITY.md).
- **Intentional differences from Bitcoin Core** — catalogued in
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md).
- **Operating satd** — observability, the full flag matrix, tuning, and the
  downstream packaging contract live in the
  [Operator Manual](https://epochbtc.github.io/satd/).
