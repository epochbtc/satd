# satd 0.5.2

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.5.2 is a patch release on the 0.5.x line. Planned scope: the defects
filed from the deep review of the 0.5.1 Bitcoin Core functional-test wave
(#660–#673), and continued Core functional-test conformance.

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- **A mistyped JSON-RPC argument no longer discards the arguments after it.**
  On `generateblock` that meant a block being mined and connected when the
  caller had asked for one back without touching the chain.
- **`validateaddress` is Bitcoin Core's.** It checks the network (it did
  not), and it says *why* a string is not an address, down to which
  characters of a Bech32 address are probably wrong.
- **Breaking:** `getdeploymentinfo` uses Core's deployment names, `bip65`
  and `bip66`.
- **`-connect=0` no longer dials the address zero**, and `getpeerinfo`
  reports each peer's real `connection_type`.

## Bitcoin Core compatibility

### `getdeploymentinfo` reports Core's deployment names (#666)

Bitcoin Core carries an asymmetry in its own naming: `-testactivationheight`
takes `cltv` and `dersig` on the way in (`GetBuriedDeployment`), while
`getdeploymentinfo` reports `bip65` and `bip66` on the way out
(`DeploymentName`, `src/deploymentinfo.cpp`). satd used the input spelling in
both places, so anything keyed on Core's reported names — including Core's own
test framework — could not find the deployment.

**Breaking** for anything reading satd's old spelling:

| Was | Now |
|---|---|
| `deployments.dersig` | `deployments.bip66` |
| `deployments.cltv` | `deployments.bip65` |

`bip34`, `csv`, `segwit` and `taproot` are unchanged, and
`-testactivationheight=cltv@…` / `dersig@…` still take the input spelling, as
in Core.

`getdeploymentinfo` also honours its `blockhash` argument, which it previously
accepted and ignored: it now reports each deployment's state as of that block
(`active` follows Core's `DeploymentActiveAfter` — true when the block *after*
the one queried must obey the rule), and answers `-5 Block not found` for a
hash it does not have.

### `validateaddress` says why an address is invalid

An address that does not decode came back as a bare `{"isvalid": false}`.
Core answers with an `error` sentence and, for a Bech32 string whose checksum
fails, an `error_locations` array pointing at the characters most likely to be
wrong — which is how a wallet highlights a typo rather than saying "invalid".

satd now reproduces both, including the error locator: BCH decoding over
GF(1024), the same construction Core uses, which identifies up to two
mistyped characters in a Bech32 address. Every message and every position is
checked against Bitcoin Core's own test vectors.

```
$ sat-cli validateaddress bcrt1qax9suht3qv95sw33xavx8crpxduefdrsvgsklu
{
  "isvalid": false,
  "error_locations": [22, 43],
  "error": "Invalid Bech32 checksum"
}
```

### `validateaddress` no longer accepts another network's addresses

Underneath that, a real defect: satd parsed the address without checking the
network and then asserted the result was checked, so a mainnet address
validated on a regtest or signet node. `validateaddress` is what a downstream
service calls before accepting a withdrawal destination; on a testnet
deployment it was answering `isvalid: true` for addresses the node could never
pay. Fixed — the decode is network-scoped, exactly as Core's
`DecodeDestination` is.

### The transaction builders check the address network too (#689)

`validateaddress` was the diagnostic; `createrawtransaction` and `createpsbt`
are the RPCs that actually build a payment, and they were still decoding
without the network:

```
$ sat-cli -regtest createrawtransaction '[]' '{"3J98t1WpEZ73CNmQviecrnyiWrnqRhWNLy":0.001}'
0200000000010001a08601000000000017a914b472a266d0bd89c13706a4132ccfb16f7c3b9fcb8700000000
```

A mainnet P2SH address, encoded into a regtest output. The harmless direction
is the one shown; the expensive one is its mirror image. A testnet address
accepted on a mainnet node pays a scriptPubKey whose key the sender does not
control, and the address prefix — the only part of the encoding that records
which network it belongs to — is not carried into the scriptPubKey, so nothing
downstream of the call can notice. Neither can a block explorer: the payment
looks ordinary.

Both now decode with the node's network, as Core's `DecodeDestination` does,
and answer `-5 Invalid Bitcoin address: <addr>`. This **rejects input satd
previously accepted**. A caller that relied on the old behaviour was building a
transaction its own node could not have paid.

While closing this, `createpsbt` was moved onto the same output parser as
`createrawtransaction`. Core reaches one implementation (`ParseOutputs`, via
`ConstructTransaction`) from both RPCs; satd had two, and the second one was
the weaker copy. `createpsbt` gains from the merge:

- the array form of `outputs` (`[{"addr": 0.01}, {"data": "…"}]`), previously
  ignored, producing a PSBT with no outputs at all;
- string amounts (`"0.01"`), previously an `Invalid amount` error;
- the duplicate-address, duplicate-`data` and amount-range checks;
- Core's error *ordering*, which is observable — a bad amount on a bad address
  reports the amount, and a repeated invalid address reports the address
  rather than the repeat.

### `validateaddress` describes destinations the way Core does

Bitcoin Core's `validateaddress` declares every field but `isvalid` optional,
and its `DescribeAddressVisitor` omits the ones that do not apply. satd emitted
`witness_version: -1` for every non-witness address — there is no such witness
version — and got two script classifications wrong: Taproot and anchor outputs
are script destinations to Core, and an unknown witness version carries no
`isscript` key at all. An anchor's witness program is not reported by Core
either.

The shape now matches: `witness_version` and `witness_program` appear only for
the destinations Core emits them for, and `isscript` is true for P2SH, P2WSH,
Taproot and anchor. A client that read `witness_version == -1` as "not a
witness address" should test for the field's absence instead — or read
`iswitness`, which has always been correct.

### `dumptxoutset` takes Core's arguments

`dumptxoutset` read its parameters with a helper that accepts exactly one, so
every Core-shaped call — `dumptxoutset("utxo.dat", "latest")` — came back as a
JSON parse error. It now takes Core's `type` argument and rejects an unknown
type with Core's message. `"rollback"` is refused by name rather than silently
answered with the tip: satd has no temporary rollback, and a historical
snapshot that is quietly the current one is worse than an error. An omitted
`type` still means `"latest"`, so existing callers are unaffected.

A relative `path` is now resolved against the network data directory, as in
Core, and the reported `path` is absolute. Previously it was resolved against
the daemon's working directory, so `dumptxoutset("utxo.dat")` wrote somewhere
the operator had not asked for.

### `addconnection`: Core's hidden outbound-dial RPC

Bitcoin Core's functional-test framework builds its *outbound* peer tests on
`addconnection`, a regtest-only RPC that makes the node dial a listener with a
chosen connection type. Without it a test can only ever be dialled *by* satd's
peers, which leaves everything satd does as the initiator untested.

satd now implements it with Core's arguments and result:

```
addconnection "address" "connection_type" v2transport
  -> {"address": "127.0.0.1:11005", "connection_type": "block-relay-only"}
```

`connection_type` is one of `outbound-full-relay`, `block-relay-only`,
`addr-fetch` or `feeler`, and the type is not decoration:

- **`getpeerinfo.connection_type`** reports the real type. It previously
  reported `manual` for an `addnode` peer and `outbound-full-relay` for every
  other outbound one, because those were the only two satd could tell apart.
- **`block-relay-only`** clears `fRelay` in the `version` satd sends, so the
  peer does not offer it transactions, and turns off address relay
  (`addr_relay_enabled` is false). That is the entire purpose of the
  connection type: a peer that sees no transaction or address traffic cannot
  be used to map the topology.
- **`feeler`** is closed as soon as the peer's `version` arrives, without a
  verack, exactly as Core closes one.
- **`addr-fetch`** is sent a `getaddr` and never a `getheaders`, is dropped
  once the peer answers with more than one address, and times out after five
  minutes if it never answers.

Capacity is checked per type, as Core does: eight full-relay slots and two
block-relay-only ones, with no limit on the short-lived types. Exceeding one
returns Core's `-34`. Outside regtest the RPC refuses outright, and it stays
out of `help` — it is a test hook, not an operator surface.

## Bug fixes

### `-connect=0` dialled the address zero

Bitcoin Core spells "open no outbound connections" as `-connect=0`. satd
parsed the `0` as a peer address, so a node started that way dialled
`0.0.0.0:8333` at startup — and, because the address landed on the dial list,
kept re-dialling it from the reconnect loop.

Where nothing answers on that port the dial is merely refused, repeatedly.
Where something does — another Bitcoin node on the same host — it gets far
enough to consume peer id 0, and the first real peer then comes back from
`getpeerinfo` as id 1 where Core reports 0, which is enough on its own to fail
Core-derived tests that identify a peer by id.

`-connect` in any form now also stops the node dialling addresses it learned
from gossip, matching Core's `m_use_addrman_outgoing`: the addresses are still
recorded in the address book, they are just never dialled. Before, a node
pinned to specific peers would quietly reconnect itself to the wider network
from gossip — including, after a restart, from every address in `peers.dat`.
The rule is applied where the dial happens rather than where the address is
recorded, so it holds however an address arrived and whatever order startup
runs in.

### RPCs that reported invented data (#667)

Several introspection RPCs returned values shaped like answers but not derived
from the node's state. Each is individually small; together they made the RPC
surface untrustworthy for the exact purpose these calls serve.

**`getpeerinfo.permissions` was hardcoded `[]`.** The peer's permissions were
populated all along — the field just never read them. An empty array reads as
"no permissions granted", not "not implemented", so a `-whitelist`ed peer
looked un-whitelisted to anything checking. It now reports Core's
`NetPermissions::ToStrings` of the real flags, in Core's order. `bloomfilter`
never appears: satd accepts the name in a `-whitelist` entry but has no flag
for it, and reporting it would claim a grant that was never recorded.

Alongside it, `noban` now carries `download`, as Core's flag value does
(`NetPermissionFlags::NoBan` is `(1U << 4) | Download`). This is a reporting
change only: `has_upload_budget` already read `perms.download || perms.noban`,
so a `noban` peer was always exempt from the `-maxuploadtarget` block-serving
limit — the array just did not say so.

Making the array truthful surfaced two grants that were wider than Core's, and
both are corrected here:

- **A bare `-whitelist=<subnet>` granted `addr`.** Core's implicit expansion is
  `relay` + `noban` + `mempool` + `download` and nothing else
  (`CreateNodeFromAcceptedSocket`); `p2p_permissions.py` asserts that list
  literally. satd also exempted the peer from address-relay rate limiting.
- **`-whitelist=@<subnet>` granted the implicit set.** The `@` form with an
  empty permission list is Core's idiom for "match this range and grant it
  nothing" — Core never sets `Implicit` for it, so no expansion follows. satd
  granted `noban`, which exempts a peer from banning *and* from the inbound
  connection caps, to a range the operator had explicitly asked to grant
  nothing.

Both were invisible while `permissions` was hardcoded `[]`, and so were the
two below.

### `-whitelist` reached peers Core excludes (#701)

**An inbound Tor peer inherited a loopback whitelist entry.** Tor forwards a
hidden-service connection to a local socket, and satd pointed its service at
the *clearnet* P2P listener — so every anonymous inbound onion peer arrived
indistinguishable from a genuine local one, with `addr.ip() == 127.0.0.1`, and
was matched against `-whitelist`. `-whitelist=127.0.0.1` is the ordinary way to
whitelist a local Electrum or BTCPay integration; it was also granting `noban`
to anyone who could reach the hidden service. A `noban` peer cannot be banned
for misbehaviour and is exempt from the inbound connection cap, the per-IP
sub-cap and `-maxuploadtarget` — so an attacker could take every inbound slot
and stay.

Core avoids this by giving the hidden service its own listener and skipping the
whitelist for sockets accepted on it:

```cpp
AddWhitelistPermissionFlags(permission_flags,
                            inbound_onion ? std::optional<CNetAddr>{} : addr,
                            vWhitelistedRangeIncoming);
```

satd now does both halves. `-listenonion` gets a listener on
`127.0.0.1:<port+1>` unless a `bind=<addr>:<port>=onion` entry names one
(Core's `onion_binds` default), the hidden service targets *that*, and the
accept loop knows which listener it is serving. `-whitebind` permissions still
apply on an onion listener, because those are attached to a listener the
operator named rather than inferred from the peer's address.

**`-whitelist` applied to outbound peers.** Core's entries are inbound-only
unless they carry an `out` token, and it consults the outgoing list only for
*manual* connections — an automatic outbound peer gets nothing from
`-whitelist` at all. satd swallowed `in` and `out` as no-op permission names
and applied every entry in both directions, so `-whitelist=noban@127.0.0.1`
followed by `addnode 127.0.0.1:<port> onetry` made the outbound peer
un-bannable and exempt from the upload budget. `p2p_permissions.py` pins the
distinction:

```text
-whitelist=noban,out@127.0.0.1  ->  ["noban", "download"]
-whitelist=noban@127.0.0.1      ->  []
```

Entries now record their direction, and both rules are reproduced.

**A direction with no permission was accepted and granted nothing.** Core
refuses such an entry outright:

```cpp
} else if (flags == NetPermissionFlags::None) {
    error = strprintf(_("Only direction was set, no permissions: '%s'"), str);
    return false;
}
```

satd started, and `-whitelist=out@10.0.0.0/8` left the operator believing a
grant was in place when the entry granted nothing at all. It is now refused,
naming the entry. `-whitebind` additionally refuses an `out` token: Core passes
a null `output_connection_direction` for a bind entry, because a bind address
describes where connections *arrive*, and satd accepted
`-whitebind=out@127.0.0.1:8333` where Core will not start.

**One deliberate divergence, recorded rather than removed.** Core adds its
`127.0.0.1:<port+1>` onion listener only when there is no `-bind` at all; with
an explicit `-bind` it points Tor at the first one and opens no extra socket —
which puts onion peers back on the clearnet listener, the thing the fix above
exists to prevent. satd adds the listener in both cases. The cost is one socket
Core would not have opened, so a bind failure on that address is a warning
rather than a fatal startup error: the operator did not name it, and the
degraded outcome is safe (Tor forwards to a socket nothing serves and the
connections are refused). See `CORE_DIFFERENCES.md`.

**`getmemoryinfo` reported the process RSS as the secure-allocator pool.**
Core's `locked` object describes `LockedPoolManager`, the mlock'd arena the
wallet keeps private keys in. satd reported its own RSS as `used` and invented
`free`, `total` and both `chunks_*` around it, with a source comment saying
outright that the values were chosen to satisfy a test's assertions. satd has
no secure allocator and no wallet, so the pool is empty and every field is
zero. The object keeps Core's shape, since clients index into it
unconditionally.

**`estimaterawfee` described a bucket estimator satd does not have.** It
returned the same feerate for all three horizons with `decay: 0` — not a value
Core's estimator can ever produce — zeroed `pass` / `fail` buckets, and
discarded `threshold` without looking at it.

It now behaves as far as satd's estimator can:

- a horizon that does not track the requested `conf_target` is omitted
  entirely, as in Core (short tracks 12 blocks, medium 48, long 1008);
- `decay`, `scale`, `pass` and `fail` are omitted rather than zeroed — satd
  keeps a rolling sample of recent block feerates, not Core's decaying buckets,
  so there is nothing to put there;
- a node with too few samples answers Core's `errors: ["Insufficient data or no
  feerate found which meets threshold"]` instead of quoting the relay floor;
- `threshold` is range-checked (`-8 Invalid threshold`) rather than dropped.

**`logging` answered from a map nothing else read.** A static
`OnceLock<BTreeMap<String, bool>>`, initialised to "everything on" and
disconnected from satd's real `EnvFilter`. A node started with no `-debug`
reported 30 categories enabled; `logging(exclude=["net"])` flipped a bit that
never reached the filter, so the node went on logging exactly as before and the
RPC went on reporting whatever it had last been told. Every answer it gave was
wrong, on the one RPC whose entire purpose is to answer that question.

It now reads and writes the live filter. The state and the filter are owned by
one object, so they cannot drift — and that ownership is why there is no longer
a separate log-reload handle for SIGHUP to reach past it.

Two consequences worth knowing:

- **satd lists the categories it can act on — twenty, not Core's thirty.** Core
  names are mapped onto six tracing subsystems, so `addrman`, `cmpctblock`,
  `proxy` and `txreconciliation` are aliases for the same target as `net` and
  all report together. Names satd has no subsystem for (`qt`, `libevent`,
  `lock`, `rand`, `selectcoins`, `walletdb`) are not listed, because
  advertising a category the RPC can neither enable nor report on is the defect
  this change exists to remove. Core's wildcard set is honoured exactly as
  `GetLogCategory` defines it — `""`, `1` and `all` all mean everything — and
  an unknown name is Core's `-8 unknown logging category <cat>`.
- **`none` and `0` are rejected, as Core rejects them.** They look like
  wildcards, and an earlier draft of this change treated them as "disable
  everything", but they are `-debug` **config** spellings only:
  `SetLoggingCategories` special-cases them as a drain over the argument list,
  and they are absent from Core's `LOG_CATEGORIES_BY_STR`, so both
  `EnableCategory` and `DisableCategory` fail on them and the RPC answers
  `unknown logging category`. Accepting them meant `logging '["none"]'`
  silently turned off all logging on a node where Core would have refused the
  call — losing an operator their logs on a call they expected to fail.
- **A SIGHUP re-derives verbosity from the config file**, discarding runtime
  `logging` changes. That matches the rest of the reload contract: the file is
  the declared state and a reload asserts it.

`txindex.synced` is the one item from #667 left reporting the flag rather than
a derived value, and it stays that way deliberately — see
`CORE_DIFFERENCES.md`. satd writes txindex entries inline during block
connection, so with `-txindex` on the index is current for everything the node
connects; what the field cannot tell you is whether history predating the flag
was indexed. Core answers that with a background index builder, which satd does
not have. Against the strict predicate `synced` would stay false forever on a
datadir first synced without `-txindex`, and Core's documented "poll `synced`,
then query" pattern would hang rather than fail. A txindex backfill is the work
that would make the field a completeness marker; until then the flag is the
honest answer, and it is now written down as a divergence instead of sitting in
an issue.

### A ban list satd could not read turned `setban` into a no-op (#669)

satd wrote `banlist.json` as a bare JSON array. Bitcoin Core writes an object —
`{"banned_nets": [...]}` — with a `version` on each entry.

The format difference was the smaller half. Point satd at a datadir Core had
used and the parse failed; satd then left the ban list with no persist path,
and **every subsequent `setban` silently vanished** — accepted by the RPC,
applied in memory, absent after a restart, with no error at any point. An
interrupted write could produce the same state on satd's own datadir, since
the file was written in place with no temporary and no rename.

Three changes:

- **The format is Core's.** satd writes the `banned_nets` object with Core's
  `_warning_` note and a `version` per entry, and reads both that and its own
  historical array, so an upgrade keeps its bans. A row Core would drop — an
  unknown `version`, an unparseable address — is dropped rather than taken as
  a reason to discard the file, matching `BanMapFromJson`. Reading the array is
  only half the upgrade, so a legacy file is marked pending the moment it is
  read and rewritten in Core's shape by the dump that follows the load: leaving
  it until some *other* change happened to mark the list dirty would keep the
  array on disk indefinitely, and Bitcoin Core reading that datadir in the
  meantime still discards every ban — which is the interop this whole change
  exists for.
- **An unreadable list is recreated, never a reason to stop persisting.**
  Core's `BanMan` constructor is `LoadBanlist(); DumpBanlist();`; satd now does
  the same. Loading cannot fail, so there is no error path left that can
  quietly produce a no-op persister.
- **The write is atomic, serialised, and off the ban-list lock.**
  `banlist.json` goes to a temporary file and is renamed into place, so a
  failed or interrupted write leaves the previous list rather than a truncated
  one. Whole dumps are serialised against each other by a second lock, as
  Core's `DumpBanlist` does with its `dump_mutex`: `setban` runs on an RPC
  thread while the automatic-ban path runs on the peer event loop, and without
  that ordering a slow dump could rename a stale snapshot over a newer one and
  leave the list marked clean — losing a ban exactly the way this change
  exists to prevent. The ban-list lock itself is released before the write, so
  a concurrent ban check on the inbound-accept path no longer waits on a disk
  write. The write is still a blocking syscall on the calling thread; taking
  it off the event loop entirely is separate work.

### `-connect` parity leftovers (#690)

Three divergences adjacent to the `-connect=0` fix above, each of which
changes startup behaviour.

**The default port ignored the network.** `-connect=1.2.3.4` and
`-addnode=1.2.3.4` appended `:8333` whatever chain the node was on, so a
signet or testnet4 operator naming a peer without a port dialled a mainnet
port. This is the same hardcoded default by which `-connect=0` used to reach
`0.0.0.0:8333`. Both options now resolve through the network's default port,
which is what `-seednode` already did. The helper carrying the hardcoded 8333
is gone, so it cannot come back.

A bare IPv6 literal takes the default port too, which it did not: the
"has no port" test was a search for a colon, and every IPv6 literal has them,
so `-connect=2001:db8::1` failed to resolve at all while `-connect=1.2.3.4`
worked.

**A `-connect`-pinned node still accepted inbound connections.** Core's
`InitParameterInteraction` lowers `-listen` to 0 for a node given `-connect`
(or `-maxconnections=0`) — the sibling of the `-dnsseed=0` interaction satd
already implemented. satd defaulted `listen` to true unconditionally, so a node
the operator had pinned to a named set of peers was still reachable from the
open internet. **Breaking**, in the direction of the operator's stated intent:

| Configuration | `listen` |
|---|---|
| no `-connect` | on (unchanged) |
| `-connect=…`, `-connect=0`, `-noconnect`, `-maxconnections=0` | **off** |
| any of those plus `-bind` or `-whitebind` | on |
| any of those plus an explicit `-listen=1` | on |

An explicit `-listen` wins from the config file as well as the command line,
matching Core's `SoftSetBoolArg`, which reads one settings namespace rather
than just argv. Core's own functional test framework appends a `-bind` to every
node it starts, which is why its `-connect=0` nodes remain reachable.

**`-noconnect` was refused rather than honoured.** satd hard-errored on it,
which was defensible only while it had no way to express "make no automatic
outbound connections". It has one now, so `-noconnect` and `--noconnect` are
rewritten to `-connect=0` and take that path in full, interactions included.
`-noconnect=0` — Core's double negation, which resolves to the *address* `1`
and dials it — is still refused rather than reproduced.

Because `-connect` is an appending list, that rewrite also had to teach satd
Core's `SettingsSpan` rule: a negation discards the values before it and keeps
the ones after. Recognising `0` only as a lone value meant
`-connect=1.2.3.4 -noconnect` left the sentinel in the dial list, where
`getaddrinfo("0")` resolves it to `0.0.0.0` — the same phantom dial #686 fixed,
in the configuration that most plainly means "connect to nothing".

Two smaller things fixed alongside. A `-listen` value satd's parser cannot read
(`listen=on`) no longer counts as an explicit setting — it used to suppress the
interaction *and* discard the value, leaving a pinned node reachable on the
strength of a setting nothing could parse. And a negative `maxconnections` in
`bitcoin.conf` now lands on Core's `<= 0` branch instead of failing to parse
and falling through to the 125 default, which left the node listening and
accepting 125 peers where Core takes none.

**`-listen=0` did not reach `-listenonion`.** Core's same
`InitParameterInteraction` block soft-sets `-listenonion=0` when `-listen` is
off, and it has to: a hidden service is an inbound surface like any other.
satd resolved `listenonion` independently.

That was reachable without ever writing `-listen=0`. satd defaults
`listenonion` on when `-torcontrol` is set, so `-connect=<peer>
-torcontrol=<addr>` — a pinned node — lowered `listen` by the rule above and
kept the onion listener: the operator asked for a pinned node and got an
anonymous inbound surface. The soft-set is soft, as Core's is, so an explicit
`-listenonion=1` still wins.

**The literal `-connect=0` is not the negation.** Core stores `-noconnect` as
a boolean `false` (`InterpretValue`), which `SettingsSpan` skips back to, and
the literal `"0"` as a *string*, which it does not — the string takes a
separate rule in `AppInitMain`:

```cpp
if (connect.size() != 1 || connect[0] != "0") { connOptions.m_specified_outgoing = connect; }
```

So `-connect=1.2.3.4 -connect=0` connects to 1.2.3.4 in Core. Draining on the
literal as well as the negation made satd connect to *nothing* — a silently
isolated node, from a configuration Core starts fine. satd will not dial the
`0` either (Core hands it to the resolver, which answers `0.0.0.0`, and the
node dials that forever), so the mixed form is now refused by name rather than
reproduced or silently dropped. `-connect=0` on its own — and repeats of it —
still mean "no peers", which is how every Core functional test starts a node.

satd still does not implement Core's *third* `-listen` soft-set: a `-proxy`
also lowers it, so a Tor-proxied satd is reachable on clearnet by default where
Core is not. That is a pre-existing privacy gap, tracked separately.

### `block-relay-only` connections were block-relay-only in name

The connection type exists to give a node links an observer cannot correlate:
no transaction announcements, no address traffic. satd set the `fRelay` bit to
zero in the `version` it sent and reported `addr_relay_enabled: false` — and
then answered the peer's `getaddr` with a full address message, recorded the
addresses that peer announced, and announced its own transactions over the
link, because the tx-relay decision read only the *remote's* `fRelay` and
never satd's own connection type.

Core's `SetupAddressRelay` refuses address relay on such a connection in both
directions, and it builds no transaction-relay state at all, which is why its
`getpeerinfo` reports `relaytxes: false` for block-relay-only and feeler peers
whatever the peer said. satd now does the same.

### An `addr-fetch` connection never noticed it had been answered

An addr-fetch connection collects one batch of addresses and hangs up. satd
applied that rule only to the legacy `addr` message, but it sends `sendaddrv2`
on every outbound connection, so every BIP155-capable peer — Bitcoin Core 22
and later, and satd itself — answers with `addrv2` instead. The rule never
fired, and the connection sat holding an outbound slot until the five-minute
expiry. Core applies it in the handler both messages share.

### Answering `getaddr` could deadlock the P2P event loop

The handler held a read lock on the peer table while sending its reply, and
sending takes the same lock again. `parking_lot`'s read lock is not reentrant:
a writer arriving between the two acquisitions makes the second read queue
behind the writer, which is waiting on the first — wedging the manager's event
drain, and with it all peer processing. The reply is now built from a snapshot
and the lock released before sending.

### A mistyped RPC argument silently discarded every argument after it (#672)

satd read each positional argument straight into its Rust type. The
underlying `ParamsSequence` clears the rest of the parameter buffer on any
deserialize error, so one argument of the wrong type did not just fail — it
erased every argument that followed, and each of those fell back to its
default without a word.

The sharp case was `generateblock`. Its `submit` argument defaults to `true`;
`submit=false` means "build the block and hand it back, do not connect it".
A mistyped `transactions` discarded `submit`, so `submit=false` mined **and
connected** a block. A caller that asked not to touch the chain got a new tip.

Arguments are now read through a checked reader that goes via JSON first, so a
type mismatch cannot poison the sequence. A wrongly-typed argument is reported
in Bitcoin Core's own shape, listing every bad argument by position and name:

```
error code: -3
error message:
Wrong type passed:
{
    "Position 1 (nblocks)": "JSON value of type string is not of expected type number",
    "Position 2 (height)": "JSON value of type array is not of expected type number"
}
```

This is a behaviour change for callers that were relying, knowingly or not, on
a bad argument being ignored: such a call now fails instead of quietly doing
something else. Well-typed calls are unaffected. `verbose`/`verbosity` slots
keep accepting either a bool or a number, as Core's `ParseVerbosity` does.

### `sat-cli -named` dropped arguments that had no `=` (#672)

`sat-cli -named getblock <hash> verbosity=2` sent only `verbosity`. Bitcoin
Core treats an argument without `=` as a positional one and passes it in the
reserved `args` slot; `sat-cli` now does the same, so mixed positional and
named arguments on one command line reach the node as typed.

### An error on one argument buried a type error on another (#672)

The fix above records a mismatched argument and reports it once every argument
has been read. Three paths returned an error *before* that report was reached:
an optional argument whose value is the right JSON type but out of the slot's
domain, a missing required argument, and a verbosity out of range. A mismatch
recorded before any of them was left unreported.

In a release build the mismatch was silently discarded and the caller was told
only about the second problem — #672's own failure mode, one argument along. In
a debug build the module's own consistency assertion fired instead, killing the
request's worker task, so the client's connection closed with no response at
all: not an error object, not a `500`, nothing.

Bitcoin Core settles the precedence in `RPCHelpMan::Check`: argument count
first, then *every* type mismatch as a single `-3`, and only then the handler,
where value-domain errors come from. satd now follows that order.

### `getnetworkhashps` rejected its own defaults, and under-reported the rate

Both arguments were read as unsigned. Core declares both signed and gives
`height` a default of `-1`, so `getnetworkhashps 120 -1` — Core's defaults
written out — returned `Invalid value for argument height`. `-1` for `nblocks`
("since the last difficulty change") was refused the same way, and an
out-of-range `height` or a zero `nblocks` returned a type error where Core
names the problem.

The estimate itself was also wrong. Core divides the work accumulated *across
the window* by the time that window spanned; satd divided the work of a single
block by the same span, understating the network hash rate by a factor of the
window size — roughly 120x at the default. The same function backs
`getmininginfo.networkhashps`, the MCP mining tool and the TUI's hash-rate
display, so all three were low together.

### `getblockstats` rejected a height and ignored its filter

`getblockstats 1000` is Bitcoin Core's own documented example. satd read the
argument as a string only, so the numeric form failed, and it read the
parameter array as a fixed array of one, so the `stats` filter was rejected as
a surplus argument rather than applied. Both now work, and an unrecognised
statistic is named (`Invalid selected statistic '...'`) instead of being
quietly dropped.

### 24 more RPCs read their arguments the same way (#687)

`params.one::<T>()` is `parse::<[T; 1]>()` — a fixed-length array — so it
refuses **any** surplus argument outright. Twenty-four handlers still read
their first argument that way, and for three of them Bitcoin Core declares
optional arguments those handlers could therefore never accept:

| Method | Argument Core declares |
|---|---|
| `submitpackage` | `maxfeerate`, `maxburnamount` |
| `converttopsbt` | `permitsigdata`, `iswitness` |
| `utxoupdatepsbt` | `descriptors` |

All twenty-four also rendered the refusal as a Rust `Debug` dump in a public
error message:

```
-1  ErrorObject { code: InvalidParams, message: "Invalid params",
    data: Some(RawValue("invalid type: integer `3`, expected a string ...")) }
```

They now read through the same argument reader as the rest of the surface, so
the error is Core's and the internal type names stay internal.

**`converttopsbt` now refuses signature data by default.** Core defaults
`permitsigdata` to false and answers `Inputs must not have scriptSigs and
scriptWitnesses`; satd stripped signatures silently, so a lossy conversion
could discard data the caller had not meant to lose. Pass `permitsigdata=true`
for the old behaviour. The MCP `psbt_workflow` `convert` action takes a
matching `permit_sigdata` parameter, defaulting the same way.

Where satd does not yet implement an argument's effect — `maxfeerate` and
`maxburnamount` on a package, `descriptors`, `iswitness` — it now refuses a
supplied value by name instead of accepting a limit it would not enforce.
Silently ignoring `maxburnamount` is the one outcome worth avoiding: a caller
passing it to protect itself would get no protection and no warning.

### Hash arguments distinguish a length error from a hex error (#692)

Core's `ParseHashV` reports a wrong-*length* hash as a length error and a
right-length non-hex string as `must be hexadecimal string`. Six satd call
sites built the length message unconditionally, so `getblock` with 64 non-hex
characters told the caller to count their characters. `getrawtransaction` was
worse: it reported a fixed length of 0 whatever was passed.

`getblockfrompeer` also names the argument `blockhash` now, as Core does; it
previously called it `hash`.

### A surplus RPC argument is an error, not something to ignore (#688)

Bitcoin Core checks a call's argument *count* before anything else:
`IsValidNumArgs` runs ahead of the type loop in `RPCHelpMan::HandleRequest`
and throws the method's help text, so the handler never sees a call with too
many arguments. satd read the arguments it knew about and ignored whatever
came after, which meant a caller who miscounted got a plausible answer:

```
getblockheader <hash> true "EXTRA" 99   -> the header
getblockcount 1 2 3                     -> the height
estimatesmartfee 1 "ECONOMICAL" 1       -> a feerate   (Core: -1)
```

The check now runs once, before dispatch, for every registered method, from
the same argument table the named-parameter layer uses — so it covers the
methods that take no arguments at all, which no handler-side check would have
reached. Two handlers that had grown their own version of it (`estimatesmartfee`,
`estimaterawfee`) and one that hand-rolled a sentinel argument
(`createrawtransaction`) no longer need to.

The error code is Core's `-1`. The message is not: Core's is the method's full
help text, which satd has no equivalent of, so it says plainly what the bound
is (`getblockcount takes no arguments (3 given)`). What Core-derived callers
assert — the code, and the method name at the front of the message — holds
either way, and `CORE_DIFFERENCES.md` records the rest.

### `generatetoaddress` honours `maxtries` (#688)

Core's third argument to `generatetoaddress` and `generatetodescriptor` is a
budget of nonce attempts, spent across the whole call; running out returns the
blocks that were mined rather than an error. satd declared the argument and
read no value for it, so a mistyped `maxtries` was silently dropped where Core
answers `-3`, and `maxtries` itself did nothing.

It does now — and it is also the first bound on satd's nonce grind, which was
an unbounded loop. On a chain whose target the node cannot reach, a mining RPC
used to pin a worker indefinitely with no way to interrupt it.

### `help` answers for every registered command (#692)

Core's `hidden` category suppresses a command from the *listing* only:
`help <hidden command>` still returns its help text, because the skip in
`CRPCTable::help` is guarded by `strMethod != strCommand`. satd answered from
its listing table instead, so every registered method absent from that table —
`addconnection`, but also `createrawtransaction`, `decodepsbt` and thirteen
others — reported `help: unknown command`.

`help <command>` now answers for anything registered, and the listing names
every method satd registers rather than a hand-maintained subset of them.
Thirty were missing: the fifteen Core lists and satd did not, and fifteen of
satd's own — the index, quarantine and address-index RPCs, which an operator
had no way to discover. satd-only methods take the category of their closest
Core analogue. `hidden` is a category in the same table now, as it is in Core,
so the three commands that should not be advertised are excluded from the
listing by construction rather than by a filter.

One layer down, the same shape: `ALL_METHODS`, the enumerable copy of the
argument table, had drifted from it by nine methods, so
`help dump_all_command_conversions` under-reported them. The startup audit
beside it only asked whether a *row* existed, and `rpc_help.py`'s cross-check
against Core's `client.cpp` is gated on a wallet build, which satd is not. The
audit now runs in both directions.

### `submitpackage` named the wrong reason for an unspent-dust refusal (#673)

Core's ephemeral dust policy lets a zero-fee transaction carry one dust output
on the condition that a child in the same package spends it. A child that
spends the parent but leaves the dust behind is refused
`missing-ephemeral-spends` — the dust would otherwise be stranded in the UTXO
set forever, which is the whole reason the condition exists.

satd computed that refusal correctly and then discarded it. The child was
retried in a later pass, failed again because its parent had not been accepted
either, and overwrote the reason with `bad-txns-inputs-missingorspent`. The
submitter was told its inputs were missing, which is a consequence of the real
problem and points at the wrong fix: it describes the parent's absence rather
than the dust the child failed to sweep. A child already refused for a
package-level reason is no longer retried.

The result for the package as a whole is now `unspent-dust` rather than
`transaction failed`. Core treats an unspent-dust failure as a property of the
package and reports it in preference to any per-member policy failure, because
`CheckEphemeralSpends` runs before the per-member script and policy checks.

### A refused child could leave its dust parent behind (#673)

More serious, and found by the same tests. The dust parent is admitted on the
strength of a child that merely *exists* in the package — some member names the
dust outpoint as an input — and that decision is made before the child has been
through acceptance. If the child was then refused for anything at all, its fee
included, the parent stayed: a zero-fee transaction resident in the mempool
with its dust stranded in the UTXO set and nothing paying to have it there.
That is precisely the state the ephemeral dust policy exists to prevent.

Core cannot reach it, because it validates the whole package before committing
any of it — `CheckEphemeralSpends` runs in `AcceptMultipleTransactions` and
returns before `FinalizeSubpackage`, so a failure anywhere leaves the mempool
untouched. satd accepts incrementally, so it now undoes the parent when no
accepted member sweeps its dust.

Reachable only through `submitpackage`; nothing on the P2P path can produce it.

### The ephemeral dust rule now holds on the single-transaction path too (#703)

Core runs `CheckEphemeralSpends` from `AcceptSingleTransaction` as well as from
the package path, gathering dust from in-mempool parents and not just in-package
ones. satd did not: `MempoolError::MissingEphemeralSpends` was never constructed
at all. A transaction submitted on its own could spend a resident dust parent's
ordinary output and leave the dust behind.

How exposed that was is a narrower question — `accept_transaction` refuses dust
outright, so a package is the only way a dust output reaches the mempool, and
the fix above closes the one path that could leave a parent resident without its
sweeping child. The check is what makes that a property of the code rather than
a coincidence of the current call graph.

### An ephemeral dust parent entered the mempool silently (#704)

The path a dust parent takes into the mempool writes the entry directly and
emitted no `Enter` event. The transaction was in `getrawmempool`, in the block
template, and relayed, while the event stream said nothing about it — so a
consumer reconstructing mempool membership from the stream, which is what the
stream is for, silently disagreed with the node.

Every member of an accepted package now gets its `Enter`. The announcement is
made after the unwind above rather than at admission, so a parent that does not
survive is never announced at all: a subscriber sees what stayed, rather than an
enter/leave pair for a transaction that was never really there.

### RPC fields that were constants chosen to look plausible (#702)

Nine fields returned a fixed value shaped like an answer. Two of them
contradicted another RPC on the same node: `getnetworkinfo.relayfee` was a
hardcoded `0.00001000` — ten times satd's own default — while
`getmempoolinfo.mempoolminfee` had the real figure all along, and
`getblockchaininfo.pruned` was a constant `false` on a node that was pruning,
so a client reading it would ask for a block that had been deleted.

Each now comes from the node: the advertised service flags (the fixed value
claimed `NODE_NETWORK_LIMITED`, which satd never sets, and never showed
`NODE_COMPACT_FILTERS`, which it does), `localrelay` as the inverse of
`-blocksonly`, the real warnings on `getnetworkinfo` and `getmininginfo`, the
BIP 324 session ID on `getpeerinfo` (the field exists for out-of-band MITM
detection and was empty for every v2 peer), and a real P2SH address from
`decodescript`. `savemempool` wrote nothing at all while returning Core's
success value; it now writes `mempool.dat` and returns Core's
`{"filename": …}`.

**PSBT fees are computed through Core's `GetInputUTXO` rules.**
`decodepsbt.fee` and `analyzepsbt.fee` were unconditionally `null` while the
input values sat a few lines away. Computing them meant getting the input
lookup right, and Core's is stricter than it looks (`src/psbt.cpp`): the
`non_witness_utxo` wins where one is present, and only after its txid has been
checked against the input's own `previous_output`. Without that check the value
is whatever the PSBT's author wrote — a PSBT handed to a user for inspection
could carry a `non_witness_utxo` that is not the transaction being spent, or a
`witness_utxo` disagreeing with a correct one, and satd would report a
plausible small fee derived from it. Core omits the field entirely in that
case, which is the signal to go and look. Both RPCs are read-only surfaces.

`analyzepsbt.estimated_feerate` stays absent. Core derives it from a
*dummy-signed* transaction — `AnalyzePSBT` signs every input with
`DUMMY_SIGNING_PROVIDER` and measures the result — and omits both it and
`estimated_vsize` when that fails. satd has no dummy signing provider, so the
only size available is the unsigned one, which understates a signed
transaction by the whole witness: a 1-in/2-out P2WPKH spend is 114 bytes
unsigned against ~141 vB signed, so the quotient would overstate the real rate
by ~24%, and by more as inputs are added. A wrong number on the one field a
signer checks before committing funds is worse than an absent one.

**`decodescript.p2sh` follows Core's `can_wrap`.** The first version of this
gated on "not already P2SH, and at most 520 bytes", which is wrong in both
directions: it minted a P2SH address for scripts that can never be spent (an
`OP_RETURN`, a Taproot or P2A anchor output script, an unknown witness
program, a truncated push) and withheld one for a redeemScript between 521 and
10,000 bytes, which Core returns — rust-bitcoin refuses that as an address and
the empty string was silently dropped, leaving the caller no address and no
error. Core's real predicate is the script *type* plus `HasValidOps`,
`IsUnspendable` and an OP_SUCCESS scan, and that is now what satd applies.
satd's `HasValidOps` was itself only checking for `OP_INVALIDOPCODE`, so it is
corrected to Core's three conditions here too.
## Upgrade notes

No action is required to upgrade: the data directory format is unchanged and
no flag is removed. The changes below alter behaviour an integration may have
been relying on.

### `-prune` is measured in MiB (#702)

Bitcoin Core's `-prune=<n>` is `n * 1024 * 1024` bytes
(`src/node/blockmanager_args.cpp`), and `getblockchaininfo.prune_target_size`
reports that number verbatim. satd read the flag as `n * 1_000_000` in both the
pruner and the report, so `-prune=550` was a 4.9% smaller budget than the same
flag on Core — on the one number an operator sizes a disk against. Both halves
now use MiB, so `-prune=550` reports `576716800` where it used to report
`550000000`, and the node keeps correspondingly more block data.

`-prune=1` is now **refused at startup**. It is Core's spelling for *manual*
pruning (`PRUNE_TARGET_MANUAL`), where the node prunes only when
`pruneblockchain` is called. satd has no `pruneblockchain` RPC, so it cannot
honour that; read as a budget instead, `-prune=1` landed on satd's 288-block
floor and deleted block data automatically — the opposite of what the operator
asked for, silently. Use `-prune=<target in MiB>` for automatic pruning, or
`-prune=0` to keep every block.

### `-whitelist` grants are narrower, and scoped by direction

`getpeerinfo.permissions` now reports what was actually granted, and two grants
were wider than Bitcoin Core's:

- a bare `-whitelist=<subnet>` no longer grants `addr` (Core's implicit set is
  `relay` + `noban` + `mempool` + `download`);
- `-whitelist=@<subnet>` — Core's "match this range, grant nothing" idiom — now
  grants nothing, where satd had been granting the whole implicit set including
  `noban`.

If you were relying on either, name the permissions explicitly:
`-whitelist=noban,relay,mempool,download,addr@<subnet>`.

Entries are also **inbound-only unless they carry an `out` token**, as in Core,
and an `out` entry applies only to manual outbound connections. If you were
relying on a `-whitelist` entry covering peers *you* dial, add `out`:
`-whitelist=noban,out@<subnet>`.

A peer arriving over the Tor hidden service is no longer matched against
`-whitelist` at all. `-listenonion` now also binds its own listener on
`127.0.0.1:<port+1>` unless a `bind=…=onion` entry names one — one extra
loopback socket on a `-listenonion` node, as in Core.

`estimaterawfee` no longer emits `decay`, `scale`, `pass` or `fail`, and omits
a horizon that does not track the requested `conf_target`. `getmemoryinfo`'s
`locked` fields are all `0`. Both are described in `CORE_DIFFERENCES.md`.

### `banlist.json` is written in Bitcoin Core's format

The upgrade is transparent: satd reads both Core's `{"banned_nets": […]}`
object and the bare array it used to write, so an existing ban list carries
over untouched. It writes only Core's form from now on.

**Downgrading is not transparent.** A pre-0.5.2 satd cannot parse the object
form, and its response to an unparseable ban list is the defect this release
fixes — it silently stops persisting bans. If you roll back to 0.5.1 or
earlier, delete `banlist.json` from the network data directory first and
re-apply any bans you need; the node recreates it on start.

### A `-connect`-pinned node no longer listens

`-connect` (in any spelling, including `-connect=0` and `-noconnect`) and
`-maxconnections` ≤ 0 now soft-set `-listen=0`, as Bitcoin Core's
`InitParameterInteraction` does. **If you run a `-connect`-pinned node that
must still accept inbound connections, add an explicit `listen=1`** — or a
`bind` / `whitebind`, either of which holds the default up.

`-connect` and `-addnode` entries written without a port now take the
*network's* default P2P port instead of 8333. On a non-mainnet node this
changes which port such an entry dials; writing `:8333` explicitly still works
and is unaffected.

`-noconnect` is now honoured rather than refused at startup, so a node that
previously failed to start on that flag will now start and open no automatic
connections.
