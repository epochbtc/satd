# satd 0.7.1

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

This file accumulates entries as changes land; it is not yet a cut release.

A bug-fix release for 0.7.0. No reindex. One RPC field changes type to match Core; see Upgrade notes.

## Highlights

- The JSON-RPC listener accepts any request `Content-Type`, as Bitcoin Core does, so Core's own `curl` examples work.
- On a 1-CPU host, RPC and P2P no longer freeze together when one task blocks during initial block download.
- `getnetworkinfo` reports `-onlynet` correctly, and `warnings` is always an array, as in Core.

## RPC

- **Any request `Content-Type` is accepted** (#824). Bitcoin Core reads the JSON-RPC body whatever the request's `Content-Type` says. satd added `application/json` only when the header was missing, so a request that named another type got `415 Unsupported Media Type`. That included Core's documented form, `-H 'content-type: text/plain;'`, and the form type plain `curl --data` sends. Every request is now read as JSON.
- **`getrawtransaction`'s not-found message matches the node's index** (#1066). With `-txindex` on, satd still told the caller to enable `-txindex`. The message now depends on the index, as Core's does:
  - With no index, it keeps that advice.
  - With a complete index, it says `No such mempool or blockchain transaction`.
  - With an index that was turned on after blocks were already connected, it says those blocks are not covered and need a block hash. satd never backfills the index. This stands in for Core's "still being indexed" case.

  The error code is still -5.
- **`testmempoolaccept` agrees with `sendrawtransaction` under an `allow` policy rule** (#999). With a `-policyfile` that holds an `allow` rule, admission records a failure in the exemptable standardness set (too many dust outputs, a non-standard output or input script, ephemeral dust that pays a fee) and forgives it when the transaction's verdict is `Allow`. `testmempoolaccept` returned the standardness refusal before it ran the policy, so it refused transactions `sendrawtransaction` accepted. It now records the same failures, runs the policy dry run, and forgives them on an `Allow` verdict. A `Pass` or `Quarantine` verdict still refuses with the standardness reason, and a node without an `allow` rule is unchanged.
- **`getnetworkinfo` reports which networks are reachable** (#1164). `ipv4` and `ipv6` were always `reachable: true, limited: false`, so a node under `-onlynet=onion` told its operator that clearnet was in use when it made no clearnet connections. Each network's flags now come from the set that drives outbound connections, as Core's `g_reachable_nets` does: `-onlynet` decides, and `onion` also needs a proxy that reaches Tor and no `-onion=0`. `networks` now lists Core's five networks: `i2p` is never reachable, because satd has no I2P transport, and `cjdns` is reachable only with `-cjdnsreachable`.
- **`warnings` is always an array** (#956). `getblockchaininfo`, `getnetworkinfo` and `getmininginfo` returned `"warnings": ""` on a node with no warnings and an array of strings otherwise, so the field's type depended on the node's state. It is now always an array, `[]` when there are none, as in Core since v28. The new `-deprecatedrpc=warnings` brings back Core's deprecated form: one string, the latest warning, or `""`. `-deprecatedrpc` with any other name is warned about at startup and ignored.
- **An open WebSocket no longer outlives its bearer token** (#821). A WebSocket on the JSON-RPC listener resolved its bearer token once, at the upgrade, and jsonrpsee copies that request onto every frame, so the token's principal rode every call for as long as the socket stayed open. Removing the token from the `-authfile` and sending `SIGHUP`, or letting its `expires` pass, did not stop a socket that was already open from calling what the token had been granted, `sendrawtransaction` included. Each frame now resolves the token again, by its digest, against the token table as it stands. A frame whose token was removed or has expired is answered with error `-32006` (`bearer token revoked or expired`), its notifications are dropped, and a `subscribemempool` subscription opened with the token ends at its next event. A reload that changes a token's capabilities or rate limit now reaches open sockets too. New connections were already refused with `401`.

## Electrum

- **Sparrow batches its requests against satd** (#1069). Sparrow decides from the `server.version` name whether a server can take batched requests, and batches only for names it knows, such as one containing `electrumx`. satd's default name, `satd-electrs-compatible/<version>`, matched none of them, so Sparrow sent one request per script hash and wallet scans were much slower than they needed to be. The default is now `satd-electrs-electrumx-compatible/<version>`, which Sparrow recognises. Cake Wallet still finds the `electrs` token it looks for before probing silent-payment tweaks, and the name still does not start with `electrs`, which would turn BlueWallet's batching off.
- **`-electrummaxbatchrequests` defaults to 345** (#1069). Once Sparrow batches, it sends up to 250 `blockchain.transaction.get_merkle` calls in one batch when it verifies a wallet's transactions, and the old cap of 100 would refuse that batch whole. 345 is Fulcrum's default.

## Mempool and relay

- **Transaction versions outside 1 to 3 are non-standard** (#1070). Core's `IsStandardTx` refuses a version below 1 or above 3 with reason `version`. satd had no version check, so `sendrawtransaction`, `testmempoolaccept` and P2P relay accepted a version 0 or version 4 transaction that Core refuses, and satd then relayed it to peers that would drop it. `-acceptnonstdtxn` lifts the rule on test chains, as in Core.

## P2P

- **Disconnect log lines give the right reason** (#1152). Every disconnect the node made for its own reasons, such as a stalling block download or misbehaviour, was logged as `Disconnecting peer on request ... reason="rpc_request"`, as if something had called `disconnectnode`. The line now reads `Disconnecting peer`. It has `reason="rpc_request"` only for `disconnectnode`, and `reason="internal"` otherwise, next to the line that already gives the cause.
- **Onion peers are logged by their onion address** (#1165). The `Peer connected` and `Peer disconnected` lines, and the IBD silent-peer warning, printed `0.0.0.0:<port>` for a `.onion` peer. They now print the address `getpeerinfo` reports, `<host>.onion:<port>`.
- **A pruned node prunes during initial sync** (#1154). The download scheduler shuffled every height up to the header tip into one pool, and its only limit was a count: no more than `-maxahead` blocks downloaded but not yet connected. Once the window filled, each slot it freed went to a random height anywhere up to the header tip. So every block file held a sprinkling of blocks tens of thousands of heights above the tip. Pruning deletes a file only once its highest block is below the cut, so on a pruned node nothing was deleted until IBD was nearly over, and a small disk filled. Blocks are now handed out in height order and never more than `-maxahead` above the tip, as Core's download window works. Two smaller paths are closed as well:
  - A block announced by `inv` during IBD is answered with `getheaders` only, as in Core, instead of being fetched and stored hours before it can connect.
  - A block nobody asked for is not stored when it lies above the window, as Core's `AcceptBlock` refuses one too far ahead.

  Blocks stored above the window by 0.7.0 stay until the tip reaches them.
- **Onion seeds for every network** (#1162). satd had no `.onion` fixed seeds for testnet4 or testnet3, so a Tor-only node (`-onlynet=onion` with `-proxy`) there had no address to dial unless the operator added one by hand. Its 20 mainnet onion seeds were down to 7 that still answered. Of its 2 signet entries, one was not a valid Tor v3 address. The lists now hold the Tor v3 entries of Bitcoin Core v31.2's fixed seeds, kept only where the node answered a version handshake over Tor with the right network magic and `NODE_NETWORK` when they were imported: 138 for mainnet, 41 for testnet3, 49 for testnet4 and 48 for signet.

## Operator

- **`reindex` and `reindexchainstate` in `bitcoin.conf` are honoured** (#840). Both keys were accepted in the config file and then ignored, so an operator who asked for a rebuild there got a normal start. They are now read from the file, as Core reads them, in Core's hyphenated spelling too. As in Core, a file value rebuilds on every start until it is removed.
- **`conf.d/local.conf` overrides what the stack writes** (#843). `satd-init` appended `local.conf` to the rendered `bitcoin.conf` so that its lines would win. satd, like Core, takes the first value of a repeated key, so a `local.conf` line for a key `satd-init` already writes, such as `port`, `txindex` or `prune`, was ignored. `local.conf`'s top-level lines now go first, and any `[section]` blocks in it go last, where a value in the active chain's section wins anyway.
- **The core runtime has at least two worker threads** (#1144). It had one worker per CPU, so a 1-CPU host had a single worker. One blocking call during IBD then stopped JSON-RPC and P2P together for minutes at a time, and RPC accepted connections without answering. A 1-CPU host now gets two workers. Larger hosts are unchanged.
- **The shadow verification queue is bounded by memory** (#1145). Under the default `-consensus=rust-shadow`, every transaction the primary engine accepts is queued for the shadow engine with its serialized bytes and a copy of each output it spends. The queue was bounded only by `-shadowqueuesize`, 4,194,304 entries, which at a few hundred bytes to several KB an entry is gigabytes. On a host with few cores the shadow engine falls behind during IBD, and the queue grew until the process reached its memory limit, without ever reaching the entry cap or logging a drop. The new `-shadowqueuemb` (default 128, in MiB) bounds the bytes the queued work holds. Work past either bound is dropped, as before, and the aggregated WARN now gives the queue's depth and bytes. The primary engine still verifies every script. `-shadowqueuemb=0` restores the entry-count bound alone.

## Upgrade notes

A drop-in upgrade from 0.7.0, with these changes to look for:

- A client that reads `warnings` from `getblockchaininfo`, `getnetworkinfo` or `getmininginfo` as a string gets `[]` on a node with no warnings. It already got an array whenever a warning was active, and Core has returned an array since v28. Start the node with `-deprecatedrpc=warnings` to keep the string form for now.
- A `bitcoin.conf` carrying `reindex=1` or `reindexchainstate=1` now rebuilds on start. Remove the line if the rebuild is not wanted.
- In the docker-compose stack, a `conf.d/local.conf` line for a key `satd-init` writes now takes effect. Check that file for stale lines before upgrading.
- A node whose shadow queue held more than 128 MiB now drops shadow work past that and logs it. Raise `-shadowqueuemb` to keep more.
- The Electrum server reports a new default name, `satd-electrs-electrumx-compatible/<version>`. A client or monitor that matched the old `satd-electrs-compatible` name exactly should match the new one, or set `electrumservername` to keep the old name. `-electrummaxbatchrequests` now defaults to 345; an operator who wants the old limit can set it to 100, but Sparrow then fails to verify a wallet with more than 100 transactions.
- Log consumers that matched `Disconnecting peer on request` should match `Disconnecting peer` with `reason="rpc_request"` instead.

## About this release

satd is free software under the [MIT License](../../LICENSE).

- **Stability & compatibility** — Tier 1 surfaces (Bitcoin Core-compatible
  JSON-RPC wire shape, CLI flag names/defaults, `bitcoin.conf` keys, on-disk
  layout, Electrum/Esplora surfaces) are governed by
  [`STABILITY_POLICY.md`](../../STABILITY_POLICY.md). satd follows
  [semantic versioning](https://semver.org/spec/v2.0.0.html): each feature
  release raises the minor version, and deprecations may be accelerated (see
  the policy).
- **Security & disclosure** — report vulnerabilities per
  [`SECURITY.md`](../../SECURITY.md). Consensus-affecting bugs are treated as
  P0 with same-day acknowledgement.
- **Verifying this release** — tarballs are signed with minisign, container
  images with cosign (keyless OIDC), and git tags with SSH signatures (no GPG).
  The key matrix and verification steps are in
  [`SECURITY.md`](../../SECURITY.md).
- **Intentional differences from Bitcoin Core** — catalogued in
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md).
- **Operating satd** — observability, the full flag matrix, tuning, and the
  downstream packaging contract live in the
  [Operator Manual](https://epochbtc.github.io/satd/).
