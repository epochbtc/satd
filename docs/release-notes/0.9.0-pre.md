# satd 0.9.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.9.0 is in development. So far it adds an optional crawl mode, off by
default: with it off nothing changes.

## Highlights

- **Opt-in network crawl, `-crawl`.** Walks the reachable network as a
  declared crawler, over BIP 324 to nodes that advertise it and v1
  otherwise, and records which
  addresses complete a handshake. `getcrawlinfo` counts the reachable
  network, nodes that speak BIP 324 only included; `dumpcrawlsnapshot`
  exports it, keyed so no clearnet address leaves the node unless asked
  for. See [P2P](#p2p) and [RPC](#rpc).

## P2P

- **Opt-in network crawl, `-crawl`.** With `-crawl=1` the node walks the
  reachable network: it seeds itself from the DNS seeds (`-dnsseed`
  respected; under a proxy the onion seeds, nothing looked up locally), the
  fixed seeds, a uniform sample of the address book, `-crawlseed` addresses
  and its own book, asks reachable nodes for addresses, dials what they
  name, and records the result in `crawlbook.dat` (at most 250,000
  addresses; the file holds peer addresses and is written with the data
  directory's permissions every 10 minutes and at shutdown).

  Each session is short and declares itself: protocol 70016, services 0,
  relay off, the node's real tip height, a fresh random nonce, a dummy
  `addr_from`, and the user agent `/satd:<version>(crawler)/`, with
  `-crawluacomment` as a second comment; then `wtxidrelay`, `sendaddrv2`
  and `verack`, and nothing else unsolicited. The node's own addresses
  and `-uacomment` never appear. As Bitcoin Core does for its own
  outbound connections, BIP 324 is tried first only to a node known to
  advertise `NODE_P2P_V2`: by its own last `version` once a handshake has
  completed, before that by the services its address was last advertised
  with (a seed carries none). Every other node is dialled over v1 with no
  BIP 324 bytes sent, since some v1-only implementations (bcoin 2.2.0,
  libbitcoin-server 3.8.0) close on them and bcoin bans the dialling
  address; a node that speaks v2 without advertising it is counted as v1.
  A node that refuses BIP 324 as a v1-only node does (closing, or never
  answering, with nothing sent back) is redialled over v1, as Bitcoin Core
  does, and a node that did v2 is checked over v1 on first contact and
  weekly, so a node that only speaks v2 is told apart. A discovery session (first contact,
  then once a day, since Core caches its `getaddr` answer for about a day)
  sends one `getaddr`, waits up to 90 seconds for the answer, and with
  `-crawlprobes` (on by default) sends the survey's four probes, each
  checked against Bitcoin Core v32.1 for no misbehaviour score and no
  disconnect. A liveness session (every `-crawlliveness` seconds, 7200 by
  default and at least that, so at most 14 sessions a target a day) closes
  once the handshake settles. Unreachable addresses back off 1 h, 4 h,
  24 h, then daily.

  Limits, each with a ceiling no option lifts: `-crawlconcurrency` (32
  clearnet sessions, at most 256), `-crawltorconcurrency` (8, at most 256),
  `-crawlrate` (10 new sessions a second, at most 100), one session per
  address and two per IPv4 `/16` or IPv6 `/32`. At startup the crawl's
  sessions are fitted into the file-descriptor limit after
  `-maxconnections`: a limit too tight lowers the crawl's concurrency with
  a line in the log, never `-maxconnections`.

  The crawl is kept apart from the node: its connections are outside
  every connection budget and never in `getpeerinfo`,
  `getconnectioncount`, `getpeerbehavior`, eviction or the behaviour flags;
  nothing is relayed over them and a `getaddr` sent over one is answered
  with nothing. The address book is read to seed the crawl and never
  written: `peers.dat` is unchanged by a crawl. What the crawl learns is
  never relayed, served on `getaddr`, or given to the node's own dialer,
  the alt-slots or the extra-network peer. It dials what the node's dialer
  may (`-onlynet`, `-proxy`, `-onion`), narrowed by `-crawlnet`, and never
  clearnet through the proxy, so a Tor-only node crawls onions only; each
  onion dial has a Tor circuit of its own. I2P and CJDNS addresses are
  recorded, never dialled. `-crawlbind` sets the source address of direct
  dials, one per family. No session starts while the node is in initial
  block download, under `-connect`, or with networking off; a panic in a
  crawl task stops the crawl and leaves the node running. All options are
  read at startup only.

  With `-crawl=1` the network survey (`-peersurvey`) opens no connection:
  the crawl measures everything it would, from more addresses.
  `getpeersurvey` still reports the survey's store and says
  `"superseded_by_crawl": true`. `getconfig` reports the settings under
  `crawl`.

  **The crawl dials tens of thousands of addresses from this host's IP
  address** (or `-crawlbind`'s). Other operators' monitors will record it
  as a crawler, it may end up on ban lists that then refuse the node's own
  connections too, and hosting providers may receive abuse reports. The
  node logs this once at startup; a dedicated host is the better place to
  run it.

## RPC

- **`getcrawlinfo` and `getcrawlnodes [verbose]`.** `getcrawlinfo` reports
  the crawl: whether it is on, `running`, `held` (with each reason:
  `initial_block_download`, `connect`, `network_inactive`) or `stopped`
  after a panic in a crawl task; the limits in force, after the ceilings
  and the file-descriptor fitting; the book's size and cap, per network,
  learned and ever reached; sessions reached and not, and those open; the
  crawl's own byte totals, which `getnettotals` does not count; and the
  aggregate over the addresses with a handshake within the liveness window:
  reachable per network (IPv4, IPv6, onion; I2P and CJDNS are only ever
  learned, never dialled), the transport split (BIP 324 and v1, v1 only
  after a failed BIP 324 attempt, v1 with BIP 324 never tried as the node
  did not advertise it, BIP 324 only, BIP 324 with v1 not checked yet, and
  those advertising
  `NODE_P2P_V2`), implementation families (observed only), the families
  only user agents claim, the fake and closed-early nodes (below), and
  mismatches, each reachable address counted once among them. It carries counts
  only and is a read, allowed on the read-only listener and to an
  `rpc:read` token.

  `getcrawlnodes` returns one row per address in the book, most recently
  reached first: the address, network, whether it is reachable now, its last
  handshake, transport class, family and fingerprint; with `verbose`, every field of the
  entry and of its last handshake (user agent, services, height and its gap
  to our tip, clock offset, handshake round trip, `getaddr` answer size and
  delay, probe outcomes). Its rows are raw peer addresses, so it is
  operator control: refused on the read-only listener, and a bearer token
  needs `rpc:write`.

- **`dumpcrawlsnapshot [raw]` and hourly snapshots.** A snapshot is the
  crawl's reachable set (a handshake within the liveness window).
  `dumpcrawlsnapshot` returns it now, shaped as a Bitnodes snapshot:
  `timestamp`, `total_nodes`, `latest_height` (our tip) and `nodes`, each
  node Bitnodes' thirteen fields (protocol version, user agent, services,
  height and ASN filled; connected-since, hostname, the geographic fields
  and organization null, since the node does no geolocation and holds no
  long-lived connection) followed by a `satd` object: network, port class,
  transport class, `NODE_P2P_V2` advertised, family and confidence,
  the family the user agent claims, mismatch, chain check and last
  handshake.

  It is keyed by default. A clearnet node is listed by its node ID,
  HMAC-SHA256 of `ip:port` under a 32-byte key, the first 16 bytes in hex:
  stable across exports, and impossible to test against a guessed address
  without the key. The key is `crawlexport.key` in the network's data
  directory, created with mode 0600 by the first keyed export, or the file
  `-crawlexportkeyfile` names, which satd never creates; satd never rotates
  it. Onions are listed as they are, I2P and CJDNS only as counts, every
  port only as `default` or `other`, and an ASN (from `-asmap` only) with
  fewer than `-crawlexportmink` nodes (default 10) as `"other"`.
  `raw=true` lists nodes by address with exact ASNs. Both forms are
  operator control: refused on the read-only listener, and a bearer token
  needs `rpc:write`.

  Once an hour the crawl also writes the snapshot to
  `crawl/<unix time>.jsonl.gz` in the network's data directory:
  gzip-compressed JSON lines, one per reachable node, raw addresses,
  written with the data directory's permissions, execute bits dropped, as
  `crawlbook.dat` is. Every snapshot of the last 7 days is kept, then the
  first of each UTC day up to 90 days; each write prunes the rest.

- **Metrics and the status page.** `satd_crawl_enabled`,
  `satd_crawl_running`, `satd_crawl_stopped`,
  `satd_crawl_book_entries{network}`, `satd_crawl_reachable{network}`,
  `satd_crawl_transport{class}`, `satd_crawl_v2_advertised`,
  `satd_crawl_family{family}`, `satd_crawl_claimed{family}`,
  `satd_crawl_fake{family}`, `satd_crawl_closed_early`,
  `satd_crawl_mismatches`,
  `satd_crawl_sessions_total{result}`,
  `satd_crawl_sessions_in_flight{network}` and
  `satd_crawl_bytes_{sent,recv}_total`; and, with the crawl on, a Crawl card
  on the status page. Counts only, never an address. Both reuse an
  aggregate for up to 10 seconds.

- **Operator Manual.** A new [Network Crawl](https://epochbtc.github.io/satd/crawl.html)
  chapter: what the crawl does, every option, how it stays apart from the
  node, networks, what `crawlbook.dat` stores, privacy, the risks of
  running one (ban lists, being flagged, ISP and hosting complaints,
  bandwidth) and Tor tuning for onion crawls.
- **Crawl fingerprints and the chain check.** A crawl session is judged
  against rows captured against the crawl's own `version` (services 0,
  relay off), not against the rows for ordinary connections: peers answer
  a crawler differently. A crawl row matches the traits that set its
  family apart rather than the whole transcript of one release, and each
  family's rows were checked, by a named test that replays every capture,
  against captures of two or more releases: Bitcoin Core 24.0.1, 28.1,
  31.1 and 32.1 with Knots 28.1 and 29.5.1 (`wtxidrelay` and `sendaddrv2`,
  then `sendcmpct` with no `feefilter` or `sendheaders` before the next
  message), satd 0.6.3, 0.7.2 and the 0.8 development tree (`feefilter`
  before its next message, or 0.6 and 0.7's `getheaders` straight after
  `verack`), rbitcoin 0.8.0, 0.8.99 and 0.9.2 (`sendheaders`, BIP 324
  only), btcd 0.24.2, 0.25.0 and 0.27.0 (`sendaddrv2` with no
  `wtxidrelay`), bcoin 2.0.0, 2.1.2 and 2.2.0 (protocol 70015 and its own
  `addr` straight after `verack`) and libbitcoin-server 3.6.0 and 3.8.0
  (protocol 70013, relay off, its own `ping` straight after `verack`). A
  row also pins what no capture of it contradicted: the BIP 324 greeting
  (no decoy packet and an empty version packet in every capture), the
  probes' answers (`notfound` for the unknown transaction from all but
  Bitcoin Core, which answers it only when its operator grants the crawler
  relay; silence for the unknown message; never a disconnect), the
  `getaddr` answer's message (`addrv2`), and whether the implementation
  completes a BIP 324 handshake at all. So a crawl session can be `known`
  with high confidence where the survey's handshake alone would be low.

  When no row matches, the session reports the family its user agent
  names at a fourth confidence, `claimed`, below `low`: a node that closed
  on a probe, or a release no capture has. A claimed family is never
  counted as observed: `getcrawlinfo` counts it per family under
  `claimed` (not under `unknown`, next item), the metrics under
  `satd_crawl_claimed{family}`, and the export gives it a null `family`. It is never a mismatch. A user
  agent that names no family stays `unknown`. Connected peers and the
  network survey now claim the same way (next item). A session no row matched keeps its
  handshake transcript, `relay` flag, BIP 324 greeting and `getaddr`
  answer in `crawlbook.dat`, bounded to 16 commands of 12 bytes, so a new
  implementation shows up as many records of one shape before it has a
  row. The book's format version is now 4 (next item); a version 2 or 3
  book, written by an earlier 0.9.0 development build, keeps its entries
  and drops their observations, and an older one is set aside and the
  crawl starts afresh.

  A discovery session's `getheaders` probe (our tip's parent as locator,
  our tip as stop, as before) is also a chain check: the answer tells a
  node on our chain (it sends our tip), one behind (nothing past the
  locator, or only our older blocks from its genesis), one on a fork
  (another block after the locator, or blocks that leave our chain) and
  one on another chain under this network's magic (its answer starts from
  a block we do not know). The check reads at most three block-index entries
  per session. It runs under `-crawlprobes` only, and the session is still
  checked against Bitcoin Core v32.1 for no misbehaviour score and no
  disconnect.

- **Crawl sessions that closed early or claim Core falsely are counted
  apart**, as the survey's records are (below), by the same rule: the
  survey's evidence, on a synced mainnet node, holds for the crawl's
  sessions too. A session whose peer closes the connection during the
  passive wait, before its handshake transcript settles, is **closed
  early**: mostly ordinary Core nodes with full inbound slots, evicting
  the youngest connection of their largest network group, which a crawl
  session seconds old often is. The node still counts as reachable, by
  network and by transport; its observation keeps the `version`'s fields
  (user agent, protocol version, services, height) and has no
  fingerprint. A session with a Core user agent, a common protocol
  version of 70016 or more, a transcript of exactly `version` then
  `verack` and a passive wait that timed out with the connection open is
  **fake**: every Core since 0.21 sends `wtxidrelay` and `sendaddrv2`
  before its `verack` at that version. Neither changes how the crawl
  dials the node, how often, or its transport class, and a later session
  replaces the verdict as any newer observation replaces the last.
  `getcrawlinfo` gains `fake` (per claimed family, `{count, share}`) and
  `closed_early` (`{count, share}`), and `families.unknown` now counts only
  the reachable addresses no row matched whose user agent names no
  family, so each reachable address is counted once among `families`,
  `claimed`, `fake` and `closed_early`. In `getcrawlnodes` (and its
  `observation`) such a row's `fingerprint` reads `fake/core` or
  `closed-early`, with a null `family` and the user agent's family in
  `claimed`; the export's `satd` object gains the same `fingerprint`, with
  a null `family` and `confidence` for both. New metrics
  `satd_crawl_fake{family}` and `satd_crawl_closed_early`;
  `satd_crawl_family{family="unknown"}` no longer counts claimed
  addresses. `crawlbook.dat` is written in format version 4, each
  observation carrying its verdict (below).

- **The crawl retries closed-early addresses, and keeps a settled
  fingerprint.** A node that closed one session early to evict it often
  has room for a later one: by hand, 2 of 5 such addresses connected
  normally on a later try. An address whose session closed early and that
  has no settled observation now has its next session brought forward: a
  liveness session 15 minutes after the closed-early one, then, after each
  further closed-early session or a retry that completed no handshake,
  30 minutes, 1 hour, 2 hours and then 4 hours for every later one, each
  wait moved at random by up to a fifth either way. At most ten retries
  are scheduled; then the address waits for its next ordinary session,
  and a closed-early result there does not start them over. The first
  session that settles clears the schedule. A retry runs under the crawl's
  usual concurrency, rate, network and BIP 324 rules, and an unreachable
  address's backoff still comes first; nothing else about scheduling
  changes. A closed-early session no longer replaces a settled
  observation: an address already observed with a fingerprint (any
  confidence) or as fake keeps that observation, and the session updates
  only its reachability, transport results and timers. A fake session
  still replaces a classified one. `getcrawlinfo` gains `retries`
  (`pending`: closed-early addresses in the book with a retry scheduled;
  `exhausted`: those with none left), and a closed-early `getcrawlnodes`
  row gains `retry` (`count`, `next_due`). New metric
  `satd_crawl_closed_early_retries`. `crawlbook.dat` is written in format
  version 5, each entry carrying its retry schedule (below).

- **Node fingerprints match traits, and claim.** Connected peers
  (`getpeerbehavior`) and the network survey (`getpeersurvey`) are judged
  against node rows that, like the crawl rows, name the traits that set a
  family apart rather than the whole transcript of one release. Before
  this, a node row was one release's exact transcript, so every other
  release came back `unknown`: on a synced mainnet node 185 of 571 survey
  addresses were unknown though every one named a family in its user agent
  (181 Bitcoin Core, 109 of them Core 25; 4 btcd). Each row is checked, by
  a named test that replays every capture, against inbound and outbound
  captures of several releases, and against captures greeted as the survey
  greets a node (`capture.py --survey`, new): Bitcoin Core 0.20.2,
  0.21.2, 22.1, 23.2, 24.2, 25.2, 28.1, 31.2 and 32.1 with Knots 28.1 and
  29.4.3 (dialing us: `wtxidrelay` and `sendaddrv2`, then `getaddr`, or for
  0.20 protocol 70015 and `getaddr`; dialed by us since 24: `sendcmpct`
  with no `sendheaders` or `feefilter` before its next message; before 24:
  `sendheaders`, then `sendcmpct` twice), satd 0.7.0, 0.7.2 and the 0.8
  tree (`getheaders` before any `sendcmpct`), rbitcoin 0.8.0, 0.8.99 and
  0.9.99 (`sendheaders` and one `sendcmpct`), btcd 0.24.2, 0.25.0 and
  0.27.0 (`sendaddrv2` with no `wtxidrelay`, relay on), bcoin 2.0.0, 2.1.2
  and 2.2.0 (protocol 70015 and its own `addr` first), and
  libbitcoin-server 3.8.0, Floresta 0.9.1 and the two crawlers as before.
  A row covers the directions it was captured in. Core before 0.21
  dialing us sends what the bitcoin-seeder sends (`version verack
  getaddr`), so both are now `low`: only the protocol version tells them
  apart. On regtest Core 25.2
  matched the old row in both greetings, so the mainnet unknowns are not
  reproduced locally; their shapes are now kept (below) to tell why.

  As in the crawl, a session no row matches reports the family its user
  agent names at `claimed`, never counted as observed and never a
  mismatch: `getpeersurvey` counts it per family in a new `claimed` (not
  under `unknown`, next item), `getpeerbehavior` reports it as
  `"result": "claimed"`, the metrics in new
  `satd_peer_survey_claimed{family}` and `satd_peer_fingerprint_claimed{family}`
  series (`satd_peer_fingerprint{family="unknown"}` still counts a
  claimed connected peer too), and an alt-slot candidate with only a claim is unverified and
  matches no `family:` rule. A survey record no row matched keeps its
  handshake transcript (at most 16 commands) and `relay` flag, shown by
  `getpeersurvey true` as `handshake` and `relay` and logged under
  `-debug=net` when its survey connection ends. `peersurvey.dat` is
  written in a new format (`satdsrv2`). A file in the old one is dropped
  as it is read, its record count logged: those records were judged
  before the trait rows, and a survey revisits an address too rarely for
  them to be replaced, so they would stand in the tallies under their
  old fingerprints indefinitely.

- **Survey records that closed early or claim Core falsely are counted
  apart.** Of 183 survey records no row matched on a synced mainnet node,
  181 claimed Core, in two groups. 105 had the transcript `version
  wtxidrelay sendaddrv2 verack` (Core 26 to 32 user agents, mostly over
  BIP 324) and no probe result, because the peer closed the connection
  during the passive wait. These are ordinary Core nodes with full inbound
  slots: on each new inbound connection Core evicts one, protecting peers
  by network group, ping time, recent relay and connection age, then
  dropping the youngest connection of the largest network group, which a
  survey connection seconds old is. Dialled again, an address closed at
  once on one try and relayed normally for over 40 seconds on another.
  Such a record is now **closed early**: it keeps the `version`'s fields
  and gets no fingerprint. 74 others claimed `/Satoshi:25.0.0/` or
  `/Satoshi:25.1.0/` over v1, sent exactly `version` then `verack` at
  protocol 70016, where every Core since 0.21 sends `wtxidrelay` and
  `sendaddrv2` before its `verack`, kept the connection open through the
  wait and sent nothing more, most not even answering a `ping`. A session
  with a Core user agent, a common protocol version of 70016 or more, a
  transcript of exactly `version verack` and a wait that timed out with
  the connection open is now **fake**. `getpeersurvey` gains `fake` (per
  claimed family, `{count, share}`) and `closed_early` (`{count,
  share}`); `families.unknown` now counts only the records no row matched
  whose user agent names no family, so each record is counted once among
  `families`, `claimed`, `fake` and `closed_early`, and every share is of
  all records. In `getpeersurvey true` such a row's `fingerprint` reads
  `fake/core` or `closed-early`, with the user agent's family in
  `claimed`. New metrics `satd_peer_survey_fake{family}` and
  `satd_peer_survey_closed_early`; `satd_peer_survey_family{family="unknown"}`
  no longer counts claimed records. Neither kind matches an alt-slot
  `family:` rule, as an unknown record does not, and both still count as
  completed survey connections. `peersurvey.dat` is written in a new
  format (`satdsrv3`); a `satdsrv1` or `satdsrv2` file is dropped as it is
  read (below).

- **The survey retries closed-early addresses, and keeps a settled
  fingerprint.** An address recorded closed early is dialled again: due
  15 minutes after its closed-early session, then, after each further
  closed-early session or a retry whose dial or handshake failed,
  30 minutes, 1 hour, 2 hours and then 4 hours for every later one, each
  wait moved at random by up to a fifth either way. A due retry takes the
  next survey connection ahead of the uniform draw, passed over as a drawn
  address would be (named by the operator, banned, connected or being
  dialled, on a network the node does not reach, a bad port); the survey
  still opens one connection at a time, and retries count in
  `connections` as any survey connection does. At most ten retries are
  scheduled; then the address stays closed early until the draw reaches it
  again, and a closed-early result there does not start them over. The
  first session that settles clears the schedule. A closed-early session
  no longer replaces a settled record: an address already recorded with a
  fingerprint (any confidence) or as fake keeps its record, transcript
  and probes, and only its `last_seen` moves on. A fake session still
  replaces a classified record. `getpeersurvey` gains `retries`
  (`pending`, `exhausted`), and a closed-early row of `getpeersurvey true`
  gains `retry` (`count`, `next_due`). New metric
  `satd_peer_survey_closed_early_retries`. `peersurvey.dat` is written in
  format `satdsrv4`, each record carrying its retry schedule (below).

## sat-tui

- **Network crawl row on the Chain view.** On a node running `-crawl`,
  the Chain view gains a row of its own below the survey's place. Network
  crawl shows the crawl's state (running; held, with each reason: initial
  block download, `-connect`, networking off; or stopped after a panic in
  a crawl task), the addresses reachable now, a bar per family (its
  observed addresses, then its claimed ones in a darker shade, as the
  survey's; the 8 largest, then other) and the non-Core share, of
  observed families only. Crawl detail shows the reachable addresses by
  network (IPv4, IPv6, onion) and by transport (v2 and v1, v1 only, v1
  with v2 not advertised, v2 only, v2 not yet checked over v1),
  mismatches, the claimed share and its 3 largest families, `fake:` and
  `closed early:` lines (not drawn against a node without `fake` and
  `closed_early`, whose claimed addresses are taken out of its `unknown`
  count, which included them), sessions reached and unreached since start, sessions open against the
  concurrency limits and the book against its cap. On a short terminal the
  row collapses to one `crawl:` line above the footer. With the crawl on,
  the Network survey row, where `-peersurvey` was asked for too, becomes
  one line, `survey: superseded by the crawl`, with the records the survey
  kept. The TUI reads only `getcrawlinfo`, which carries counts, and never
  `getcrawlnodes` or `dumpcrawlsnapshot`; a family or hold name is drawn
  only as a plain word, so no address can reach the screen. With the
  crawl off, or against a node without `getcrawlinfo`, the row is not
  drawn. See the [sat-tui](https://epochbtc.github.io/satd/tui.html)
  chapter.
- **Claimed families in the survey and peer panels.** Each family bar in
  the Network survey row is now the family's observed addresses followed
  by its claimed ones in a darker shade; `unknown` holds only addresses
  whose user agent names no family. Survey detail gains a `claimed` line,
  the share of addresses no row matched whose user agent names a family,
  and the 3 largest such families, and `fake:` and `closed early:` lines.
  Against a node without `fake` and `closed_early`, those two lines are
  not drawn and the claimed addresses are taken out of its `unknown`
  count, which included them. Peer clients counts a connected peer whose fingerprint is only
  claimed as `unknown [core]`, and the peer detail overlay says the user
  agent names the family. Against a node without `claimed`, nothing
  changes.

## Upgrade notes

No action required: the crawl is off by default.

A node that runs the network survey drops the records of a
`peersurvey.dat` in an older format (`satdsrv1` or `satdsrv2`) when it
starts, logs how many it dropped, and the survey fills again from empty;
the file is rewritten in the new format (`satdsrv3`) on its next save.
Older records cannot be sorted into the new categories, since whether the
peer closed the connection early was never stored, and a uniform survey
revisits an address too rarely to replace them. A damaged old file is
still set aside. An older build cannot read a `satdsrv3` file: on a
downgrade it sets the file aside and the survey starts empty.

A `peersurvey.dat` in format `satdsrv3` (written by an earlier 0.9.0
development build) keeps every record and its verdict, each with no retry
scheduled: a closed-early address gets its first retry after its next
closed-early session. The file is rewritten as `satdsrv4` on its next
save; an older build cannot read it and sets it aside. Likewise a
`crawlbook.dat` in format version 4 keeps every entry and observation,
each with no retry scheduled, and is rewritten in format 5, which an
older build sets aside.

`getpeersurvey`'s `families.unknown` and
`satd_peer_survey_family{family="unknown"}` no longer include claimed
records; add `claimed`, `fake` and `closed_early` to get the old count
(for a node whose records were all written by this build).

A node that runs the crawl and has a `crawlbook.dat` from an earlier
0.9.0 development build (format version 2 or 3) keeps every entry, with
its reachability, transport results, sources and timers, and drops each
entry's last observation, logging how many: neither version stored
whether the peer closed the connection during the passive wait, so no
observation can be sorted into the new categories. The crawl revisits
every reachable address within the liveness window (`-crawlliveness`,
2 hours by default), which observes it again; until then such an
address counts as reachable under `families.unknown`, with null
observation fields in `getcrawlnodes` and the export, and the next
session to it is dialled as its advertised services say rather than as
its last `version` did. Probe answers, the `getaddr` answer and the
chain check return with its next discovery session (within a day). The
file is rewritten in format 4 on its next save; an older build cannot
read it and sets it aside. `getcrawlinfo`'s `families.unknown` and
`satd_crawl_family{family="unknown"}` no longer include claimed
addresses; add `claimed`, `fake` and `closed_early` to get the old
count.

## About this release

satd is free software under the [MIT License](../../LICENSE).

- **Stability & compatibility** — Tier 1 surfaces (Bitcoin Core-compatible
  JSON-RPC wire shape, CLI flag names/defaults, `bitcoin.conf` keys, on-disk
  layout, Electrum/Esplora surfaces) are governed by
  [`STABILITY_POLICY.md`](../../STABILITY_POLICY.md). satd follows
  [semantic versioning](https://semver.org/spec/v2.0.0.html): each feature
  release raises the minor version, and deprecations may be accelerated (see
  the policy).
- **Security & disclosure** — report vulnerabilities per
  [`SECURITY.md`](../../SECURITY.md). Consensus-affecting bugs are treated as
  P0 with same-day acknowledgement.
- **Verifying this release** — tarballs are signed with minisign, container
  images with cosign (keyless OIDC), and git tags with SSH signatures (no GPG).
  The key matrix and verification steps are in
  [`SECURITY.md`](../../SECURITY.md).
- **Intentional differences from Bitcoin Core** — catalogued in
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md).
- **Operating satd** — observability, the full flag matrix, tuning, and the
  downstream packaging contract live in the
  [Operator Manual](https://epochbtc.github.io/satd/).
