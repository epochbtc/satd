# satd 0.7.2

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

A bug-fix release for 0.7.1. No reindex.

## Highlights

- **Initial sync is about ten times faster early on.** Blocks and headers
  no longer wait for the P2P loop's 500 ms tick, and header sync no longer
  downloads the header chain many times over ([details](#ibd)).
- **A fresh testnet4 sync gets past block 51,540.** In 0.7.0 and 0.7.1 it
  stopped there for good ([details](#ibd)).
- **Esplora no longer copies the whole mempool per request**, and five more
  fixes for what peers, clients and the Tor control port can make the node
  do ([details](#p2p-esplora-electrum-and-tor)).

## IBD

**Blocks and headers no longer wait for the P2P loop's tick (#1228).** Each
peer's connection hands its messages to one loop, which woke at once only
for a `getdata` and otherwise ran every 500 ms. An arriving `block` or
`headers` message waited for that tick, so each tick took in the blocks
that had landed, asked for the next ones and went back to sleep. A peer
delivered about 25 blocks a second whatever their size, and header sync
advanced one 2,000-header batch per tick. The cost was per message, not per
byte, so it dominated the early chain, where blocks are small: from one
peer on local storage, a fresh mainnet sync reached about 6,700 blocks in
its first five minutes. Every message now wakes the loop as it arrives, and
the same sync reaches about 67,000. Below the first ~100,000 blocks the
limit is now the storage's flush latency, since every stored block is
synced to disk.

**Header sync fetches each header once per peer, not many times (#1229).**
During initial sync the node sent a fresh `getheaders` every two seconds,
and asked three other peers for headers after every full batch. Each of
those requests started its own chain of follow-ups to the header tip, so the
number running at once grew for as long as header sync lasted. A fresh
mainnet sync from one peer received 5.6 GB of `headers` messages for a
78 MB header chain, and the duplicate answers queued ahead of block
requests at the peer. A new request now goes out only after the header tip
has stood still for 10 seconds, at most once per 10 seconds, and a full
batch asks only the peer that sent it for the next one. The same sync now receives 79 MB.

A fresh testnet4 sync on 0.7.0 or 0.7.1 stopped at height 51,539 and never
got further (#1216). Block 51,540 holds ten transactions of 1,420 inputs
each. The script engine re-reads the whole transaction for every input, so
checking that block takes minutes on a busy machine, while connecting no
block and blocking the P2P loop. After 300 s the stall watchdog took that
for a wedge and shut the node down, and every restart came back to the same
block.

Two changes, either of which gets the sync through:

- **Default `-assumevalid` for testnet4 and testnet3.** They now ship
  Bitcoin Core's defaults: testnet4 block 123,613
  (`0000000002368b1e4ee27e2e85676ae6f9f9e69579b29093e9a82c170bf7cf8a`) and
  testnet3 block 4,842,348
  (`000000007a61e4230b28ac5cb6b5e5a0130de37ac1faf2f8987d2fa6505b67f4`).
  Before, neither had a default, so every script was verified. Scripts are
  skipped only under Core's conditions, as for mainnet and signet. Mainnet
  and signet keep their defaults. `-assumevalid=0` still verifies
  everything.
- **The stall watchdog counts script verification as progress.** Script
  inputs verified now reset its timer, as a connected block or a turn of
  the P2P loop already did. A block that takes minutes to verify no longer
  triggers it. A real wedge still does: when nothing is verified, nothing
  connects and the P2P loop is stuck, the watchdog fires after
  `-stallwatchdogsecs` as before.

## P2P, Esplora, Electrum and Tor

**Esplora no longer copies the whole mempool on every request.** `GET /`,
`/mempool`, `/mempool/txids`, `/mempool/recent` and `/tx/:txid/outspends`
each took a copy of every mempool entry, transaction included, while
holding the mempool's lock; `GET /` did it only to count them. These routes
need no credentials, so any client that could reach the Esplora port could
make the node copy hundreds of megabytes per request and hold up mempool
writers while it did. They now read the mempool in place, and
`/outspends` looks up each output's spender instead of indexing every
mempool input.

**An empty `getblocktxn` disconnects the peer.** A `getblocktxn` that names
no transaction has no honest use, but satd answered it: with a disk read,
or for a block more than 10 deep with the whole block. A 33-byte request
could make the node upload up to 4 MB. Bitcoin Core v32 disconnects such a
peer, without a ban, and satd now does too.

**A new block is announced only after its transaction rules pass.** satd
sends a compact announcement for a block that extends its tip before
connecting it, as Core does. It sent it before checking the coinbase's
BIP 34 height and each transaction's finality, so a block that broke them
could be announced and then refused, and a peer that checks before relaying
could disconnect us for it. Core announces only after those checks
(`ContextualCheckBlock`); satd now does the same. Such a block still needs
valid proof of work.

**Tor replies and the saved onion key are checked before use.** The onion
address `ADD_ONION` returned was advertised, and the private key saved,
without any check, and the saved key was sent back to Tor unquoted, so a key
file holding a space could add arguments of its own to the command. As in
Core's next release: a key must be `ED25519-V3:` followed by the base64 of 64 bytes;
a malformed key from Tor is refused, and a malformed saved key is refused
with a warning naming the file (remove it to get a new key and a new onion
address); the service ID must be a valid v3 onion address. A control-port
line longer than 100,000 bytes is refused instead of buffered until the
read timeout.

**The Electrum server skips notifications.** A request with no `id` ran its
handler, and only the reply was dropped. With no reply written, the
backpressure that slows a client that stops reading never applied, and one
batch line could carry up to `-electrummaxbatchrequests` calls. Electrum
clients do not send notifications; they are now skipped without running.
An `"id": null` request is treated as a notification, as before.

**`addnode` refuses an empty node.** `addnode "" add` kept the empty entry
and retried it for as long as the node ran. An empty or blank node is now
refused for every command with `-8 Error: Node address cannot be empty`,
as in Core.

## Memory and chain

**`-dbcache=auto` respects the node's memory limit (#1272).** The starting
cap was half of the host's `MemTotal` (up to 8 GiB), and the adaptive
controller sized the cache from the host's `MemAvailable`. Neither read a
cgroup limit, so a node confined by a systemd `MemoryMax=`, a Docker
`--memory` or an app-store container limit started with a cache sized for
the whole host and could be OOM-killed during initial sync. satd now reads
the memory cgroup the process runs in, and every ancestor up to the root,
and uses the smaller of the host figure and the cgroup's for both: the
total is the tightest `memory.max` or `memory.high`, and the available
memory is that limit less `memory.current`, plus the reclaimable page cache
(`active_file` and `inactive_file` in `memory.stat`). cgroup v1
(`memory.limit_in_bytes`, `memory.usage_in_bytes`) is read the same way.
Container and app-store installs (Umbrel, StartOS, Docker) benefit most.
Where the cgroup files are absent or unreadable the host figures apply as
before; nothing changes off Linux.

**`invalidateblock` and `reconsiderblock` end on the best valid chain
(#1261).** When re-activating the chain met an invalid block on the best
candidate branch, satd marked that block invalid, rolled back, and stopped:
the node stayed on the invalidated block's parent and the call returned an
error, even when another branch with more work than the parent was valid.
Core's `ActivateBestChain` looks for the next-best chain after each invalid
block and tries again, and satd now does the same, until a branch connects
or none is left. The call then succeeds. An error that is not about a block
(a block that cannot be read, a database write) still stops it and is
returned as before. `preciousblock`, and the startup repair of a tip left
invalid by a crash during `invalidateblock`, take the same path.

## Upgrade notes

No action required; a drop-in upgrade from 0.7.1. A testnet4 or testnet3
node already past the default block keeps running as before. A node stuck
at 51,539 on 0.7.1 continues its sync after the upgrade.

A node run with `-dbcache=auto` under a memory cgroup limit lower than host
memory starts with a smaller cache and keeps it within that limit. Set a
number, `-dbcache=<MB>`, to size it by hand.
