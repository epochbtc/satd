# satd 0.6.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.6.0 is a minor release on the 0.x line. Planned scope: a **native
Stratum V1/V2 solo-mining server**, so a home miner can point hardware at its
own node without a pool or a translation proxy; **BIP 375 silent-payment
sending**, completing the send side of the receive support shipped in 0.5.0;
and a round of sync/reindex robustness and Bitcoin Core parity work.

A new listening surface is minor-version material, which is why this is 0.6.0
rather than a patch on the 0.5.x line.

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- **Metrics over TLS.** Prometheus can scrape satd from another machine
  without a reverse proxy.
- **Install from Umbrel's community store, or boot a signed appliance
  image.** Umbrel users add `https://github.com/epochbtc/umbrel-apps`; the
  StartOS package is submitted to Start9's community registry; appliance VM
  images for amd64 and arm64 are attached to this release for the first time.
  See [Installing satd](https://epochbtc.github.io/satd/installing.html).
- **A written SDK ↔ node compatibility rule.** The events gRPC API advertises
  the node's version, and the stability policy now says which SDK versions
  work with which nodes.
- **Stratum V1 and V2 solo-mining server.** Point a miner at the node and mine
  to your own address, with no pool and no proxy.
- **`getblocktemplate` is correct at a retarget boundary.** Templates used to
  carry the previous block's difficulty, which is wrong once every 2016 blocks.

## Mining

### Stratum V1 solo-mining server

`--stratum=1` starts a Stratum V1 server inside the node. A miner connects,
receives work built from the node's own block template, and any block it finds
is accepted, taken out of the mempool and relayed by the same process. The
username a miner presents is the payout address (`<address>.<worker>`), with
`--stratumaddress` as the fallback; the coinbase pays that address the whole
reward. There is no share accounting and no payout splitting — this is a solo
server, in the model of `ckpool -B`.

- **Loopback by default.** The plaintext listener binds `127.0.0.1:3333`. A
  Stratum V1 session carries the payout address in cleartext, where anyone on
  the path can rewrite it, so a non-loopback `--stratumbind` with no TLS
  listener is refused unless `--stratumallowplaintextremote=1` is set.
- **TLS and mTLS** on `--stratumtlsbind`, with the same flag shape as the
  Electrum and Esplora listeners. ESP-Miner-based firmware (AxeOS) stores at
  most 511 bytes of custom CA certificate; the manual gives a CA recipe that
  fits, and satd warns at startup when the configured chain ends in a larger
  one.
- **Vardiff** toward one share per 30 seconds, BIP 310 version rolling,
  `mining.suggest_difficulty`, and a clean job on every tip change plus a
  refresh every 30 seconds.
- **No work during initial block download** (regtest exempt). **Refused on
  signet**, whose blocks need the network's signing key.
- `getserverstatus` reports the `stratum` and `stratum_tls` listeners.

### Stratum V2

`--stratumv2bind` adds a Stratum V2 listener to the same server: the Mining
Protocol over a Noise NX connection authenticated by the server's authority
key. Standard and extended channels are both served (AxeOS 2.14 and later
uses extended channels natively), jobs follow the future-job /
`SetNewPrevHash` sequence, and vardiff is sent as `SetTarget`. The listener
may bind a network address without TLS.

The authority key is created once at `<datadir>/stratum_v2.key`
(`--stratumv2key` to override), mode 0600, and its public key is logged in hex
and in the base58check form miner firmware accepts. Miners pin that key, so it
survives restarts, a malformed key file stops the node instead of being
replaced, and it belongs in datadir backups. The Stratum V2 message types and
the Noise implementation come from the `stratum-core` crate (MIT or
Apache-2.0).

### Job Declaration and `getstratuminfo`

`--stratumv2jd=1` serves the Stratum V2 Job Declaration Protocol on the V2
listener, so a miner running a Job Declarator Client can choose the
transactions in its blocks: it allocates a token, declares a coinbase and a
transaction list by wtxid, and mines a `SetCustomMiningJob` on an extended
channel. The semantics are solo-mining ones. Every declared transaction must
already be in this node's mempool, in minable order; the server never fetches
missing transactions. The coinbase must build on the current tip, pay the
token's address, and claim no more than the subsidy plus the declared fees.

`getstratuminfo` reports the server's listeners, authority key, connections,
channels, share counters, blocks found and current job. It answers
`enabled: false` on a node with the server off. See the
[Stratum Mining Server](../manual/src/stratum.md) chapter of the Operator Manual.

### Verifying a miner from the node

`-debug=stratum` (or `debug=stratum` in the config, or
`sat-cli logging '["stratum"]'` at runtime) turns on the Stratum server's
per-miner debug lines. They name the device: the user agent a Stratum V1 miner
subscribes with, or a Stratum V2 miner's vendor, hardware and firmware. They
show the version-rolling mask the miner was granted and any difficulty it
suggested, log every accepted share with the difficulty its header achieved,
and give each miner a status line every five minutes with its share counts and
an estimated hashrate. The category is off by default, so a node with miners
attached logs no per-share lines unless asked.

Some lines are logged without it. When a miner disconnects, one info line
gives how long it was connected, its accepted, rejected and stale shares, its
best share and its estimated hashrate. Every refused share is logged at warn
with its reason. Before this, a Stratum V1 submit that was malformed, came
before authorize or had a bad extranonce was counted in `getstratuminfo` but
never logged. A low-difficulty refusal also names the difficulty the header
achieved, which tells a miner hashing the wrong header (every share far below
target) apart from an unlucky one. The
[Verifying a miner](../manual/src/stratum.md#verifying-a-miner) section of the
Operator Manual says what to look for.

`getstratuminfo` now has a `miners` array: one entry per authorized Stratum V1
connection or open Stratum V2 channel, with its peer, payout address, worker,
device, current difficulty, share counts, best share, last share time and
estimated hashrate. There is also a node-wide `hashrate`. While the server
runs, the metrics endpoint exports `satd_stratum_connections`,
`satd_stratum_miners`, `satd_stratum_shares_total` (by `result`),
`satd_stratum_blocks_found_total` and `satd_stratum_hashrate_hashes_per_second`.
The metrics are node-wide only, since a label on a miner-chosen worker name
would be unbounded.

### A found block is saved before it is submitted

A block with valid proof of work is the one thing a solo miner cannot make
again. Until now a block found through the Stratum server lived only in memory
between the share and `submitblock`'s path: had the node refused it, or had
block acceptance panicked, the block would have been gone. The server now
writes every found block to `<datadir>/stratum/found/<height>-<hash>.hex`
first — the serialized block as one line of hex, written to a temporary file,
synced and renamed into place — and only then submits it. A failed write is
logged at error and does not hold up the submission. A refused block's warning
names the saved file, which any node will take:

```sh
sat-cli -stdin submitblock < <datadir>/stratum/found/<height>-<hash>.hex
```

The files are kept after a successful submission too; there is one per block
found, so they do not accumulate.

### Block templates at a retarget boundary

Block templates took the previous block's `nBits` on every network except
regtest. On mainnet that is wrong at every height divisible by 2016, and on
testnet3/testnet4 also at every retarget and after any 20-minute gap between
blocks, so a miner working such a template found a block the node itself
rejected as `bad-diffbits`. This affected `getblocktemplate` and any pool
software driven by it. Templates now take the difficulty from the same
computation that validates a received block, evaluated at the template's
timestamp; on testnet4 the timestamp is also lifted to the BIP 94 timewarp
floor at a period boundary, as Bitcoin Core does.

`getblocktemplate` reported `mintime` equal to `curtime`. It now reports the
median time past of the tip plus one, which is Core's value and the actual
earliest valid timestamp.

### Block templates keep to the sigop limit

A block may carry at most 80,000 signature-operation cost, and a template was
built to the weight limit alone. A mempool dense in sigops fills that budget in
a fraction of a block's weight: a bare multisig output counts 20 sigops (80
cost), so a thousand of them do it. The template then held a block the node
itself refuses as `bad-blk-sigops`. That reached `getblocktemplate` and any pool
software driven by it, `generatetoaddress`, and the Stratum server, whose
miners would have been hashing a block that could not be accepted.

Templates now budget sigops as Bitcoin Core's block assembler does: 400 of the
80,000 are reserved for the coinbase, and a transaction that would bring the
total to 80,000 is left out for one that fits. The Stratum server's coinbase
costs at most 4, for a P2PKH payout. `getblocktemplate` now reports each
transaction's `sigops`, as Core does, so a client assembling its own block can
keep to `sigoplimit`.

Stratum V2 Job Declaration applies the same limit. A declaration whose
transactions and coinbase could exceed it is refused with
`invalid-job-param-value-wtxid_list`, and a custom job whose own coinbase
outputs push the block over is refused with
`invalid-job-param-value-coinbase_tx_outputs`. When the extranonce is not
inside a push in the coinbase scriptSig, its bytes are opcodes chosen after the
check, so the scriptSig is counted at the most any opcode can cost.

## Networking

### Compact block relay hardening

satd now checks the header of a BIP 152 `cmpctblock` — proof of work, a known
parent, more work than the tip — before it reconstructs the block from its
mempool, and only reconstructs blocks right at the tip. Partial
reconstructions waiting on a `blocktxn` are held one per peer, a few per block,
and are dropped when they time out, when the peer disconnects, or when the
block arrives another way. The note of which blocks were asked of a peer,
which decides whether an arriving compact block was solicited, is likewise
capped per peer: a peer announcing block hashes cannot make the node remember
more of them than any peer legitimately has outstanding.

A block being reconstructed is also no longer downloaded in full alongside
the reconstruction. The header of a `cmpctblock` is accepted before the block
is rebuilt, so until the block connects the periodic tip-following fetch saw
it as missing and asked for it — spending the bandwidth the compact form had
just saved, every time, for any block whose reconstruction needed a
`getblocktxn` round trip. A reconstructed block that fails its merkle check,
which a short-ID collision can cause on an honest relay, is fetched in full
from the same peer instead of penalising it, as Bitcoin Core does; `getpeerinfo`
now reports `bip152_hb_from` and `bip152_hb_to`.

### High-bandwidth compact block relay

A block satd mined, including every block a miner finds through the Stratum
server, used to leave the node as a `headers` or `inv` announcement, then wait
for each peer's `getdata`, then go out as a full `block`. Bitcoin Core sends a
new block to up to three high-bandwidth peers as a `cmpctblock` (header,
nonce, a six-byte ID per transaction) before it has even finished validating
it, and those peers rebuild it from their own mempools. So a block found on
satd reached the network later than the same block found on Core, which a
solo miner pays for in stale blocks.

satd now does what Core does. It picks as high-bandwidth peers the peers that
delivered its recent tips, at most three, keeping at least one outbound. It
announces a new block to peers that asked for high-bandwidth relay as soon as
the block passes proof of work and the checks that need no UTXO lookups,
before the block is connected. It answers `MSG_CMPCT_BLOCK` requests within
five blocks of the tip with a `cmpctblock`, and serves `getblocktxn` from a
cache of the latest block. `getpeerinfo` shows the selection in both
directions (`bip152_hb_to`, `bip152_hb_from`), and
`satd_net_compact_block_sent_total` counts what went out. Core's
`p2p_compactblocks_hb.py` now runs against satd.

Receiving those announcements needed one more thing than the first release of
this work had. The node tracks, per peer, the highest block it believes that
peer holds — Bitcoin Core's `UpdateBlockAvailability` — and the parallel
download scheduler will not ask a peer for anything above it. That belief was
updated only from `headers` messages, and a high-bandwidth peer announces with
`cmpctblock` *instead of* `headers`. A node following such a peer therefore
learned the headers, raised its download target, and asked nobody for the
blocks. With a single peer — a regtest pair, or a node with one upstream —
that is a permanent wedge rather than a slow sync: the node sits with the
whole chain pending, nothing in flight, and a peer that has every block of it.
Every path that accepts a header from a peer now records availability.

### Opt-in compact block prefill

`-cmpctblockprefill=1` announces a new block with the transactions this node
did not have when the block arrived already inside the `cmpctblock`: ones it
had to request, ones a miner put in a template that nobody relayed, and, last,
replaced or policy-refused ones from the extra pool. A peer that lacks them too
then rebuilds the block without a `getblocktxn` round trip. The prefill is
capped at `-cmpctblockprefillbytes` (default 8192 bytes beyond the coinbase),
under a typical TCP congestion window, so the larger message still leaves in
one flight. Receivers need nothing new: BIP 152 requires accepting any
well-formed prefill.

It is **off by default**. The design is Bitcoin Core's proposal (#35558), which
Core has not merged, and the reconstruction statistics below are how to tell
whether it helps: with it on, a peer running satd should show more `direct`
and fewer `round_trip` reconstructions. Sizing the prefill to each peer's
actual congestion window, as the Core proposal does, is left for later.

### Compact block reconstruction statistics

Every block received as a compact block now logs one `compact block
reconstructed` line: how many of its transactions came prefilled, from the
mempool, from the extra pool, or had to be requested, and whether that took a
round trip. The same counts are exported as
`satd_net_compact_block_reconstructions_total`,
`satd_net_compact_block_txs_total` and
`satd_net_compact_block_fetched_bytes_total`; see
[Observability](https://epochbtc.github.io/satd/observability.html#compact-block-relay).

`blockreconstructionextratxn` was accepted and ignored. It now sizes Bitcoin
Core's extra-transaction pool: transactions pushed out of the mempool by a
replacement, or refused by policy, are kept (100 by default, `0` keeps none),
so a block from a miner who took one of them still reconstructs locally.

### Stratum work after catching up

A node that caught up with the chain through block download — rather than by
following a peer block by block — went on handing out mining work for its old
tip until the next periodic refresh, up to 30 seconds later. Those blocks
connect on a path that emits no chain event, and the Stratum server only
rebuilt work on an event. A Job Declaration client that declared a job in that
window was refused, since the node was still expecting the coinbase of a much
earlier height. The tip is now polled as well.

### Miners are no longer dropped between shares

Every Stratum connection used to be closed after 120 seconds in which the
miner sent nothing. A miner sends nothing but shares, and shares arrive at
random. A miner whose difficulty put it at one share every 72 seconds (a
BM1370 Bitaxe at difficulty 20,160) had one gap in five longer than that. Even
at vardiff's target of one share every 30 seconds, one gap in 55 is. Each drop
was followed by a reconnect that started the miner again at its lowest
difficulty.

The limit now depends on how often the miner should find a share. Once it has
four accepted shares, an authorized Stratum V1 miner, or a Stratum V2
connection with a channel open, may go quiet for twenty expected share
intervals at its current difficulty, between 2 minutes and a day. Before
that it gets a day too: a slow device can take over an hour to find its
first share (see *Steadier share difficulty* below). A miner that has gone
away is still noticed when the operating system gives up on the connection
it has stopped acknowledging. A connection that has not authorized or opened a
channel is still closed after 120 seconds. A Stratum V2 miner pointed at the
V1 port is now disconnected with a reason that says so, instead of
`invalid UTF-8`. See [Idle connections](../manual/src/stratum.md#idle-connections).

### Steadier share difficulty

Vardiff used to rescale each miner's difficulty every 90 seconds by the ratio
of the shares it saw to the three it expected, by up to a factor of four. Three
expected shares are too few to judge a miner by: on target, a window of seven
happens about 3% of the time and more than doubled the difficulty. Observed
with a BM1370 Bitaxe on a synced mainnet node, the difficulty wandered between
1,326 and 23,328 in one hour of steady hashing.

The difficulty now changes only when the shares since the last change are
significantly off target: a count that a miner on target would produce with
probability below 1 in 100,000, or below 1 in 1,000 once 40 shares were
expected, or below 1 in 100 for a miner that has not had a share accepted
yet. A rate within 15% of target is left alone, and a change moves by at most
a factor of eight. Simulated over six hours at 100 GH/s, 1.2 TH/s and
100 TH/s, from difficulties ten times too high and too low (300 runs):

| | Before | After |
|---|---|---|
| Difficulty range, hours 1–6 | median ×17, 95% within ×25, worst ×34 | median ×1.23, 95% within ×1.55, worst ×2.19 |
| Changes, hours 1–6 | median 169, worst 183 | 95% at most 2, worst 5 |
| Mean share interval off 30 s | 95% within 8.5 s, worst 9.6 s | 95% within 4.5 s, worst 6.7 s |
| Within ×2 of best, from 10× too low | median 180 s, worst 270 s | median 20 s, worst 70 s |
| Within ×2 of best, from 10× too high | median 180 s, worst 360 s | median 140 s, worst 38 min |

**Slow "lottery" miners.** ESP32-class devices (tens of kH/s to a few MH/s)
and sub-TH devices connecting at the default difficulty without
`mining.suggest_difficulty` were never served. The old vardiff lowered the
difficulty at most fourfold every 90 seconds, a 1 MH/s device reached
difficulty 1 only after the ten-minute idle limit had closed the connection,
and each reconnect started it at 10,000 again: simulated over a day, a 1 MH/s
device was reconnected about 140 times and averaged two shares. Now a miner
that has never had a share is lowered on much less evidence (from 10,000 to
difficulty 1 in about twelve minutes), and the idle limit before a miner's
share rate is known, and its ceiling after, are a day.

| Device, from difficulty 10,000 | First share (median), before → after | Idle disconnects a day, before → after |
|---|---|---|
| 1.2 TH/s | 24 s → 22 s | 2 → 0 |
| 100 GH/s | 2.4 min → 2.6 min | 2 → 0 |
| 1 GH/s | 7.4 min → 7.5 min | 3 → 0 |
| 1 MH/s | 10 h, most runs → 76 min | ~140 → 0 |
| 50 kH/s | almost never → 16 h | ~140 → about one |

A share difficulty is a whole number, so a device below about 1 MH/s cannot
find the twenty difficulty-1 shares a day the idle limit is built on, and now
and then reconnects. Its chance of finding a block is unaffected: that does
not depend on shares, and every connection gets current work.

The idle limit that closes silent miners is judged at the difficulty of the
miner's last share, so vardiff lowering the difficulty of a quiet miner can no
longer close it on the spot. See
[Difficulty and vardiff](../manual/src/stratum.md#difficulty-and-vardiff).

## Silent payments

### Sending: PSBT version 2 and the BIP 375 fields

BIP 375 is how a wallet sends *to* a silent payment address through a PSBT.
Every field it defines is PSBT version 2 only, and until now satd could not
read a version 2 PSBT at all: the `bitcoin` crate rejects any PSBT whose
`PSBT_GLOBAL_VERSION` is above zero, so all 42 of the BIP's published vectors
came back as `PSBT decode failed`.

Every PSBT method now accepts a version 2 PSBT and answers with one. The BIP
375 fields — the ECDH shares, their BIP 374 proofs, and the silent payment
code on an output — are carried losslessly, along with anything else satd does
not recognise: a pair that goes in comes out with the same bytes in the same
place. That is what lets a PSBT pass through this node on its way between two
wallets that do understand it.

Two places where satd is deliberately stricter than the version 0 rules.
`combinepsbt` refuses two PSBTs that give the same key different values,
naming the field, where Core keeps whichever it saw first — for an ECDH share
that value decides where the money goes. And `joinpsbts` refuses a silent
payment PSBT that has already committed to its input set, because every silent
payment output script derives from that set.

Version 0 behaviour has not moved, error text included, and a snapshot test
records what it answered before this change so that it stays that way.

### Verifying a silent payment before it is broadcast

Carrying the fields is the easy half. The hard half is that a silent payment
output is a bare taproot script: on chain it looks like any other, so if the
ECDH share a Signer supplied is wrong, the derived script is wrong, the money
goes to a key nobody holds, the recipient finds nothing, and the sender sees a
confirmed transaction. There is no recovery. BIP 374's discrete-logarithm
equality proofs exist so that this can be checked without anyone's private
key, and `analyzepsbt` and `finalizepsbt` now do the checking.

`analyzepsbt` returns a `silent_payments` object: which inputs contribute,
where each previous output came from, and a status per output — `ready`,
`missing_shares`, `invalid_proof`, `invalid_script`, `invalid_inputs`,
`invalid_prevout` or `unverifiable` — along with the output script satd derived
independently, so a coordinator can see where the money is going before anyone
signs. `finalizepsbt` is BIP 375's Transaction Extractor and refuses unless
every silent payment output verifies and carries that derived script. There is
no override flag, and `extract=false` is refused too: a finalised PSBT is one
`sendrawtransaction` away from the chain.

Two checks go beyond what BIP 375's reference validator does, and both are
there because skipping them is silently unsafe.

The reference reads an input's public key out of the PSBT and never checks it
against the output being spent. A PSBT can therefore name a key its author
controls, prove an ECDH share against it, derive the output from it, and pass
every published check — while the transaction actually spends a different key.
satd keeps only a key that hashes to the previous output's script. The second
is that a `witness_utxo` is whatever the PSBT's author wrote, and for a taproot
input it *is* the key the share is supposed to belong to, so satd looks each
previous output up in its own UTXO set. That one is the check a node can do
and a hardware wallet cannot.

One place is deliberately more permissive. Within a scan key, BIP 352 states no
ordering for the `k` counter — only that every value from zero upwards is used,
because a receiver stops scanning at the first miss — and the two
specifications' vectors disagree about which order their generators used. Both
pay the recipient identically. satd accepts either and reports which it used;
an assignment that is neither is refused.

Verification work is counted before it is done and capped, because
`analyzepsbt` is a read-capability method and the proof checks are a product of
inputs and scan keys rather than a sum.

The verifier is refereed against three specifications' own vectors: BIP 374's
proofs in both directions, BIP 375's 42 PSBTs, and BIP 352's 28 sending cases.
The end-to-end tests build a payment through the real flow —
`utxoupdatepsbt`, a Signer, `analyzepsbt`, `finalizepsbt`,
`sendrawtransaction` — and then require the node's own tweak index and a
registered scan-key watch to both find it. The sender in those tests shares no
code with the verifier.

### Creating one

`createpsbt` now takes a silent payment address as an output key, with a new
trailing `psbt_version` argument (0 default, 2 for the version 2 PSBT a
recipient needs). It sits after Core's own `replaceable` and `version`, so a
positional call written against Core keeps meaning what it meant, and an
`sp1…` key without it is refused by name rather than dropped — a caller whose
signer speaks only version 0 finds out at creation, not at signing.
`createrawtransaction` refuses an `sp1…` key and says why: a raw transaction
has nowhere to put the information a Signer needs.

A repeated `sp1…` key is legal, unlike a repeated ordinary address: two
payments to one recipient get `k = 0` and `k = 1`, and each keeps its own
amount. Use the array form of `outputs` when the order matters, because a JSON
object's key order is the serialiser's business and the output order decides
both the transaction and the `k` values.

`decodepsbt` and `analyzepsbt` spell the recipient back as the `sp1…` address
it came from. The PSBT carries only the two keys, so that is the only way an
operator can check the recipient against what they were handed. The address
codec is refereed against every address in BIP 352's vectors, in both
directions — a silent payment address is about 117 characters, well past
BIP 173's 90-character cap, so anything reusing a segwit address decoder
rejects all of them.

### Signing one

`sat-cli signpsbtwithkey` is a BIP 375 Signer. The node cannot be one: computing
an ECDH share needs an input's private key, and satd holds none. Given a
version 2 PSBT and a key on stdin, it refuses a transaction that cannot carry a
silent payment, records the public key of every input it holds so that anyone
else can check whose key a share belongs to, computes and proves those shares,
checks every share it did not produce, derives each output's script once every
eligible input is covered, freezes the transaction, and only then signs.

Never signing while an output has no script is the point, not a detail: a
signature commits to the outputs, so signing first would commit to a
transaction that is still going to change. A signer holding only some of the
inputs therefore writes its shares, names the inputs that still owe one, emits
the PSBT and exits 2 — the same code a partially signed version 0 PSBT gets.
The next signer continues, and a test drives exactly that: two signers, neither
holding every input, between them completing a transaction neither could alone.

`sat-cli signpsbtwithsigner` passes a version 2 PSBT to an external signer
untouched — a device is the right party to ask, and `sat-cli` cannot know which
devices have learned BIP 375 — and checks what comes back with the same code
the node runs. A reply describing a different transaction, one whose silent
payment script is not what its own shares derive to, or one carrying a
signature while an output still has no script, is refused rather than emitted.
So is one that restates what an input spends: a proof says a share came from
the key bound to an input, and which key that is comes from the previous output
the document claims — so a device that substitutes one paying a key of its own
can do the rest of the work honestly and still pay a script the recipient will
never find. The reply is compared against the document that was sent.
No shipping device writes BIP 375 fields today, but the other half works now:
BIP 375 says a PSBT is plain PSBTv2 once every output has a script, so an
unaware device can sign one another signer has completed.

BIP 375 is still a draft; the field set has not moved since 0.1.0.

See [Sending](https://epochbtc.github.io/satd/silent-payments.html#sending-bip-375)
and [PSBT version 2](https://epochbtc.github.io/satd/json-rpc-extensions.html#psbt-version-2-bip-370-and-bip-375)
in the Operator Manual.

## Storage

### Transaction ordinals

Every index satd keeps used to be keyed on a 32-byte txid. A txid is a
hash: incompressible, and written once per index that mentions the
transaction. On a fully indexed mainnet node that repetition was the
single largest line in the chainstate — the same transaction identifiers
stored five to seven times over.

An **ordinal** replaces it. Transactions are numbered in chain order from
the genesis coinbase at 0, so the transaction at position *i* of a block
takes `nchaintx(parent) + i` — the cumulative count satd already kept per
block for `getchaintxstats`. Five bytes hold 2^40 of them, roughly 880
times the chain's current transaction count, and the encoding is
big-endian so the byte order of a key is the order the transactions were
mined.

This release moves the transaction index onto that encoding. `tx_loc`
(txid to ordinal) and `txseq_txid` (the inverse) replace the old
`tx_index` (txid to block hash), and `txseq_block` maps an ordinal back
to the block that holds it. Because an ordinal carries the position
inside the block as well as the block itself, `getrawtransaction` now
indexes straight into the block's transaction list instead of reading the
block and comparing every txid in it — a scan that cost up to several
thousand hashes per lookup on a full block.

The ordinal is a storage encoding, not a new public identifier. Nothing
on any wire changes: the storage layer resolves ordinals back to txids
before a row leaves it, in one batched lookup per scan.

The address and spend indexes still key on txids in this release; moving
them is what the encoding is groundwork for.

**Upgrading.** The chainstate schema moves to version 4. A datadir from
an earlier release is refused at startup with a message naming
`-reindex-chainstate`, which rebuilds the chainstate from the block files
in one pass. The block files themselves are never touched, so nothing is
re-downloaded. A **pruned** datadir cannot do that rebuild — the replay
needs every block — and has to resync.

A node that runs neither `-txindex` nor `-addressindex` writes no index
rows and pays nothing for this, as before.

### The spend index

Every confirmed input had a row saying which output it consumed and
which input consumed it: 76 bytes, of which 64 were two 32-byte
transaction identifiers stored nowhere else in that shape. Both ends are
now named by ordinal, and the row is 16 bytes. The identifiers come back
through the ordinal map, resolved inside the storage layer — Esplora's
`/tx/:txid/outspend/:vout` and `/tx/:txid/outspends` return exactly what
they returned before.

The ordinal of a spent output's funding transaction has to be known at
connect time, and looking it up per input would be a point read for every
input ever mined. Instead the coin carries it: `Coin` gains the ordinal
of the transaction that created it, so the connect path — which already
resolves every input's coin — has it in hand. That costs about a byte a
coin and five a spend in the undo data.

The keying also makes a transaction's spends contiguous, so
`/tx/:txid/outspends` is one prefix scan where it used to be one point
lookup per output.

**AssumeUTXO.** Bitcoin Core's snapshot format carries no ordinal, so a
coin loaded from a snapshot has none until background validation reaches
its funding block. Spending one before then writes no spend row, counted
by `satd_addrindex_unresolved_spends_total`; `backfillindex address`
after validation completes fills the gap, which is the procedure that
already applied.

That procedure was documented but not enforced: loading a snapshot left
the address and spend indexes *marked complete*, so both surfaces
answered "this address has no history" and "this output is unspent" with
the authority of a full index, for the whole chain below the snapshot
base. A snapshot load now marks them incomplete, and they refuse until
the backfill has run.

### Address funding rows

The second-largest family in a fully indexed chainstate stored
`scripthash[16] ‖ height[4] ‖ txid[32] ‖ vout[4]` for every output paying
a script. The height and the txid are both recoverable from a 5-byte
ordinal, so the key is now `scripthash[16] ‖ txseq[5] ‖ vout[3]` — 32
bytes a row against 64.

The documented iteration order, `(height, txid, vout)` ascending, is
unchanged. On disk the rows sort by ordinal, which is block position, and
that disagrees with txid order *within* a block — so the store resolves
and sorts before a row leaves it. That keeps Electrum's `listunspent`,
`get_balance` and `get_history`, Esplora's `/address/*` endpoints and
`getaddressutxos` answering exactly as they did, and it means nothing
above the storage layer had to change.

Resolution is batched: one lookup per scan, not one per row. A scan over
a busy scripthash's history returns tens of thousands of rows and costs
a single reverse-map read.

### Address spending rows

The largest family in a fully indexed chainstate, and the only one that
carried *two* 32-byte transaction identifiers: the spending transaction's
in the key and the consumed output's in the value.

```
addr_spending_v3  key:   scripthash[16] || txseq[5] || vin_be[3]      (24 B)
                  value: funding_txseq[5] || funding_vout_be[3]        (8 B)
```

32 bytes a row against 92. Spend-by-address remains what it was — one
prefix scan over a single scripthash — and `getaddresshistory` still puts
`prev_txid` and `prev_vout` on the wire, resolved from the value.

Both ends of a row resolve in one batched lookup per scan, not two per
row: a spend's two transactions are usually in different blocks, and the
batch dedups across the whole scan anyway.

One behaviour follows from the value being an ordinal. An input whose
funding transaction has no ordinal — an AssumeUTXO coin spent before
background validation reached its funding block — no longer produces an
address spending row at all, where it previously produced one carrying
the outpoint. It shares the spend index's treatment: the row is skipped,
`satd_addrindex_unresolved_spends_total` counts it, and `backfillindex
address` after validation completes fills the gap. That backfill was
already the documented procedure for an AssumeUTXO node's address index.

### A missing transaction count is now an error, not a guess

The cumulative transaction counts stopped being a `getchaintxstats`
nicety: they are the series every index row's ordinal is offset from.
`connect_block` used to read a missing count for a block's parent as
zero, which silently restarted the series; it now fails the connect and
names `-reindex-chainstate`. A node that will write index rows also
refuses to start on a datadir whose counts are known incomplete. A
validating-only node keeps the previous warn-and-continue, because a gap
there costs it one wrong RPC field rather than a mis-keyed index.

Closing that also fixed a defect the old behaviour hid.
`-reindex-chainstate` cleared genesis' own cumulative-count row and never
re-seeded it, and the replay starts at height 1 — so the first replayed
block read its parent's count as zero and every `getchaintxstats` total
afterwards was one short, for the life of the datadir.

## Observability

### Where a chainstate's disk went: `getstoragefootprint`

A fully indexed mainnet node carries several hundred gigabytes of index, and
until now the only way to see which column family held them was to stop the
node and run an offline `ldb` dump. `getstoragefootprint`, and
`sat-cli debug storage-footprint` in front of it, report per family the
on-disk SST bytes, an estimate of the live key count, their quotient — the
effective post-compression cost of one row — and the bytes still owed to
compaction.

It reads RocksDB properties and LSM metadata only, with no iteration, so it is
cheap enough to call on a live node under IBD. The key estimate is exact while
data is still memtable-resident and approximate once compaction has merged
overwrites and tombstones, so a family whose rows are frequently rewritten
reads high.

Two families were missing from the startup and 60-second diagnostics
altogether: `chain_tx` was never listed, so its bytes were reported nowhere.
The three per-family diagnostics now share one list, and a test fails if a
column family the binary can create is absent from it.

### Metrics and health endpoints over TLS

`/metrics`, `/healthz` and `/readyz` were plain HTTP with no authentication,
so reaching them from another machine meant putting a TLS proxy in front.
`-metricstlsbind=<addr:port>`, with `-metricstlscert` and `-metricstlskey`,
now serves the same endpoints over TLS on a second port. The plain listener
keeps running beside it, so container healthchecks and local tools see no
change, and `-metricstlsbind` requires `-metricsport`.

TLS encrypts the scrape; it does not choose who may scrape. `-metricsmtls=1`
with `-metricsmtlsclientca` requires a client certificate, and
`-metricsmtlsclientallow` narrows that to named clients. Prometheus supports
both through `scheme: https` and `tls_config`. The certificate reloads on
`SIGUSR1`, as on the other TLS listeners. A certificate that does not load or
a port that cannot be bound stops satd at startup. See
[Observability](https://epochbtc.github.io/satd/observability.html#over-tls).

### A bounded mempool aggregate: `getmempoolsummary`

Drawing a mempool panel — a size histogram, a table of the top transactions by
ancestor feerate — previously meant calling `getrawmempool verbose` and
throwing away nearly all of it. On a mainnet-sized mempool (~71,000
transactions) that reply is around 85 MiB, of which a caller rendering an
aggregate reads about 9%: the `depends` and `spentby` arrays alone, which such
a caller never looks at, are 72% of it. Worse than the bytes is the work —
building that reply takes the node roughly 4 seconds of CPU, because every
entry costs a transaction clone, a witness hash, and three graph walks.

`getmempoolsummary [top_n]` returns that aggregate directly:

```
$ sat-cli getmempoolsummary 3
{
  "size": 71594,
  "bytes": 117777467,
  "vsize_histogram": [
    { "min_vsize": 0, "max_vsize": 100, "count": 4127 },
    ...
    { "min_vsize": 50000, "max_vsize": null, "count": 6 }
  ],
  "top": [ { "txid": "...", "vsize": 141, "ancestorcount": 1, ... } ]
}
```

The reply is bounded by `top_n` (default 50, ceiling 1000) rather than by
mempool size — on the order of 9 KB instead of 85 MiB — and the whole-mempool
pass costs one read lock, no per-entry clone, and one ancestor walk per
transaction. Bucket edges are published beside the counts so a client labels
its axis from the response instead of hardcoding edges. Row fields carry the
same names and semantics as the `getrawmempool verbose` entries they are
derived from, and an integration test asserts the two agree field for field.

`getrawmempool verbose` is unchanged; this is an addition, for callers that
want the aggregate rather than the dump.

### Exact recent UTXO ages in `gettxoutsetinfo`

`utxo_age_distribution` splits the UTXO set into eight age buckets, from `<1h`
to `3y+`. It was computed from a histogram that counts coins per 1000-block
chunk, placing each chunk in the bucket of its midpoint. The youngest buckets
are narrower than a chunk — `<1h` is six blocks, `<1d` is 144 — so they could
not be right: on a synced mainnet node at height 968170 the distribution read
`[391947, 0, 997122, 2014141, …]`. `<1h` held every coin created since height
968000, 171 blocks, and `<1d` was empty. `<1d` could only ever be empty or a
whole 1000-block chunk.

satd now keeps an exact count of unspent coins per creation height for the
most recent 4320 heights, the `<1mo` edge, updated in the same atomic write as
the coins. The `<1h`, `<1d`, `<1w` and `<1mo` buckets come from it exactly. The
four older buckets still come from the 1000-block histogram, with each chunk
now spread evenly over its heights rather than dropped on its midpoint, so they
are estimates to within one chunk at their edges. The eight counts still sum to
`txouts`.

A new `exact` field inside `utxo_age_distribution` says which you are looking
at. The window is a new metadata key, not a schema step: nothing to reindex,
and an older binary ignores it. A datadir that does not have one yet builds it
with a single background scan of the coins at startup, while the node runs
normally. Until the scan lands, `exact` is `false` and the young buckets are
the same chunk-spread estimate as the old ones. A fresh or reindexed datadir
never scans. The window survives restarts, and is rebuilt if it was left
behind by a binary that did not maintain it.

### sat-tui: histograms you can read at both ends

The steady view drew the mempool size distribution and the UTXO age
distribution as one-row sparklines, eight levels tall on a linear scale. Both
distributions span several decades — mainnet's age buckets run from under a
million coins to over seventy million, and a mempool can hold ten thousand
transactions in one size bucket and three in another — so each chart showed
its largest bucket and a row of near-empty cells.

Both are now bar charts four rows tall on a log scale, with each bucket's count
printed on its bar and its label beneath, so the small buckets on either side
of the bulk stay visible and the exact numbers are on screen. While the node
is still building its exact recent-age counts, the age chart's heading reads
`(est.)` and its four youngest bars are drawn in yellow. The mempool and UTXO
panels are two rows taller, and on an 80-column terminal the left-hand panels
are two columns wider, to fit them.

### The `tip_stall` alert no longer fires during a long sync (#814)

`tip_stall` raises when nothing has connected for `alerttipstallseconds` — an
hour by default, on every network but regtest. It measured that from a clock
advanced by chain events, and the initial-block-download path connects blocks
without emitting any. So the clock read "time since this process started"
rather than "time since the chain last moved", and an initial sync that ran
longer than the threshold raised a **critical** alert an hour in and held it
for the rest of the sync, while the node was connecting blocks as fast as it
could. On mainnet that is every first sync: `getwarnings` pinned, the TUI's
blocking modal up, and `-alertnotify` fired, as the operator's first experience
of the node.

The detector now advances its clock from the polled tip as well, so the age it
reports is the age it claims to report regardless of which path connected the
block. This is not an IBD suppression — `is_initial_block_download` compares
the tip's timestamp against the wall clock, so a node that was synced and then
stopped re-enters it a day later, exactly when the alert matters most, and
gating on it would silence that. A node genuinely wedged mid-sync connects
nothing, its tip does not move, and it still pages.

## Large RPC replies are served, not refused (#723)

satd bound both directions of the JSON-RPC pipeline to one 20 MiB constant.
That number was chosen as a *request* cap — Core's functional suite sends
`echo` two 8 MiB arguments — and it ended up policing replies too. But a reply's
size is set by the chain and the mempool, not by the caller who asked for it:
`getrawmempool verbose` crosses 20 MiB at roughly 17,000 mempool transactions,
an ordinary mainnet mempool rather than a fee-spike condition. Past that, satd
answered `-32008 Response is too big` — after building the reply — where
bitcoind answers the call. Core caps the request body
(`evhttp_set_max_body_size`) and writes whatever the method produced.

The two caps are now separate constants. The request cap is unchanged at
20 MiB: that one is the DoS guard, bounding what a caller can make the node
buffer before it has decided anything. Replies are bounded at 256 MiB,
derived rather than picked — verbose mempool JSON measures about 0.76x the
mempool's own serialised bytes, so the default `-maxmempool=300` tops out near
217 MiB, and 256 MiB covers it with headroom. The guarantee is that a node at
its default mempool ceiling can answer `getrawmempool verbose`.

Two consequences worth stating plainly. A node configured with a larger
`-maxmempool` can still outgrow the bound; making it configurable is a
follow-up. And because the engine buffers a reply whole, this figure is also
the per-in-flight-request memory ceiling.

The JSON-RPC 1.0 compatibility layer keeps its own, much smaller limit on what
it will DOM-parse, because parsing costs several times the body in live
allocations — tying that to the transport cap would mean a 256 MiB reply
triggering a parse measured in gigabytes. A reply above the parse limit is
forwarded in jsonrpsee's 2.0 shape: the answer is correct JSON, only its
envelope is 2.0, which beats truncating or refusing it. That fallback was
documented in 0.5.2 but unreachable — the engine refused anything that could
have reached it — and is now live and tested.

### The TUI's mempool panels were frozen, and said nothing about it

Two faults compounded. The mempool size histogram and the top-transactions
table were fed by `getrawmempool verbose`, which stops fitting in the node's
20 MiB response cap at roughly 17,000 mempool transactions — an ordinary
mainnet mempool, not a fee-spike condition. And the steady-state poll loop
applied each result as `if let Ok(v) = res`, with no `else`, so the error was
discarded. The panels went on rendering whatever they had last managed to
fetch, for as long as the condition lasted, with nothing on screen to say the
numbers were old.

Both are fixed. The panels now read `getmempoolsummary`, whose reply is
bounded and which is cheap enough to poll; and every polled method's outcome
is recorded, with the failing ones named in the title bar as
`rpc failing: <method>`. The health dot still tracks the connection — this is
the separate case of one method failing while the connection is fine, which
previously had no indicator anywhere.

The histogram's axis labels are now built from the bucket edges the node
sends rather than a fixed string, which had drifted: it named six edges for an
eight-bucket histogram.

## `verificationprogress` is Core's estimate (#744)

`getblockchaininfo` and `getchainstates` reported `verificationprogress` as
the tip's timestamp divided by the current time, both counted from 1970. A
node at genesis read 0.69, and a year of blocks moved it by under two points.
The background chainstate's entry in `getchainstates` used a height ratio
instead.

Both now compute Bitcoin Core's `GuessVerificationProgress`: the chain's
cumulative transaction count against Core's per-network estimate of all
transactions to date, with a tip inside two hours of the clock placed by its
height against the best header. A synced node reads exactly 1, and drops below
it when a new header arrives. The values equal Bitcoin Core v31.1's for the
same chain and clock. That was checked on regtest across clock offsets from the
tip, with a header above it, and at genesis on mainnet, testnet3, testnet4 and
signet. A custom signet (`-signetchallenge`) has no estimate data, as in Core.

## Relayed transactions reach a node that mined its own chain (#759)

satd decides it is in initial block download, and ignores transactions its
peers announce, by comparing its tip with the best header a peer has sent. A
node that mined every block of its chain itself, as a fresh regtest node does,
has never been sent a header, so it read as still syncing for as long as that
lasted: a wallet or a Bitcoin Core node connected to it could broadcast, and
the transaction never entered satd's mempool. The node's own tip now counts as
a known header, so it leaves initial block download as soon as it has a chain.
Found by the Stratum V2 Job Declaration canary, whose Bitcoin Core peer relays
the transaction a job declares.

## The TLS RPC listener's connection cap now counts every connection (#813)

Every JSON-RPC listener caps open connections at 100 with a permit taken at
accept. On the TLS listener (`-rpctlsbind`) the permit was released as soon
as the connection began serving, so it bounded in-flight handshakes only.
Established connections were uncounted: a client that opened idle keepalive
connections and never closed them could exhaust the node's file descriptors
and wedge the listener behind accept errors. The permit is now held until
the connection closes, matching the plain listener. A unit test boots the
surface with a cap of two, holds two idle connections, and proves a third is
refused until one closes.

The cap is taken before authentication, so 100 open connections from anyone
who can reach a listener lock out every other client of that listener, the
operator's `sat-cli` included. `-rpcservertimeout` (default 30 s) frees an
idle slot; `-rpcservertimeout=0` leaves it held until the client hangs up.
The cap and that trade-off are now documented in the manual's
[API scaling](https://epochbtc.github.io/satd/api-scaling.html) chapter,
which did not list it. Three
related changes: a peer outside `-rpcallowip` no longer takes one of the
100 slots, where before it took one at accept and kept it for as long as it
held the socket open — until `-rpcservertimeout` if it sent nothing, and
indefinitely with `-rpcservertimeout=0` — so outsiders could lock out every
allowlisted client. The allowlist is now checked first, and a denied peer
is answered `403` with `Connection: close` from a separate pool of 16
refusals under a fixed two-second deadline. The TLS listeners honour
their allowlist at all (see below), and every listener that sheds at
capacity (JSON-RPC, Electrum, Stratum, metrics, MCP, events gRPC) now logs
the first five refusals a minute and then a suppressed count, where each
refusal was a warning line before — a connection flood could fill the log
with the report of itself.

### `-rpcallowip` now applies to the JSON-RPC TLS listeners

`-rpcallowip` gated the plain-HTTP JSON-RPC binds only (and
`-rpcreadonlyallowip` the plain read-only binds). `-rpctlsbind` and
`-rpcreadonlytlsbind` ran their own accept loop that never consulted
either list, so any peer that could complete the TLS handshake reached the
RPC stack — still behind cookie/`-rpcauth`/bearer authentication and, where
configured, mTLS, but with no source-address gate, and holding one of the
listener's 100 connection slots for as long as it kept the socket open.

A TLS listener now refuses a peer that is not on its allowlist
(`-rpcallowip` for `-rpctlsbind`, `-rpcreadonlyallowip` for
`-rpcreadonlytlsbind`), dropping it
at accept: before the TLS handshake, before it is shown a certificate, and
before it takes a connection slot. The refusal is logged under the same
per-minute budget as the other at-capacity and denial warnings.

**This applies only when the allowlist has at least one entry.** On a plain
bind an empty allowlist means loopback-only, enforced at startup by the
refusal to bind `-rpcbind` on a public address without one. That startup
guard has never covered a TLS bind, so a `-rpctlsbind` on a public address
with no `-rpcallowip` is a configuration operators are already running, and
reading the empty list as loopback-only would lock those clients out on
upgrade. It keeps working. Once an allowlist exists, it covers both
transports.

If you run a public `-rpctlsbind` alongside an `-rpcallowip` that lists
only the clients of your plain-HTTP bind, add the TLS clients' addresses to
the same list before upgrading, or they will be refused. The same goes for
`-rpcreadonlytlsbind` and `-rpcreadonlyallowip`.

On a dual-stack bind (`[::]`), an IPv4 client is now matched as the IPv4
address it is. It reached the listener as `::ffff:a.b.c.d`, which matched no
IPv4 entry and missed the loopback exemption, so a plain `[::]` bind
answered `127.0.0.1` with `403`.

## Esplora and streamws cap their sockets

Esplora (plain and TLS) and `streamws` had no socket-level cap and never
closed an idle keep-alive connection. `-esploramaxconns` is a per-request
concurrency limit and `-streamwsmaxconns` is taken inside the handlers, so
neither ever saw a socket that sent nothing; and `axum::serve`, which
served both, builds hyper without a timer, so hyper's default idle timeout
was discarded and a keep-alive connection lived until the client hung up.
A client that opened connections and never closed them was limited only by
the process's file-descriptor table — the failure the TLS RPC listener had
before #813, on the surfaces the manual calls remotely consumed. Once the
table is full every listener in the process wedges behind accept errors,
not just the one being flooded.

Both surfaces now run the same capped accept loop the JSON-RPC listeners
use. A permit per socket is taken at accept, before the TLS handshake and
before any HTTP is parsed, and held until the socket closes, so an open
WebSocket keeps its slot: `-esploramaxsockets` is one cap shared by both
Esplora listeners and `--streamws-max-sockets` covers the streamws one, each defaulting to
1024 with `0` for unlimited; over the cap a socket is dropped. A keep-alive
connection that idles between requests is closed — after
`-esplorarequesttimeout` (30 s by default) on Esplora and after 30 s on
streamws — so an idle client cannot hold a slot; an open SSE or WebSocket
stream is not idle in that sense. Esplora's TLS handshake also moves off
the accept loop onto the connection's own task: it used to run inline, so
one client that stalled its handshake held up every other connection for
the handshake budget, a limitation the code had carried as a known
follow-up. The listener cap and idle budget are covered by tests on the
shared loop, on the Esplora TLS path, and on the existing mTLS allowlist
cases, which were ported to the new loop.

Every socket and connection cap is now clamped to 100,000. tokio panics
when asked for a semaphore that large, and these options accept any
number, so a mistyped `-esploramaxconns`, `-esploramaxsockets`,
`-esplorasseconns`, `--streamws-max-sockets`, `--streamws-max-conns`,
`--events-grpc-max-conns`, `-electrummaxconns`, or `-stratummaxconns`
stopped satd at boot.

The permit is carried by the socket itself rather than by the task serving
it. hyper's connection future completes when it hands a socket to an HTTP
upgrade, so a permit held by that task went back to the pool while the
WebSocket stayed open. The JSON-RPC listeners had the same problem: they
serve WebSocket as well as HTTP, and an open WebSocket there held no slot of
the 100. On every capped listener an upgraded socket now keeps its slot until
it closes.

Building the idle budget turned up a gap in the existing one. hyper serves
HTTP/1 and HTTP/2 on one port by sniffing the first bytes for the HTTP/2
preface, and HTTP/1's header-read timer is armed only after that sniff has
decided. A client that connected and sent *nothing* therefore sat in the
sniff forever — on the JSON-RPC listeners too, where `-rpcservertimeout`
was documented as covering "a client that opens a TCP connection but never
completes a request head", and did, for any client that sent at least one
byte. A first fix put a deadline on the first byte, but one byte of the
HTTP/2 preface (`P`) ended it and left the sniff waiting again, and a
client that sent the whole preface got an HTTP/2 connection, which has a
keep-alive ping but no idle timeout. The JSON-RPC, Esplora and streamws
listeners now serve HTTP/1.1 only, so there is no sniff: the header
timer covers a request head from its first byte, and a regtest test holds
a silent socket against a `-rpcservertimeout=2` node and proves it is cut.
None of these listeners offered HTTP/2 over TLS, so only a client that
started HTTP/2 unasked (h2c "prior knowledge") ever reached it; see the
upgrade note.

## Consensus: the BIP 34 height must be Core's exact encoding

BIP 34 requires every block's coinbase to commit to its height at the start of
the scriptSig. Bitcoin Core checks this by comparing bytes: the scriptSig must
begin with exactly `CScript() << height`, which is `OP_1`–`OP_16` for heights
1 to 16 and otherwise the shortest little-endian push, with a trailing zero
byte only when the top bit is set. satd decoded the pushed number and compared
the value, so it accepted the right height written any other way: padded with
zero bytes, with a sign byte it did not need, as `OP_PUSHDATA1`, or as a data
push for a height of 16 or less. Core rejects all of these as
`bad-cb-height`.

A block like that could only come from a miner, and no block on mainnet,
testnet3, testnet4 or signet uses one: the rule applies from each network's
BIP 34 activation height, and Core has enforced the exact encoding since then.
But a node that accepts one follows a chain the rest of the network rejects,
so a single such block would have split satd nodes from Bitcoin Core. The
check now compares the scriptSig's first bytes with the minimal encoding, and
Stratum V2 Job Declaration applies the same rule to a declared coinbase and a
custom job's scriptSig prefix, so a miner is refused before hashing on a
coinbase the network would reject.

The block-acceptance differential fuzzer's seed corpus now includes blocks
with non-minimal height pushes.

## Bitcoin Core parity

These came out of running more of Bitcoin Core's functional test suite against
satd. `mining_mainnet`, `mempool_expiry`, `feature_signet`,
`feature_fastprune`, `feature_maxtipage`, `rpc_bind`, `rpc_users`,
`p2p_net_deadlock`, `p2p_nobloomfilter_messages`, `p2p_ping`,
`p2p_v2_transport`, `rpc_setban`, `p2p_timeouts`, `p2p_handshake` and
`mining_getblocktemplate_longpoll` now run in the pull-request gate.

### RPC fields

- `getmininginfo` reports the tip's `bits` and `target`, `blockmintxfee`, and a
  `next` object with the next block's `height`, `bits`, `difficulty` and
  `target`, computed as Core's `NextEmptyBlockIndex` does: timestamped at the
  later of the node clock and median time past plus one, so on testnet3 and
  testnet4 it reflects the 20-minute minimum-difficulty rule.
- `getblock`, `getblockheader`, `getblockchaininfo` and each entry of
  `getchainstates` report `target` beside `bits`, and `getblockchaininfo` and
  `getchainstates` now report `bits` too.
- On signet, `getblockchaininfo` and `getmininginfo` report
  `signet_challenge`: the `-signetchallenge` in use, or the default signet's.
- `getprioritisedtransactions` reports `modified_fee`, the base fee plus the
  delta, for a prioritised transaction in the mempool.
- `getmempoolentry` (and the verbose forms of `getrawmempool`,
  `getmempoolancestors` and `getmempooldescendants`) reports `wtxid`.

### Options

- **`-maxtipage` is honoured.** It was accepted and ignored, so a node always
  used 24 hours to decide whether it had left initial block download. The IBD
  test is now Core's: the tip is older than `-maxtipage` seconds.
- **The RPC server listens on `::1` too by default.** With no `-rpcbind`, Core
  binds both loopback addresses and satd bound only `127.0.0.1`. A client
  resolving `localhost` to `::1` could not connect. A host without IPv6
  skips `::1` with a warning.
- **Startup errors in Core's words.** A malformed `-rpcbind` port
  (`127.0.0.1:0`, `[::1]:notaport`) stops the node with
  `Invalid port specified in -rpcbind: '<value>'`. An empty or malformed
  `-rpcauth`, including a bare `-rpcauth`, and a cookie file that cannot be
  written stop it with `Unable to start HTTP server. See debug log for
  details.`, with the reason in the log. The cookie is written through
  `<cookie>.tmp`, Core's temporary name.
- **`-norpcauth`** discards every `-rpcauth` before it, including the config
  file's, and **`-norpccookiefile`** starts the node without a cookie file.
- **`-rpcallowip`** accepts a bracketed IPv6 address (`[::1]`, `[fd00::]/8`),
  the spelling `-rpcbind` requires. **`-cjdnsreachable`** is accepted: satd
  has no CJDNS transport, and the only effect is Core's refusal of an
  fc00::/8 `-rpcallowip` while it is set.
- **Double negatives.** `-nolisten=0` means `-listen=1`, as in Core, with
  Core's `Parsed potentially confusing double-negative` warning; satd refused
  it. This applies to every negatable boolean option.
- Startup logs Core's `init message: Done loading` once the RPC server is up.

### P2P

- **BIP 324 v2 transport.** Inbound detection is Core's. A peer speaks v1
  only if its first 16 bytes are the network magic and the `version` command,
  and `getpeerinfo` reports it as `detecting` until then. A v1 `version` under
  another network's magic is refused as such. `localservices` advertises
  `NODE_P2P_V2` when `-v2transport` is on. `addnode`'s `v2transport` argument
  is honoured, and refused when v2 is off. The largest valid v2 packet (a 4 MB
  message) was refused as too large and is now accepted. Handshake bytes
  count toward `bytesrecv` as they arrive, and `version`/`verack` appear in
  `bytessent_per_msg`/`bytesrecv_per_msg` on both transports.
- **Fee filters.** A peer gets no `feefilter` under `-blocksonly`, on a
  block-relay-only link, or with the `forcerelay` permission. While in initial
  block download the node asks for the maximum, so it is sent no transactions.
  The filter is re-sent when it changes, rounded into Core's fee buckets.
- **Protocol violations disconnect**, as in Core: a transaction or transaction
  inv from a peer told not to send them (a block-relay-only link, or any peer
  of a `-blocksonly` node without `relay`), a BIP 37 `filterload`, `filteradd`
  or `filterclear`, and a `mempool` request without the `mempool` permission.
- **Ping.** Keepalive timing follows the node clock, so `setmocktime` drives
  the ping interval and timeout. Pong problems (a nonce mismatch, a short
  payload, an unsolicited pong) are logged in Core's words.
- **Block download follows announcements.** During initial block download a
  peer is asked only for blocks up to the highest header it has announced or
  claimed in its `version`. A peer with nothing the node needs gets no requests,
  where before it held them until the stall timeout.
- **Logging.** Each message is logged as `received: <type> (<n> bytes)
  peer=<id>` when it arrives, and `getdata` as `received getdata for: <inv>`,
  with the v2 handshake and downgrade lines Core writes.
- The hidden test RPC `sendmsgtopeer` sends a raw message to a peer.

### Connection handshakes and timeouts

- **`-rpcservertimeout` from `bitcoin.conf` was ignored.** The key was not on
  satd's known-key list, so a value in the file was dropped with an "option
  satd does not implement" warning and every RPC connection used the 30-second
  default. A client that sat idle longer than that — a long poll, a slow
  batch — found its connection closed. The command-line flag always worked.
- **`-peertimeout`** is implemented: a new connection has that long (60 seconds
  by default) to finish its handshake, measured on the node clock, before the
  inactivity check drops it with Core's reason — `version handshake timeout`,
  or `socket no message in first N seconds, never received from peer, never
  sent to peer`. satd bounded each handshake step by `-timeout` instead, which
  is Core's *socket connect* budget. `-peertimeout=0` is refused at startup.
- **Core's handshake rules.** An outbound full-relay, block-relay-only or
  addr-fetch peer that does not offer `NODE_NETWORK | NODE_WITNESS` (or
  `NODE_NETWORK_LIMITED | NODE_WITNESS` while our tip is within a day) is
  dropped, as are our own connections back to ourselves, recognised by the
  `version` nonce. A message before `version`, or between `version` and
  `verack`, is logged and ignored rather than silently dropped.
- **`getblocktemplate` long polling.** A request carrying `longpollid` now
  waits, as Core's does, until the tip moves or — from a minute in, then every
  ten seconds — the mempool changes. `longpollid` is Core's
  `<tip hash><mempool sequence>`. satd answered immediately, so a miner
  polling for work spun.
- New log lines Core writes: `Added connection peer=N`, `Cleared nodestate for
  peer=N`, `connection from <addr> dropped (banned)`, `ignoring redundant
  verack message`, `feeler connection completed`, `ThreadRPCServer
  method=<name>`, `Block mutated: <reason>`, a transaction rejection in Core's
  shape, and `DNS seeding disabled`.

### P2P

- **An honest peer is no longer banned for headers we cannot connect.** Bitcoin
  Core's `HandleUnconnectingHeaders` charges no misbehaviour score: it sends a
  `getheaders` to fill the gap and keeps the peer as a download source. satd
  charged a point per message, on the reasoning that an honest peer sends one
  and stays far under the threshold. It does not — a node syncing 999 regtest
  blocks from a peer that was still mining answered each `getheaders` with a
  batch that no longer connected, reached 100 points in half a second, and
  banned the only peer it had, leaving the sync stopped at 21 of 551 blocks.
- **The P2P loop keeps draining while its queue is full.** The loop takes up to
  64 peer messages per pass before yielding to its periodic maintenance. That
  bound is for fairness, but a pass that filled it then waited out the full
  500 ms tick, capping every inbound path at 64 messages per tick — during
  initial block download, the whole of the node's throughput. A full pass now
  comes straight back to the queue, up to eight times in a row before
  maintenance runs anyway.

### Chain

- **`invalidateblock` takes the header tip with it.** satd's header tip only
  ever moved up, so after an `invalidateblock` it stayed on the branch that had
  just been refused: `getblockchaininfo` reported a `headers` height the node
  had decided it would never reach, and the figure kept growing with every
  block the rest of the network mined on that branch. Everything that reads the
  distance between the header tip and the active tip — the initial-block-download
  heuristic, the block scheduler's target, the stall detector — was aimed at it
  too. It is now recomputed from the block index, as Bitcoin Core's
  `RecalculateBestHeader` does, and `reconsiderblock` lets it back up. A restart
  no longer re-seeds it from an invalidated branch either (#778).
- **`reconsiderblock` clears the marks below the block it is given.** Bitcoin
  Core's `ResetBlockFailureFlags` clears the reconsidered block's ancestors as
  well as its descendants. satd cleared only the subtree, so reconsidering the
  *tip* of an invalidated branch — the natural thing to reach for — left the
  path from the fork up to it still marked, and the branch could never
  reconnect however much work it carried.
- **`preciousblock` works, and equal-work tips are ordered the way Core orders
  them.** The RPC was a stub: it accepted a block hash, returned `null`, and
  changed nothing. Underneath it, satd broke a tie between two equal-work tips
  on the block hash — an arbitrary rule that the operator had no way to
  override and that could disagree with every other node on the network for no
  reason anyone could see.

  Bitcoin Core breaks that tie on `nSequenceId`: the order in which each
  block's data became *connectable*, earliest first. satd now keeps the same
  id, assigned at the same point (Core's `ReceivedBlockTransactions`, including
  the walk over descendants that a newly-connectable parent unblocks — so a
  block whose data arrived early but whose parent was missing is numbered when
  the parent lands, not when its own bytes did). As in Core the id is memory
  only, so the block index keeps its on-disk shape; what a restart loses is the
  arrival order, and, again as in Core, the chain loaded at startup is scored
  ahead of everything else so the tip a node shut down on holds its ground.

  `preciousblock` then does what it does in Core: it hands a block an id below
  every naturally-assigned one, so it wins the tie it would otherwise lose.
  Calling it again on another tip overrides the first. It cannot override
  *work* — a block with less work than the active tip is left alone, because a
  tie-break is only ever consulted between candidates of equal work — and, as
  in Core, that case is a no-op success rather than an error.

### Mempool policy

- **A full mempool raises its minimum fee.** Eviction sets a rolling minimum
  to the evicted package's feerate plus `-incrementalrelayfee`. Nothing paying
  less is accepted until a block arrives, and after that the minimum halves
  every 12 hours (faster while the pool is under half full) until it drops
  away. A transaction below it is refused with Core's `mempool min fee not
  met`, and `getmempoolinfo.mempoolminfee` reports it. satd reported the
  static relay floor and kept admitting low-fee transactions into a full pool
  by evicting whatever paid least. The minimum is also what the node now
  advertises in `feefilter`, as Core does, so peers stop offering transactions
  it is about to refuse; satd advertised the static floor.
- **Rejection messages in Core's shape.** `sendrawtransaction`'s `-26` message
  and `testmempoolaccept`'s `reject-details` are Core's `reason, detail`
  (`min relay fee not met, 0 < 15`); satd sent the detail alone.
  `reject-details` is now present on every rejection, as in Core.
- **`getrawmempool` with `mempool_sequence=true`** returns
  `{txids, mempool_sequence}`. The sequence counts every transaction added to
  or removed from the pool, as Core's does, so a snapshot can be lined up with
  a notification stream. Asking for it with `verbose=true` is refused with
  Core's error.

### A rejected script says which rule it broke

A script rejection reported `ERR_SCRIPT` — true, and useless. That is the
coarse code `bitcoinconsensus_verify_script` returns; the specific
`ScriptError_t` that script verification actually produced never crosses the
C API boundary, so the name Bitcoin Core puts in its rejection —
`mempool-script-verify-flag-failed (Non-canonical DER signature)` — was not
available to report.

satd's own script engine computes the same error and already carried Core's
full name table, so it is now asked for the name whenever libconsensus
rejects an input. The verdict is not revisited: the authoritative engine has
already decided, and this runs only on the failure path and only to write the
message. If the two disagree about an input, there is no name to borrow, the
coarse code is reported as before, and the disagreement is logged — that
would be a parity bug worth knowing about.

`testmempoolaccept`'s `reject-details` also names the input, as Core's does:
`…, input 0 of <txid> (wtxid <wtxid>), spending <outpoint>`. And a block that
fails to connect logs Core's `Block validation error: <reason>` line, from
every path that connects one.

### A `pong` answers for what came before it

Bitcoin Core processes one connection's messages one at a time, in the order
they arrived. A `pong` therefore answers for everything the peer sent ahead of
the `ping`, which is what makes `send_and_ping(block)` mean "the block is
connected" — the standard way for a peer, or a test, to wait for the node to
catch up.

satd answered `ping` on the peer's own socket task, deliberately, so the
manager's drain cadence would not land in the round-trip time the peer
measures. But `block` and `tx` travelled a queue to the manager and on to the
block processor, so the pong could be — and routinely was — sent before the
block it followed was connected. A peer that asked for the node's height the
instant the pong arrived got the height from before the block.

satd now counts each message in as it is taken off the socket and out where
the work actually ends, and a `ping` waits for that peer's outstanding work
before it is answered. An idle peer's keepalive, which is nearly all of them,
is still answered immediately; the wait is bounded so a stuck message costs a
delayed pong rather than the connection.

A waiting pong also wakes the manager's event drain, which otherwise runs on
a 500 ms tick. Without that the wait would be paced by exactly the cadence
this node answers `ping` off the socket task to keep out of the peer's
measured round-trip time — `getpeerinfo`'s `pingtime` on a loopback peer went
from sub-millisecond to 0.47 s in testing before the wake was added. The
loop's periodic maintenance still runs on the interval alone.

### Manual pruning (`-prune=1`)

Core reserves `-prune=1` for *manual* pruning: prune mode is on, the node
deletes nothing on its own, and `pruneblockchain` is the only thing that ever
does. satd read the value as a budget, which lands on the 288-block floor and
deletes block data automatically — the opposite of what was asked — so the
flag was refused at startup instead.

Both halves now exist. `-prune=1` puts the node in manual mode, and
`pruneblockchain <height>` deletes block data at or below it, returning the
height of the last block pruned. The height may be given as a Unix timestamp
instead, and a request that reaches into the last 288 blocks is clamped to
them rather than refused, as Core does. `getblockchaininfo` reports a manual
pruner as `pruned` with `automatic_pruning: false` and no
`prune_target_size` — there is no budget for an operator to size a disk
against.

`-fastprune` comes with it: Core's 64 KiB block-file size. Pruning deletes
whole files, so without it a short chain of small blocks sits in one file and
a prune has nothing it can delete.

### Mempool expiry

`-mempoolexpiry` was applied by a sweep every 30 seconds, and the sweep removed
only the transactions that had aged out. A child of an expired transaction
stayed in the pool, spending an output the pool no longer had. Expiry now
runs whenever a transaction is accepted, as in Core, and removes each expired
transaction's descendants with it.

### Mining RPCs on every chain

`generatetoaddress`, `generatetodescriptor` and `generateblock` refused to run
off regtest. Core allows them on every chain: they grind real proof of work
within their try budget, so outside regtest and signets with a trivial
challenge they return no blocks. satd now does the same.

Every block these RPCs mine now carries the BIP 141 witness commitment, as
Core's do once segwit is active, not only blocks with witness transactions.
The coinbase of an empty regtest block therefore has two outputs, the payout
and the commitment. On a custom signet the commitment is where the block
solution goes, so an empty block without it was rejected.

### Signet

A block whose signet solution fails is rejected as `bad-signet-blksig`, the
reason Core's `submitblock` returns; satd said `bad-signet-solution`. At
startup, a second `-signetchallenge` is refused
(`-signetchallenge cannot be multiple values.`) rather than the last one
silently selecting a signet, and a non-hex challenge is reported as
`-signetchallenge must be hex, not '<value>'.` The node logs its signet's
message start at startup.

## Authentication

### A submit-only bearer capability

The read-only listener has always told "hand a transaction to the mempool"
apart from "control the node": it admits `sendrawtransaction` and
`submitpackage` and rejects `stop`. The bearer-token layer collapsed that
distinction into `rpc:write`, so a token minted for a payment processor or a
wallet backend that only needed to broadcast could also stop the node, add
peers, or invalidate a block.

`rpc:submit` is the missing capability. A token with
`capabilities = ["rpc:read", "rpc:submit"]` reads and broadcasts; every
control, mining and unclassified method is denied with the usual `-32004`
error, which now names `rpc:submit` or `rpc:write` as the capability the call
lacked. `rpc:write` implies `rpc:submit`, so a token minted before this
release keeps broadcasting; the converse does not hold. See
[Authentication](https://epochbtc.github.io/satd/authentication.html).

### Esplora `POST /tx` is a broadcast, and is gated like one

Esplora's broadcast endpoint was admitted by the surface-wide `esplora:read`
gate alone, so a token minted as read-only for a block explorer could hand
transactions to the mempool. Now that `rpc:submit` names the broadcast
capability, `POST /tx` requires it (or `rpc:write`) alongside
`esplora:read`; a read-only token is refused with `403` naming the
capability. Operator credentials (`-esploraauth`) and the unauthenticated
loopback default hold every capability and are unaffected. See the upgrade
note below if you issued `esplora:read` tokens that broadcast.

### Batches and WebSocket calls are charged per call

A bearer token's `rate_limit` was charged once per HTTP request, before the
body was parsed, so a JSON-RPC batch counted as one call however many it
carried: a `1/s` token could submit thousands of `sendrawtransaction` calls
per second in one body. The JSON-RPC listeners also accept WebSocket, and a
WebSocket is one HTTP request, the upgrade, so every call sent over it after
that ran free. Both are now charged per call. In a batch, the first call
rides on the unit the HTTP layer took and each later call costs one; on a
WebSocket, every call costs one. A call that
crosses the budget is answered in-band with error `-32005` and
`data.retry_after_secs` (the same figure the HTTP `Retry-After` header
carries), while the calls before it in the batch are still served. The
operator and loopback principals are unlimited, as before.

Both store packages now have public repositories, and move to the 0.6.0 image
with this release:

- **Umbrel:** in umbrelOS, **App Store → ⋯ → Community App Stores**, add
  `https://github.com/epochbtc/umbrel-apps`, then install **satd**. It installs
  beside Bitcoin Node, Fulcrum and Ride The Lightning.
- **StartOS:** the package is submitted to Start9's community registry. Until
  it is listed, build [`epochbtc/satd-startos`](https://github.com/epochbtc/satd-startos)
  and sideload it.
- **Appliance image:** `satd-appliance-0.6.0-<core|desktop>-<amd64|arm64>`,
  as `.qcow2` and, for the desktop flavour, `.ova`, attached to this release
  and signed with the release minisign key. It boots on signet.

The Operator Manual's new [Installing satd](https://epochbtc.github.io/satd/installing.html)
chapter has the steps for each, along with the container image and the
tarballs. `contrib/packaging/sync-store.sh` copies each package into the
repository that serves it, after checking the image pin names a release
matching the package version.

### Umbrel: its own host ports

Umbrel has one host port space for every app on a device. The package used
3001, 8333 and 50002, which Ride The Lightning, Bitcoin Node and Fulcrum own,
so it could not be installed beside any of them. It now uses 8430 for the app
page, 8433 for P2P, 50012 for Electrum over TLS, 8436 for JSON-RPC over TLS
and 8439 for MCP, none of them used by another app in the store.

Each is mapped 1:1 with satd listening on the same number. P2P in particular
cannot be remapped on the host alone: satd advertises the port it listens on,
so peers would be sent to whichever node owns 8333. A client configured
against the old ports needs the new ones.

The package's backups leave out the chain and chainstate, and keep the
install's CA, MCP token and configuration. Before, a user with Umbrel backups
on backed up the whole chain.

### Both packages open onto the status page

The Umbrel app opens onto satd's status page, behind Umbrel's login, with
connection strings built from the device's name and the app's ports. Esplora
moves off Umbrel's proxy onto its own TLS port, 8431. The StartOS package
exports the page as its UI, without connection strings, since StartOS lists
each interface's addresses itself. The appliance turns the page on as well.

The reference stack and the appliance also turn on satd's metrics TLS
listener on 9336, so the page, `/metrics` and `/readyz` are reachable from
another machine with the install's certificate, without the proxy overlay.
The appliance firewall opens 9336; the plain listener stays on loopback and
the container network.

`satd-init` writes the page's and the TLS listener's keys only for a satd that has them, so a
package or appliance image pinned to an older release still starts, without
a page.

### StartOS: backups and sync progress

Backups now leave out `chainstate_background/`, which holds a full coin set
while an AssumeUTXO snapshot validates. The list had been written from Bitcoin
Core's datadir layout; it named `indexes/` and `debug.log`, which satd never
creates, and those are gone.

The **Blockchain Sync** check showed `verificationprogress` as a percentage.
In 0.5.2 that field is the tip's timestamp over the current time, so a node at
genesis reported about 69%. The check now shows the block count against the
header count. The field itself is fixed separately.

The package's instructions now cover every action, its storage, its lack of
dependencies and its limitations, and it builds for `x86_64` and `aarch64`
only, matching the image, where the SDK's default would also attempt riscv.

## A status page (`statuspage=1`)

A node in an app store needs something to open in a browser, and the headless
appliance image had nothing. `--statuspage=1` serves one on the metrics
listener at `/status`: a simplified, single-page `sat-tui` showing whether the
node is syncing or ready, sync progress weighted by the work each part of the
chain takes, the ETA, AssumeUTXO background validation, each index, whether a
wallet can connect yet, the latest block, the mempool, fee estimates and peer
counts.

The page is complete without JavaScript, and refreshes itself every 5 seconds
when it can. It marks itself stale when the node stops answering rather than
going on showing the last reading. Its top line says ready only when `/readyz`
is 200, and it adds a phase `/readyz` cannot see, a header chain still
downloading.

It is off by default and requires `--metricsport`. Like `/metrics` it is
unauthenticated, and it is built to be safe that way: no credentials, no peer
or listen addresses, no error text, every value escaped, and a strict
`Content-Security-Policy`. Connection strings come only from
`--statusadvertise=<surface>=<url>`, never from the request. `/status.json` is
internal to the page and unstable. See the Operator Manual's Observability
chapter.

## Streaming API & SDKs

**The node advertises its version on every stream.** `Subscribe` and `Watch`
responses now carry two gRPC response headers, `satd-version` (e.g. `0.6.0`)
and `satd-events-schema` (`1`), sent when the stream opens, before any event.
No proto change; existing clients ignore them.

**The compatibility rule is written down** in
[`STABILITY_POLICY.md`](../../STABILITY_POLICY.md#streaming-api--sdk-compatibility),
which now lists the events gRPC API and both SDKs as Tier 2 surfaces:

- An SDK works with any node that has the same schema version and is at or
  above the SDK's own version.
- A newer SDK warns when the node is one minor version behind, and refuses
  when the node is two or more behind.
- New request fields must degrade to a superset of events when an older node
  ignores them.

**The SDKs apply the rule.** `satd-events-client` compares the node's
advertised version with its own each time a stream opens. A node one minor
version behind gets a `tracing` warning, once per node version. A node two or
more minor versions behind is refused with `StreamError::NodeTooOld`, which
`StreamClientBuilder::allow_old_node()` turns back into the warning. A schema
mismatch is always refused (`StreamError::SchemaMismatch`). Both errors are
non-retryable, so the resilient layers stop instead of reconnecting.
`StreamClient::node_version()` reports what the node advertised. A node older
than 0.6.0 sends no header and counts as 0.5, so a 0.6 SDK against a 0.5 node
warns and a 0.7 SDK refuses it. The crate now depends on `tracing`.

The Go SDK does the same: `ErrNodeTooOld` (overridden by `WithAllowOldNode()`),
`ErrSchemaMismatch`, `Client.NodeVersion()`, and a warning logged through
`log/slog` (`WithLogger`, default `slog.Default()`). `Watch` now waits for the
node's response headers before returning, as `Subscribe` already did. satd
sends them when the stream is set up, so a quiet watch-set does not delay it.

**The Go SDK is versioned with the node.** `satdevents.Version` equals the node
version, and a test pins it to the workspace `Cargo.toml`. The module is tagged
`clients/go/vX.Y.Z` at the node's `vX.Y.Z` from now on.

## Upgrade notes

- **One `-reindex-chainstate`, once.** The chainstate schema moved from 3 to
  7 across four changes in this release, and an earlier datadir is refused at
  startup with a message naming the flag. That is **one** rebuild, not four:
  the replay discards the RocksDB chainstate and replays the block files into
  a new one, building every enabled index inline as it goes. The block files
  are never touched, so nothing is downloaded again, and because the old
  column families are dropped before the replay starts, the datadir never
  grows beyond its current size during the rebuild. Budget roughly what an
  `-assumevalid` sync of the same chain costs on your hardware.

  Two cases need more:

  - **Pruned nodes must resync.** The replay needs every block and a pruned
    node does not have them.
  - **AssumeUTXO nodes**: unchanged procedure — run `backfillindex address`
    once background validation has reached the snapshot base. This release
    also *enforces* it: loading a snapshot now marks the address and spend
    indexes incomplete, where it previously left them marked complete and let
    those surfaces answer "no history" and "unspent" for the chain below the
    base.

- **A configured `-rpcallowip` now also gates `-rpctlsbind`**, and a
  configured `-rpcreadonlyallowip` gates `-rpcreadonlytlsbind`. The TLS
  JSON-RPC listeners never consulted either list. If you run one on a
  public address and its allowlist names only the clients of the
  plain-HTTP bind, add the TLS clients to the same list before upgrading.
  An empty `-rpcallowip` is unchanged: a TLS bind stays reachable from
  wherever it is bound, gated by TLS/mTLS and RPC auth.
- **The JSON-RPC, Esplora and streamws listeners serve HTTP/1.1 only.**
  They answered HTTP/2 as well to a client that started it without
  negotiation (h2c prior knowledge); none of them advertised it over TLS.
  A client configured for HTTP/2 prior knowledge against one of them must
  switch to HTTP/1.1. The events gRPC listener is separate and still speaks
  HTTP/2.
- **Esplora bearer tokens that broadcast need `rpc:submit`.** `POST /tx` no
  longer accepts a token holding only `esplora:read`; add `rpc:submit` (or
  `rpc:write`) to any token that broadcasts through Esplora, or it gets `403`.
  Operator credentials and the loopback default are unaffected.
- **Go SDK tag jumps from `v0.1.0` to `v0.6.0`.** It now follows the node
  version: `go get github.com/epochbtc/satd/clients/go@v0.6.0`.
- **An SDK newer than its node now complains.** A 0.6 SDK (Rust or Go) logs a
  warning against a 0.5 node, and from 0.7 on an SDK refuses a node two minor
  versions behind. Upgrade nodes before clients, or pass `allow_old_node()` /
  `WithAllowOldNode()` while a rollout is in progress.

- **Stability & compatibility** — Tier 1 surfaces (Bitcoin Core-compatible
  JSON-RPC wire shape, CLI flag names/defaults, `bitcoin.conf` keys, on-disk

  [`STABILITY_POLICY.md`](../../STABILITY_POLICY.md). satd follows

  `0.x` pre-1.0 line, deprecations may be accelerated (see the policy).

  [`SECURITY.md`](../../SECURITY.md). Consensus-affecting bugs are treated as
  P0 with same-day acknowledgement.

  images with cosign (keyless OIDC), and git tags with SSH signatures (no GPG).
  The key matrix and verification steps are in
  [`SECURITY.md`](../../SECURITY.md).
- **Intentional differences from Bitcoin Core** — catalogued in
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md).
- **Operating satd** — observability, the full flag matrix, tuning, and the
  downstream packaging contract live in the
  [Operator Manual](https://epochbtc.github.io/satd/).
