# satd 0.5.1

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.5.1 is a patch release on the 0.5.x line. Planned scope: the regtest
halving-interval divergence from Bitcoin Core (#608) and spending the
untweaked-P2TR output shape — the BIP 352 silent-payment form — through
`signrawtransactionwithkey` (#609).

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- Silent-payment outputs can now be spent through the node's own signing paths:
  `signrawtransactionwithkey` and `sat-cli`'s PSBT signer handle untweaked P2TR
  key-path spends the way Bitcoin Core does (#609).
- A batch of Bitcoin Core parity fixes: the regtest halving interval (#608),
  `-testactivationheight` support, the `bad-blk-length` / `bad-blk-weight`
  reject-reason split, an always-present `default_witness_commitment` (#548),
  and a consistency fix for `gettxoutsetinfo` (#556).
- **[satd now runs Bitcoin Core's own functional test suite](#satd-now-runs-bitcoin-cores-own-test-suite)**
  — unmodified, pinned to a Core release, with all 264 test files inventoried as
  run-or-skip-with-a-reason. Pointing Core's framework at satd immediately found
  five Core-compatibility defects, four of which affect real Core-derived
  clients: RPC replies carried a `Content-Type` Core clients reject outright,
  and the startup listener answered "no such method" where Core answers
  "warming up".

## Fixed

### A block that stored without connecting confirms nothing (#639)

`accept_block` has two success outcomes: the block connected to the active
chain, or it was valid and stored but a sibling had already won the race and
the tip did not move. Callers could not tell them apart, and the mining path
treated every acceptance as a connect: it purged the accepted block's
transactions from the mempool as *confirmed* and emitted `LeaveConfirmed`
events for a block `getblock` reports with `confirmations: -1` — dropping
live transactions the node would otherwise relay and mine.

`accept_block` now returns the outcome explicitly, and every caller gates its
post-connect work (mempool purge, fee-estimator sample, confirmation events)
on the block actually having connected. The confirming height those events
carry now comes from the connected block's own index entry rather than a
separate tip read, which a later connect could already have moved past —
this also fixes the background connect path, whose purge could label a
block's confirmations with a neighbour's height under concurrent submission.

### `gettxout` answers from one chain state (#640)

Every chain mutator commits its coin batch a moment before it moves the
in-memory tip, and the committed coins become visible immediately. `gettxout`
read the coin, the tip hash and the tip height as three independent samples,
so inside that window it could report a coin under a `bestblock` in which the
coin was in fact already spent — or report freshly created coins under the
parent tip. Clients use `gettxout` as *the* UTXO-existence probe, and an
answer no single chain state ever supported is worse than a stale one.

The node now carries a generation token that is held across the whole
commit-to-tip-write window, and `gettxout` retries its read until it lands on
a settled state — waiting out an in-flight commit (bounded by wall clock)
rather than failing through it. Only if the chain advances continuously
through every attempt does the call return an explicit retry error instead
of a silently inconsistent answer.

The same change makes two neighbouring RPCs answer honestly. `getblockstats`
now prices a connected block's fees from its **undo data**: connecting a
block removes exactly the coins its inputs spend, so the old live-UTXO
lookup missed every prevout and reported `totalfee`, `minfee`, `maxfee`,
the fee rates and `medianfee` as zero for every connected block — and
`swtotal_size`/`swtotal_weight` were hardcoded to zero beside a non-zero
`swtxs`. An undo row that disagrees with its block (corruption) now refuses
the call by name instead of pairing coins with the wrong inputs.
`verifychain` walks parent pointers from the tip under the same consistent
view rather than trusting the height→hash index, which non-consensus writers
also populate — and it now counts a pruned block body as pruned rather than
failing verification over the operator's own retention policy.

### Answers assembled while the chain moves underneath them (#641)

Three surfaces made a multi-read decision against chain state that a
concurrent connect or reorg could change between the reads.

`getblocktemplate` now assembles its template under the same consistency
token `gettxout` uses, retrying when a block connects mid-assembly. If the
chain advances through every attempt — continuous connects for several
seconds — it emits a coinbase-only template built from a single tip snapshot
rather than a transaction set priced against one chain and anchored to
another. The fallback logs a warning; miners lose that poll's fees, never
the block.

Esplora's `/blocks/:start_height` resolved its page top from the height→hash
index, which non-consensus writers also populate, and could stitch two
branches into one page. The page top now comes from walking the active chain
when the requested height is within 200 of the tip (one index read per
height crossed, bounded); deeper heights — beyond any plausible reorg — use
the height index. Every subsequent entry follows the previous entry's parent
pointer, so a page is always a contiguous slice of one chain.

A `TxidFinalized` watch alarm — terminal, and evicting — could compute its
depth from a queued `BlockConnected` event's tip after the node had reorged
to a shorter, higher-work chain, overstating how buried the transaction was.
Depth is now taken against the lower of the event tip and the live tip:
understating depth only delays the alarm one tick, overstating it is
unrecoverable.

### Spending silent-payment outputs through the node's own signing paths (#609)

A BIP 352 silent-payment output is a P2TR output whose key **is** the derived key,
with no taptweak applied. Both of satd's signers — the `signrawtransactionwithkey`
RPC and `sat-cli`'s local PSBT signer — assumed every P2TR key-path spend was the
BIP 341/86 shape and unconditionally applied the taptweak, so a wallet backend
that located its silent-payment outputs through satd's tweak index was then told
`"Unable to sign input, no matching key"` when it handed the node the exact
private key that controls them.

Both signers now mirror Bitcoin Core's two-attempt key-path signing: each key is
first tried as a BIP 341/86 internal key (taptweak applied), and if no key
matches, tried directly against the output key with no tweak. The tweaked
reading is attempted first, so existing BIP 86 spends are unchanged.

### Regtest block subsidy halves at Core's interval (#608)

The halving interval was a network-blind 210,000; Core's
`nSubsidyHalvingInterval` is 150 on regtest. From height 150 a regtest satd
accepted coinbases Core rejects (and its own `getblocktemplate` overpaid).
`block_subsidy` is now network-aware; no other network changes.

### Core-compat gaps from the #541 review (#548)

Three independent parity fixes, each small:

- **`-testactivationheight=name@height` is implemented** rather than
  warn-and-ignored. Core's syntax and semantics: repeatable, names `bip34` /
  `dersig` / `cltv` / `csv` / `segwit`, heights validated as Core validates
  them (non-negative and below `INT_MAX`), single-dash spelling accepted.
  Command-line and config-file occurrences are merged the way Core merges
  them — command line first, config file after, last value winning per name,
  so the config file wins for a name given in both. The option applies only
  to regtest; on any other chain it is warned about and ignored, exactly as
  Core ignores it (its `ReadRegTestArgs` runs only for the regtest branch),
  so a bitcoin.conf shared with a test bench cannot break a mainnet node.
  Moving `segwit` up drags `taproot` with it so the script-flag set stays
  coherent (a taproot spend is a witness spend). This unlocks the Core
  functional-test shapes that relocate buried deployments.
- **Over-weight blocks now reject `bad-blk-weight`**, computed after the
  witness rules exactly as Core orders `ContextualCheckBlock`, with
  `bad-blk-length` reserved for `CheckBlock`'s stripped-size test. Verdicts
  are unchanged — only the reject reason and its position moved — but the
  live block-acceptance differential compares reasons, and the previously
  conflated label diverged for over-weight blocks inflated by witness data.
- **`getblocktemplate` matches Core's template shape on both sides of segwit
  activation.** Post-segwit it emits `default_witness_commitment` on every
  template, witness transactions or not, as Core does; previously a
  witness-free template carried an empty string, pushing external mining
  software toward computing its own commitment — newly hazardous since #541
  made a wrong coinbase witness nonce a hard rejection. Below an overridden
  segwit height the whole of Core's `fPreSegWit` shape now applies: the
  `segwit` and `taproot` rules are not advertised, `sigoplimit` and
  `sizelimit` report the unscaled pre-segwit values (20000 and 1000000), and
  `weightlimit` and the commitment are absent. Advertising post-segwit
  limits on a pre-segwit template would have invited a miner to build a
  block the advertising node then rejects. The segwit rule is also spelled
  `!segwit` as Core spells it, marking it as one a client must understand
  before using the template as-is.

### `gettxoutsetinfo` reads one consistent view (#556)

The RPC read its tip, coin count, total amount and height histogram as
independent lookups; a block connecting mid-call could pair a tip at height
H with totals from H+1, breaking the documented "histogram sums to `txouts`"
invariant and mis-stating the total by a block's subsidy and fees. All five
fields are now read under the chain's accept lock after the coin-cache
flush, so they always describe the same height. Same shape as the backfill
cursor fix in 0.5.0 (#549/#554), applied to the UTXO-set statistics.

If that flush fails — a full or failing disk — the RPC now returns an error
instead of an answer. A failed flush rolls the count and amount deltas back
while leaving the coins dirty, so the totals would no longer describe any
single state; reporting the failure is the honest response, and Core
likewise errors rather than guessing.

## Core functional-test conformance

### satd now runs Bitcoin Core's own test suite

There are three ways to argue a node is Core-compatible. You can check it agrees
with Core on recorded inputs — satd's ported fixture corpora. You can check it
accepts the same blocks off the real network — satd's live block-acceptance
differential against `bitcoind`. Or you can hand it to Core's own test suite and
see what happens. Only the third puts satd in front of a client written by
people who were not thinking about satd at all, and that turns out to be the
useful part.

`contrib/core-functional/` runs Bitcoin Core's functional tests **unmodified**
against satd, pinned to a specific Core release (v31.1 today). Every one of the
264 test files in that release has a row in `inventory.toml` saying either "we
run this" or "we skip it, and here is the reason". A schema checker rejects a
missing row, an orphan row, a skip with no reason, a reason outside the
taxonomy, and an open-ended skip that does not name the follow-up work. A
nightly workflow runs the run-set; the scoreboard is a chapter in the Operator
Manual.

The rule that makes the number mean anything is that **a test flips to `run`
only in the pull request that makes it pass**. There is no batch re-labelling
step. The shim between Core's framework and satd is correspondingly narrow: it
supplies a `debug.log` (satd logs to stdout and has none), rewords satd's log
lines onto the substrings `assert_debug_log` greps for, and switches off the
Esplora server so two nodes can share a machine. It does not translate, drop, or
invent node options. A test needing something satd lacks is an honest skip, not
a shim special case.

### What pointing it at satd found

Standing the harness up was itself the first result. Core's framework drives a
node the way Core's developers assume a node behaves, and five places where satd
had drifted only became visible under that assumption. Four of the five affect
real Core-derived software, not just tests.

**RPC replies carried the wrong `Content-Type`.** satd answered with
`application/json; charset=utf-8`; Core answers with exactly `application/json`.
The parameter is redundant — RFC 8259 fixes JSON's encoding as UTF-8 — but
Core-derived clients compare the header for equality rather than parsing the
media type, so the suffix reads to them as a non-JSON response. Core's own test
client rejected every reply satd sent, with `-342 non-JSON HTTP response`,
having never looked at the perfectly valid JSON body. Any client modelled on
Core's `authproxy` would have done the same.

**The startup listener said "no such method" instead of "not yet".** While a
Bitcoin Core node is coming up it answers *every* RPC with `-28` and a status
line. That code is a contract: it is how a client distinguishes "alive, ask
again shortly" from "this node cannot do that". satd's startup listener served
`getstartupinfo` and left everything else to jsonrpsee's `-32601 Method not
found` — a permanent-failure answer from a node that would have the method a
moment later. It now answers `-28` with the live progress line, so a polling
client sees "Verifying blocks..." rather than a bare retry code.

**Core options were accepted in `bitcoin.conf` but fatal on the command line.**
satd skips a recognized-but-unsupported Core key in the config file with a
warning, which is what makes an existing `bitcoin.conf` drop in. The same option
passed as a flag hit the argument parser as an unknown argument and aborted
startup. Core treats the two as one namespace, so `-fallbackfee=0.0002` and a
`fallbackfee=0.0002` line now behave identically. Unrecognized options are still
rejected: swallowing `-daatdir=/x` would start the node against the wrong
directory, which is worse than a hard error.

**56 of satd's own flags were unreachable in Core's spelling.** Core spells
every option with a single dash. satd translated single-dash options via a
hand-maintained table, and the table had drifted from the parser — including on
two flags that are Core's own names, `-blockfilterindex` and
`-peerblockfilters`. The set is now derived from the parser itself, and a test
asserts the property over the whole CLI surface, so a flag added later cannot
quietly become double-dash-only.

**`-version` and bad-flag errors did not match Core's shape.** `satd -version`
printed `satd 0.5.0-pre`, which does not contain the word "version"; it now
prints `satd version 0.5.0-pre`. A bad flag is now reported as `Error parsing
command line arguments: ...`, Core's wording.

### What the harness found next

Running the blocked tests again after the first round turned up three more
option-handling defects. Two of them are drop-in compatibility failures an
operator would meet on their first start; the third is a crash.

**Core's fee-rate options were spelled in the wrong unit.** Bitcoin Core
denominates `-minrelaytxfee` and `-dustrelayfee` in BTC per kvB — `0.00001` is
Core's own default. satd has always documented them as an integer sat/kvB rate,
and `1000` is satd's default: the *same* fee rate, written differently. Both
spellings are now accepted, which is unambiguous because the two are disjoint in
practice — a Core value is a fraction of a coin, a satd value is a whole number
of satoshis.

The unit mismatch was the visible half. The dangerous half was what happened to
a value satd could not parse. On the command line it aborted startup, which is at
least loud. In `bitcoin.conf` it was silently discarded and the built-in default
used instead — so a dropped-in Core config asking for a specific minimum relay
fee produced a node relaying at a rate the operator never chose, with nothing
said. Both paths now report the bad value and stop, which is the rule the rest of
satd's config parser already follows: every recognised key is honoured or
explicitly rejected, never accepted-and-ignored.

**`-blockfilterindex` required a value.** Core accepts the option bare, meaning
`basic`, and its own tests pass it that way. satd demanded `=basic` or `=1`.

**A `-bind` value satd could not parse panicked.** satd builds its P2P listen
address by joining `-bind` to `-port` and unwrapped the result, so anything that
did not parse aborted on a stack trace rather than an error message — the one
outcome satd's operator-input handling is supposed to rule out. The contrast was
visible in the same function: a bind *failure* (port in use, permission denied)
already produced a careful three-line explanation, while a bind *parse* failure
crashed.

Fixing it exposed a second defect underneath. An IPv6 literal has to be bracketed
before it is joined to a port, and satd was not doing it: `-bind=::1` built
`::1:18444`, which is not an address, so satd could not bind an IPv6 address at
all — it panicked on every attempt. Core's fuller `-bind=addr[:port][=onion]`
syntax is still unsupported and is tracked in the inventory.

### `getpeerinfo` grew three fields Core-derived clients expect

Core's `getpeerinfo` reports `addrbind` — the local end of each connection —
and `bytessent_per_msg` / `bytesrecv_per_msg`, which break the byte totals down
by message type. satd reported none of them, and Core's own framework reads all
three without a null guard, so their absence raised `KeyError` and aborted the
client rather than degrading.

`addrbind` answers a question a single `-bind` value cannot: on a node
listening on several addresses, which listener did this peer arrive on. The
per-message tallies are the cheapest way to see what a link is actually
spending its bandwidth on — a peer pulling blocks and a peer flooding `inv`
look identical in `bytesrecv` alone.

Two details worth stating. The key set is bounded by satd's own message-type
enum plus Core's `*other*` catch-all, so no peer can make satd allocate a map
key it chose — that is the memory exhaustion Core guards against by counting
only message types it knows. And the tallies are recorded so they sum to the
byte totals: bytes are counted the moment a frame comes off the wire, then
attributed once decryption and decoding have resolved the type, with
undecodable frames and BIP 324 decoy packets landing under `*other*` rather
than being dropped.

The counts are on-wire sizes for the transport actually in use. On a v2
connection a `ping` is 29 bytes — three length, one header, one message id,
eight payload, sixteen authentication tag — not the 32 it occupies on a v1
link.

Adding the three fields unblocked none of the 27 Core tests that wanted them,
and that is the useful part of the result rather than a disappointment. With the
fields in place those tests get far enough to fail on what is actually stopping
them, and for 22 of them it is the same thing: Core's `connect_nodes()` waits
for a `pong` in both directions, and satd never sends a ping. It has no
keepalive, no inactivity disconnect, and `-peertimeout` is unimplemented — so a
half-open connection holds its slot indefinitely. That is an availability
question rather than a compatibility one, it is a change to how every connection
behaves, and it is being handled on its own rather than folded in here.

### `-bind` became plural, and a repeated option stopped being fatal

Two option-handling gaps that show up the moment satd is driven by something
other than a hand-typed command line.

**A repeated command-line option aborted startup.** Bitcoin Core resolves an
option given twice by taking the last value, and — a quirk its own source
comments on — resolves the same key repeated in `bitcoin.conf` by taking the
first. satd's parser rejected the duplicate outright. That is fine for a human
typing one command and wrong for everything else: appending an override onto a
base command line is how wrappers, service managers, and test harnesses
parameterise a node, and Core's own tests pass `-v2transport` twice for exactly
that reason. satd now matches Core on both sources. Genuinely repeatable
options are unaffected and still accumulate, which matters more than it sounds
— collapsing `-connect` or `-whitebind` to a single value would quietly drop
peers or listeners the operator asked for.

**`-bind` took one address, in a shape Core does not use.** Core's `-bind` is
repeatable and spelled `addr[:port][=onion]`; satd accepted a single bare
address and always took the port from `-port`. A node that needs to listen on
more than one interface could not, and `-bind=127.0.0.1:8333` — a form Core
documents — did not parse.

satd now follows Core's rules, which come from Core's own `feature_port.py`: an
entry carrying a port uses it and `-port` is ignored for that entry; an entry
without one combines with `-port`; and an explicit `-bind` *replaces* the
default listener rather than adding to it. The `=onion` suffix is recognised and
the listener bound.

A duplicate binding is now refused at startup, as Core does: `-bind=X` twice, or
`-bind=X` alongside `-whitebind=…@X`, is a contradiction in the operator's own
config. Two listeners cannot share an address, and without the check the second
one failed later with a bare "address already in use" — which reads like a clash
with some other program rather than a mistake in the config file.

One Core behaviour is deliberately not adopted here. When `-listen` is set and
no `-bind` is given at all, Core additionally opens `127.0.0.1:<port + 1>` as an
onion target. That is an extra listening socket on every default node, which is
a change to what a stock satd exposes rather than a parsing fix, so it is left
to a separate decision.

### `disconnectnode` did not disconnect

`disconnectnode` looked up the peer by address, sent it a `ping`, and returned
success. It never closed the connection. An operator cutting off a misbehaving
peer was told the call worked while the peer stayed connected and kept relaying
-- and because the RPC returned success, nothing anywhere reported a problem.

Dropping the peer's handle is what actually ends a connection: it closes the
peer task's message channel, which the write loop treats as "the manager
dropped our handle" and returns on, aborting the reader and closing the socket.
The task then emits the same disconnect event an organic drop would, so IBD
block reassignment and background-range requeue run exactly as usual.

The RPC also gained Core's second form. Core selects the peer either by address
or by `nodeid` and requires exactly one of the two -- its own test framework
disconnects with `disconnectnode("", 3)`, an empty address plus an id. satd
accepted only a single address argument, so the id form failed as invalid
parameters. Passing both or neither is now refused, and a peer that matches
nothing is reported rather than answered with success.

### `-uacomment` is honored

satd recognised `-uacomment` and ignored it, which cost more than the
operator's label. Every satd node on a host advertised exactly the same
`subversion`, and that string is how peers -- and Bitcoin Core's test framework
-- tell two otherwise-identical nodes apart.

Comments now append to the advertised user agent as Core formats them,
`/satd:0.5.1(comment1; comment2)/`, with `-uacomment` repeatable. Two rules are
enforced at startup rather than silently applied: a comment may not contain the
user agent's own delimiters (`/`, `:`, `(`, `)`) or non-ASCII, since those
would let a comment forge extra fields in a string other implementations parse,
and the whole user agent may not exceed 256 bytes. Both refusals use Core's
exact wording. Because the option was previously ignored, a value that has been
sitting harmlessly in a `bitcoin.conf` may now stop the node — see the upgrade
notes.

Command-line and config-file occurrences accumulate rather than one replacing
the other, which is what Core does: its `GetSettingsList` walks both sources and
stops early only for a negated or forced setting. So `-uacomment=a` on the
command line with `uacomment=b` in the config file advertises `(a; b)`, command
line first.

### P2P keepalive pings

satd never sent a `ping`. It answered one, and exposed a `ping` RPC that pinged
every peer on demand, but nothing on the node pinged of its own accord -- the
RPC was the only caller. A connection that went quiet therefore produced no
evidence it was still alive in both directions, and `getpeerinfo` reported no
`pingtime` for any peer, ever.

satd now pings each peer as soon as the connection is set up and every two
minutes after that, matching Bitcoin Core's cadence, and sends at most one ping
at a time per peer. A peer that never answers is not handed a fresh nonce every
two minutes, so `pingwait` keeps measuring from the ping that actually went
unanswered rather than resetting. The `ping` RPC shares that accounting, as it
does in Core, so an operator-issued ping now populates `pingtime` instead of
having its pong discarded. `getpeerinfo` gained `pingtime`, `minping` and
`pingwait`, each emitted only once it has a value -- a peer that has not yet
completed a round trip reports no `pingtime` rather than a zero, which would
read as an instantaneous link.

Round trips are timed on a monotonic clock, and stamped on the peer's own
connection task. Wall-clock time would make `setmocktime` and NTP steps show up
as nonsense ping times; measuring anywhere but the connection task would fold
that task's own scheduling delay into every number, and `minping` -- a lifetime
minimum -- would settle on the scheduler rather than on the link.

A peer that keeps talking but stops answering pings is now disconnected after
twenty minutes without a pong, matching Core's `TIMEOUT_INTERVAL`. That
qualifier is the whole point of the deadline. A peer that goes *fully* silent
was already dropped, and sooner: the read side has long had a ten-minute
receive timeout. What neither that timeout nor a socket error can see is a peer
that is demonstrably present -- still sending inventory, still relaying -- and
simply will not answer. That is the case this covers, and it is the first
disconnect satd performs on its own judgement of a peer rather than on an error
the connection reported. It gets a counter of its own,
`satd_peer_ping_timeouts_total`, and a log line with a `reason` field, because
the failure mode to watch for is a peer count that falls with no external
cause.

The deadline is evaluated on the same task that records the pong. Splitting
those across tasks would mean a backlog anywhere in the node counted against
every peer's deadline at once -- with the pongs sitting unprocessed in a queue
while the peers that sent them were dropped together.

The drop takes the ordinary teardown path, so in-flight block reassignment runs
exactly as it would for a peer that hung up cleanly.

Core additionally gates its inactivity checks on the connection being older
than `-peertimeout`. That gate is subsumed here rather than reimplemented:
satd's first ping goes out when the connection is set up, so a ping cannot have
been outstanding for twenty minutes unless the connection is at least that old.
Detection lands within one ping interval of the deadline, so up to two minutes
later than Core, which polls more often. `-peertimeout` itself stays accepted
and ignored, which has one consequence worth naming: Core documents it as the
knob for tests that drive ping timing with `setmocktime`, and since satd's ping
clock is deliberately not mockable, `p2p_ping.py` cannot pass here either way.

This is also what unblocked a group of Core's functional tests. The framework's
`connect_nodes()` helper waits for a pong on *both* sides of a new connection
before it considers two nodes joined, so every multi-node test hung for its full
timeout against a node that never pinged.

Unblocked is not the same as passing, and the difference is the honest number:
23 rows named the missing ping as their blocker, and re-measuring them turned
two of them green (`feature_framework_testshell.py` and `p2p_block_sync.py`,
taking the scoreboard to 12). The other 21 get past `connect_nodes()` and stop
on something else — `generatetodescriptor` for five of them, `getdeploymentinfo`,
`sendmsgtopeer`, pruning, `-maxtipage`, and eight that now fail somewhere not yet
attributed. Their rows carry what was measured rather than what used to block
them, which matters because a note naming already-completed work satisfies the
inventory's "name the follow-up" rule while telling the reader nothing.

### One test moved into the run set, and the harness caught itself

`feature_bind_extra.py` now passes, taking the scoreboard from two to three.

Getting it there exposed a defect in the harness rather than in satd, which is
worth recording because it had already been written down as a satd failure. The
`bitcoind` shim spawned satd as a child process, so the pid the framework held
was the shim's. The framework does more with that pid than wait on it — it reads
`/proc/<pid>/fd` to discover which sockets a node is listening on — and a shim
owns none of satd's sockets. Two bind tests therefore reported that satd had
bound nothing at all, which is both alarming and false. The shim now execs satd
in its own process and tees the log from a forked child, so the pid is the
node's. Both rows have been re-measured: one passes, and the other turned out to
name a real and much narrower gap, that satd binds only the first `-rpcbind`
address.

That is the `needs-triage` bucket doing its job. It exists to hold measured
failures whose cause is not yet attributed, and this took it from four rows to
one. It does not stay there — clearing the ping blocker later in this release
put eight new rows into it, which is the bucket working rather than failing:
those tests now fail somewhere real, and where is written down.

### Named JSON-RPC parameters

Bitcoin Core accepts a JSON *object* as a request's `params`, mapping it onto
the method's declared arguments by name. satd read `params` as a sequence
everywhere, so an object failed on **every** method — not an obscure corner,
since Core documents named parameters as a first-class way to call any RPC and
some clients use nothing else. Core's own test framework is one of them: its
`authproxy` switches to the object form the moment a caller passes a keyword
argument, which the framework does on the very first thing it runs.

satd now translates object `params` into the positional form its handlers
expect, before dispatch, so the handlers are untouched. The translation is a
port of Core's `transformNamedArguments`, including the parts that are easy to
miss: renamed arguments keep both spellings (`verbosity|verbose`); arguments
left out *before* a named one become explicit nulls while trailing ones stay
absent, because handlers branch on how many arguments arrived; the fields of an
options argument are named at the top level and gathered back into an object;
and an `args` array may supply leading positional values with named ones after.
An unknown name is refused with Core's `-8`, rather than ignored — ignoring it
would run the call with a default the caller never asked for.

The risk in this change is not the algorithm, it is the table of argument names:
a wrong name does not fail, it binds a value to the wrong position. So the table
is generated from Core's own `RPCHelpMan` declarations at the pinned release
rather than transcribed, cross-checked against the independent
`(method, index, name)` triples Core keeps in `src/rpc/client.cpp` — 65 of them
cover satd's methods, and all 65 agree — and re-checked in CI on every run, so a
future pin bump that reorders an argument fails the build instead of silently
mis-binding.

### A mockable node clock, and `setmocktime`

Core routes behaviour-affecting time through one clock so `setmocktime` can
move it; that is what makes its functional tests deterministic, letting them
mine at a chosen timestamp or age a mempool entry past its expiry without
sleeping. satd called the system clock directly at each such site, so there was
nothing to move.

There is now a single node clock (`node/src/time.rs`), and the reads that change
node *behaviour* go through it: block-template timestamps, the `time-too-new`
future-block check, and mempool entry time and expiry. Log lines, metrics and
on-disk audit timestamps deliberately still read the real clock — mocking those
would make a mocked run's logs lie about when it happened, and Core does not
mock them either.

`setmocktime` is gated to regtest, which is exactly where Core gates it: only
`CRegTestParams` sets `m_is_mockable_chain`, and mainnet, testnet3, testnet4 and
signet all reject the call. satd returns Core's message off regtest.

satd adds one restriction Core does not have. Moving the clock reaches
consensus-adjacent checks, so it is carved out of `rpc:write` into its own
`test:clock` capability. The cookie/`rpcauth` operator holds every capability
and is unaffected, but a bearer token issued for ordinary writes cannot move the
clock unless `auth.toml` grants `test:clock` explicitly. That keeps the RPC
surface Core-shaped while making the clock something you delegate deliberately
rather than by implication.

### `syncwithvalidationinterfacequeue`, and the cache finally builds

Core's validation callbacks run on one serialized queue, and
`syncwithvalidationinterfacequeue` enqueues a no-op behind whatever is pending
and blocks until it runs. Its test framework calls this from `sync_all()` so
assertions do not race a callback that has not landed yet — which made it the
last thing standing between satd and the shared chain nearly every test starts
from.

satd has no equivalent queue, and for most of what tests assert it does not
need one: block connection writes its indexes inline and the mempool updates
under its own lock, both before the originating RPC returns, so RPC-visible
state is already settled. What *is* asynchronous is outbound event delivery —
chain and mempool events crossing broadcast channels to become `NodeEvent`s on
the event bus. That is the queue satd has, so that is what the RPC drains,
rather than returning immediately and hoping.

Read the scope narrowly: it waits for events to reach the bus, not for a given
subscriber to have received one. The gRPC, WebSocket and ZMQ sinks consume the
bus as independent tasks and are not counted, and neither are the other
consumers of the chain-event broadcast — the address-index status notifier, the
P2P block-announcement task, `-stopatheight`, `-blocknotify`. Core's drain does
cover its equivalents of those, so a test that needs a block *announced* to a
peer, or a `-blocknotify` hook to have fired, needs more than this call.

Per stream it tracks what was emitted and what has been published; a caller
waits for the count that existed when it called. Three cases would otherwise
turn the call into a hang rather than an answer, and each is handled: a stream
with no bridge running is already drained (a node without the events surface
must not block); events skipped by a lagged receiver count as published, since
they will never arrive; and a bridge that starts late does not inherit events
broadcast before it subscribed, which it never received and could never
acknowledge. The wait is bounded and reports a stuck queue rather than pinning
an RPC worker.

With this in place Core's framework builds its 199-block cache against satd for
the first time.

### The scoreboard, and why it starts small

Three tests ran when this release's harness work started. That number measures
how much of Core's *test framework* satd can drive, not how Core-compatible satd
is, and the inventory says so test by test. The framework leaned on two
test-only facilities satd did not implement — `setmocktime`, which it uses for
deterministic time and to seed the 199-block chain most tests start from, and
`syncwithvalidationinterfacequeue`, which it calls from `sync_all()` — and
between them those accounted for 128 of the 261 skipped rows. Another 68 rows
are the legacy Core wallet, which satd does not have by design.

Named parameters were the blocker in front of all of that, and measuring the
ordering is what this release's harness work bought: named parameters, then
`setmocktime`, then `syncwithvalidationinterfacequeue`, each revealing the next
only once the one before it was gone.

With all three the cache builds, and the honest result is a small number.
Running the 76 cache-gated tests, three now pass and are flipped to `run`
(`feature_dirsymlinks`, `feature_startupnotify`, `p2p_getdata`), taking the
scoreboard from three to six. The rest reach their test bodies and stop on
satd's own gaps rather than on the framework — which is the useful outcome,
because those gaps are now measured instead of assumed. The single biggest is
`scantxoutset`: the framework's MiniWallet calls it from `rescan_utxos()`, so
one missing RPC accounts for 22 of the failures on its own. That, not the
current score, is the ranking worth acting on — and the next section acts on
it.

### `scantxoutset`, and satd's first descriptors

Acting on that ranking meant implementing `scantxoutset`, which meant
implementing output descriptors, which satd had none of.

Not all of them. Core's descriptor language spans key expressions, xpub
derivation with ranges, miniscript and taproot trees; the half that carries no
keys is `raw(<hex script>)` and `addr(<address>)`, and that is the whole surface
the test framework uses — MiniWallet scans for `raw(<its own script>)`. Both are
implemented, with BIP380 checksums, which are optional on input and verified
when present, as in Core.

Every other descriptor function is refused *by name*. This matters more than it
sounds: a scan that matched nothing and a scan that never understood the request
return the same empty list, so quietly accepting `wpkh(...)` and finding nothing
would be worse than not implementing it. `scantxoutset` with a descriptor satd
cannot parse says which one and what it does support.

The other half of a descriptor implementation is inference — given an output
script that matched, name it. Core does this against whatever keys the scan
objects supplied, and `raw()` and `addr()` supply none, so the hash-committed
scripts (P2PKH, P2SH, P2WPKH, P2WSH) cannot be named by key and come back as
`addr()`. Rather than derive that from reading Core, it was measured: fund one
output of each script type on a regtest Bitcoin Core, then read what its
`scantxoutset` actually reports. Three of those answers are not what reading the
source first suggested — a P2PK key that is well-formed but off the curve is
still named `pk()`, because Core checks the prefix and length and not the curve;
a taproot output key that is *not* on the curve cannot be `rawtr()` and falls
back to `addr()`; and pay-to-anchor and unknown witness versions are addressable,
so they infer as `addr()` rather than `raw()`. Those measurements are the test
vectors.

A full pass over the UTXO set is minute-scale on mainnet, so the scan runs on a
blocking thread with `status` and `abort` answerable while it does — an `abort`
queued behind the scan it is meant to stop would be useless. It reuses the
point-in-time iteration `dumptxoutset` already had, so blocks may connect during
a pass without disturbing it, and the tip it reports is the one its coins
actually belong to rather than whatever the in-memory tip has become. One scan
runs at a time, as in Core.

The measured result: of the 22 tests `scantxoutset` was blocking, one now passes
(`mempool_resurrect`), and the other 21 reach further into their test bodies and
stop on something else. That is the point of the exercise — those 21 rows now
name a measured cause instead of a stale one. Four want `generatetodescriptor`,
which the descriptor work above has now made cheap; the rest are spread across
missing RPC fields (`getmempoolinfo.permitbaremultisig`,
`testmempoolaccept.wtxid`), policy differences satd should probably adopt (Core
v31 no longer caps `OP_RETURN` output size; satd still rejects a large one as
nonstandard), an error code returned as `-25` where Core returns `-26`, and the
missing P2P keepalive that was already the joint-largest blocker.

The remaining 50 rows still marked `cache` name a blocker that no longer applies.
Re-triaging them the same way is the immediate follow-up.

Every skip carries the reason that actually blocked it, taken from a full run
rather than from reading the test, and `contrib/core-functional/README.md` ranks
the resulting work by how many tests each item unblocks. That ranking, not the
current score, is the useful output of this release's harness work.

## Silent-payment scanning: durable resume in the examples

The two client-side scan examples — `satd-events-client/examples/sp_light_scan.rs`
and `clients/go/examples/sp_light_scan` — subscribed to the tweak firehose live
and kept no resume anchor, so a restart began again from wherever it was told to
start. They now run under each SDK's `ResilientSubscription` with a file-backed
cursor store, and take the cold-sync start height as an argument:

```sh
cargo run -p satd-events-client --example sp_light_scan -- \
    http://127.0.0.1:50051 /tmp/satd-sp.cursor 709632
go run ./sp_light_scan -endpoint 127.0.0.1:50051 \
    -cursor /tmp/satd-sp.cursor -from-height 709632
```

The point is which cursor gets written and when. Both SDKs commit **on poll**: an
event's cursor reaches the store only when the caller comes back for the next
event, so the anchor never runs ahead of the scanning, and an interrupted scan
replays its last block rather than stepping over it. A scanner that persists what
it was handed rather than what it finished skips blocks after a crash, and a
skipped block is a missed payment. The Silent Payments chapter and the Rust SDK
chapter now say so explicitly — the Go SDK chapter already did.

The opposite slip, persisting the *previous* event's cursor, only costs a repeated
scan; it is also a live bug in a shipped wallet
([cake_wallet#3574](https://github.com/cake-tech/cake_wallet/issues/3574)), which
is what prompted the audit of our own client story. Two end-to-end tests now pin
the property against a live node on the tweaks path: an uncommitted kill rescans
exactly the block it had in hand, and a committed shutdown rescans none.

Two things did change in the SDKs, both found reviewing the examples against each
other. `FileCursorStore` now writes the cursor file `0600` in Rust as well as Go:
it records how far a wallet has scanned, which on a shared host says a
silent-payment wallet lives there and when it last ran. And the Go example's
`-from-height` sentinel moved from `0` to `-1`, because `0` is a height someone
can legitimately mean — "scan everything" — and reading it as "live only" attached
the scanner forward-only and reported an empty balance for a wallet that had been
paid. The Rust example already treated `0` as a height; the two now agree.

## Silent-payment cut-through (`tweak_unspent_only`)

A new per-subscription filter on the streaming `tweaks` category. With it set,
the node drops any `BlockTweaks` entry whose taproot outputs are **all** already
spent on the confirmed chain. Spentness decides only whether an entry survives,
never which outputs it carries: an entry with one spent and one live output
survives carrying **both**. That matters because BIP 352 scanning walks
`k = 0, 1, 2, …` and stops at the first `k` that does not match a carried output
— serving only the unspent one would truncate the walk and hide a live coin at a
higher `k`. Cut-through decides that a coin is gone, never that a coin is not
yours.

For a phone cold-syncing the taproot era, most of what it scans is coins that
were spent years ago. Skipping them is the largest single saving available on
that scan, and it composes with the existing `tweak_dust_limit` and `tweaks_only`
knobs.

The caveat is in the name of the thing it is not: **this is a balance scan, not a
restore.** Spentness is a live UTXO-set test at serve time, not "was this spent as
of that height", so a payment received at height `H` and spent at `H+100` is
absent from a scan of `H` that runs after `H+100`. A wallet reconstructing its
transaction history must leave the flag off. Dropped entries set the block's
`filtered` flag, so an empty block is never read as "no eligible transactions
here". Like `tweak_outputs`, the filter re-derives outputs from the block, so it
needs a block source and reads one block per event; a block that cannot be read
serves its entries unfiltered rather than failing, since a superset costs the
client redundant work while an error would end the scan. It never applies to
`MempoolTweak`, whose outputs are unconfirmed by definition.

Both SDKs carry the flag (`tweak_unspent_only` in Rust, `TweakUnspentOnly` in
Go). Defaults are unchanged: a subscription that does not set it sees every
eligible entry, spent or not, exactly as before.

## Silent payments for wallets that exist today (`blockchain.tweaks.subscribe`)

satd's streaming tweak firehose is the better protocol — durable cursors,
mempool-time tweaks, a block hash on every event — but no third-party wallet
speaks it. The wallets that scan silent payments today speak
`blockchain.tweaks.subscribe`, a de-facto Electrum method whose shape is fixed by
its clients rather than by a spec. satd now serves it, from the same `sp_tweaks`
index the firehose reads, so the two surfaces cannot disagree about a block:

```ini
electrum=1
silentpaymentindex=1
```

It is a stream, not a call: the JSON-RPC `result` carries the first height, every
further height arrives as an unsolicited notification, and `{"message":"done"}`
ends the chunk. Each height carries every eligible transaction's tweak *and its
taproot outputs*, so a client confirms a match without fetching the block. Params
are `[start_height, count, historical_mode]`, and `historical_mode=false` (what
Cake Wallet sends) cuts through coins that are already spent — the same trade as
`tweak_unspent_only` above, and with the same caveat: a restore that needs
transaction history passes `true`.

Heights below taproot activation stream as one notification carrying up to 1024
empty height keys, so a wallet restoring from an old height sees progress without
the server writing ~700k lines. A chunk ends after 60 seconds at a height
boundary and the client resubscribes from the next unscanned height. Without the
index — or while it is still backfilling — the method refuses in-band rather than
answering a scan with silence, and `server.features.tweaks` reports up front
whether this node can serve it — index present *and* complete, the same test the
subscribe makes, so a node still backfilling advertises `false` rather than
accepting a wallet it will refuse for hours.

The Electrum server name changes with this release: `server.version` and
`server.features.server_version` now report `satd-electrs-compatible/<version>`
rather than `satd/<version>`. Electrum's handshake carries no capability field,
so clients feature-detect by matching on that string — Cake Wallet will not
probe `blockchain.tweaks.subscribe` unless it contains the substring `electrs`
(`electrs`, not `electrum`; only one of them matches). Leading with satd's own
identity and following it with a compatibility token is the same bargain every
browser strikes by still sending `Mozilla`. The new `electrumservername=`
overrides it. This is scoped to the Electrum surface: peers still see
`/satd:<version>/`, and no setting here can change that. Other tweak clients do
not need the substring — they identify the chain from
`server.features.genesis_hash`. Sparrow's
silent-payment path is a different method that uploads a scan key to the server;
satd does not implement that one.

## Upgrade notes

Most of this release either fixes satd's handling of a Bitcoin Core option or
config value it previously mishandled, or adds a field to an RPC response.
Three things do change behaviour, and two of them can stop a node that
currently starts.

**A `bitcoin.conf` value satd cannot parse now stops the node.** This applies to
`minrelaytxfee` and `dustrelayfee`. That is the point of the fix — the old
behaviour left the node relaying at a rate the operator never chose — but a
config carrying such a typo, which used to start, now reports the bad value and
exits.

**`uacomment` is now validated, and it was previously ignored.** Before this
release satd accepted the key and did nothing with it, so any value at all was
harmless. It is now honored, which means it is also checked: a comment may
contain only alphanumerics and `` .,;-_?@``, and the resulting user agent may
not exceed 256 bytes. A node whose `bitcoin.conf` carries something like
`uacomment=host:1` or `uacomment=eu-west/2` starts today and **will not start
after upgrading** — the `:` and `/` are the user agent's own delimiters and
Core refuses them too. This is worth checking before a fleet-wide rollout;
`grep uacomment` across your configs is the whole of it. The node prints the
offending comment and Core's error text.

**satd now disconnects peers that stop answering pings.** It is the first
disconnect satd performs on its own judgement of a peer rather than on a
reported error, and it applies to every connection with no option to turn it
off — Core has no such option either. A peer must go twenty minutes without
answering while still otherwise present on the wire, so a healthy connection
never approaches it; peers that simply go quiet were already dropped sooner by
the read timeout, and that is unchanged. If you graph anything, the new counter
to watch is `satd_peer_ping_timeouts_total`, alongside a `reason="ping_timeout"`
field on the log line.
