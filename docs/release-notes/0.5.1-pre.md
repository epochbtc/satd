# satd 0.5.1

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.5.1 is a patch release on the 0.5.x line. Planned scope: the regtest
halving-interval divergence from Bitcoin Core (#608) and spending the
untweaked-P2TR output shape — the BIP 352 silent-payment form — through
`signrawtransactionwithkey` (#609).

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- Silent-payment outputs can now be spent through the node's own signing paths:
  `signrawtransactionwithkey` and `sat-cli`'s PSBT signer handle untweaked P2TR
  key-path spends the way Bitcoin Core does (#609).
- A batch of Bitcoin Core parity fixes: the regtest halving interval (#608),
  `-testactivationheight` support, the `bad-blk-length` / `bad-blk-weight`
  reject-reason split, an always-present `default_witness_commitment` (#548),
  and a consistency fix for `gettxoutsetinfo` (#556).
- **[satd now runs Bitcoin Core's own functional test suite](#satd-now-runs-bitcoin-cores-own-test-suite)**
  — unmodified, pinned to a Core release, with all 264 test files inventoried as
  run-or-skip-with-a-reason. Pointing Core's framework at satd immediately found
  five Core-compatibility defects, four of which affect real Core-derived
  clients: RPC replies carried a `Content-Type` Core clients reject outright,
  and the startup listener answered "no such method" where Core answers
  "warming up".

## Fixed

### Spending silent-payment outputs through the node's own signing paths (#609)

A BIP 352 silent-payment output is a P2TR output whose key **is** the derived key,
with no taptweak applied. Both of satd's signers — the `signrawtransactionwithkey`
RPC and `sat-cli`'s local PSBT signer — assumed every P2TR key-path spend was the
BIP 341/86 shape and unconditionally applied the taptweak, so a wallet backend
that located its silent-payment outputs through satd's tweak index was then told
`"Unable to sign input, no matching key"` when it handed the node the exact
private key that controls them.

Both signers now mirror Bitcoin Core's two-attempt key-path signing: each key is
first tried as a BIP 341/86 internal key (taptweak applied), and if no key
matches, tried directly against the output key with no tweak. The tweaked
reading is attempted first, so existing BIP 86 spends are unchanged.

### Regtest block subsidy halves at Core's interval (#608)

The halving interval was a network-blind 210,000; Core's
`nSubsidyHalvingInterval` is 150 on regtest. From height 150 a regtest satd
accepted coinbases Core rejects (and its own `getblocktemplate` overpaid).
`block_subsidy` is now network-aware; no other network changes.

### Core-compat gaps from the #541 review (#548)

Three independent parity fixes, each small:

- **`-testactivationheight=name@height` is implemented** rather than
  warn-and-ignored. Core's syntax and semantics: repeatable, names `bip34` /
  `dersig` / `cltv` / `csv` / `segwit`, heights validated as Core validates
  them (non-negative and below `INT_MAX`), single-dash spelling accepted.
  Command-line and config-file occurrences are merged the way Core merges
  them — command line first, config file after, last value winning per name,
  so the config file wins for a name given in both. The option applies only
  to regtest; on any other chain it is warned about and ignored, exactly as
  Core ignores it (its `ReadRegTestArgs` runs only for the regtest branch),
  so a bitcoin.conf shared with a test bench cannot break a mainnet node.
  Moving `segwit` up drags `taproot` with it so the script-flag set stays
  coherent (a taproot spend is a witness spend). This unlocks the Core
  functional-test shapes that relocate buried deployments.
- **Over-weight blocks now reject `bad-blk-weight`**, computed after the
  witness rules exactly as Core orders `ContextualCheckBlock`, with
  `bad-blk-length` reserved for `CheckBlock`'s stripped-size test. Verdicts
  are unchanged — only the reject reason and its position moved — but the
  live block-acceptance differential compares reasons, and the previously
  conflated label diverged for over-weight blocks inflated by witness data.
- **`getblocktemplate` matches Core's template shape on both sides of segwit
  activation.** Post-segwit it emits `default_witness_commitment` on every
  template, witness transactions or not, as Core does; previously a
  witness-free template carried an empty string, pushing external mining
  software toward computing its own commitment — newly hazardous since #541
  made a wrong coinbase witness nonce a hard rejection. Below an overridden
  segwit height the whole of Core's `fPreSegWit` shape now applies: the
  `segwit` and `taproot` rules are not advertised, `sigoplimit` and
  `sizelimit` report the unscaled pre-segwit values (20000 and 1000000), and
  `weightlimit` and the commitment are absent. Advertising post-segwit
  limits on a pre-segwit template would have invited a miner to build a
  block the advertising node then rejects. The segwit rule is also spelled
  `!segwit` as Core spells it, marking it as one a client must understand
  before using the template as-is.

### `gettxoutsetinfo` reads one consistent view (#556)

The RPC read its tip, coin count, total amount and height histogram as
independent lookups; a block connecting mid-call could pair a tip at height
H with totals from H+1, breaking the documented "histogram sums to `txouts`"
invariant and mis-stating the total by a block's subsidy and fees. All five
fields are now read under the chain's accept lock after the coin-cache
flush, so they always describe the same height. Same shape as the backfill
cursor fix in 0.5.0 (#549/#554), applied to the UTXO-set statistics.

If that flush fails — a full or failing disk — the RPC now returns an error
instead of an answer. A failed flush rolls the count and amount deltas back
while leaving the coins dirty, so the totals would no longer describe any
single state; reporting the failure is the honest response, and Core
likewise errors rather than guessing.

## Core functional-test conformance

### satd now runs Bitcoin Core's own test suite

There are three ways to argue a node is Core-compatible. You can check it agrees
with Core on recorded inputs — satd's ported fixture corpora. You can check it
accepts the same blocks off the real network — satd's live block-acceptance
differential against `bitcoind`. Or you can hand it to Core's own test suite and
see what happens. Only the third puts satd in front of a client written by
people who were not thinking about satd at all, and that turns out to be the
useful part.

`contrib/core-functional/` runs Bitcoin Core's functional tests **unmodified**
against satd, pinned to a specific Core release (v31.1 today). Every one of the
264 test files in that release has a row in `inventory.toml` saying either "we
run this" or "we skip it, and here is the reason". A schema checker rejects a
missing row, an orphan row, a skip with no reason, a reason outside the
taxonomy, and an open-ended skip that does not name the follow-up work. A
nightly workflow runs the run-set; the scoreboard is a chapter in the Operator
Manual.

The rule that makes the number mean anything is that **a test flips to `run`
only in the pull request that makes it pass**. There is no batch re-labelling
step. The shim between Core's framework and satd is correspondingly narrow: it
supplies a `debug.log` (satd logs to stdout and has none), rewords satd's log
lines onto the substrings `assert_debug_log` greps for, and switches off the
Esplora server so two nodes can share a machine. It does not translate, drop, or
invent node options. A test needing something satd lacks is an honest skip, not
a shim special case.

### What pointing it at satd found

Standing the harness up was itself the first result. Core's framework drives a
node the way Core's developers assume a node behaves, and five places where satd
had drifted only became visible under that assumption. Four of the five affect
real Core-derived software, not just tests.

**RPC replies carried the wrong `Content-Type`.** satd answered with
`application/json; charset=utf-8`; Core answers with exactly `application/json`.
The parameter is redundant — RFC 8259 fixes JSON's encoding as UTF-8 — but
Core-derived clients compare the header for equality rather than parsing the
media type, so the suffix reads to them as a non-JSON response. Core's own test
client rejected every reply satd sent, with `-342 non-JSON HTTP response`,
having never looked at the perfectly valid JSON body. Any client modelled on
Core's `authproxy` would have done the same.

**The startup listener said "no such method" instead of "not yet".** While a
Bitcoin Core node is coming up it answers *every* RPC with `-28` and a status
line. That code is a contract: it is how a client distinguishes "alive, ask
again shortly" from "this node cannot do that". satd's startup listener served
`getstartupinfo` and left everything else to jsonrpsee's `-32601 Method not
found` — a permanent-failure answer from a node that would have the method a
moment later. It now answers `-28` with the live progress line, so a polling
client sees "Verifying blocks..." rather than a bare retry code.

**Core options were accepted in `bitcoin.conf` but fatal on the command line.**
satd skips a recognized-but-unsupported Core key in the config file with a
warning, which is what makes an existing `bitcoin.conf` drop in. The same option
passed as a flag hit the argument parser as an unknown argument and aborted
startup. Core treats the two as one namespace, so `-fallbackfee=0.0002` and a
`fallbackfee=0.0002` line now behave identically. Unrecognized options are still
rejected: swallowing `-daatdir=/x` would start the node against the wrong
directory, which is worse than a hard error.

**56 of satd's own flags were unreachable in Core's spelling.** Core spells
every option with a single dash. satd translated single-dash options via a
hand-maintained table, and the table had drifted from the parser — including on
two flags that are Core's own names, `-blockfilterindex` and
`-peerblockfilters`. The set is now derived from the parser itself, and a test
asserts the property over the whole CLI surface, so a flag added later cannot
quietly become double-dash-only.

**`-version` and bad-flag errors did not match Core's shape.** `satd -version`
printed `satd 0.5.0-pre`, which does not contain the word "version"; it now
prints `satd version 0.5.0-pre`. A bad flag is now reported as `Error parsing
command line arguments: ...`, Core's wording.

### The scoreboard, and why it starts small

Two tests run today. That number measures how much of Core's *test framework*
satd can currently drive, not how Core-compatible satd is, and the inventory
says so test by test. The framework leans on two test-only facilities satd does
not implement — `setmocktime`, which it uses for deterministic time and to seed
the 199-block chain most tests start from, and
`syncwithvalidationinterfacequeue`, which it calls from `sync_all()` — and
between them those account for 119 of the 262 skipped rows. Another 68 rows are
the legacy Core wallet, which satd does not have by design.

Every skip carries the reason that actually blocked it, taken from a full run
rather than from reading the test, and `contrib/core-functional/README.md` ranks
the resulting work by how many tests each item unblocks. That ranking, not the
current score, is the useful output of this release's harness work.

## Upgrade notes

Nothing to do. Every change here either fixes satd's handling of a Bitcoin Core
option or config value it previously mishandled, or adds a field to an RPC
response. No default changes, and no existing configuration becomes invalid.

  JSON-RPC wire shape, CLI flag names/defaults, `bitcoin.conf` keys, on-disk

  `0.x` pre-1.0 line, deprecations may be accelerated (see the policy).

  [`SECURITY.md`](../../SECURITY.md). Consensus-affecting bugs are treated as
  P0 with same-day acknowledgement.

  images with cosign (keyless OIDC), and git tags with SSH signatures (no GPG).
  The key matrix and verification steps are in
  [`SECURITY.md`](../../SECURITY.md).
- **Intentional differences from Bitcoin Core** — catalogued in
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md).
- **Operating satd** — observability, the full flag matrix, tuning, and the
  downstream packaging contract live in the
  [Operator Manual](https://epochbtc.github.io/satd/).
