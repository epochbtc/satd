# satd 0.5.1

> Released 2026-09-04 · git tag [`v0.5.1`](https://github.com/epochbtc/satd/releases/tag/v0.5.1) · [Changelog](../../CHANGELOG.md)

satd 0.5.1 is a patch release on the 0.5.x line. It is a Bitcoin Core
compatibility release: satd now runs Core's own functional test suite,
unmodified, and most of what follows is a defect that suite found. Two of those
defects are ones an operator meets on first start — a Core `bitcoin.conf` value
that satd silently ignored, and an IPv6 `-bind` that crashed the node.

Alongside that, silent payments become usable by wallets that exist today:
satd serves the de-facto Electrum method `blockchain.tweaks.subscribe`, and the
node's own signers can now spend silent-payment outputs.

**Upgrade action:** three changes can stop a node that currently starts. See
[Upgrade notes](#upgrade-notes) before rolling this out — `grep uacomment` across
your configs is most of it.

## Highlights

- **[satd runs Bitcoin Core's functional test suite](#core-functional-test-conformance)**,
  unmodified and pinned to a Core release, with all 264 test files inventoried
  as run-or-skip-with-a-reason. It found twelve defects in shipped behaviour,
  and now gates every pull request.
- **[Silent payments for wallets that exist today](#silent-payments-for-wallets-that-exist-today)** —
  `blockchain.tweaks.subscribe` on the Electrum server, the method Cake Wallet
  and kiss-bdk already speak.
- **[Silent-payment outputs can be spent](#spending-silent-payment-outputs-609)**
  through `signrawtransactionwithkey` and `sat-cli`'s PSBT signer (#609).
- **[`getindexinfo` is now Core's method](#getindexinfo-became-cores)**; satd's
  richer view moved to `getsatdindexinfo`. **Breaking for anything reading the
  old shape.**
- **[Cut-through for cold sync](#silent-payment-cut-through)** —
  `tweak_unspent_only` drops tweak entries whose outputs are all already spent.
- **[The mempool event broadcast holds a whole block](#the-mempool-event-broadcast-holds-a-whole-block-682)** —
  its ring was smaller than a single mainnet block, so every subscriber silently
  lost part of every block.
- Core parity fixes: the regtest halving interval (#608), `-testactivationheight`,
  the `bad-blk-length`/`bad-blk-weight` split, an always-present
  `default_witness_commitment` (#548), and a consistent `gettxoutsetinfo` (#556).

## Fixed

### Spending silent-payment outputs (#609)

A BIP 352 output is a P2TR output whose key **is** the derived key, with no
taptweak applied. Both of satd's signers assumed every P2TR key-path spend was
the BIP 341/86 shape and unconditionally applied the taptweak, so a wallet that
found its silent-payment outputs through satd's tweak index was then told
`"Unable to sign input, no matching key"` when it handed the node the exact
private key controlling them.

Both signers now mirror Core's two-attempt key-path signing: each key is tried
first as a BIP 341/86 internal key, then directly against the output key with no
tweak. The tweaked reading is attempted first, so BIP 86 spends are unchanged.

### Regtest block subsidy halves at Core's interval (#608)

The halving interval was a network-blind 210,000; Core's is 150 on regtest. From
height 150 a regtest satd accepted coinbases Core rejects, and its own
`getblocktemplate` overpaid. `block_subsidy` is now network-aware. No other
network changes.

### Core-compat gaps from the #541 review (#548)

- **`-testactivationheight=name@height` is implemented** rather than
  warn-and-ignored, with Core's syntax, validation and merge order (command line
  first, config file after, last value winning per name). Regtest only, warned
  and ignored elsewhere exactly as Core does, so a `bitcoin.conf` shared with a
  test bench cannot affect a mainnet node.
- **Over-weight blocks reject `bad-blk-weight`**, computed after the witness
  rules as Core orders `ContextualCheckBlock`, with `bad-blk-length` reserved for
  `CheckBlock`'s stripped-size test. Verdicts are unchanged — only the reason
  moved — but the live block-acceptance differential compares reasons.
- **`getblocktemplate` matches Core's shape on both sides of segwit
  activation**: `default_witness_commitment` is emitted on every post-segwit
  template, and below an overridden segwit height Core's full `fPreSegWit` shape
  applies. Advertising post-segwit limits on a pre-segwit template invites a
  miner to build a block the advertising node then rejects.

### `gettxoutsetinfo` reads one consistent view (#556)

The RPC read its tip, coin count, total amount and height histogram as
independent lookups, so a block connecting mid-call could pair a tip at height H
with totals from H+1 — breaking the documented "histogram sums to `txouts`"
invariant and mis-stating the total by a block's subsidy and fees. All five
fields are now read under the chain's accept lock after the coin-cache flush.

If that flush fails, the RPC now returns an error rather than an answer: a failed
flush rolls the deltas back while leaving the coins dirty, so the totals would no
longer describe any single state.

### The mempool event broadcast holds a whole block (#682)

Connecting a block emits one `LeaveConfirmed` per confirmed transaction in a
tight loop, so each block fires a burst the size of the block's transaction
count. The broadcast ring was 1024 slots — **smaller than a single mainnet
block**, which carries 3,000–4,500. Every subscriber therefore lost roughly 37%
of each block's confirmation burst: measured on a synced mainnet node, 313,065
events dropped over 24 hours, with 100% of the lag reports falling inside the
block-connection window and none between blocks.

The channel is deliberately lossy and stays that way. Never backpressuring the
publisher is a non-negotiable safety invariant — the publisher here is
`connect_block` and the mempool accept path — so no finite capacity can promise
zero drops, and an unbounded one is an out-of-memory risk. What was wrong was
sizing a lossy channel *below the smallest burst the system can produce*. The
ring is now 32768, sized from the consensus bound on transactions per block
rather than from today's average. `MempoolEvent` carries no heap allocation, so
that costs about 2.5 MiB, allocated once at startup.

## Core functional-test conformance

### satd runs Core's own test suite

`contrib/core-functional/` runs Bitcoin Core's functional tests **unmodified**
against satd, pinned to a Core release (v31.1 today). Every one of the 264 test
files has a row in `inventory.toml` saying either "we run this" or "we skip it,
and here is the reason". A schema checker rejects a missing row, an orphan row, a
skip with no reason, a reason outside the taxonomy, and an open-ended skip that
does not name the follow-up work.

The rule that makes the number mean anything is that **a test flips to `run` only
in the pull request that makes it pass** — there is no batch re-labelling step.
The shim between Core's framework and satd is correspondingly narrow: it supplies
a `debug.log` (satd logs to stdout and has none), rewords satd's log lines onto
the substrings `assert_debug_log` greps for, and switches off the Esplora server
so two nodes can share a machine. It does not translate, drop, or invent node
options. A test needing something satd lacks is an honest skip, not a shim
special case.

The set runs on every pull request in under a minute, and nightly. The scoreboard
is a chapter in the
[Operator Manual](https://epochbtc.github.io/satd/core-functional.html).

### What it found

Twelve defects in shipped behaviour. Four affect any Core-derived client:

- **RPC replies carried the wrong `Content-Type`.** satd answered
  `application/json; charset=utf-8`; Core answers exactly `application/json`.
  The parameter is redundant, but Core-derived clients compare the header for
  equality rather than parsing the media type, so the suffix reads as a non-JSON
  response. Core's own test client rejected *every* reply satd sent with `-342
  non-JSON HTTP response`, having never looked at the valid JSON body.
- **The startup listener said "no such method" instead of "not yet".** A Core
  node coming up answers every RPC with `-28` and a status line; that code is how
  a client distinguishes "alive, ask again" from "this node cannot do that".
  satd served `getstartupinfo` and left everything else to `-32601 Method not
  found` — a permanent-failure answer from a node that would have the method a
  moment later.
- **Core options were accepted in `bitcoin.conf` but fatal on the command line.**
  satd skips a recognised-but-unsupported Core key in the config file with a
  warning, which is what makes an existing `bitcoin.conf` drop in; the same
  option as a flag aborted startup. Core treats the two as one namespace.
  Unrecognised options are still rejected — swallowing `-daatdir=/x` would start
  the node against the wrong directory.
- **`getpeerinfo` was missing `addrbind`, `bytessent_per_msg` and
  `bytesrecv_per_msg`.** Core's own framework reads all three without a null
  guard, so their absence raised `KeyError` and aborted the client rather than
  degrading. The key set is bounded by satd's own message-type enum plus Core's
  `*other*` catch-all, so no peer can make satd allocate a map key it chose, and
  the tallies are recorded so they sum to the byte totals.

Three are drop-in compatibility failures or crashes an operator meets directly:

- **Core's fee-rate options were spelled in the wrong unit.** Core denominates
  `-minrelaytxfee` and `-dustrelayfee` in BTC/kvB (`0.00001` is Core's default);
  satd documented them as integer sat/kvB (`1000` is satd's default) — the same
  rate, written differently. Both spellings are now accepted, which is
  unambiguous because the two are disjoint in practice. The dangerous half was
  what happened to a value satd could not parse: on the command line it aborted,
  but in `bitcoin.conf` it was **silently discarded** and the built-in default
  used, so a dropped-in Core config asking for a specific minimum relay fee
  produced a node relaying at a rate the operator never chose. Both paths now
  report the bad value and stop.
- **A `-bind` value satd could not parse panicked**, rather than producing the
  careful error a bind *failure* already produced in the same function. Fixing it
  exposed a second defect underneath: an IPv6 literal was not bracketed before
  being joined to the port, so `-bind=::1` built `::1:18444` and satd could not
  bind an IPv6 address at all.
- **`-blockfilterindex` required a value.** Core accepts it bare, meaning
  `basic`, and its own tests pass it that way.

Five more were found by running the set **as a set** — each had passed on its own
branch, and three were introduced by merging the conformance work rather than by
any single change in it:

- **Mempool chain limits were the wrong limit entirely.** satd refused a 26th
  connected transaction with `too-long-mempool-chain`. Core v31 has neither that
  limit nor that string: it replaced the ancestor/descendant counts with a single
  limit over a transaction's whole connected component, and its own
  `-limitancestorcount` help now calls the old settings "deprecated … only used
  by wallet for coin selection". satd now enforces the cluster limit, exposes it
  as `-limitclustercount` (default and maximum 64, so the option can only lower
  it), and reports Core's `too-large-cluster`. Chains of up to 64 transactions
  are accepted where 26 was refused — a payment chain Core relays and satd
  dropped.
- **An oversized locator banned the peer.** A `getheaders`/`getblocks` with more
  than 101 locator hashes scored 100 misbehaviour points — satd's ban threshold —
  so the peer's next connection was refused. Core sets `fDisconnect` and returns,
  with no misbehaviour score.
- **`OP_RETURN` over the budget reported `scriptpubkey`**, which in Core means
  "not a standard output type at all", where Core reports `datacarrier`.
- **`getindexinfo("txindex").synced` could never become true.** It required the
  historical-backfill marker, which stays false on any datadir first synced
  without `-txindex`. satd writes txindex entries inline as blocks connect, so
  `synced` now reports that; Core's documented poll-then-query pattern previously
  hung forever.
- **56 of satd's own flags were unreachable in Core's single-dash spelling** —
  including `-blockfilterindex` and `-peerblockfilters`, which are Core's own
  names. The set is now derived from the parser itself, with a test asserting the
  property over the whole CLI surface.

`satd -version` also now prints `satd version <v>` (it did not contain the word
"version"), and a bad flag reports Core's `Error parsing command line arguments:`.

### The scoreboard

**Thirty of Core's 264 functional tests run against satd**, up from two when the
harness landed. That number measures how much of Core's *test framework* satd can
currently drive, not how Core-compatible satd is, and the inventory says so test
by test.

Of the 234 that do not run, **90 are out of scope by construction** and will
never move: 68 need the legacy Core wallet, 9 need a Core-only binary, 5 need
previous-release binaries, and the rest need USDT tracepoints, Core's IPC layer
or ZMQ topics, or assert on Core internals satd does not share. The eligible
universe is therefore **174**, of which 30 pass. The remaining 144 are blocked by
an RPC or RPC field satd does not implement (84), a node feature it does not have
(41), a measured failure not yet attributed (10), a `debug.log` line satd has no
equivalent of (6), and the harness itself (3).

Every skip carries the reason that actually blocked it, taken from a full run
rather than from reading the test, and `contrib/core-functional/README.md` ranks
the work by how many tests each item unblocks. That ranking, not the score, is
the useful output of this release's harness work.

## Silent payments for wallets that exist today

satd's streaming tweak firehose is the better protocol — durable cursors,
mempool-time tweaks, a block hash on every event — but no third-party wallet
speaks it. The wallets scanning silent payments today speak
`blockchain.tweaks.subscribe`, a de-facto Electrum method whose shape is fixed by
its clients rather than by a spec. satd now serves it, from the same `sp_tweaks`
index the firehose reads, so the two surfaces cannot disagree about a block:

```ini
electrum=1
silentpaymentindex=1
```

It is a stream, not a call: the JSON-RPC `result` carries the first height, every
further height arrives as an unsolicited notification, and `{"message":"done"}`
ends the chunk. Each height carries every eligible transaction's tweak *and its
taproot outputs*, so a client confirms a match without fetching the block. Params
are `[start_height, count, historical_mode]`, and `historical_mode=false` (what
Cake Wallet sends) cuts through coins that are already spent — the same trade as
`tweak_unspent_only` below, with the same caveat: a restore that needs
transaction history passes `true`.

Heights below taproot activation stream as one notification carrying up to 1024
empty height keys, so a wallet restoring from an old height sees progress without
the server writing ~700k lines. A chunk serves at most 1000 heights whatever
`count` asks for, and the client resubscribes.

That cap is what keeps the end marker honest. Clients disagree about what
`{"message":"done"}` means: Cake reads it as "this chunk is over, resubscribe",
kiss-bdk as "the range I asked for was served in full". Those readings agree only
if the server finishes every range it accepts, so satd bounds the range up front
instead of truncating an accepted one. A chunk that stops early anyway ends with
`{"message":"incomplete: …; resume from height <h>"}`, so a client reading the
sentinel as completion is never told that unserved heights were scanned and found
empty.

Without the index — or while it is still backfilling — the method refuses in-band
rather than answering a scan with silence, and `server.features.tweaks` reports
up front whether this node can serve it.

**The Electrum server name changes with this release**: `server.version` and
`server.features.server_version` report `satd-electrs-compatible/<version>` rather
than `satd/<version>`. Cake Wallet feature-detects on that string and will not
probe `blockchain.tweaks.subscribe` unless it contains the substring `electrs`.
Leading with satd's own identity and following it with a compatibility token is
the same bargain every browser strikes by still sending `Mozilla`. The new
`electrumservername=` overrides it. This is scoped to the Electrum surface: peers
still see `/satd:<version>/`, and no setting here changes that.

## Silent-payment cut-through

`tweak_unspent_only` is a new per-subscription filter on the streaming `tweaks`
category. With it set, the node drops any `BlockTweaks` entry whose taproot
outputs are **all** already spent on the confirmed chain. Spentness decides only
whether an entry survives, never which outputs it carries: an entry with one
spent and one live output survives carrying **both**. That matters because BIP
352 scanning walks `k = 0, 1, 2, …` and stops at the first `k` that does not
match a carried output — serving only the unspent one would truncate the walk and
hide a live coin at a higher `k`. Cut-through decides that a coin is gone, never
that a coin is not yours.

For a phone cold-syncing the taproot era, most of what it scans is coins spent
years ago; skipping them is the largest single saving available on that scan.

The caveat is in the name of the thing it is not: **this is a balance scan, not a
restore.** Spentness is a live UTXO-set test at serve time, so a payment received
at height `H` and spent at `H+100` is absent from a scan of `H` that runs after
`H+100`. A wallet reconstructing transaction history must leave the flag off.
Dropped entries set the block's `filtered` flag, so an empty block is never read
as "no eligible transactions here". It never applies to `MempoolTweak`, whose
outputs are unconfirmed by definition.

Both SDKs carry the flag (`tweak_unspent_only` in Rust, `TweakUnspentOnly` in
Go). Defaults are unchanged.

## Silent-payment scanning: durable resume in the examples

The two client-side scan examples subscribed to the tweak firehose live and kept
no resume anchor, so a restart began again from wherever it was told to start.
They now run under each SDK's `ResilientSubscription` with a file-backed cursor
store, and take the cold-sync start height as an argument:

```sh
cargo run -p satd-events-client --example sp_light_scan -- \
    http://127.0.0.1:50051 /tmp/satd-sp.cursor 709632
go run ./sp_light_scan -endpoint 127.0.0.1:50051 \
    -cursor /tmp/satd-sp.cursor -from-height 709632
```

The point is which cursor gets written and when. Both SDKs commit **on poll**: an
event's cursor reaches the store only when the caller comes back for the next
event, so the anchor never runs ahead of the scanning, and an interrupted scan
replays its last block rather than stepping over it. A scanner that persists what
it was handed rather than what it finished skips blocks after a crash, and a
skipped block is a missed payment. The Silent Payments and Rust SDK manual
chapters now say so explicitly.

Two SDK changes came out of the audit. `FileCursorStore` now writes the cursor
file `0600` in Rust as well as Go — it records how far a wallet has scanned,
which on a shared host says a silent-payment wallet lives there. And the Go
example's `-from-height` sentinel moved from `0` to `-1`, because `0` is a height
someone can legitimately mean; reading it as "live only" attached the scanner
forward-only and reported an empty balance for a wallet that had been paid.

## `getindexinfo` became Core's

satd had been serving its own index view under Core's method name. The two
disagreed on nearly everything: Core reports one flat entry per index it was
asked to build, `{synced, best_block_height}`, and `{}` on a node with no index
flags; satd reported its address and silent-payment indexes with backfill
cursors, states and ETAs whether or not anything had been requested.

`getindexinfo` is now Core's method. satd's richer view is unchanged and moved to
**`getsatdindexinfo`** — same fields, same substructure, new name. `sat-tui`
follows it.

Two Core index flags are now accepted so a Core `bitcoin.conf` drops in
unchanged. `-txospenderindex` is answered from the `outpoint_spend` index that
already backs `gettxspendingprevout`, so its `synced` is a real answer.
`-coinstatsindex` has nothing behind it, so it is reported as never synced — a
client following Core's poll-then-query pattern will wait, rather than be told
that data it is about to read wrongly is ready.

One difference is worth stating because no field expresses it: Core's indexes
catch up by themselves, so `synced` there is a "wait for it" flag. satd's
`synced` reads an on-disk completeness marker plus an operator-driven
`backfillindex`, so an index that is behind stays behind until someone runs one.
Polling `synced` on a satd node that needs a backfill waits forever.

## Upgrade notes

Most of this release either fixes satd's handling of a Bitcoin Core option it
previously mishandled, or adds a field to an RPC response. Three things change
behaviour, and two of them can stop a node that currently starts.

**`uacomment` is now validated, and it was previously ignored.** Before this
release satd accepted the key and did nothing with it, so any value was harmless.
It is now honored, which means it is also checked: a comment may contain only
alphanumerics and `` .,;-_?@``, and the resulting user agent may not exceed 256
bytes. A node whose `bitcoin.conf` carries something like `uacomment=host:1` or
`uacomment=eu-west/2` starts today and **will not start after upgrading** — the
`:` and `/` are the user agent's own delimiters, and Core refuses them too. This
is worth checking before a fleet-wide rollout; `grep uacomment` across your
configs is the whole of it.

**A `bitcoin.conf` value satd cannot parse now stops the node.** This applies to
`minrelaytxfee` and `dustrelayfee`. That is the point of the fix — the old
behaviour left the node relaying at a rate the operator never chose — but a
config carrying such a typo, which used to start, now reports the bad value and
exits.

**`getindexinfo` returns a different shape, and `{}` on most nodes.** It is now
Bitcoin Core's method: only indexes named by a Core flag (`-txindex`,
`-blockfilterindex`, `-coinstatsindex`, `-txospenderindex`) appear. A default
node sets none of those, so it returns `{}`. Everything satd used to report there
is unchanged under the new name `getsatdindexinfo`. Monitoring or scripts reading
the old shape must be pointed at it; `sat-tui` already is.

**A node running the Electrum server reports a different `server.version`** —
`satd-electrs-compatible/<version>`, previously `satd/<version>`. No action is
needed: the name is advertisement only and the P2P user agent is untouched. An
`electrumservername=` override should not *begin* with `electrs`, because
BlueWallet tests that prefix and permanently disables request batching on a match.

**satd now disconnects peers that stop answering pings.** It is the first
disconnect satd performs on its own judgement of a peer rather than on a reported
error, and it applies to every connection with no option to turn it off — Core
has no such option either. A peer must go twenty minutes without answering while
still otherwise present on the wire, so a healthy connection never approaches it.
The new counter to watch is `satd_peer_ping_timeouts_total`, alongside a
`reason="ping_timeout"` field on the log line.

No storage-format change: this is a drop-in binary upgrade with no reindex or
migration.
