# satd 0.8.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

This file accumulates entries as changes land; it is not yet a cut release.

satd 0.8.0 includes every fix shipped in 0.7.1.

## Highlights

- [The C++ script engine verifies a transaction's inputs in linear time](#consensus):
  Bitcoin Core's interpreter now comes through `libbitcoinkernel`, about 27x
  faster on many-input blocks.
- [The Rust engine is the default primary](#the-rust-script-engine-decides-by-default):
  `-consensus` now defaults to `cpp-shadow`, with the Rust engine deciding and
  Core's interpreter checking every script behind it.

## Consensus

- **Signet blocks must carry the scheduled difficulty** (#838). On signet, satd accepted any `nBits` a block claimed, as long as the block's hash met it and its signature checked out. Bitcoin Core checks signet `nBits` against the retarget schedule like on every other chain, and refuses a mismatch with `bad-diffbits`. satd now does the same, against signet's proof-of-work limit and with no minimum-difficulty exception. The default signet's whole header chain passes the check. Also in 0.7.1.

- **The Rust engine names a malformed tapscript push as Core does.** Before running a tapscript, Core reads it from start to end looking for an `OP_SUCCESSx` opcode, and if a push's length or data runs past the end of the script it stops with `SCRIPT_ERR_BAD_OPCODE` ("Opcode missing or not understood"). The Rust engine skipped that error and let execution report whatever it reached first, so the leaf `OP_RETURN OP_PUSHDATA4 <length past the end>` failed with "OP_RETURN was encountered". It now reports `BAD_OPCODE`. Execution fails at the same push at the latest, so no verdict changes, only the reason a rejection quotes. Found by the conformance suites of [bitcoin-consensus-spec](https://github.com/coreyphillips/bitcoin-consensus-spec), which satd now runs nightly against its own consensus code (`satd-conformance-harness`).

- **`-test=bip94` on regtest** (#1245). Core's `-test=bip94` makes a regtest chain enforce BIP 94, the rules testnet4 runs under. satd had no such option, so a test that sets it could not run. satd now takes it: the first block of each difficulty period (144 blocks on regtest, as in Core since v28) may not be timestamped more than 600 seconds before its parent (`time-timewarp-attack`). BIP 94's other change, seeding a retarget from the period's first block, has no effect on regtest, which never retargets. As in Core, `-test` is refused off regtest and an unknown option name only warns. Core's other two options, `addrman` and `reindex_after_failure_noninteractive_yes`, are refused by name, since satd does not have them.

### The Rust script engine decides by default

`-consensus` now defaults to `cpp-shadow`: the Rust engine is primary and
Bitcoin Core's C++ interpreter is the shadow, re-verifying every script in the
background and logging any disagreement. Up to 0.7.x the default was
`rust-shadow`, the other way round.

Both engines still run, so every script is still checked by two independently
written implementations. What changes is which verdict the node acts on. The
Rust engine passes Core's script test suite, found no divergence from Core's
interpreter across mainnet history, and has run as the primary engine, Core's
interpreter shadowing it, under sustained production use on mainnet, signet
and testnet4 for months without a disagreement. The two engines verify at
about the same speed.

`-consensus=rust-shadow` keeps Core's interpreter as the deciding engine. The
Operator Manual now has a chapter on the engines, [Consensus Engines & Shadow
Verification](https://epochbtc.github.io/satd/consensus.html).

### The C++ script engine is Core's interpreter through libbitcoinkernel (#874)

Under `-consensus=rust-shadow` and `cpp`, satd's authoritative script engine
is Bitcoin Core's C++ interpreter, and under the new default `cpp-shadow` it is
the shadow. Up to 0.7.x it
came through `libbitcoinconsensus`. That library's API takes a serialized
transaction and one input index, so for every input it deserialized the whole
transaction again, recomputed its txid and wtxid, and rebuilt the BIP 143 /
BIP 341 hashes of all prevouts, amounts, sequences and outputs. A transaction
with *n* inputs cost *n* passes over itself, and each pass allocated, which on
the static musl build also meant contention on its single malloc lock. Bitcoin
Core itself never paid this: its `CheckInputScripts` builds one
`PrecomputedTransactionData` per transaction and every input's check reuses it.

satd now uses `libbitcoinkernel`, the library Core ships for embedding its
validation code, whose C API has the same split: the precomputed data is built
once per transaction and each input is verified against it. The Rust engine
already worked this way. Measured on script verification alone, one thread:

| Block | 0.7.x (`libbitcoinconsensus`) | 0.8.0 (`libbitcoinkernel`) |
|---|---|---|
| signet 227,466 (3,373 inputs), glibc / static musl | 4.57 s / 6.53 s | 0.17 s / 0.24 s |
| mainnet 974,146 (7,990 inputs), glibc / static musl | 656 ms / 773 ms | 283 ms / 303 ms |

The same path also checks scripts at mempool acceptance and the signet block
solution, so both get the change.

No verdict changes. The kernel's interpreter (`interpreter.cpp`) is identical
to Bitcoin Core v32.1's; `libbitcoinconsensus` was Core 26's. Both accept every
input of both blocks above, and the Rust engine keeps shadow-checking the C++
one. Bitcoin Core deprecated `libbitcoinconsensus` in v27 and removed it in
v28, and the Rust crate's last release builds Core 26, so it would have
received no further fixes.

satd pins `bitcoinkernel` 0.3.2 and `libbitcoinkernel-sys` 0.4.1, whose
bundled Core source is the consensus code satd builds.
- **`-reindex` checks every block's header as header sync does** (#506). A full `-reindex` rebuilds the block index from the block files, and it checked each block's proof of work but none of the header rules `accept_header` applies when a header arrives from a peer. A block whose `nBits` broke the difficulty schedule, whose timestamp was not above its branch's median time past, whose version was below the minimum for its height, or that contradicted a checkpoint could therefore be indexed. Block connection checks neither the difficulty nor the checkpoints, so a block that broke those was also connected: either at once, when its branch claimed the most work, or later, when a reorg moved onto a side branch the reindex had indexed. The reindex now applies those rules, along with the checkpoint rule against forks below the last checkpoint and the network's proof-of-work limit, to every block before it picks the chain to replay. A block that breaks one is logged with the rule, and neither it nor any block built on it is replayed or indexed, as header sync never indexes them. A side-chain block whose parent was not indexed is no longer indexed either. The rule against timestamps more than two hours ahead is not applied to blocks from the files, as the node does not apply it to stored blocks elsewhere. Block files a node wrote while following the network hold no such block, so a reindex over them gives the same result as before. Also in 0.7.1.

## RPC

- **Any request `Content-Type` is accepted** (#824). Bitcoin Core reads the JSON-RPC body whatever the request's `Content-Type` says. satd added `application/json` only when the header was missing, so a request that named another type got `415 Unsupported Media Type`. That included Core's documented form, `-H 'content-type: text/plain;'`, and the form type plain `curl --data` sends. Every request is now read as JSON. Also in 0.7.1.
- **`getrawtransaction`'s not-found message matches the node's index** (#1066). With `-txindex` on, satd still told the caller to enable `-txindex`. The message now depends on the index, as Core's does:
  - With no index, it keeps that advice.
  - With a complete index, it says `No such mempool or blockchain transaction`.
  - With an index that was turned on after blocks were already connected, it says those blocks are not covered and need a block hash. satd never backfills the index. This stands in for Core's "still being indexed" case.

  The error code is still -5. Also in 0.7.1.
- **`testmempoolaccept` agrees with `sendrawtransaction` under an `allow` policy rule** (#999). With a `-policyfile` that holds an `allow` rule, admission records a failure in the exemptable standardness set (too many dust outputs, a non-standard output or input script, ephemeral dust that pays a fee) and forgives it when the transaction's verdict is `Allow`. `testmempoolaccept` returned the standardness refusal before it ran the policy, so it refused transactions `sendrawtransaction` accepted. It now records the same failures, runs the policy dry run, and forgives them on an `Allow` verdict. A `Pass` or `Quarantine` verdict still refuses with the standardness reason, and a node without an `allow` rule is unchanged. Also in 0.7.1.
- **`getnetworkinfo` reports which networks are reachable** (#1164). `ipv4` and `ipv6` were always `reachable: true, limited: false`, so a node under `-onlynet=onion` told its operator that clearnet was in use when it made no clearnet connections. Each network's flags now come from the set that drives outbound connections, as Core's `g_reachable_nets` does: `-onlynet` decides, and `onion` also needs a proxy that reaches Tor and no `-onion=0`. `networks` now lists Core's five networks: `i2p` is never reachable, because satd has no I2P transport, and `cjdns` is reachable only with `-cjdnsreachable`. Also in 0.7.1.
- **`warnings` is always an array** (#956). `getblockchaininfo`, `getnetworkinfo` and `getmininginfo` returned `"warnings": ""` on a node with no warnings and an array of strings otherwise, so the field's type depended on the node's state. It is now always an array, `[]` when there are none, as in Core since v28. The new `-deprecatedrpc=warnings` brings back Core's deprecated form: one string, the latest warning, or `""`. `-deprecatedrpc` with any other name is warned about at startup and ignored. Also in 0.7.1.
- **`getblockstats` reports what Core reports, in Core's units.** Several of its statistics did not match Bitcoin Core:
  - **Feerates were a thousand times too high.** `minfeerate`, `maxfeerate` and `avgfeerate` were in sat/kvB under Core's names, so a 5 sat/vB block reported 5000. They are now in sat/vB, each transaction's rate its fee times four over its weight, truncated, as in Core. `sat-tui`'s "Avg Rate", which was already labelled sat/vB, now shows the right number.
  - **`avgfeerate` divided by the whole block's weight,** header and coinbase included. It now divides the fees by the non-coinbase transactions' weight, as Core does.
  - **Sizes counted the header and coinbase.** `total_size` and `total_weight` were the whole block's; `avgtxsize` divided that size by every transaction, coinbase included; `mintxsize` and `maxtxsize` included the coinbase. All of them now cover the non-coinbase transactions only, as in Core, and a block with only a coinbase reports 0 for each.
  - **`mediantxsize` was a mean.** It was the block's total size divided by its transaction count. It is now the median total size, witness included, of the non-coinbase transactions, with the two middle sizes averaged when the count is even.
  - **`feerate_percentiles` is new:** the feerate, in sat/vB, at the 10th, 25th, 50th, 75th and 90th percentile weight unit of the block's non-coinbase transactions, so a heavy transaction moves the percentiles more than a light one. `[0, 0, 0, 0, 0]` for a coinbase-only block.

  Every statistic is checked against Bitcoin Core 32.1 on the same blocks: a zero-fee spend, a parent and its fee-paying child in one block, witness spends and rates that truncate. Four still differ and are left for later: `total_out` counts the coinbase's outputs, `utxo_size_inc` charges a flat 50 bytes per output, and `utxo_increase_actual` and `utxo_size_inc_actual` are missing.

  Fees come from the block's undo data, which also prices a child whose parent is in the same block. The undo data stays when a node prunes, but the block does not, so a pruned block still answers `Block data not available`. A block whose undo data does not match it is refused, now also when the undo data holds more coins than the block spends, and so is a block whose undo data cannot be read, with Core's `Can't read undo data from disk` (-1); that block used to report every fee as zero. The same per-block computation will feed the new fee estimator; it changes no fee estimate yet.
- **An open WebSocket no longer outlives its bearer token** (#821). A WebSocket on the JSON-RPC listener resolved its bearer token once, at the upgrade, and jsonrpsee copies that request onto every frame, so the token's principal rode every call for as long as the socket stayed open. Removing the token from the `-authfile` and sending `SIGHUP`, or letting its `expires` pass, did not stop a socket that was already open from calling what the token had been granted, `sendrawtransaction` included. Each frame now resolves the token again, by its digest, against the token table as it stands. A frame whose token was removed or has expired is answered with error `-32006` (`bearer token revoked or expired`), its notifications are dropped, and a `subscribemempool` subscription opened with the token ends at its next event. A reload that changes a token's capabilities or rate limit now reaches open sockets too. New connections were already refused with `401`. Also in 0.7.1.
- **The capability check comes before parameter checks** (#826). On a listener with `-rpcauthbearer`, the named-parameter rewrite ran before the capability filter, so a token without `rpc:submit` that called `sendrawtransaction` with an unknown named parameter got `-8 Unknown named parameter` instead of the capability error. The method filters (capabilities, the read-only listener's method list and the startup listener's `-28`) now run first, as Core's `-rpcwhitelist` check does, and the caller gets `-32004`. A call the token may make has its parameters checked as before. Also in 0.7.1.
- **Initial block download is judged as Core judges it** (#1071). satd counted itself in initial block download whenever its tip was more than `-maxtipage` (24 h) old, and nothing more. Core also stays in IBD while the tip has less than the network's minimum chain work (`-minimumchainwork`), so a short chain with recent timestamps and little work does not take it out, and once Core leaves IBD it never re-enters it while the process runs. satd now does both. A node whose tip goes stale after it has synced (no block for a day on a test network, a long gap between blocks, a stalled set of peers) used to drop back into IBD; `getblockchaininfo` then reported `initialblockdownload: true`, mainnet `getblocktemplate` refused with -10, Stratum stopped issuing work and the node sent peers a fee filter that turned off transaction relay. It now stays out of IBD until it restarts. The node also stays in IBD while it replays blocks at startup, as Core does while it loads blocks.
- **`estimatesmartfee` takes Core 32.1's shape and floors every answer** (#1200). This is new in 0.8.0 and is not yet the new fee estimator: the number still comes from the same history estimator, and the reworked estimator that replaces it lands later in 0.8.0.
  - **Floors.** Every answer is at least the rolling mempool minimum (`mempoolminfee` once the pool is full), the relay floor and 1 sat/vB. With a full mempool satd used to quote a rate it would itself refuse to relay. The same floor now applies to `estimatefees`, Esplora `/fee-estimates`, Electrum `blockchain.estimatefee`, the MCP fee tool and the status page.
  - **`options`.** The third argument takes Core's `fee_rate_estimator` and `verbosity`. `block_policy` answers from history and `mempool_policy` from the mempool; `auto`, the default, answers as before. Unlike Core, an unknown `fee_rate_estimator` value (`none`, the empty string) means `auto` instead of an error. An unknown key in `options` is ignored, where Core refuses it. `verbosity` 2 adds `mempool_health_statistics`.
  - **`estimator`.** Every answer names its source: `block_policy`, `mempool_policy`, or `floor` when the floor set the number. Core reports it only under `auto`, and has no `floor`.
  - **`blocks`.** It is the target the estimate was found at, as in Core, not the requested one. A request for 1 block is answered for 2 blocks, so the default answer at target 1 changes: it is history's 2-to-3-block rate, which is lower than the 1-block rate satd quoted before. `mempool_policy` always answers for 2 blocks, as Core's mempool estimator does.
  - **No history.** With no fee history (a node that just started, or one that has not yet seen blocks from peers) the answer is Core's `errors: ["Insufficient data or no feerate found"]` with `blocks: 0`. satd used to quote the relay floor there. `errors` now appears only when there is an error, where it used to be an empty list on every answer.
- **Bitcoin Core v32.1 options and arguments** (#1203).
  - **Config.** `bitcoin.conf` and the command line accept the options Core v31 and v32.1 added. `prevoutfetchthreads`, `inboundrelaypercent`, `rpcmaxconnections` and `txsendrate` are recognized, warned about and skipped, as other Core options satd does not implement are; they were refused as typos before, so a configuration written for Core v32 would not start. `privatebroadcast` is refused at startup: satd does not implement private broadcast, and running without it would announce transactions to every peer.
  - **`fees/`.** The node creates `<datadir>/fees/` at startup, where Core v32 keeps its fee estimator files.
  - **`converttopsbt`** takes Core v32's fourth argument, `psbt_version`. satd converts to a version 0 PSBT, so `psbt_version=0` works and any other value is refused with `-8`, rather than ignored. Core v32 defaults to version 2; satd still defaults to 0.
- **`estimatesmartfee`'s `mempool_policy` is Bitcoin Core 32's mempool estimator** (#1202). This is new in 0.8.0, and opt-in: the default answer still comes from history, and `estimatefees`, Esplora, Electrum and the status page are unchanged.
  - **Answer.** With `options.fee_rate_estimator` set to `mempool_policy`, the answer is the feerate at which the next block template, best packages first, reaches 50% of a block's weight under `conservative`, or 75% otherwise. Where the template does not reach that far, the floor answers. This is the number a Core 32.1 node gives on the same mempool. It is always answered for 2 blocks.
  - **Health gate.** The answer is refused, with Core's error text, until the startup mempool load is over and while the mempool is not representative: less than 75% of the last six blocks' non-coinbase weight was in it before they arrived. A window lighter than one full block passes, as in Core. The six rows persist in `fees/mempool_health.dat` and are kept across a restart that brings the mempool back. Without one (`-persistmempool=0`, or no `mempool.dat`) the rows are cleared, and the estimator waits for six new blocks.
  - **`verbosity` 2** now fills `mempool_health_statistics` with those rows, newest first, and adds `mempool_health`, the verdict over them (`healthy`, `insufficient_data` or `low_coverage`).
  - **Arrivals.** The node now tracks how much weight enters the mempool per feerate band, for the reworked estimator to price the next two blocks with. A transaction counts only after ten seconds in the mempool and only in the template class. Nothing answers from this yet.
- **`estimatesmartfee`'s `block_policy` reads the chain's own fee history** (#1250). This is new in 0.8.0, and opt-in: `auto`, the default, still answers from the old history estimator until the reworked estimator becomes the default later in 0.8.0.
  - **What it measures.** For each block, the **hurdle**: the feerate at the 10th percentile of the block's weight, over transactions paying at least the relay floor. That is roughly what it took to get into that block, where the old estimator measured what transactions paid, overpayers included. The node keeps the hurdles of the last 3,200 blocks of the active chain.
  - **How it answers.** For a target of N blocks, every run of N blocks in the history is a window, and its outcome is the lowest hurdle in it. The estimate keeps only the windows that started in a fee market like today's (the median hurdle of the few blocks before the window within ×1.25 of the median of the last few blocks, and at least the 200 closest), and takes a high quantile of their outcomes: 99.9% at 1 block, and 95% (economical) or 99% (conservative) at 2 blocks and more. A fee spike earlier in the history therefore does not keep estimates high once the market is calm, and a spike in progress is answered from past spikes. This is the analog-window method of rbitcoin's fee estimator (`docs/mempool-fee-estimation.md` in reardencode/rbitcoin), reimplemented in satd. Until a target has 2,000 windows it answers a plain quantile over the windows it has, and before it has one, the old estimator.
  - **Saved across restarts.** The history is saved to `fees/fee_history.dat` (about 140 KB) every 144 blocks and at shutdown, through a temporary file and a rename. A start loads it, keeps the rows up to the newest block still on the active chain, and reads from block and undo data, newest block first and in the background, only what the file lacks: the blocks connected while the node was down, and older blocks when the file is new or short. A damaged file, or one written for another network, is logged and the history is read again from the blocks. The file is what lets a pruned node, which keeps only a few hundred blocks, reach a full history: it gathers the hurdles as it connects blocks, across restarts. Reading 3,200 blocks back on a synced mainnet node took about 72 seconds (some 22 ms a block) in a measurement through `getblockstats`, which reads the same block and undo data; with the file, a restart reads only the blocks since the last save.
  - **Reorgs.** Each pass walks back from the tip, by parent hash, to the first block the history already holds, and replaces everything above it, so a reorg, including one while the node was down, never leaves a row from an abandoned branch.
  - **Backtest.** Over 30,000 mainnet blocks (heights 945,330 to 975,330), estimating every 36 blocks from the 3,200 blocks before and scoring against the lowest hurdle in the next N blocks, the analog windows covered as often as a plain quantile over the same history and overpaid much less (economical, median estimate ÷ realised hurdle):

    | Target | Plain quantile | Analog windows |
    |---|---|---|
    | 1 block (99.9%) | 99.9% covered, 14.9× | 99.9% covered, 9.4× |
    | 2 blocks | 94.8%, 5.9× | 94.1%, 3.0× |
    | 6 blocks | 95.0%, 3.3× | 95.4%, 1.9× |
    | 24 blocks | 94.9%, 1.5× | 94.9%, 1.2× |
    | 144 blocks | 92.0%, 1.2× | 92.6%, 1.1× |

    `conservative` (99%) covered 99.1% to 99.3% at 2 to 12 blocks, at 2.8× to 6.7×. The hurdle is a stand-in for inclusion: beating a block's 10th-percentile rate is not a guarantee of getting into it.
- **A too-long Bech32 address names one error location** (#1204). `validateaddress` on a Bech32 string longer than 90 characters reported every position past the limit (capped at 256). It now reports the single position where the string passes the limit, as Core v32 does. The error message is unchanged.
- **A JSON-RPC connection from outside `-rpcallowip` is closed without a reply** (#1204). The plain-HTTP listener answered such a connection with `403 Forbidden: source IP not permitted`, as Core did up to v31. Core v32 aborts the connection at accept instead, before any HTTP is exchanged, and satd now does the same. The TLS listener already did. A client outside the allowlist now sees the connection closed or reset rather than a 403.
- **A transaction announced twice in one `inv` is processed once** (#1204). Core v32 handles each transaction hash once per `inv` message, counting `MSG_WITNESS_TX` as a txid, and logs `got inv: <type> <hash> <have|new> peer=<n>` for it outside initial block download, and for a block announcement at any time. satd now does both; the line appears under `-debug=net`. Nothing satd sends changes: a duplicate already led to the same single request.
- **A request for a filtered block disconnects the peer** (#1204). satd never offers `NODE_BLOOM`, so a `getdata` for `MSG_FILTERED_BLOCK` asks for something it does not serve. satd ignored it; Core v32 disconnects the peer and logs `filtered block request received when NODE_BLOOM service disabled`, and satd now does the same. A peer that follows the protocol never sends one.
- **A `-blocksonly` node ignores compact blocks** (#1204). A node with no mempool to rebuild them from never asks for compact blocks, but satd still processed one a peer pushed, header included, and could connect a block from it. Core v32 ignores every `cmpctblock` under `-blocksonly`, and satd now does too. The full block, which such a node requests, is unaffected.

## Electrum

- **Sparrow batches its requests against satd** (#1069). Sparrow decides from the `server.version` name whether a server can take batched requests, and batches only for names it knows, such as one containing `electrumx`. satd's default name, `satd-electrs-compatible/<version>`, matched none of them, so Sparrow sent one request per script hash and wallet scans were much slower than they needed to be. The default is now `satd-electrs-electrumx-compatible/<version>`, which Sparrow recognises. Cake Wallet still finds the `electrs` token it looks for before probing silent-payment tweaks, and the name still does not start with `electrs`, which would turn BlueWallet's batching off. Also in 0.7.1.
- **`-electrummaxbatchrequests` defaults to 345** (#1069). Once Sparrow batches, it sends up to 250 `blockchain.transaction.get_merkle` calls in one batch when it verifies a wallet's transactions, and the old cap of 100 would refuse that batch whole. 345 is Fulcrum's default. Also in 0.7.1.

## Mempool and relay

- **Transaction versions outside 1 to 3 are non-standard** (#1070). Core's `IsStandardTx` refuses a version below 1 or above 3 with reason `version`. satd had no version check, so `sendrawtransaction`, `testmempoolaccept` and P2P relay accepted a version 0 or version 4 transaction that Core refuses, and satd then relayed it to peers that would drop it. `-acceptnonstdtxn` lifts the rule on test chains, as in Core. Also in 0.7.1.

## P2P

- **Blocks and headers no longer wait for the P2P loop's tick** (#1228). Each peer's connection hands its messages to one loop, which woke at once only for a `getdata` and otherwise ran every 500 ms. An arriving `block` or `headers` message waited for that tick, so a peer delivered about 25 blocks a second whatever their size, and header sync advanced one 2,000-header batch per tick. The cost was per message, not per byte, so it dominated the early chain, where blocks are small: from one peer on local storage, a fresh mainnet sync reached about 7,400 blocks in its first five minutes, and now reaches about 58,000. Below the first ~100,000 blocks the limit is now the storage's flush latency, since every stored block is synced to disk. A block that arrives as an initial sync winds down still makes its sender a high-bandwidth compact-block peer, as in Core. Also in 0.7.2.
- **Header sync fetches each header once per peer, not many times** (#1229). During initial sync the node sent a fresh `getheaders` every two seconds, and asked three other peers for headers after every full batch. Each request started its own chain of follow-ups to the header tip, so the number running at once grew for as long as header sync lasted: a fresh mainnet sync from one peer received 5.6 GB of `headers` messages for a 78 MB header chain, and the duplicate answers queued ahead of block requests at the peer. A new request now goes out only after the header tip has stood still for 10 seconds, at most once per 10 seconds, and a full batch asks only the peer that sent it for the next one. The same sync now receives 90 MB. Also in 0.7.2.
- **Header sync runs with one peer while the node is far behind, as in Bitcoin Core.** Every new connection opened with its own `getheaders`, and each peer then answered its full batches to the end, so a fresh node received the whole header chain once from every peer it connected to. Now, while the best header is more than a day old, header sync runs with a single peer, preferably an outbound one; once the best header is recent, every peer is asked, as before. A peer that answers with less than a full batch has no more headers past ours, so the next peer starts straight away, and if header sync stalls for 10 seconds, a peer that has not synced yet is asked. A block announced by `inv` from a peer whose header sync has not started brings a `getheaders` once per peer and once per block, as in Core's `inv` handler. A fresh testnet4 node with seven peers received 13.0 MB of `headers`, one copy of the chain, where the same node had received 75.5 MB from ten peers.
- **A fresh initial sync runs without RocksDB's write-ahead log, as intended.** Initial sync is meant to switch the log off (BulkLoad) for any catch-up of 10,000 blocks or more, since the block files can replay what a crash loses. The connector decided once, from the height its download scheduler was aiming for, and a fresh node starts its first scheduler on the first 2,000-header batch, so it kept the log on for the whole chain. The gap is now measured to the best header, and checked again as headers arrive.
- **The coin cache counts what it holds.** A coin created and spent between two flushes stayed in the cache as a spent marker until the next flush dropped it, and the flush threshold added one for each operation, so such a coin counted twice. During initial sync those markers were most of the cache: each flush found about 480,000 of them among 710,000 entries, and the cache flushed at about a third of its budget. A spend now erases a coin that has never been written, as Bitcoin Core's `SpendCoin` erases a FRESH coin, and the threshold counts entries. The index rows a block connect buffers until the same flush (block index, undo data, the transaction, address and spent indexes) now count toward it too, so they cannot pile up while the coins stay under it. With the same indexes as Core (`-txindex`, `-addressindex=0`), a mainnet sync from one local peer reached about 240,000 blocks in its first five minutes, against 231,500 before and 246,700 for Core 29.3 on the same machine.
- **The coin cache flushes when it is full, as Bitcoin Core's does.** During initial sync the cache flushed every 1,000 blocks, and on its own once a quarter of the `-dbcache` budget was dirty. Each flush wrote coins that a later block would have spent before the next one, and synced the block files; stack samples of a mainnet sync put the block connector in a flush more than half the time. Dirty coins may now fill the whole budget, and the 1,000-block flush is gone. Two other costs went with it: blocks below `-assumevalid`, whose scripts are not checked, no longer start a set of verification threads each, and storing a block no longer reads the index all the way back to the connected tip, which during initial sync was tens of thousands of entries under a lock the connector needs. From one peer on local storage, the first five minutes of a fresh mainnet sync reached about 211,000 blocks, up from about 155,000. Two things change for operators. Peak memory during initial sync is higher, by up to the `-dbcache` budget. And after a crash the node reconnects every block since its last flush from the blocks it has stored, which can now be a few thousand. Nothing is lost: a prune always flushes the chainstate first, so the blocks to reconnect are never deleted. At the chain tip the cache still flushes after every block.
- **Initial sync syncs the block files once per batch, not once per block.** Every block stored during initial sync used to fsync its block file before its index entry was written, so that no index entry could ever point at bytes a power loss had taken. That kept the early chain, where blocks are a few hundred bytes, to one disk flush per block: about 250 blocks a second on a SATA SSD, and far fewer on a spinning or virtual disk. A stored block's entry now waits in memory, visible to every reader, until 64 have gathered or the oldest is 100 ms old; one sync of the block files then covers them all, and they are written together. The guarantee is unchanged: no entry reaches the database ahead of the bytes it names, and a block connected in the meantime has its entry written only after that sync. A crash loses at most the waiting entries, and their blocks are downloaded again, as in Bitcoin Core. From one peer on local storage, a fresh mainnet sync reached height 100,000 in about 70 seconds (it took about 7 minutes before), and 162,000 in five minutes. Blocks that arrive at the tip, one at a time, still sync before they are connected.
- **Disconnect log lines give the right reason** (#1152). Every disconnect the node made for its own reasons, such as a stalling block download or misbehaviour, was logged as `Disconnecting peer on request ... reason="rpc_request"`, as if something had called `disconnectnode`. The line now reads `Disconnecting peer`. It has `reason="rpc_request"` only for `disconnectnode`, and `reason="internal"` otherwise, next to the line that already gives the cause. Also in 0.7.1.
- **Onion peers are logged by their onion address** (#1165). The `Peer connected` and `Peer disconnected` lines, and the IBD silent-peer warning, printed `0.0.0.0:<port>` for a `.onion` peer. They now print the address `getpeerinfo` reports, `<host>.onion:<port>`. Also in 0.7.1.
- **A pruned node prunes during initial sync** (#1154). The download scheduler shuffled every height up to the header tip into one pool, and its only limit was a count: no more than `-maxahead` blocks downloaded but not yet connected. Once the window filled, each slot it freed went to a random height anywhere up to the header tip. So every block file held a sprinkling of blocks tens of thousands of heights above the tip. Pruning deletes a file only once its highest block is below the cut, so on a pruned node nothing was deleted until IBD was nearly over, and a small disk filled. Blocks are now handed out in height order and never more than `-maxahead` above the tip, as Core's download window works. Two smaller paths are closed as well:
  - A block announced by `inv` during IBD is answered with `getheaders` only, as in Core, instead of being fetched and stored hours before it can connect.
  - A block nobody asked for is not stored when it lies above the window, as Core's `AcceptBlock` refuses one too far ahead.

  Blocks stored above the window by 0.7.0 stay until the tip reaches them. Also in 0.7.1.
- **Peer handling no longer stops while a block connects during initial sync** (#875). Each block that arrived during IBD was stored on the task that handles every peer's messages, and storing takes the lock the block connector holds for the whole of a connect, script checks included. On a block of large transactions that is tens of seconds, and for that long the node read no peer's messages, asked for no blocks and answered no pings. Once the connect finished, the stall check could then drop peers whose blocks had arrived but were still waiting behind it. Blocks are now stored on a thread of their own, and a peer counts as having delivered a block when it arrives rather than when it is stored. The blocks waiting to be stored are bounded at 128 MiB; past that, a block is stored the old way. A ping sent after a block is still answered only once that block is stored.
- **A `headers` message no longer stops peer handling while a block connects** (#1187). #875 moved IBD block storage off the task that handles every peer's messages; a `headers` message was still accepted there, and committing it waits for the lock a block connect holds from start to finish. A batch that arrived during a long connect stopped every peer's messages, block requests and ping replies until the connect finished, and its proof-of-work checks on up to 2,000 headers ran on that task too. Header batches are now accepted on a thread of their own, in the order they arrived. While one is waiting, the block-relay messages that arrive behind it (a block `inv`, `cmpctblock`, `blocktxn`, and `block` outside initial sync) wait behind it too, so each still sees the batches before it, as in Core, and a `ping` sent after a batch is still answered after it.
- **Onion seeds for every network** (#1162). satd had no `.onion` fixed seeds for testnet4 or testnet3, so a Tor-only node (`-onlynet=onion` with `-proxy`) there had no address to dial unless the operator added one by hand. Its 20 mainnet onion seeds were down to 7 that still answered. Of its 2 signet entries, one was not a valid Tor v3 address. The lists now hold the Tor v3 entries of Bitcoin Core v31.2's fixed seeds, kept only where the node answered a version handshake over Tor with the right network magic and `NODE_NETWORK` when they were imported: 138 for mainnet, 41 for testnet3, 49 for testnet4 and 48 for signet. Also in 0.7.1.
- **Automatic dials draw from the whole address book** (#1148). At startup satd put 256 entries of `peers.dat` on its dial list, the most recently reached first, and added only what gossip named after that. The rest of the book, up to 16,384 entries, was never dialled until a peer gossiped it again, so a restarted node went back to much the same peers. Automatic outbound connections now draw from the whole book, as Bitcoin Core's do, and take each drawn entry with Core's odds: a hundredth of the usual if it was dialled in the last ten minutes, and 0.66 times as likely for each failed attempt, down to 1/28th after eight. A candidate is also skipped before it is dialled, as in Core, if the services the book holds for it lack the ones the node needs, or if it is on a port another well-known service uses (SSH, SMTP, DNS and the rest of Core's list) until 50 other candidates have been looked at. satd learned a peer's services only in the handshake and dropped it there, after spending the connection. `-connect` still turns automatic dials off.
- **Onion addresses are in the address book** (#1157). The address book was keyed by IP address and port, so it could not hold a `.onion` address. The onions a node learned from `addrv2` gossip, and its onion seeds, went to a separate list of at most 512, kept in memory only: a restart forgot every onion the node had learned, and the list had none of the book's tried table, test-before-evict or draw odds. The book now holds Tor v3 onions as Bitcoin Core's holds every BIP 155 network. They are written to `peers.dat`, drawn for automatic dials with the rest at Core's odds, moved to the tried table when a dial connects, and replaced when they turn terrible.
  - An onion's network group is Core's: the network and the first four bits of its key, which puts the onions in sixteen groups. `-asmap` groups IP addresses only.
  - Anyone can make onion addresses in every group, so one source (the network group of the peer that announced them) holds at most 64 onion entries in the new table, the share the old list kept.
  - A pass of the reconnect loop starts at most 16 onion dials, as before, and onions are dialled only while a proxy reaches Tor and `-onion=0` is not set. A `peers.dat` written while the node had a proxy can hold onions it then leaves alone.
  - `getnodeaddresses`, `getaddrmaninfo` and `getrawaddrman` report onion entries under `onion`, and `addpeeraddress` takes a v3 onion address, as in Core.
  - The onions an operator names (`-connect`, `-addnode`, `-seednode`) stay off the book, as manual clearnet peers do until they connect.
- **Feeler connections** (#1149). satd never opened a feeler of its own: only the test-only `addconnection` RPC could. So a new-table address was tested only when it was dialled as a full outbound peer, and the tried table grew only from those. The node now opens feelers as Bitcoin Core does. Once the automatic outbound slots are full, a timer that fires every two minutes on average opens one short connection to an address from the new table. It is closed as soon as the peer answers with its `version`, and the address moves to the tried table; a dial that fails counts as a failed attempt. A feeler needs only `NODE_NETWORK` or `NODE_NETWORK_LIMITED` (a peer whose address book is worth having), may test an address in a network group the node already has a peer in, and waits a random time of up to a second before it dials so that nodes do not fall in step. It has a slot of its own and takes none of the eight automatic ones. When a newcomer is waiting for the tried slot another address holds, the feeler tests that address first (test-before-evict), as in Core; since #1127 the node's next full-relay dial did that. Not under `-connect`.
- **Two block-relay-only outbound peers** (#1225). Bitcoin Core keeps two outbound connections that carry only blocks: no transactions and no addresses. They make an eclipse attack or a network partition harder, and a transaction-graph observer cannot see them. satd opened none of them, so a synced node held only its eight full-relay peers. Now, once the eight full-relay peers are up, the node opens two block-relay-only peers, drawn from the address book as the others are and kept to one per network group, the same as every automatic peer. As in Core, `-maxconnections` caps them: one at 9, none at 8 or fewer. They do not count against the full-relay target, and the surplus eviction never drops one. The automatic feeler and the extra peer for a network with none now wait until both kinds of peer are up, which is the order Core opens them in. A block-relay-only connection opened with `addconnection` no longer takes a full-relay slot either. During initial block download, satd's full-relay target is 64, so these peers open once the node leaves it.
- **Block-relay-only peers survive a restart: `anchors.dat`** (#1150). Bitcoin Core writes its block-relay-only peers to `anchors.dat` when it stops cleanly, and dials them first when it starts again. An attacker who fills the address book while the node is down still has to displace peers the node chose before. satd had no such file, so after a restart every peer came from the address book. Now, on a clean stop, satd writes up to two block-relay-only peers to `anchors.dat` in the network data directory. The next start reads the file and deletes it at once, so a bad anchor is tried only once. Those peers are then dialled before any other automatic connection, as block-relay-only, even before the eight full-relay peers are up. An anchor is passed over, as in Core, if it is one of the node's own addresses, lacks the services the node needs, is on a network the node cannot reach, or shares a network group with an outbound peer already held. A crash or a kill writes nothing. Under `-connect` the file is neither read nor written. The file is byte-compatible with Core's, so it carries over when a data directory moves between Core and satd; `peers.dat` remains satd's own format. Core's `feature_anchors.py` now runs in satd's Core functional test set.
- **`addconnection` opens onion connections** (#1150). The test-only `addconnection` RPC refused an `.onion` target with "cannot open a typed connection to an onion address", because satd's onion dial could not carry a connection type. It can now, so the call opens the connection through the proxy with the type asked for, as Core does; `v2transport` is honoured for it. A dial that fails is logged, not returned as an error, as for any other `addconnection` target.
- **An outbound peer on every reachable network** (#1156). satd's surplus eviction already kept the only manual or full-relay peer on a network, but nothing opened that peer. A node that could reach IPv4 and onion, say, could run with all eight peers on IPv4, so a single network's view decided what it saw. The node now does what Bitcoin Core does: when it has exactly its eight full-relay peers and a reachable network has none of its manual or full-relay peers, a timer that fires every five minutes on average dials one extra full-relay peer from the addresses it holds on that network. The ninth peer pushes the node one over its target, and the surplus eviction then drops a peer on another network, never the only one on its own. The networks are IPv4, IPv6 and onion (onion with a proxy that reaches Tor); satd has no I2P or CJDNS transport. Nothing extra is opened when `-maxconnections` lowers the target below eight, during initial block download, or under `-connect`.
- **An extra block-relay-only peer every few minutes** (#1155). Once its initial sync is over, Bitcoin Core opens one more block-relay-only connection about every five minutes (an exponential timer with a five-minute mean), long enough to learn the peer's headers. It then keeps two block-relay-only peers: the youngest is dropped, unless it gave the node a block more recently than the second-youngest, which is dropped instead. So the node keeps meeting new peers to learn headers from, and an attacker must eclipse each one in turn. satd did neither. It now does both, as Core does. The extra peer is drawn from the address book like any block-relay-only peer, needs an outbound slot of its own (so none is opened at `-maxconnections` 10 or below, where the full-relay and block-relay-only peers hold every slot), and is never opened under `-connect`. A peer is not dropped in its first 30 seconds or while blocks are being downloaded from it.
- **The onion address no longer reaches peers that can see the node's IP** (#1209). With `-listenonion`, satd announced its hidden service to every peer that asked for BIP 155 addresses, clearnet peers included. A clearnet peer received the onion over a connection from the node's own IP, which tied the two together and undid much of what running an onion service is for. It now goes only to peers whose link keeps that IP from them: those that came in on the onion listener, and those reached through the proxy (an onion, or a routable address under `-proxy`). Such a link is told the onion and not the `-externalip` address, since the two on one link tie them together. The version message's `addr_from` is now Core's dummy address for every peer: it carried the first `-externalip` to every peer, onion ones included. A `getaddr` reply also never carries one of the node's own addresses (any onion of the node's, advertised or not, or an `-externalip` IP), even after the address has been gossiped back to it. Core does neither, so this is a deliberate difference, listed in `CORE_DIFFERENCES.md`. Nothing needs setting, and the onion still spreads: the onion peers it is announced to mostly also answer clearnet nodes' `getaddr`s.
- **`-discover`, off by default** (#1209). Core's `-discover` is now honoured instead of skipped with a warning. With it on, satd announces to each outbound clearnet peer the address that peer says it sees the node at, with the P2P port, so a node behind NAT without `-externalip` can still be found over clearnet. It is off unless set, where Core's is on: announcing the address puts the node's clearnet IP in every crawler's list, which is the operator's choice. It is never sent on a link through the proxy (that peer sees the proxy's exit), `-externalip` wins on its IP family, and the announced address is kept out of `getaddr` replies like any other address of the node's, at the P2P port only. The peer chooses the IP it reports, so a peer the node dialled can name another node's IP; if that node uses the same port, its address is left out of the replies. At most the eight latest such addresses are kept, and turning `-discover` off forgets them. Unlike Core, satd does not add interface or `-bind` addresses. Reloadable with SIGHUP.

## HTTP surfaces

- **A client that stops reading gives its slot back** (#823). The JSON-RPC, Esplora and streamws listeners bounded the wait for a request and the idle gap between requests, but not a write. A client that asked for a large response, or opened an SSE stream or WebSocket, and then stopped reading kept its socket, and its slot under the listener's cap (100 per JSON-RPC listener, 1024 by default on Esplora and streamws), for as long as it kept the connection open. A write that makes no progress now closes the connection after `-rpcservertimeout` on JSON-RPC, as libevent's write timeout does in Core, and after 60 s on Esplora and streamws and on JSON-RPC with `-rpcservertimeout=0`. The clock runs only while a write is stuck and restarts with every byte the client takes, so a large response to a slow reader, or a stream waiting for its next event, is not cut off. Also in 0.7.1.
- **Shutdown closes WebSockets and SSE streams** (#822). At shutdown the listeners stopped accepting and closed idle connections, but an upgraded streamws `/ws` socket had no shutdown signal, and hyper's graceful shutdown waited for an SSE response, on streamws `/sse` and on Esplora, that never finished. Both stayed open until the process exited, and their clients got no close. A `/ws` socket now gets a `1001 Going Away` close frame and an SSE stream ends its response. Also in 0.7.1.
- **Timeouts too large for the clock are clamped** (#826). An `-rpcservertimeout` or `-esplorarequesttimeout` above about 9.2e18 seconds made every connection task panic when hyper computed its deadline, so the process stayed up and the listener answered nothing. Timeouts above a year are now treated as a year. Also in 0.7.1.
- **`-esplorarequesttimeout=0` leaves TLS working** (#826). The value doubled as the Esplora TLS handshake budget, so `0`, documented as leaving idle connections open, also gave every TLS handshake no time and TLS on Esplora could not complete. With `0` the handshake now gets 30 s, the option's default. Also in 0.7.1.
- **The plain metrics listener has a connection cap and a header timeout** (#826). It ran hyper without a timer and accepted every socket, so a socket that sent nothing was held forever, and any number of them were. It now serves at most 64 connections, as its TLS sibling does, and closes one that sends no request head within 30 s. On both metrics listeners, and on MCP, a write that makes no progress for 60 s closes the connection, as on the other HTTP surfaces. It still binds loopback by default. Also in 0.7.1.

## Operator

- **`reindex` and `reindexchainstate` in `bitcoin.conf` are honoured** (#840). Both keys were accepted in the config file and then ignored, so an operator who asked for a rebuild there got a normal start. They are now read from the file, as Core reads them, in Core's hyphenated spelling too. As in Core, a file value rebuilds on every start until it is removed. Also in 0.7.1.
- **`conf.d/local.conf` overrides what the stack writes** (#843). `satd-init` appended `local.conf` to the rendered `bitcoin.conf` so that its lines would win. satd, like Core, takes the first value of a repeated key, so a `local.conf` line for a key `satd-init` already writes, such as `port`, `txindex` or `prune`, was ignored. `local.conf`'s top-level lines now go first, and any `[section]` blocks in it go last, where a value in the active chain's section wins anyway. Also in 0.7.1.
- **The core runtime has at least two worker threads** (#1144). It had one worker per CPU, so a 1-CPU host had a single worker. One blocking call during IBD then stopped JSON-RPC and P2P together for minutes at a time, and RPC accepted connections without answering. A 1-CPU host now gets two workers. Larger hosts are unchanged. Also in 0.7.1.
- **The shadow verification queue is bounded by memory** (#1145). Under the shadow modes, `cpp-shadow` and `rust-shadow`, every transaction the primary engine accepts is queued for the shadow engine with its serialized bytes and a copy of each output it spends. The queue was bounded only by `-shadowqueuesize`, 4,194,304 entries, which at a few hundred bytes to several KB an entry is gigabytes. On a host with few cores the shadow engine falls behind during IBD, and the queue grew until the process reached its memory limit, without ever reaching the entry cap or logging a drop. The new `-shadowqueuemb` (default 128, in MiB) bounds the bytes the queued work holds. Work past either bound is dropped, as before, and the aggregated WARN now gives the queue's depth and bytes. The primary engine still verifies every script. `-shadowqueuemb=0` restores the entry-count bound alone. Also in 0.7.1.
- **Floodable warnings are budgeted per listener** (#825). Most accept loops already logged the first five refusals a minute and then a count. Three lines were left out:
  - "TLS handshake timed out" was logged once per socket on the JSON-RPC TLS and Esplora TLS listeners (and on Electrum, MCP and events gRPC TLS), so a client opening sockets and sending nothing could drive it at the cap divided by the handshake budget, about 34 lines a second on Esplora with its defaults.
  - "accept error" was logged on every failed `accept`, which during fd exhaustion is about 20 lines a second per listener. The Electrum, Stratum and plain metrics loops did not back off at all, and now wait 50 ms as the others do.
  - Stratum's at-capacity budget was shared by its V1, V1-TLS and V2 listeners, so a flood on one silenced the others' reports. Each listener now has its own, and the line names the listener.

  Each of these now has its own budget per listener. Also in 0.7.1.
- **AssumeUTXO background validation retries a failed connect** (#557). When a historical block failed to connect behind a loaded snapshot, the background connector logged it and stopped, for the life of the process, so one transient RocksDB or block-file write error ended background validation until a restart. It now retries as the IBD connector does: an attempt a second, a `getwarnings` notice `assumeutxo.connect_retry` every tenth attempt, and after 30 the `assumeutxo_catchup_stalled` alert, while it keeps retrying. Both clear when the block connects. A block that fails validation is not retried: the connector stops and raises the same alert with `reason=invalid_block`, and the snapshot stays unvalidated rather than rejected. A block that cannot connect to the background chain at all (it does not extend the background tip, its parent is unknown, or its stored bytes do not decode) stops it the same way, with `reason=cannot_connect`. Also in 0.7.1.
- **AssumeUTXO conditions are alerts on every surface** (#557). A stalled catch-up, a failing handoff and a snapshot proven invalid reached `getwarnings` only, so the `status` stream, the `alertfile` webhooks and `satd_alert_active` never saw them. They are now the standing alert kinds `assumeutxo_catchup_stalled`, `assumeutxo_handoff_failing` and `assumeutxo_validation_failed`, raised and cleared once per episode like the others. The Operator Manual lists them under Node-health alerts, with their `details`. Also in 0.7.1.
- **AssumeUTXO gauges** (#557). `/metrics` exports `satd_assumeutxo_background_attached` and `satd_assumeutxo_snapshot_rejected` on every node, and `satd_assumeutxo_background_tip_height` and `satd_assumeutxo_snapshot_height` while a snapshot is loaded. Also in 0.7.1.
- **A fresh testnet4 sync gets past block 51,540** (#1216). In 0.7.0 and 0.7.1 it stopped there for good: the block's 14,200 inputs held the connector in script verification, with the P2P loop blocked, for over 300 s, the stall watchdog shut the node down, and every restart came back to the same block. Two changes, either of which gets the sync through. testnet4 and testnet3 now ship Bitcoin Core's default `-assumevalid` (testnet4 block 123,613, testnet3 block 4,842,348); neither had one. And the stall watchdog counts the script inputs the connect path verifies as progress, beside a connected block and a turn of the P2P loop, so a block that takes minutes to verify no longer trips it; mempool admission, prefetch and the shadow engine do not count, so they cannot keep a wedged connector looking alive. This release's script engine already verifies the block in seconds (#874). Also in 0.7.2.

## Storage

- **Block reads no longer wait behind each stored block's fsync** (#547). Storing a block held the block-file lock across its fsync, and every block read takes that lock: `getblock`, Esplora, Electrum and the index backfills. On slow or network storage a 10-50 ms fsync per block queued them all behind it during sync. The fsync now runs after the lock is released, on its own handle to the file, and the block is still on disk before the node records where it is. Also in 0.7.1.
- **A block file never grows past its size cap** (#547). When a block file filled up, the next record moved to the following file. If that file already existed with too little room left, as can happen after pruning, the record was appended past the 128 MiB cap anyway. It now moves on until the record fits. Also in 0.7.1.
- **A re-fetched block frees its download slot during initial sync** (#547). A block that `getblockfrompeer` asked for, arriving while the node was in initial block download, did not release the IBD download slot its peer held for that height, so the peer had one less slot until the download timed out. Also in 0.7.1.

## Release tooling

- **`sign-tarballs.sh` keeps its downloads across a failed run** (#903). The maintainer's signing script downloaded every tarball and SBOM into a temporary directory and deleted it on exit, failed runs included, so a mistyped passphrase meant downloading all of them again, 431 MB for 0.6.0. It now works in `${SATD_SIGN_DIR:-${XDG_CACHE_HOME:-~/.cache}/satd-sign/<tag>}`, created mode 0700, and refuses a directory it does not own, a symlink, or one others can write to. A rerun fetches `SHA256SUMS` and the `.sha256` files fresh, keeps a downloaded file only if its SHA-256 matches both `SHA256SUMS` and the digest GitHub reports for the asset, and keeps each `.minisig` that still verifies. The directory is removed after a successful upload or `--dry-run`. `--images` is unchanged. Also in 0.7.1.

## SDKs

- **A resilient watch re-anchors after a drop before its first confirmed event** (#777). The node puts a resume cursor on a connected block and on a confirmed match only, so a resilient watch or subscription started without `FromCursor` (Go) or `from_cursor` (Rust) and with an empty cursor store had nothing to resume from until one arrived. A reconnect in that window sent no `SetCursor`, got no `CursorAccepted`, and did not replay the outage, and an event in flight at the drop, such as the block confirming a payment whose mempool match had just arrived, was never delivered. `Subscribe` and `Watch` responses now carry a `satd-head-cursor` header, the position the stream starts from, built like a connected block's cursor at the tip and read after the stream has subscribed to the live bus. Both SDKs adopt it when they have no anchor of their own, so the next reconnect replays from it and the cursor store holds it after the next commit. Against an older node, or one with no block source, the SDKs behave as before. The Go end-to-end test that failed about one run in two on this window now has a variant that cuts on the unconfirmed match. Also in 0.7.1.

## Packaging

- **The Nix build of `satd` is reproducible across x86_64 CPUs** (#321). jemalloc's build script reads the virtual-address width of the CPU it is built on, 48 bits on most x86_64 CPUs and 57 on those with 5-level paging, and sizes its internal radix tree from it. Two `nix build .#satd` runs of the same commit therefore produced different `satd` binaries whenever one build host had 5-level paging, which is why the two-replica check in CI failed now and then. The flake now pins the address width, page size and hugepage size on x86_64, so the binary is the same whichever CPU builds it. `sat-cli` does not link jemalloc and was never affected. The CI check also keeps both binaries and reports a per-section diff when they differ. Also in 0.7.1.
- **`flake.lock` is committed** (#321). The flake had no committed lock, so each Nix build resolved nixpkgs, crane, rust-overlay and flake-utils on the day it ran. Two builds on the same day matched, but a rebuild of a release tag weeks later could pick up newer inputs and produce a different `satd`. Every build of a commit now evaluates the same inputs. Also in 0.7.1.
- **The x86_64 Linux release tarballs no longer depend on the build runner's CPU** (#321). `release.yml` builds its tarballs with cargo, not Nix, and jemalloc read the runner's address width and page sizes there too, so two builds of one tag could differ by which runner built them. The gnu and musl x86_64 builds now pin the same values as the flake. Matching a Nix build to a release tarball byte for byte is still out of scope (packaging chapter, "Reproducible build via Nix"). Also in 0.7.1.

- `rmcp` 3.9.0 (from 2.2.0; RUSTSEC-2026-0457, -0462). Both advisories are
  in rmcp's client transports and OAuth client, which satd does not build; the
  MCP server uses only the server, stdio and Streamable HTTP server features.
  The HTTP server keeps per-client sessions for MCP protocol versions before
  2026-07-28, as before; clients negotiating 2026-07-28 are served without
  sessions, as that version requires. rmcp now caps an MCP request body at
  4 MiB.

## Upgrade notes

These changes, also in 0.7.1, need attention when upgrading from 0.7.0:

- A client that reads `warnings` from `getblockchaininfo`, `getnetworkinfo` or `getmininginfo` as a string gets `[]` on a node with no warnings. It already got an array whenever a warning was active, and Core has returned an array since v28. Start the node with `-deprecatedrpc=warnings` to keep the string form for now.
- A `bitcoin.conf` carrying `reindex=1` or `reindexchainstate=1` now rebuilds on start. Remove the line if the rebuild is not wanted.
- In the docker-compose stack, a `conf.d/local.conf` line for a key `satd-init` writes now takes effect. Check that file for stale lines before upgrading.
- A node whose shadow queue held more than 128 MiB now drops shadow work past that and logs it. Raise `-shadowqueuemb` to keep more.
- Log consumers that matched `Disconnecting peer on request` should match `Disconnecting peer` with `reason="rpc_request"` instead.
- The Electrum server reports a new default name, `satd-electrs-electrumx-compatible/<version>`. A client or monitor that matched the old `satd-electrs-compatible` name exactly should match the new one, or set `electrumservername` to keep the old name. `-electrummaxbatchrequests` now defaults to 345; an operator who wants the old limit can set it to 100, but Sparrow then fails to verify a wallet with more than 100 transactions.
- A custom signet (`-signetchallenge`) whose blocks do not follow the standard retarget schedule, such as one run by a modified bitcoind with a shorter block interval, no longer syncs. Bitcoin Core refuses it too.
- A JSON-RPC client that pauses mid-response, reading nothing for longer than `-rpcservertimeout` while the server has more to send, is now disconnected. Raise `-rpcservertimeout` if a client legitimately does that.

New in 0.8.0:

- `-consensus` defaults to `cpp-shadow`, so the Rust engine decides and Core's interpreter checks it. A node that set no `consensus` now runs that way; set `consensus=rust-shadow` to keep Core's interpreter deciding. A node that already sets `consensus` is unaffected.
- `peers.dat` is written in format version 3, which can hold onion addresses (#1157). A 0.7 or earlier `peers.dat` loads. An older satd refuses a version 3 file and starts with an empty address book, so a node downgraded from 0.8.0 rebuilds its peers from the DNS and fixed seeds.

- `getblockstats`' `minfeerate`, `maxfeerate` and `avgfeerate` are in sat/vB, a thousandth of what 0.7 reported for the same block, and `total_size`, `total_weight`, `avgtxsize`, `mintxsize`, `maxtxsize`, `mediantxsize` and `avgfeerate` leave out the header and coinbase, as in Core. A dashboard or script that divided satd's feerates by 1000, or read `total_size` as the block's size, should drop the division or read `size` from `getblock` instead. Clients written for Core need no change.
- A synced node no longer drops back into initial block download when its tip goes stale (#1071). A monitor that read `initialblockdownload: true` as the sign of a stalled node should watch the tip's age instead, as the `tip_stall` alert does. A `-minimumchainwork` set above the chain the node can reach now keeps it in IBD, as in Core.

- `estimatesmartfee` (#1200): a node with no fee history now returns Core's `errors` answer instead of a feerate; a client must read `feerate` as optional, as it must with Core. Target 1 is answered for 2 blocks and `blocks` says so. `errors` is absent from a successful answer. Each answer carries a new `estimator` field.

- **Building from source** now also needs **cmake** and the **Boost headers,
  1.74 or later** (`apt install libboost-dev`, `brew install boost`; header-only,
  nothing is linked). `libbitcoinkernel-sys` builds Bitcoin Core's kernel with
  them. A static musl build through cargo-zigbuild must also point that cmake
  build at zig and pass `-UNDEBUG`, since zig defines `NDEBUG` at `-O2` and Core
  refuses to build without assertions; `release.yml` shows how.
- The AssumeUTXO warnings have new `getwarnings` ids: `assumeutxo-validation-failed` is now `alert.assumeutxo_validation_failed`, `assumeutxo.catchup_halted` is now `alert.assumeutxo_catchup_stalled`, and `assumeutxo.handoff_failing` is now `alert.assumeutxo_handoff_failing`. A `status` consumer sees three new kinds (proto values 8 to 10); the Rust and Go SDKs in this release name them, and an older SDK reports them as unknown kinds with their severity and message intact. Also in 0.7.1.
