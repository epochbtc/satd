# satd 0.8.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

This file accumulates entries as changes land; it is not yet a cut release.

satd 0.8.0 includes every fix shipped in 0.7.1.

## Highlights

- [The C++ script engine verifies a transaction's inputs in linear time](#consensus):
  Bitcoin Core's interpreter now comes through `libbitcoinkernel`, about 27x
  faster on many-input blocks.
- [The Rust engine is the default primary](#the-rust-script-engine-decides-by-default):
  `-consensus` now defaults to `cpp-shadow`, with the Rust engine deciding and
  Core's interpreter checking every script behind it.
- [A new default fee estimate](#rpc): the mempool for the next two blocks and
  the chain's own fee history beyond, on `estimatesmartfee` and every other fee
  surface. Wallets get lower numbers in a calm market.
- **Opt-in network crawl, `-crawl`.** Walks the reachable network as a
  declared crawler, over BIP 324 to nodes that advertise it and v1
  otherwise, and records which
  addresses complete a handshake. `getcrawlinfo` counts the reachable
  network, nodes that speak BIP 324 only included; `dumpcrawlsnapshot`
  exports it, keyed so no clearnet address leaves the node unless asked
  for. See [P2P](#p2p) and [RPC](#rpc).

## Consensus

- **Signet blocks must carry the scheduled difficulty** (#838). Also in 0.7.1.
- **The Rust engine names a malformed tapscript push as Core does.** A tapscript push running past the end of the script now fails with `SCRIPT_ERR_BAD_OPCODE`, as Core's pre-execution `OP_SUCCESSx` scan reports it, not with whatever execution reached first. No verdict changes. Found by [bitcoin-consensus-spec](https://github.com/coreyphillips/bitcoin-consensus-spec)'s conformance suites, which satd now runs nightly (`satd-conformance-harness`).
- **`-test=bip94` on regtest** (#1245). Enforces BIP 94's timewarp rule as Core's option does: the first block of each 144-block period may not be more than 600 seconds older than its parent (`time-timewarp-attack`); BIP 94's retarget seeding has no effect on regtest, which never retargets. As in Core, `-test` is refused off regtest and an unknown name only warns; Core's `addrman` and `reindex_after_failure_noninteractive_yes` are refused, as satd lacks them.
- **Script flags follow Core's model: on from genesis, with three exceptions** (#1244, #724). P2SH, WITNESS and TAPROOT are on for every block except Core's three exception blocks (mainnet 170,060 and 692,261, testnet3 394), keyed on block hash, and block sigops use the same flags; satd used activation heights. Main-chain verdicts are unchanged, but on regtest `-testactivationheight=segwit@N` no longer turns WITNESS and TAPROOT off below N (it moves only NULLDUMMY and the witness commitment rules), taproot is active from genesis, and `getdeploymentinfo`'s `script_flags` shows an exception block's own flags. DERSIG, CLTV, CSV and NULLDUMMY keep their buried heights. Found by bitcoin-consensus-spec's block corpus.
- **`-reindex` checks every block's header as header sync does** (#506). Also in 0.7.1.
- **Transactions are decoded as Core decodes them** (#1242). `version | 00 00 | lock_time` is a transaction with no inputs, as in Core's `UnserializeTransaction`, so the P2P messages and RPCs that carry one refuse it as `bad-txns-vin-empty` where satd refused the bytes, and a witness flag followed by no inputs is a decode failure; no verdict changes. Such a transaction is written, measured and hashed as Core does (`createrawtransaction` with no inputs returns Core's bytes; `decoderawtransaction`, `testmempoolaccept` and `submitpackage` report Core's size and wtxid), `submitpackage` refuses it as `conflict-in-package`, and the RPCs that take a transaction answer a decode failure with Core's message ("TX decode failed. Make sure the tx has at least one input." and its variants). Found by bitcoin-consensus-spec's `custom` suite.

### The Rust script engine decides by default

`-consensus` now defaults to `cpp-shadow`: the Rust engine decides and Bitcoin
Core's C++ interpreter re-verifies every script behind it, logging any
disagreement. Up to 0.7.x the default was `rust-shadow`, the other way round.
The Rust engine passes Core's script tests, matched Core's interpreter across
mainnet history, and has run as primary under sustained production use on
mainnet, signet and testnet4 for months without a disagreement.
`-consensus=rust-shadow` keeps Core's interpreter deciding. New manual chapter:
[Consensus Engines & Shadow Verification](https://epochbtc.github.io/satd/consensus.html).

### The C++ script engine is Core's interpreter through libbitcoinkernel (#874)

Core's interpreter (authoritative under `rust-shadow` and `cpp`, the shadow
under `cpp-shadow`) now comes through `libbitcoinkernel` instead of
`libbitcoinconsensus`, whose per-input API rebuilt a transaction's signature
hashes for every input. The kernel precomputes them once per transaction, as
Core's `CheckInputScripts` does. Script verification, one thread:

| Block | 0.7.x (`libbitcoinconsensus`) | 0.8.0 (`libbitcoinkernel`) |
|---|---|---|
| signet 227,466 (3,373 inputs), glibc / static musl | 4.57 s / 6.53 s | 0.17 s / 0.24 s |
| mainnet 974,146 (7,990 inputs), glibc / static musl | 656 ms / 773 ms | 283 ms / 303 ms |

Mempool acceptance and the signet block solution use the same path. No verdict
changes: the kernel's interpreter is Core v32.1's, `libbitcoinconsensus` was
Core 26's (removed from Core in v28). satd pins `bitcoinkernel` 0.3.2 and
`libbitcoinkernel-sys` 0.4.1.

## RPC

- **Any request `Content-Type` is accepted** (#824). Also in 0.7.1.
- **`getrawtransaction`'s not-found message matches the node's index** (#1066). Also in 0.7.1.
- **A package member spending one outpoint twice gets Core's answer.** Core's `IsConsistentPackage` compares inputs only across members, so `submitpackage` answers `transaction failed` with the member's `bad-txns-inputs-duplicate`, and a multi-transaction `testmempoolaccept` refuses that member with it; satd refused the whole package as `conflict-in-package`, which still covers two members spending one outpoint.
- **`testmempoolaccept` agrees with `sendrawtransaction` under an `allow` policy rule** (#999). Also in 0.7.1.
- **`getnetworkinfo` reports which networks are reachable** (#1164). Also in 0.7.1.
- **`warnings` is always an array** (#956). Also in 0.7.1.
- **`getblockstats` reports what Core reports, in Core's units.** `minfeerate`, `maxfeerate` and `avgfeerate` are in sat/vB (they were sat/kvB, 1000x too high; `sat-tui`'s "Avg Rate" is fixed with them); size, weight and feerate statistics leave out the header and coinbase; `mediantxsize` is a median, not a mean; and `feerate_percentiles` is new. `total_out` leaves out the coinbase, `utxo_size_inc` is Core's figure from the real output and spent-coin sizes, and `utxo_increase_actual` and `utxo_size_inc_actual` are new (#1208); every statistic matches Core 32.1 on the same blocks. Fees come from undo data, which pruning keeps, though a pruned block still answers `Block data not available`; a mismatched one is refused and an unreadable one answers Core's `Can't read undo data from disk` (-1) instead of zero fees.
- **An open WebSocket no longer outlives its bearer token** (#821). Also in 0.7.1.
- **The capability check comes before parameter checks** (#826). Also in 0.7.1.
- **Initial block download is judged as Core judges it** (#1071). The node stays in IBD until its tip has `-minimumchainwork` as well as a timestamp within `-maxtipage`, and while replaying blocks at startup, and once out it does not re-enter until restart. A synced node with a stale tip used to fall back into IBD, which made mainnet `getblocktemplate` refuse, stopped Stratum work and turned off transaction relay through the fee filter.
- **`estimatesmartfee` takes Core 32.1's shape and floors every answer** (#1200). New in 0.8.0; #1254 below changed the number again.
  - Every fee surface (`estimatesmartfee`, `estimatefees`, Esplora `/fee-estimates`, Electrum `blockchain.estimatefee`, MCP, status page) floors at the rolling mempool minimum and `-minrelaytxfee`, as in Core 32; with a full mempool satd quoted rates it would not relay.
  - `options` takes Core's `fee_rate_estimator` (`block_policy`, `mempool_policy`, `auto` by default) and `verbosity` (2 adds `mempool_health_statistics`). Unlike Core, an unknown `fee_rate_estimator` means `auto` and an unknown `options` key is ignored, where Core refuses both.
  - `estimator` names the source: `block_policy`, `mempool_policy` or `floor`. Core reports it only under `auto` and has no `floor`.
  - `blocks` is the target answered, as in Core: target 1 is answered for 2, at history's lower 2-to-3-block rate, and `mempool_policy` always for 2.
  - With no fee history the answer is Core's `errors: ["Insufficient data or no feerate found"]` with `blocks: 0`, not the relay floor; `errors` appears only on an error.
- **Bitcoin Core v32.1 options and arguments** (#1203). `prevoutfetchthreads`, `rpcmaxconnections` and `txsendrate` are warned about and skipped instead of refused as typos; `privatebroadcast` is refused, since satd does not implement it and would announce transactions to every peer. The node creates `<datadir>/fees/` as Core v32 does. `converttopsbt` takes `psbt_version`, accepting only `0` (`-8` otherwise); satd still defaults to 0, where Core v32 defaults to 2.
- **`estimatesmartfee`'s `mempool_policy` is Bitcoin Core 32's mempool estimator** (#1202). New in 0.8.0. It answers, for 2 blocks, the feerate at which the next template reaches 50% of a block's weight (`conservative`) or 75%, else the floor, as Core 32.1 does on the same mempool. A health gate refuses it, with Core's error text, during the startup mempool load and while under 75% of the last six blocks' weight was in the mempool beforehand; the rows persist in `fees/mempool_health.dat` (cleared under `-persistmempool=0` or without `mempool.dat`), and `verbosity` 2 reports them with a `mempool_health` verdict (`healthy`, `insufficient_data`, `low_coverage`). The node also tracks arrival weight per feerate band; nothing answers from it yet.
- **`estimatesmartfee`'s `block_policy` reads the chain's own fee history** (#1250). New in 0.8.0. Each of the last 3,200 blocks has a hurdle, the feerate at the 10th percentile of its weight over transactions paying the relay floor. For N blocks the estimate takes past N-block windows that began in a fee market like today's and answers a high quantile of their lowest hurdles (99.9% at 1 block, 95% economical, 97.5% conservative), rbitcoin's analog-window method (`docs/mempool-fee-estimation.md` in reardencode/rbitcoin); with too few windows it uses a plain quantile, and with none the old estimator. The history is kept in `fees/fee_history.dat` (about 140 KB) and filled in the background from block and undo data for what the file lacks, so a pruned node gathers it across restarts. A damaged or wrong-network file is logged and rebuilt from the blocks, and a reorg never leaves an abandoned branch's row. In a 30,000-block mainnet backtest it covered as often as a plain quantile and overpaid much less (median 1.9× the realised hurdle at 6 blocks, against 3.3×).
- **The default fee estimate reads the mempool for the next two blocks and the chain's fee history beyond** (#1254). This completes #1200, #1202 and #1250; the old estimator remains only as a fallback while history fills.
  - Targets 1 and 2, while the health gate passes, answer Core 32's template percentile (75% of the next block, 50% under `conservative`); every other target, and all of them while the gate fails, answer from history, held at or below the 2-block answer.
  - `conservative` is never below history's estimate or `economical`, and history answers it at 97.5%, down from 99% (at 6 blocks, 91.0% coverage at 5.5× against 96.8% at 10×).
  - Used by `estimatesmartfee` `auto` (default), `unset`, `economical`, `conservative` and satd's `blend`; `historical` is the history estimate alone. `estimatefees` (default `blend`), Esplora, Electrum, MCP and the status page use the same economical numbers.
  - Unlike Core 32.1's `auto`, which takes the lower of its two estimators, satd's mempool side sets the 1- and 2-block answer even when it is dearer than history.
  - The floor is the rolling mempool minimum or `-minrelaytxfee` (0.1 sat/vB by default); #1200's 1 sat/vB floor is gone. A target history cannot answer gets the floor while the mempool side answers, where Core 32.1 errors (Esplora omits it, Electrum answers `-1`); with neither, Core's `Insufficient data or no feerate found`.
  - On mainnet, beside a Core 32.1 node: _numbers to come before release_.
- **A too-long Bech32 address names one error location** (#1204). `validateaddress` reports only the position where the string passes 90 characters, as Core v32.
- **A JSON-RPC connection from outside `-rpcallowip` is closed without a reply** (#1204), at accept, as Core v32 does, instead of `403 Forbidden`.
- **A transaction announced twice in one `inv` is processed once** (#1204), `MSG_WITNESS_TX` counted as a txid, and logged under `-debug=net` as Core v32's `got inv:` line.
- **A request for a filtered block disconnects the peer** (#1204). satd never offers `NODE_BLOOM`, and now disconnects on `MSG_FILTERED_BLOCK` as Core v32 does instead of ignoring it.
- **A `-blocksonly` node ignores compact blocks** (#1204), header included, as Core v32 does; satd could connect a block from a pushed one.
- **`invalidateblock` and `reconsiderblock` end on the best valid chain** (#1261). When activation meets an invalid block the node tries the next-best chain, as Core's `ActivateBestChain`, and succeeds; it stopped on the invalid block's parent with an error. `preciousblock` and the startup repair after a crash in `invalidateblock` share the path.
- **`addnode` refuses an empty node**. Also in 0.7.2.
- **Script `asm` is Core's** (#1265). Every `asm` field follows Core's `ScriptToAsmStr`: bare hex for pushes over four bytes, numbers for short pushes and `OP_0`..`OP_16`, `OP_CHECKSEQUENCEVERIFY`/`OP_CHECKLOCKTIMEVERIFY`, `[error]` for a truncated push, and a scriptSig signature's sighash by name (`[ALL]`). It was rust-bitcoin's (`OP_PUSHBYTES_20`, `OP_PUSHNUM_1`, `OP_CSV`). Covers `decoderawtransaction`, `getrawtransaction`, `getblock` 2 and 3, `gettxout`, `decodescript` and Electrum's verbose `blockchain.transaction.get`; Esplora's `scriptsig_asm` and `scriptpubkey_asm` keep Esplora's format.
- **`desc` in every scriptPubKey, and `decodescript` in full** (#1266). Every scriptPubKey object carries Core's inferred `desc` (`decoderawtransaction`, `getrawtransaction`, `getblock` 2 and 3, Electrum's verbose transaction), not only in `gettxout`, and `decodescript` adds `desc`, `address` and Core's `segwit` object, checked against Core 32.1 on 53 scripts (`rpc_decodescript.py` now runs in the functional suite). A wrong-length v0 witness program gets `p2sh` and `segwit`, as in Core. One difference: a sane miniscript with an off-curve key is `addr(…)` in satd, `wsh(…)` in Core.
- **Integer and verbosity arguments are parsed as Core parses them** (#1267). Each integer is read as Core's `UniValue::getInt<T>` for the handler's C++ type, then range-checked as the method does, checked against Core 32.1:
  - `getblock` and `getrawtransaction` take any verbosity: 0 or below is hex, above the top level is the top level.
  - A fraction or out-of-type value is `-1 JSON integer out of range`, not `-8 Invalid value for argument ...`.
  - Range errors match Core for `getblockhash`, `getblockstats`, `getchaintxstats` (now refuses instead of clamping), `estimatesmartfee`/`estimaterawfee` (negative target, checked before the mode) and `createpsbt`; negative values in `waitforblockheight`, `waitfornewblock`, `waitforblock`, `verifychain`, `generatetoaddress`, `generatetodescriptor`, `setban`, `disconnectnode` and `sendmsgtopeer` are handled as Core handles them.
  - Also converted: `gettxout`, `pruneblockchain`, `getnetworkhashps`, `getorphantxs`, `createrawtransaction`, `createpsbt`, `converttopsbt`, `getnodeaddresses`, `getblockfrompeer`, `prioritisetransaction` and `setmocktime` (bound `4294967295`, mistyped value `-3`).

  JSON `-0` in an unsigned argument is still read as 0, where Core refuses it.
- **`getchaintxstats` defaults to one month of blocks, and takes `nblocks=0`** (#1297). With no `nblocks` the window is Core's 4320 blocks (capped at the final block's height - 1), not 30, so `window_*` and `txrate` match Core's.
- **`decodepsbt` decodes the transaction and its scripts** (#1296). `tx` is now Core's `TxToUniv` without `hex`, as `decoderawtransaction` answers, instead of only the txid, version, locktime and input and output counts. Its script objects follow Core's `ScriptToUniv`.
- **`decodepsbt` writes what Core v32.1 writes** (#1311), for version 0 and version 2 PSBTs, checked field for field against Core v32.1's output for its wallet's PSBTs and for PSBTs carrying every other field.
  - Version 0 gains `psbt_version`, `global_xpubs`, `proprietary` and `unknown` at the top level.
  - Each input gains, when set, `non_witness_utxo` (decoded as `decoderawtransaction` decodes it), `sighash`, `bip32_derivs`, `ripemd160_preimages`, `sha256_preimages`, `hash160_preimages`, `hash256_preimages`, `taproot_key_path_sig`, `taproot_script_path_sigs`, `taproot_scripts`, `taproot_bip32_derivs`, `taproot_internal_key`, `taproot_merkle_root`, `musig2_participant_pubkeys`, `musig2_pubnonces`, `musig2_partial_sigs`, `proprietary` and `unknown`; each output `bip32_derivs`, `taproot_internal_key`, `taproot_tree`, `taproot_bip32_derivs`, `musig2_participant_pubkeys`, `proprietary` and `unknown`.
  - `partial_signatures` is an object from public key to signature, not an array of `{pubkey, signature}`.
  - `sighash` is Core's name for the value (`"ALL"`, `"SINGLE|ANYONECANPAY"`, ...; `""` for one it cannot name), not a number.
  - `fee` is absent when an input's UTXO is missing, not `null`, and negative when the outputs pay more than the inputs hold.
  - A version 2 PSBT's `unknown` is Core's: present only when the map has such a pair, and holding the BIP 375 pairs too, which also stay in `silent_payments`, `sp_shares` and `silent_payment`.
  - `tx_hex` and each input's `has_utxo` and `is_final` stay, as satd's own.
- **Mempool entries carry Core v31's chunk fields** (#1068). `getmempoolentry` and the verbose mempool views report `chunkweight` and `fees.chunk`, the weight and modified fees of the chunk the transaction is mined in, as Core does; Bark's `captaind` needs them. The fees are signed, as in Core.
- **`vsize_bip141` and `vsize_adjusted` beside `vsize`** (#1326), as in Core v32.1. `vsize` in mempool entries, `testmempoolaccept` and `submitpackage` is the sigop-adjusted size (`-bytespersigop`), which Core's help now marks deprecated; `vsize_adjusted` is that same size by an explicit name, and `vsize_bip141` is the size by weight alone. The two differ only for a transaction dense in signature checks: a P2WSH spend of 583 weight with 3941 sigops is 146 by BIP 141 and 19705 adjusted.
  - `getmempoolentry`, `getrawmempool true`, `getmempoolancestors`/`getmempooldescendants true`: both fields.
  - `testmempoolaccept`: both, when `allowed` is true. `submitpackage`: both, in each accepted or already-resident result.
  - `getorphantxs` 1 and 2: `vsize_bip141`, equal to its `vsize`, which there was always the BIP 141 size.
  - `getrawtransaction` 1 and 2: `vsize_adjusted` for a transaction found in the mempool; its `vsize` stays the BIP 141 size.

  Bark's `captaind` and NBitcoin read `vsize_adjusted` when present.
- **`getnetworkinfo.version` is 320000** (#1068), up from 280000, so clients with a Core v29 or v31 floor (Bark, Eclair) start. No client found switches on anything else between the two.
- **`getmempoolcluster` and `getmempoolfeeratediagram`** (#1327), Core v31's cluster-mempool RPCs, checked against Core v32.1. `getmempoolcluster <txid>` answers the transaction's cluster: `clusterweight` (sigop-adjusted), `txcount`, and `chunks` in linearization order, each with `chunkfee`, `chunkweight` and `txs`. The hidden `getmempoolfeeratediagram` answers the whole mempool's feerate diagram, the cumulative `weight` and `fee` after each chunk in mining order, from zero. Fees are modified fees, signed as Core's are, so a chunk a negative `prioritisetransaction` takes below zero is reported negative. Both come from the linearization behind `getrawmempool`'s order, which can differ from Core's on a tangled cluster (see `CORE_DIFFERENCES.md`).
- **`getmempoolinfo` reports the cluster limits.** `limitclustercount` and `limitclustersize` are Core v31's fields: the values of `-limitclustercount` and `-limitclustersize`, the size in virtual bytes (101000 by default) though the option is in kvB. A client that requires them, as one written against Core v31's answer does, failed to read satd's. Core's `optimal` is not reported (see `CORE_DIFFERENCES.md`).
- **`getcrawlinfo` and `getcrawlnodes [verbose]`.** `getcrawlinfo` reports
  the crawl: whether it is on, `running`, `held` (with each reason:
  `initial_block_download`, `connect`, `network_inactive`) or `stopped`
  after a panic in a crawl task; the limits in force, after the ceilings
  and the file-descriptor fitting; the book's size and cap, per network,
  learned and ever reached; sessions reached and not, and those open; the
  crawl's own byte totals, which `getnettotals` does not count; and the
  aggregate over the addresses with a handshake within the liveness window:
  reachable per network (IPv4, IPv6, onion; I2P and CJDNS are only ever
  learned, never dialled), the transport split (BIP 324 and v1, v1 only
  after a failed BIP 324 attempt, v1 with BIP 324 never tried as the node
  did not advertise it, BIP 324 only, BIP 324 with v1 not checked yet, and
  those advertising
  `NODE_P2P_V2`), implementation families (observed only), the families
  only user agents claim, the fake and closed-early nodes (below), and
  mismatches, each reachable address counted once among them. It carries counts
  only and is a read, allowed on the read-only listener and to an
  `rpc:read` token.

  `getcrawlnodes` returns one row per address in the book, most recently
  reached first: the address, network, whether it is reachable now, its last
  handshake, transport class, family and fingerprint; with `verbose`, every field of the
  entry and of its last handshake (user agent, services, height and its gap
  to our tip, clock offset, handshake round trip, `getaddr` answer size and
  delay, probe outcomes). Its rows are raw peer addresses, so it is
  operator control: refused on the read-only listener, and a bearer token
  needs `rpc:write`.

- **`dumpcrawlsnapshot [raw]` and hourly snapshots.** A snapshot is the
  crawl's reachable set (a handshake within the liveness window).
  `dumpcrawlsnapshot` returns it now, shaped as a Bitnodes snapshot:
  `timestamp`, `total_nodes`, `latest_height` (our tip) and `nodes`, each
  node Bitnodes' thirteen fields (protocol version, user agent, services,
  height and ASN filled; connected-since, hostname, the geographic fields
  and organization null, since the node does no geolocation and holds no
  long-lived connection) followed by a `satd` object: network, port class,
  transport class, `NODE_P2P_V2` advertised, family and confidence,
  the family the user agent claims, mismatch, chain check and last
  handshake.

  It is keyed by default. A clearnet node is listed by its node ID,
  HMAC-SHA256 of `ip:port` under a 32-byte key, the first 16 bytes in hex:
  stable across exports, and impossible to test against a guessed address
  without the key. The key is `crawlexport.key` in the network's data
  directory, created with mode 0600 by the first keyed export, or the file
  `-crawlexportkeyfile` names, which satd never creates; satd never rotates
  it. Onions are listed as they are, I2P and CJDNS only as counts, every
  port only as `default` or `other`, and an ASN (from `-asmap` only) with
  fewer than `-crawlexportmink` nodes (default 10) as `"other"`.
  `raw=true` lists nodes by address with exact ASNs. Both forms are
  operator control: refused on the read-only listener, and a bearer token
  needs `rpc:write`.

  Once an hour the crawl also writes the snapshot to
  `crawl/<unix time>.jsonl.gz` in the network's data directory:
  gzip-compressed JSON lines, one per reachable node, raw addresses,
  written with the data directory's permissions, execute bits dropped, as
  `crawlbook.dat` is. Every snapshot of the last 7 days is kept, then the
  first of each UTC day up to 90 days; each write prunes the rest.

- **Per-country totals, `-countryfile`.** With a country file in MaxMind
  DB format (DB-IP IP to Country Lite or GeoLite2 Country), `getcrawlinfo`
  and the snapshot summary count reachable nodes per country, folded into
  `other` below `-crawlexportmink`. No per-node row carries a country.

- **Metrics and the status page.** `satd_crawl_enabled`,
  `satd_crawl_running`, `satd_crawl_stopped`,
  `satd_crawl_book_entries{network}`, `satd_crawl_reachable{network}`,
  `satd_crawl_transport{class}`, `satd_crawl_v2_advertised`,
  `satd_crawl_family{family}`, `satd_crawl_claimed{family}`,
  `satd_crawl_fake{family}`, `satd_crawl_closed_early`,
  `satd_crawl_mismatches`,
  `satd_crawl_sessions_total{result}`,
  `satd_crawl_sessions_in_flight{network}` and
  `satd_crawl_bytes_{sent,recv}_total`; and, with the crawl on, a Crawl card
  on the status page. Counts only, never an address. Both reuse an
  aggregate for up to 10 seconds.

- **Operator Manual.** A new [Network Crawl](https://epochbtc.github.io/satd/crawl.html)
  chapter: what the crawl does, every option, how it stays apart from the
  node, networks, what `crawlbook.dat` stores, privacy, the risks of
  running one (ban lists, being flagged, ISP and hosting complaints,
  bandwidth) and Tor tuning for onion crawls.
- **Crawl fingerprints and the chain check.** A crawl session is judged
  against rows captured against the crawl's own `version` (services 0,
  relay off), not against the rows for ordinary connections: peers answer
  a crawler differently. A crawl row matches the traits that set its
  family apart rather than the whole transcript of one release, and each
  family's rows were checked, by a named test that replays every capture,
  against captures of two or more releases: Bitcoin Core 24.0.1, 28.1,
  31.1 and 32.1 with Knots 28.1 and 29.5.1 (`wtxidrelay` and `sendaddrv2`,
  then `sendcmpct` with no `feefilter` or `sendheaders` before the next
  message), satd 0.6.3, 0.7.2 and the 0.8 development tree (`feefilter`
  before its next message, or 0.6 and 0.7's `getheaders` straight after
  `verack`), rbitcoin 0.8.0, 0.8.99 and 0.9.2 (`sendheaders`, BIP 324
  only), btcd 0.24.2, 0.25.0 and 0.27.0 (`sendaddrv2` with no
  `wtxidrelay`), bcoin 2.0.0, 2.1.2 and 2.2.0 (protocol 70015 and its own
  `addr` straight after `verack`) and libbitcoin-server 3.6.0 and 3.8.0
  (protocol 70013, relay off, its own `ping` straight after `verack`). A
  row also pins what no capture of it contradicted: the BIP 324 greeting
  (no decoy packet and an empty version packet in every capture), the
  probes' answers (`notfound` for the unknown transaction from all but
  Bitcoin Core, which answers it only when its operator grants the crawler
  relay; silence for the unknown message; never a disconnect), the
  `getaddr` answer's message (`addrv2`), and whether the implementation
  completes a BIP 324 handshake at all. So a crawl session can be `known`
  with high confidence where the survey's handshake alone would be low.

  When no row matches, the session reports the family its user agent
  names at a fourth confidence, `claimed`, below `low`: a node that closed
  on a probe, or a release no capture has. A claimed family is never
  counted as observed: `getcrawlinfo` counts it per family under
  `claimed` (not under `unknown`, next item), the metrics under
  `satd_crawl_claimed{family}`, and the export gives it a null `family`. It is never a mismatch. A user
  agent that names no family stays `unknown`. Connected peers and the
  network survey now claim the same way (next item). A session no row matched keeps its
  handshake transcript, `relay` flag, BIP 324 greeting and `getaddr`
  answer in `crawlbook.dat`, bounded to 16 commands of 12 bytes, so a new
  implementation shows up as many records of one shape before it has a
  row. The book's format version is now 4 (next item); a version 2 or 3
  book, written by an earlier 0.8.0 development build, keeps its entries
  and drops their observations, and an older one is set aside and the
  crawl starts afresh.

  A discovery session's `getheaders` probe (our tip's parent as locator,
  our tip as stop, as before) is also a chain check: the answer tells a
  node on our chain (it sends our tip), one behind (nothing past the
  locator, or only our older blocks from its genesis), one on a fork
  (another block after the locator, or blocks that leave our chain) and
  one on another chain under this network's magic (its answer starts from
  a block we do not know). The check reads at most three block-index entries
  per session. It runs under `-crawlprobes` only, and the session is still
  checked against Bitcoin Core v32.1 for no misbehaviour score and no
  disconnect.

- **Crawl sessions that closed early or claim Core falsely are counted
  apart**, as the survey's records are (below), by the same rule: the
  survey's evidence, on a synced mainnet node, holds for the crawl's
  sessions too. A session whose peer closes the connection during the
  passive wait, before its handshake transcript settles, is **closed
  early**: mostly ordinary Core nodes with full inbound slots, evicting
  the youngest connection of their largest network group, which a crawl
  session seconds old often is. The node still counts as reachable, by
  network and by transport; its observation keeps the `version`'s fields

  fingerprint. A session with a Core user agent, a common protocol
  version of 70016 or more, a transcript of exactly `version` then
  `verack` and a passive wait that timed out with the connection open is
  **fake**: every Core since 0.21 sends `wtxidrelay` and `sendaddrv2`
  before its `verack` at that version. Neither changes how the crawl
  dials the node, how often, or its transport class, and a later session
  replaces the verdict as any newer observation replaces the last.
  `getcrawlinfo` gains `fake` (per claimed family, `{count, share}`) and
  `closed_early` (`{count, share}`), and `families.unknown` now counts only

  observation carrying its verdict (below).

- **The crawl retries closed-early addresses, and keeps a settled
  fingerprint.** A node that closed one session early to evict it often
  has room for a later one: by hand, 2 of 5 such addresses connected
  normally on a later try. An address whose session closed early and that
  has no settled observation now has its next session brought forward: a
  liveness session 15 minutes after the closed-early one, then, after each
  further closed-early session or a retry that completed no handshake,
  30 minutes, 1 hour, 2 hours and then 4 hours for every later one, each
  wait moved at random by up to a fifth either way. At most ten retries
  are scheduled; then the address waits for its next ordinary session,
  and a closed-early result there does not start them over. The first
  session that settles clears the schedule. A retry runs under the crawl's
  usual concurrency, rate, network and BIP 324 rules, and an unreachable
  address's backoff still comes first; nothing else about scheduling
  changes. A closed-early session no longer replaces a settled
  observation: an address already observed with a fingerprint (any
  confidence) or as fake keeps that observation, and the session updates
  only its reachability, transport results and timers. A fake session
  still replaces a classified one. `getcrawlinfo` gains `retries`
  (`pending`: closed-early addresses in the book with a retry scheduled;
  `exhausted`: those with none left), and a closed-early `getcrawlnodes`
  row gains `retry` (`count`, `next_due`). New metric
  `satd_crawl_closed_early_retries`. `crawlbook.dat` is written in format
  version 5, each entry carrying its retry schedule (below).

- **Node fingerprints match traits, and claim.** Connected peers
  (`getpeerbehavior`) and the network survey (`getpeersurvey`) are judged
  against node rows that, like the crawl rows, name the traits that set a
  family apart rather than the whole transcript of one release. Before
  this, a node row was one release's exact transcript, so every other
  release came back `unknown`: on a synced mainnet node 185 of 571 survey
  addresses were unknown though every one named a family in its user agent
  (181 Bitcoin Core, 109 of them Core 25; 4 btcd). Each row is checked, by
  a named test that replays every capture, against inbound and outbound
  captures of several releases, and against captures greeted as the survey
  greets a node (`capture.py --survey`, new): Bitcoin Core 0.20.2,
  0.21.2, 22.1, 23.2, 24.2, 25.2, 28.1, 31.2 and 32.1 with Knots 28.1 and
  29.4.3 (dialing us: `wtxidrelay` and `sendaddrv2`, then `getaddr`, or for

  with no `sendheaders` or `feefilter` before its next message; before 24:
  `sendheaders`, then `sendcmpct` twice), satd 0.7.0, 0.7.2 and the 0.8
  tree (`getheaders` before any `sendcmpct`), rbitcoin 0.8.0, 0.8.99 and
  0.9.99 (`sendheaders` and one `sendcmpct`), btcd 0.24.2, 0.25.0 and
  0.27.0 (`sendaddrv2` with no `wtxidrelay`, relay on), bcoin 2.0.0, 2.1.2
  and 2.2.0 (protocol 70015 and its own `addr` first), and
  libbitcoin-server 3.8.0, Floresta 0.9.1 and the two crawlers as before.
  A row covers the directions it was captured in. Core before 0.21
  dialing us sends what the bitcoin-seeder sends (`version verack
  getaddr`), so both are now `low`: only the protocol version tells them
  apart. On regtest Core 25.2
  matched the old row in both greetings, so the mainnet unknowns are not
  reproduced locally; their shapes are now kept (below) to tell why.

  As in the crawl, a session no row matches reports the family its user
  agent names at `claimed`, never counted as observed and never a
  mismatch: `getpeersurvey` counts it per family in a new `claimed` (not
  under `unknown`, next item), `getpeerbehavior` reports it as
  `"result": "claimed"`, the metrics in new
  `satd_peer_survey_claimed{family}` and `satd_peer_fingerprint_claimed{family}`
  series (`satd_peer_fingerprint{family="unknown"}` still counts a
  claimed connected peer too), and an alt-slot candidate with only a claim is unverified and
  matches no `family:` rule. A survey record no row matched keeps its
  handshake transcript (at most 16 commands) and `relay` flag, shown by
  `getpeersurvey true` as `handshake` and `relay` and logged under
  `-debug=net` when its survey connection ends. `peersurvey.dat` is
  written in a new format (`satdsrv2`). A file in the old one is dropped

  before the trait rows, and a survey revisits an address too rarely for
  them to be replaced, so they would stand in the tallies under their

- **Survey records that closed early or claim Core falsely are counted
  apart.** Of 183 survey records no row matched on a synced mainnet node,
  181 claimed Core, and two groups made up 179 of them. 105 had the transcript `version
  wtxidrelay sendaddrv2 verack` (Core 26 to 32 user agents, mostly over

  during the passive wait. These are ordinary Core nodes with full inbound
  slots: on each new inbound connection Core evicts one, protecting peers
  by network group, ping time, recent relay and connection age, then
  dropping the youngest connection of the largest network group, which a
  survey connection seconds old is. Dialled again, an address closed at
  once on one try and relayed normally for over 40 seconds on another.
  Such a record is now **closed early**: it keeps the `version`'s fields
  and gets no fingerprint. 74 others claimed `/Satoshi:25.0.0/` or
  `/Satoshi:25.1.0/` over v1, sent exactly `version` then `verack` at
  protocol 70016, where every Core since 0.21 sends `wtxidrelay` and
  `sendaddrv2` before its `verack`, kept the connection open through the
  wait and sent nothing more, most not even answering a `ping`. A session
  with a Core user agent, a common protocol version of 70016 or more, a

  claimed family, `{count, share}`) and `closed_early` (`{count,
  share}`); `families.unknown` now counts only the records no row matched

  `families`, `claimed`, `fake` and `closed_early`, and every share is of

  `satd_peer_survey_closed_early`; `satd_peer_survey_family{family="unknown"}`

  completed survey connections. `peersurvey.dat` is written in a new
  format (`satdsrv3`); a `satdsrv1` or `satdsrv2` file is dropped as it is
  read (below).

- **The survey retries closed-early addresses, and keeps a settled
  fingerprint.** An address recorded closed early is dialled again: due
  15 minutes after its closed-early session, then, after each further
  closed-early session or a retry whose dial or handshake failed,
  30 minutes, 1 hour, 2 hours and then 4 hours for every later one, each
  wait moved at random by up to a fifth either way. A due retry takes the
  next survey connection ahead of the uniform draw, passed over as a drawn
  address would be (named by the operator, banned, connected or being
  dialled, on a network the node does not reach, a bad port); the survey
  still opens one connection at a time, and retries count in
  `connections` as any survey connection does. At most ten retries are
  scheduled; then the address stays closed early until the draw reaches it
  again, and a closed-early result there does not start them over. The
  first session that settles clears the schedule. A closed-early session
  no longer replaces a settled record: an address already recorded with a

  and probes, and only its `last_seen` moves on. A fake session still

## Electrum

- **Sparrow batches its requests against satd** (#1069). Also in 0.7.1.
- **`-electrummaxbatchrequests` defaults to 345** (#1069). Also in 0.7.1.
- **Notifications are skipped**: a request with no `id` is no longer run with its reply dropped. Also in 0.7.2.
- **The protocol version is negotiated per connection.** `server.version` agrees a version by the spec's rule, and each method is served only at its spec versions. As the spec requires, a second `server.version` answers `server.version already sent`, and one with no common version closes the connection after its error, as ElectrumX does.
- **Electrum protocol 1.6** (spesmilo/electrum-protocol `b3db795b`). satd speaks 1.4 to 1.6; Electrum 4.7+ and BDK's `electrum-client` get 1.6. At 1.6 `blockchain.block.headers` returns a `headers` list (nonzero `cp_height` still refused), `mempool.get_info` adds `mempoolminfee`, `minrelaytxfee` and `incrementalrelayfee`, and `blockchain.relayfee` is gone; the spec's `(-height, tx_hash)` mempool order is the one satd already used. At every version, as ElectrumX: `blockchain.estimatefee` takes `ECONOMICAL` or `CONSERVATIVE` (other modes get `unknown estimatefee mode: <MODE>`), and `blockchain.transaction.broadcast_package` is Core's `submitpackage` (one child and its parents, child last, so a child can pay for a parent; `verbose=true` returns its answer).

## Mining

- **A negative `prioritisetransaction` delta stays negative in block templates** (#1274). Template selection keeps the modified fee signed, as Core does, so a child no longer pulls in a deprioritised parent whose delta it does not cover, and a negative package is left out even at `-blockmintxfee=0`. Actual fees still go to the coinbase and `getblocktemplate`.

## Mempool and relay

- **Transaction versions outside 1 to 3 are non-standard** (#1070). Also in 0.7.1.
- **A transaction may carry several OP_RETURN outputs**, as in Core v30. Their scripts draw on one `-datacarriersize` budget together (default 100000 bytes; `-datacarrier=0` leaves none), and a transaction over it is refused as `datacarrier`. satd refused a second OP_RETURN output whatever its size. In the same check, as in Core's `IsStandardTx`: an OP_RETURN output must be followed by pushes only, or it is refused as `scriptpubkey`; outputs are checked in order before the dust count, so the first failing output gives the reason; and an up-to-3-key bare multisig under `-permitbaremultisig=0` is refused as `bare-multisig`, not `scriptpubkey`. The `-datacarriersize` help and the manual gave its default as 83; it has been 100000 since 0.6.0.

## P2P

- **Peer fingerprints and behaviour flags** (#1351). The node matches every peer's handshake against shapes measured from Core (with Knots), btcd, bcoin, libbitcoin, Floresta, rbitcoin, satd and two crawlers, and raises seven flags (`C` crawler, `S` spy, `F` fingerprint mismatch, `A` addr abuse, `H` height lie, `N` notfound pattern, `T` stalling), each with the numbers behind it. New `getpeerbehavior [peer_id]`, `satd_peer_flagged{flag}` and `satd_peer_fingerprint{family}`, flag counts on the status page, a `-debug=net` line per new flag. Nothing carries an address and no flag changes how a peer is treated; the thresholds are provisional. See [Peer Behaviour Flags](https://epochbtc.github.io/satd/peer-behavior.html).
- **Alt-slots and `-maxoutboundfullrelay`** (#1355). `-maxoutboundfullrelay` sets the full-relay outbound count (default 8, as in Core; a warning above 8, an error above 16 without `-enable-dangerously-large-outbound-peer-limit`, never above 64). `-altslots=N` (default 0) sets aside N of them for peers matching `-altprefer` rules (observed family, claimed user agent as far as `-altuatrust` allows, or a service bit); flagged crawlers, spies and mismatches never fill one under the default trust, and an empty slot takes an ordinary peer after `-altfillwait` seconds (600). A smaller matching pool eases an eclipse attack on transaction and address relay, so the node warns above 4. Reloads on SIGHUP; `getpeerbehavior`, `getpeersurvey` and `satd_peer_alt_slots{state}` show the slots. With the defaults nothing changes. See [Alt-slots](https://epochbtc.github.io/satd/peer-behavior.html#alt-slots).
- **Soft enforcement of peer flags, `-peerflagpolicy`** (#1356). Default `observe` leaves Core's inbound eviction unchanged. Under `evict`, an inbound peer flagged `C`, `S` or `F` loses Core's eviction protections and goes first when an inbound slot is needed (reason `evicted-flagged`): nothing is disconnected while slots are free, nothing is banned, and outbound peers and `noban`, `relay` or `forcerelay` peers are never affected. The thresholds are provisional, so who goes first may change between releases. `getconfig` reports `p2p.peer_flag_policy`. See [Soft enforcement](https://epochbtc.github.io/satd/peer-behavior.html#soft-enforcement--peerflagpolicy).
- **Opt-in network survey** (#1353). With `-peersurvey=1` the node opens one short `survey` connection every `-peersurveyinterval` seconds (60) to an address drawn from the whole address book, under the usual `-onlynet` and proxy rules. It takes no outbound slot, is not in `getpeerinfo`, listens up to 10 seconds and, with `-peersurveyprobes`, sends a few probes checked against Core v32.1 to cost no misbehaviour score; the probes make survey connections recognisable. `getpeersurvey [verbose]` reports the implementation families, mismatches, the BIP 324 share and the busiest autonomous systems; `peersurvey.dat` holds peer addresses (at most 250,000, none older than 30 days). Off by default. The node's own disconnects now log a reason (`banned`, `block-download-stall` and so on) instead of `internal`. See [Network survey](https://epochbtc.github.io/satd/peer-behavior.html#network-survey).
- **Blocks and headers no longer wait for the P2P loop's tick** (#1228). Also in 0.7.2.
- **Header sync fetches each header once per peer, not many times** (#1229). Also in 0.7.2.
- **Header sync runs with one peer while the node is far behind, as in Bitcoin Core.** Until the best header is less than a day old, one peer, preferably outbound, serves headers, with a hand-over when it runs out or stalls; a fresh testnet4 node took 13.0 MB of `headers` instead of 75.5 MB.
- **Headers presync** (#1132). Header sync now stores a header chain only once it has shown enough work, as Core does: below the threshold a chain is downloaded once to measure its work, then again to store it. `getpeerinfo` reports `presynced_headers`. A clock more than two hours behind the chain stops the node with a clean shutdown where Core aborts. Core's `feature_minchainwork.py` now runs in the functional set.
- **Core's checks on blocks from peers** (#1247). A block or `cmpctblock` whose header claims too little chain work is now ignored and nothing of it is stored, as Core does (`too-little-chainwork`). A block the node did not ask for is stored only if its chain has at least the tip's work, is no more than 288 blocks above the tip, and has the minimum chain work; otherwise only its header is kept.
- **Header sync follows Core's timers** (#1122). The one header-sync peer gets Core's header-download timeout (15 minutes plus 1 ms per expected header). When it runs out, the peer is replaced, which takes the place of the 10-second stall probe and the post-IBD `getheaders` poll of every peer. An outbound peer whose chain stays behind our tip's work is challenged after 20 minutes and disconnected 2 minutes later if it has not caught up (`CHAIN_SYNC_TIMEOUT`). A tip unchanged for 30 minutes opens one extra full-relay outbound peer, removed again once it has connected, as in Core.
- **A `getheaders` waits for its answer** (#1262). As Core's `MaybeSendGetHeaders`, an outstanding `getheaders` under two minutes old suppresses new ones from announcements, so a looping peer no longer draws one every 2 seconds.
- **A fresh initial sync runs without RocksDB's write-ahead log, as intended.** The 10,000-block catch-up test now measures to the best header, not a fresh node's first header batch.
- **The coin cache counts what it holds.** A coin created and spent between flushes is erased, as Core's `SpendCoin` erases a FRESH coin, and the flush threshold counts entries and buffered index rows; the cache had flushed at a third of its budget. With Core's indexes (`-txindex`, `-addressindex=0`) a mainnet sync reached about 240,000 blocks in five minutes (Core 29.3: 246,700).
- **The coin cache flushes when it is full, as Bitcoin Core's does**, not every 1,000 blocks or at a quarter of `-dbcache`. Blocks below `-assumevalid` no longer start verification threads, and storing a block no longer walks the index. Peak IBD memory rises by up to the `-dbcache` budget, and a crash replays up to a few thousand stored blocks; a prune flushes first, so none is lost.
- **Initial sync syncs the block files once per batch, not once per block.** Index entries wait for one fsync per 64 blocks or 100 ms, never reaching the database ahead of their bytes; a crash re-downloads only the waiting blocks, as in Core. Height 100,000 now takes about 70 seconds instead of 7 minutes; blocks at the tip still sync before they connect.
- **Disconnect log lines give the right reason** (#1152). Also in 0.7.1.
- **Onion peers are logged by their onion address** (#1165). Also in 0.7.1.
- **A pruned node prunes during initial sync** (#1154). Also in 0.7.1.
- **Peer handling no longer stops while a block connects during initial sync** (#875). IBD blocks are stored on their own thread (up to 128 MiB queued) instead of the peer task, which waited out long connects and then dropped peers as stalled.
- **A `headers` message no longer stops peer handling while a block connects** (#1187). Header batches are accepted on their own thread, in order; block-relay messages and pings behind a batch still wait for it, as in Core.
- **Onion seeds for every network** (#1162). Also in 0.7.1.
- **Automatic dials draw from the whole address book** (#1148), with Core's odds for recent and failed attempts, not only 256 `peers.dat` entries plus gossip. As in Core, candidates without the needed services or on another service's well-known port are skipped before dialling. `-connect` still turns automatic dials off.
- **Onion addresses are in the address book** (#1157). Tor v3 onions are kept in `peers.dat` with the rest, as Core keeps BIP 155 networks, instead of an in-memory list. Their network group is Core's (first four bits of the key), one source holds at most 64 in the new table, they are dialled only with a Tor proxy and without `-onion=0`, at most 16 a pass, onions named by `-connect`, `-addnode` or `-seednode` stay out, and `getnodeaddresses`, `getaddrmaninfo`, `getrawaddrman` and `addpeeraddress` handle them as in Core. `-asmap` groups IP addresses only.
- **Feeler connections** (#1149). With its outbound slots full the node opens a short feeler to a new-table address about every two minutes, and tests a contested tried slot first, as Core does (since #1127 the next full-relay dial did that). Not under `-connect`.
- **Two block-relay-only outbound peers** (#1225). Once its eight full-relay peers are up the node opens Core's two block-relay-only peers, capped by `-maxconnections` (one at 9, none at 8 or fewer). A block-relay-only `addconnection` no longer takes a full-relay slot. satd's IBD full-relay target is 64, so they open after IBD.
- **Block-relay-only peers survive a restart: `anchors.dat`** (#1150). A clean stop writes them to `anchors.dat`, byte-compatible with Core's; the next start deletes it and dials them first, skipping unsuitable ones as Core does. Not under `-connect`. `peers.dat` stays satd's own format. Core's `feature_anchors.py` now runs in the functional set.
- **`addconnection` opens onion connections** (#1150) through the proxy, with the requested type and `v2transport`, as Core does.
- **An outbound peer on every reachable network** (#1156). As in Core, a node with its eight full-relay peers and none on a reachable network (IPv4, IPv6, onion) dials an extra peer there about every five minutes; eviction never drops a network's only peer. Not below eight slots, during IBD or under `-connect`.
- **An extra block-relay-only peer every few minutes** (#1155). After IBD, as Core does, the node opens one about every five minutes, then drops the youngest of its block-relay-only peers unless it gave a block more recently than the second-youngest, which goes instead. Needs a spare slot (none at `-maxconnections` 10 or below); not under `-connect`. A peer is not dropped in its first 30 seconds or while blocks download from it.
- **One source cannot fill the address book** (#1264). Each source's network group holds at most 1,024 new entries, a sixteenth of the book, as Core's bucketing limits one source; one peer could fill an empty book. An older `peers.dat` loads only the first 1,024 per source.
- **The onion address no longer reaches peers that can see the node's IP** (#1209). With `-listenonion` it goes only to peers on the onion listener or through the proxy, without `-externalip` beside it; `addr_from` is Core's dummy address, and `getaddr` replies never carry the node's own addresses. A deliberate difference from Core, listed in `CORE_DIFFERENCES.md`.
- **200 connections, and half the inbound slots for transaction relay** (#1263). As in Core v32, `-maxconnections` defaults to 200, and transaction-relaying inbound peers are capped at `-inboundrelaypercent` (default 50, SIGHUP-reloadable) of the inbound slots (94 of 189 by default), evicting by Core's inbound eviction rules, which protect `noban` peers among others. Outbound and manual connections are unaffected.
- **`-maxconnections` is capped at 2000** (#1295), with Core v32.1's warning (bitcoin/bitcoin#35919); the inbound slots follow the capped value. A value too large for an integer reads as 2147483647, as in Core.
- **File-descriptor budget** (#1294). As Core does, satd raises its soft descriptor limit at startup and fits `-maxconnections` to it, or refuses to start with Core's error when its hard minimum (the fixed needs, every cap the operator set, and a floor of 64 per cap left at its default) does not fit. Caps left at their defaults then shrink to fit what is left, one log line each; the manual's packaging chapter has the formula.
- **`-discover`, off by default** (#1209). Honoured instead of skipped: each outbound clearnet peer is told the address it reports seeing. Unlike Core it defaults off, as it lists the node's IP with crawlers, and adds no interface or `-bind` addresses. Never sent through the proxy; kept out of `getaddr` replies, so a peer that reports another node's IP on the same port gets that address withheld too. SIGHUP-reloadable.
- **A `getheaders` with an empty locator gets one header, or none** (#1298): the header `hashStop` names, and only for a block Core's `BlockRequestAllowed` admits; satd answered with headers from height 1, even for a block it had only as a header.
- **A block is not announced back to a peer that has it** (#1299). Core's `PeerHasHeader` decides: no `inv`, `headers` or `cmpctblock` goes to a peer that announced the block or one built on it; satd skipped only a peer whose last known block was that very block.
- **A full node makes room for a new inbound peer** (#1293). With every inbound slot taken, a new inbound peer evicts one chosen by Core's eviction rules and is dropped only if every one is protected; satd refused every newcomer. Inbound slots are `-maxconnections` less 11, as in Core, not less 8.
- **An empty `getblocktxn` disconnects the peer**. Also in 0.7.2.
- **A `cmpctblock` needs `sendcmpct` first** (#1275). One from a peer that never sent `sendcmpct` version 2 is ignored, header included, as in Core v32.
- **A new block is announced only after its transaction rules pass.** Also in 0.7.2.
- **Tor replies and the saved onion key are checked before use**. Also in 0.7.2.
- **A peer is not penalised for the transactions it relays**, as in Bitcoin Core since v30, which removed `MaybePunishNodeForTx`. satd charged a peer 10 misbehaviour points for a transaction failing its scripts under the consensus flags or spending more than its inputs, and 1 for an orphan over the standard weight, so ten invalid transactions disconnected the peer and banned its address. Such a transaction is still refused.
- **A `headers` message's transaction counts are ignored, as in Core** (#1346). Core reads the count after each header as a CompactSize and ignores it; satd read one byte and refused the message unless it was zero.
- **`getblocktxn` indexes are 16-bit, as in Core** (#1347). Core's `DifferenceFormatter` refuses an index above 65535 as a decode failure ("differential value overflow"); satd read indexes as 64-bit and accepted the message.
- **A transaction with no inputs has its txid as its wtxid** (#1348), as Core's `ComputeWitnessHash` returns the txid for a transaction without witnesses. rust-bitcoin hashes such a transaction in the extended form, a wtxid Core never produces, and several of satd's call sites (the log line refusing it among them) used that. Every wtxid satd computes now goes through one helper. Such a transaction is invalid (`bad-txns-vin-empty`), so verdicts are unchanged.

### Opt-in network crawl, `-crawl`

With `-crawl=1` the node walks the
reachable network: it seeds itself from the DNS seeds (`-dnsseed`
respected; under a proxy the onion seeds, nothing looked up locally), the
fixed seeds, a uniform sample of the address book, `-crawlseed` addresses
and its own book, asks reachable nodes for addresses, dials what they
name, and records the result in `crawlbook.dat` (at most 250,000
addresses; the file holds peer addresses and is written with the data
directory's permissions every 10 minutes and at shutdown).

Each session is short and declares itself: protocol 70016, services 0,
relay off, the node's real tip height, a fresh random nonce, a dummy
`addr_from`, and the user agent `/satd:<version>(crawler)/`, with
`-crawluacomment` as a second comment; then `wtxidrelay`, `sendaddrv2`
and `verack`, and nothing else unsolicited. The node's own addresses
and `-uacomment` never appear. As Bitcoin Core does for its own
outbound connections, BIP 324 is tried first only to a node known to
advertise `NODE_P2P_V2`: by its own last `version` once a handshake has
completed, before that by the services its address was last advertised
with (a seed carries none). Every other node is dialled over v1 with no
BIP 324 bytes sent, since some v1-only implementations (bcoin 2.2.0,
libbitcoin-server 3.8.0) close on them and bcoin bans the dialling
address; a node that speaks v2 without advertising it is counted as v1.
A node that refuses BIP 324 as a v1-only node does (closing, or never
answering, with nothing sent back) is redialled over v1, as Bitcoin Core
does, and a node that did v2 is checked over v1 on first contact and
weekly, so a node that only speaks v2 is told apart. A discovery session (first contact,
then once a day, since Core caches its `getaddr` answer for about a day)
sends one `getaddr`, waits up to 90 seconds for the answer, and with
`-crawlprobes` (on by default) sends the survey's four probes, each
checked against Bitcoin Core v32.1 for no misbehaviour score and no
disconnect. A liveness session (every `-crawlliveness` seconds, 7200 by
default and at least that, so at most 14 sessions a target a day) closes
once the handshake settles. Unreachable addresses back off 1 h, 4 h,
24 h, then daily.

Limits, each with a ceiling no option lifts: `-crawlconcurrency` (32
clearnet sessions, at most 256), `-crawltorconcurrency` (8, at most 256),
`-crawlrate` (10 new sessions a second, at most 100), one session per
address and two per IPv4 `/16` or IPv6 `/32`. At startup the crawl's
sessions are fitted into the file-descriptor limit after
`-maxconnections`: a limit too tight lowers the crawl's concurrency with
a line in the log, never `-maxconnections`.

The crawl is kept apart from the node: its connections are outside
every connection budget and never in `getpeerinfo`,
`getconnectioncount`, `getpeerbehavior`, eviction or the behaviour flags;
nothing is relayed over them and a `getaddr` sent over one is answered
with nothing. The address book is read to seed the crawl and never
written: `peers.dat` is unchanged by a crawl. What the crawl learns is
never relayed, served on `getaddr`, or given to the node's own dialer,
the alt-slots or the extra-network peer. It dials what the node's dialer
may (`-onlynet`, `-proxy`, `-onion`), narrowed by `-crawlnet`, and never
clearnet through the proxy, so a Tor-only node crawls onions only; each
onion dial has a Tor circuit of its own. I2P and CJDNS addresses are
recorded, never dialled. `-crawlbind` sets the source address of direct
dials, one per family. No session starts while the node is in initial
block download, under `-connect`, or with networking off; a panic in a
crawl task stops the crawl and leaves the node running. All options are
read at startup only.

With `-crawl=1` the network survey (`-peersurvey`) opens no connection:
the crawl measures everything it would, from more addresses.
`getpeersurvey` still reports the survey's store and says
`"superseded_by_crawl": true`. `getconfig` reports the settings under
`crawl`.

**The crawl dials tens of thousands of addresses from this host's IP
address** (or `-crawlbind`'s). Other operators' monitors will record it
as a crawler, it may end up on ban lists that then refuse the node's own
connections too, and hosting providers may receive abuse reports. The
node logs this once at startup; a dedicated host is the better place to
run it.

**`-crawlproxy=<ip:port>`** sends the crawl's clearnet dials through a
SOCKS5 proxy on another host, with no direct fallback. See the
[manual](https://epochbtc.github.io/satd/crawl.html#crawling-through-a-proxy--crawlproxy).

- **Esplora no longer copies the whole mempool on every request.** Also in 0.7.2.
- **Esplora lists a whole block in one small answer.** New `GET /block/:hash/txs/summary` returns a JSON array with one `[txid, fee, weight, value]` row per transaction in block order, the coinbase first with fee 0: fee and total output value in sats, BIP 141 weight. It is not part of upstream Esplora; the route and its shape are those of rbitcoin's Esplora, so the rbitcoin-space explorer lists a block's transactions from satd without falling back to `getblock` verbosity 2. Fees come from the block's undo data, as in `getblock` verbosity 2. A hash that is unknown, not on the best chain or pruned is 404, and the answer carries the `X-Bitcoin-Chain-Tip` headers like the other block routes.
- **Esplora lists an address's history as compact rows.** New `GET /address/:address/txs/summary[/:last_seen_txid]` and `GET /scripthash/:hash/txs/summary[/:last_seen_txid]` return the transactions `/txs/chain` pages, in the same order, 25 a page, each as `{txid, value, height, time, tx_position}`: `value` is the script's net change in sats in that transaction (what it receives less what it spends, so negative for a spend), `height` and `time` are the confirming block's, `tx_position` the transaction's index in it. Confirmed transactions only. They are not part of upstream Esplora; the routes and their shape are those of rbitcoin's Esplora, so the rbitcoin-space explorer draws an address's balance chart and history summary from satd. `?asof=<blockhash>` answers as of that block. A cursor that is not in the script's confirmed history is 422 `after_txid not found`, and `?after_txid=` is accepted in place of the path cursor. The values are summed from the script's history rows without reading a transaction or a block, which takes the whole history: a script over `-addrindexmaxhistory` gets 400 `Too many history entries`, as on the stats. Malformed input is 400, as on the other address routes, where rbitcoin answers 404.
- **Esplora transactions carry their sigop cost, and outspends can be asked for in batches.** Every transaction object (`/tx/:txid`, the block, address and scripthash lists) has a new `sigops` number: the BIP 141 sigop cost as Bitcoin Core's `GetTransactionSigOpCost` counts it, from the counter block validation uses. A legacy sigop costs 4, a sigop of a P2SH redeem script 4, a P2WPKH input 1, a P2WSH input one per sigop of its witness script, and a taproot spend nothing. An input whose previous output cannot be found adds nothing (the transaction's `fee` is then `null`), and an OP_RETURN-stripped transaction is counted over its stored scripts, which leaves out only sigop opcodes a non-standard stripped script held outside its pushes. New `GET /txs/outspends?txids=a,b,...` returns one array per txid, in request order, each the array `/tx/:txid/outspends` returns, read at one pinned tip; `?asof=<blockhash>` answers as of that block. At most 50 txids: more is 400 `Too many txids requested`, and none is 400 `No txids specified`. A txid that is malformed or unknown gets an empty array in its place, and one given twice is answered twice. Neither is part of upstream Esplora; the field, the route, its limit and its refusals are those of rbitcoin's Esplora, which the rbitcoin-space explorer reads.

- **MCP has a read-only token, `mcp:read`**: only the tools that answer questions, none that signs, broadcasts, mines, manages peers, shows peer addresses or host details, or costs the node far more than the request. Withheld tools look absent. `mcp:*` implies it. The list is in the [MCP chapter](https://epochbtc.github.io/satd/mcp.html).

## Upgrade notes

These changes, also in 0.7.1, need attention when upgrading from 0.7.0:

- A client that reads `warnings` from `getblockchaininfo`, `getnetworkinfo` or `getmininginfo` as a string gets `[]` on a node with no warnings. It already got an array whenever a warning was active, and Core has returned an array since v28. Start the node with `-deprecatedrpc=warnings` to keep the string form for now.
- A `bitcoin.conf` carrying `reindex=1` or `reindexchainstate=1` now rebuilds on start. Remove the line if the rebuild is not wanted.
- In the docker-compose stack, a `conf.d/local.conf` line for a key `satd-init` writes now takes effect. Check that file for stale lines before upgrading.
- A node whose shadow queue held more than 128 MiB now drops shadow work past that and logs it. Raise `-shadowqueuemb` to keep more.
- Log consumers that matched `Disconnecting peer on request` should match `Disconnecting peer` with `reason="rpc_request"` instead.
- The Electrum server reports a new default name, `satd-electrs-electrumx-compatible/<version>`. A client or monitor that matched the old `satd-electrs-compatible` name exactly should match the new one, or set `electrumservername` to keep the old name. `-electrummaxbatchrequests` now defaults to 345; an operator who wants the old limit can set it to 100, but Sparrow then fails to verify a wallet with more than 100 transactions.
- A custom signet (`-signetchallenge`) whose blocks do not follow the standard retarget schedule, such as one run by a modified bitcoind with a shorter block interval, no longer syncs. Bitcoin Core refuses it too.
- A JSON-RPC client that pauses mid-response, reading nothing for longer than `-rpcservertimeout` while the server has more to send, is now disconnected. Raise `-rpcservertimeout` if a client legitimately does that.
- The AssumeUTXO warnings have new `getwarnings` ids: `assumeutxo-validation-failed` is now `alert.assumeutxo_validation_failed`, `assumeutxo.catchup_halted` is now `alert.assumeutxo_catchup_stalled`, and `assumeutxo.handoff_failing` is now `alert.assumeutxo_handoff_failing`. A `status` consumer sees three new kinds (proto values 8 to 10); the Rust and Go SDKs in this release name them, and an older SDK reports them as unknown kinds with their severity and message intact.

New in 0.8.0:

- `-consensus` defaults to `cpp-shadow`, so the Rust engine decides and Core's interpreter checks it. A node that set no `consensus` now runs that way; set `consensus=rust-shadow` to keep Core's interpreter deciding. A node that already sets `consensus` is unaffected.
- A node run with `-dbcache=auto` under a memory cgroup limit lower than host memory (#1272) starts with a smaller cache and keeps it within that limit. Set a number, `-dbcache=<MB>`, to size it by hand.
- A custom signet (`-signetchallenge`) now keeps its data in `<datadir>/signet_<message start>`, as Bitcoin Core does from its next release (#1271). A node that ran a custom signet in `<datadir>/signet/` refuses to start after the upgrade and prints the move to make, for example `mv ~/.bitcoin/signet ~/.bitcoin/signet_54d26fbd`, plus a second `mv` for `<blocksdir>/signet` when `-blocksdir` is set. Stop anything else using the directory, run the printed commands, and start again; nothing is synced again. Scripts and tools that read `signet/.cookie` on such a node read `signet_<message start>/.cookie` instead, or pass `-signetchallenge` to `sat-cli` or `sat-tui`. The default signet is unaffected.
- `-maxconnections` defaults to 200, up from 125 (#1263). A listening node can hold up to 72 more inbound peers, each with a socket and its buffers, so it uses more file descriptors and some more memory. The packaged systemd units already allow 65,536 descriptors; a node started by hand under a shell limit of 1,024 should raise it or set `maxconnections`. Transaction-relaying inbound peers are now capped at `-inboundrelaypercent` (default 50) of the inbound slots, including on a node that sets `maxconnections`. `maxconnections=128` with `inboundrelaypercent=100` keeps 0.7's 117 inbound slots, all free to relay transactions (#1293).
- A node takes 3 fewer inbound peers for the same `-maxconnections` (#1293): the inbound slots are `maxconnections` less 11, as in Core, where 0.7 used less 8 (189 at the default 200; 114 instead of 117 at 125). The value is the one left after the 2000 cap and the file-descriptor fit. Add 3 to `maxconnections` to keep the old count. Once the slots are full, a new inbound peer evicts an existing one instead of being refused.
- `peers.dat` is written in format version 3, which can hold onion addresses (#1157). A 0.7 or earlier `peers.dat` loads. An older satd refuses a version 3 file and starts with an empty address book, so a node downgraded from 0.8.0 rebuilds its peers from the DNS and fixed seeds.
- `-maxconnections` above 2000 is lowered to 2000, with a warning (#1295).
- satd checks its file-descriptor limit at startup (#1294). Under a low limit a default node shrinks `maxopenfiles` and Esplora's socket cap to fit (under 1,024: 288 and 172); a node whose explicitly set caps do not fit refuses to start.
- A custom-signet blocks directory written before 0.8.0 holds records framed with the default signet's message start (#1283). satd reads them, but Bitcoin Core does not, so sync such a directory again from scratch before pointing Core at it.
- The default `-assumevalid` block is higher on every network (#1217). A node still in initial sync, or started fresh, skips script verification up to the new block (126,143 more blocks on mainnet); set `-assumevalid=<hash>` to keep the old one or `-assumevalid=0` to verify every script. With the higher minimum chain work, a syncing node skips scripts only once its best header has that much work.

- Electrum: a client that offers protocol 1.6, such as Electrum 4.7 and later or BDK's `electrum-client`, now gets 1.6: `blockchain.block.headers` answers with a `headers` list instead of one `hex` string, and `blockchain.relayfee` is gone in favour of `mempool.get_info`'s `minrelaytxfee`. A client that offers 1.6 must read the 1.6 shapes, as the spec requires; one that cannot should offer 1.4 only. `blockchain.transaction.broadcast_package` now takes `submitpackage`'s shape at every version: a package that is not one child with its direct parents, sorted with the child last, is refused, where satd used to submit the members one by one in any order.
- Electrum: a client whose `server.version` names no version satd speaks now gets its error and then the connection closes; it used to stay open. A second `server.version` on one connection is refused with `server.version already sent`. A connection that never sends `server.version` is served as before.

- `getblockstats`' `minfeerate`, `maxfeerate` and `avgfeerate` are in sat/vB, a thousandth of what 0.7 reported for the same block, and `total_size`, `total_weight`, `avgtxsize`, `mintxsize`, `maxtxsize`, `mediantxsize` and `avgfeerate` leave out the header and coinbase, as in Core. A dashboard or script that divided satd's feerates by 1000, or read `total_size` as the block's size, should drop the division or read `size` from `getblock` instead. `total_out` no longer includes the block reward, and `utxo_size_inc` is Core's figure rather than 0.7's estimate (#1208). Clients written for Core need no change.
- Integer arguments (#1267): a value that does not fit an argument is now `-1 JSON integer out of range`, as in Core, where satd answered `-8 Invalid value for argument ...`. `getchaintxstats` refuses an `nblocks` that reaches the final block's height instead of shrinking it to fit, and `setmocktime` refuses a time past `4294967295`.
- A synced node no longer drops back into initial block download when its tip goes stale (#1071). A monitor that read `initialblockdownload: true` as the sign of a stalled node should watch the tip's age instead, as the `tip_stall` alert does. A `-minimumchainwork` set above the chain the node can reach now keeps it in IBD, as in Core.
- `sat-cli` sends an argument as JSON only when Bitcoin Core's conversion table lists it, as `bitcoin-cli` does (#1268). A script that relied on the old guess, passing a number, boolean, `null`, array or object to an argument Core treats as a string, now sends the text; one that passed text to a listed argument, such as `getblock <hash> verbose`, is refused with `Error parsing JSON`. A command line that works with `bitcoin-cli` works the same way with `sat-cli`.
- `getnetworkinfo.version` is 320000 (#1068). A client that checks it against an exact list of Core versions (`corepc`'s v28 client) no longer matches.
- `decodepsbt`'s `tx.vin` and `tx.vout` are arrays, not counts (#1296). A client that read the counts should take the arrays' lengths, or `inputs` and `outputs`.
- `decodepsbt` (#1311): `partial_signatures` is an object from public key to signature, not an array; a version 2 input's `sighash` is a name such as `"ALL"`, not a number; and `fee` is absent, not `null`, when an input's UTXO is missing. A client reading the old shapes should read the new ones, as it would from Core.
- `getchaintxstats` with no `nblocks` measures one month of blocks (4320), not 30 (#1297). A client that wanted the recent rate should pass `nblocks` itself.
- A peer that relays invalid transactions is no longer disconnected or banned for it, as in Core v30 and later. An operator who relied on satd banning such peers can ban them with `setban`.

- Fee estimates (#1200, #1254): the default on `estimatesmartfee`, `estimatefees`, Esplora, Electrum, MCP and the status page comes from the new estimators, and is lower than 0.7's in a calm market. `estimatefees` in `blend` mode no longer answers from the mempool simulator; ask for `mempool` mode to keep it. A node with no fee history and no mempool side yet (the first six blocks after a cold start) has `estimatesmartfee` return Core's `errors` answer instead of a feerate; a client must read `feerate` as optional, as it must with Core. `estimatefees` (and the MCP fee tool) leaves out `economy_feerate` when it would be 0, which only a zero relay floor allows. Target 1 is answered for 2 blocks and `blocks` says so. `errors` is absent from a successful answer. Each answer carries a new `estimator` field.
- Every RPC `asm` field is now in Core's format (#1265). A script that parsed satd's `OP_PUSHBYTES_<n>`, `OP_0`, `OP_PUSHNUM_<n>`, `OP_CSV` or `OP_CLTV` tokens must read Core's instead; one written for Core needs no change.

No action required: the crawl is off by default.

The network survey and the crawl are new in 0.8.0, so the notes below
concern only a node that ran an earlier 0.8.0 development build.

A node that runs the network survey drops the records of a
`peersurvey.dat` in an older format (`satdsrv1` or `satdsrv2`) when it
starts, logs how many it dropped, and the survey fills again from empty;
the file is rewritten in the current format (`satdsrv4`) on its next save.
Older records cannot be sorted into the new categories, since whether the
peer closed the connection early was never stored, and a uniform survey
revisits an address too rarely to replace them. A damaged old file is
still set aside. An older build cannot read a `satdsrv4` file: on a
downgrade it sets the file aside and the survey starts empty.

A `peersurvey.dat` in format `satdsrv3` (written by an earlier 0.8.0
development build) keeps every record and its verdict, each with no retry
scheduled: a closed-early address gets its first retry after its next
closed-early session. The file is rewritten as `satdsrv4` on its next
save; an older build cannot read it and sets it aside. Likewise a
`crawlbook.dat` in format version 4 keeps every entry and observation,
each with no retry scheduled, and is rewritten in format 5, which an
older build sets aside.

`getpeersurvey`'s `families.unknown` and
`satd_peer_survey_family{family="unknown"}` no longer include claimed
records; add `claimed`, `fake` and `closed_early` to get the old count
(for a node whose records were all written by this build).

A node that runs the crawl and has a `crawlbook.dat` from an earlier
0.8.0 development build (format version 2 or 3) keeps every entry, with
its reachability, transport results, sources and timers, and drops each
entry's last observation, logging how many: neither version stored
whether the peer closed the connection during the passive wait, so no
observation can be sorted into the new categories. The crawl revisits
every reachable address within the liveness window (`-crawlliveness`,
2 hours by default), which observes it again; until then such an
address counts as reachable under `families.unknown`, with null
observation fields in `getcrawlnodes` and the export, and the next
session to it is dialled as its advertised services say rather than as
its last `version` did. Probe answers, the `getaddr` answer and the
chain check return with its next discovery session (within a day). The
file is rewritten in format 5 on its next save; an older build cannot
read it and sets it aside. `getcrawlinfo`'s `families.unknown` and
`satd_crawl_family{family="unknown"}` no longer include claimed
addresses; add `claimed`, `fake` and `closed_early` to get the old
count.

- **Building from source** now also needs **cmake** and the **Boost headers,
  1.74 or later** (`apt install libboost-dev`, `brew install boost`; header-only,
  nothing is linked). `libbitcoinkernel-sys` builds Bitcoin Core's kernel with
  them. A static musl build through cargo-zigbuild must also point that cmake
  build at zig and pass `-UNDEBUG`, since zig defines `NDEBUG` at `-O2` and Core
  refuses to build without assertions; `release.yml` shows how.
