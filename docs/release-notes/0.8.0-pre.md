# satd 0.8.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

This file accumulates entries as changes land; it is not yet a cut release.

satd 0.8.0 includes every fix shipped in 0.7.1.

## Highlights

- [The C++ script engine verifies a transaction's inputs in linear time](#consensus):
  Bitcoin Core's interpreter now comes through `libbitcoinkernel`, about 27x
  faster on many-input blocks.
- [The Rust engine is the default primary](#the-rust-script-engine-decides-by-default):
  `-consensus` now defaults to `cpp-shadow`, with the Rust engine deciding and
  Core's interpreter checking every script behind it.
- [A new default fee estimate](#rpc): the mempool for the next two blocks and
  the chain's own fee history beyond, on `estimatesmartfee` and every other fee
  surface. Wallets get lower numbers in a calm market.

## Consensus

- **Signet blocks must carry the scheduled difficulty** (#838). Signet `nBits` is checked against the retarget schedule and signet's proof-of-work limit, with no minimum-difficulty exception, and a mismatch is refused with `bad-diffbits`, as in Core; satd accepted any `nBits` the block's hash met. Also in 0.7.1.
- **The Rust engine names a malformed tapscript push as Core does.** A tapscript push running past the end of the script now fails with `SCRIPT_ERR_BAD_OPCODE`, as Core's pre-execution `OP_SUCCESSx` scan reports it, not with whatever execution reached first. No verdict changes. Found by [bitcoin-consensus-spec](https://github.com/coreyphillips/bitcoin-consensus-spec)'s conformance suites, which satd now runs nightly (`satd-conformance-harness`).
- **`-test=bip94` on regtest** (#1245). Enforces BIP 94's timewarp rule as Core's option does: the first block of each 144-block period may not be more than 600 seconds older than its parent (`time-timewarp-attack`); BIP 94's retarget seeding has no effect on regtest, which never retargets. As in Core, `-test` is refused off regtest and an unknown name only warns; Core's `addrman` and `reindex_after_failure_noninteractive_yes` are refused, as satd lacks them.
- **Script flags follow Core's model: on from genesis, with three exceptions** (#1244, #724). P2SH, WITNESS and TAPROOT are on for every block except Core's three exception blocks (mainnet 170,060 and 692,261, testnet3 394), keyed on block hash, and block sigops use the same flags; satd used activation heights. Main-chain verdicts are unchanged, but on regtest `-testactivationheight=segwit@N` no longer turns WITNESS and TAPROOT off below N (it moves only NULLDUMMY and the witness commitment rules), taproot is active from genesis, and `getdeploymentinfo`'s `script_flags` shows an exception block's own flags. DERSIG, CLTV, CSV and NULLDUMMY keep their buried heights. Found by bitcoin-consensus-spec's block corpus.
- **`-reindex` checks every block's header as header sync does** (#506). A full reindex checked only proof of work, so a block breaking the difficulty schedule, median time past, minimum version or a checkpoint could be indexed and connected. It now applies those rules, the checkpoint fork rule and the proof-of-work limit, and indexes or replays neither a failing block nor anything built on it, nor a side-chain block with an unindexed parent; the two-hours-ahead rule is not applied to stored blocks. Also in 0.7.1.
- **Transactions are decoded as Core decodes them** (#1242). `version | 00 00 | lock_time` is a transaction with no inputs, as in Core's `UnserializeTransaction`, so the P2P messages and RPCs that carry one refuse it as `bad-txns-vin-empty` where satd refused the bytes, and a witness flag followed by no inputs is a decode failure; no verdict changes. Such a transaction is written, measured and hashed as Core does (`createrawtransaction` with no inputs returns Core's bytes; `decoderawtransaction`, `testmempoolaccept` and `submitpackage` report Core's size and wtxid), `submitpackage` refuses it as `conflict-in-package`, and the RPCs that take a transaction answer a decode failure with Core's message ("TX decode failed. Make sure the tx has at least one input." and its variants). Found by bitcoin-consensus-spec's `custom` suite.

### The Rust script engine decides by default

`-consensus` now defaults to `cpp-shadow`: the Rust engine decides and Bitcoin
Core's C++ interpreter re-verifies every script behind it, logging any
disagreement. Up to 0.7.x the default was `rust-shadow`, the other way round.
The Rust engine passes Core's script tests, matched Core's interpreter across
mainnet history, and has run as primary under sustained production use on
mainnet, signet and testnet4 for months without a disagreement.
`-consensus=rust-shadow` keeps Core's interpreter deciding. New manual chapter:
[Consensus Engines & Shadow Verification](https://epochbtc.github.io/satd/consensus.html).

### The C++ script engine is Core's interpreter through libbitcoinkernel (#874)

Core's interpreter (authoritative under `rust-shadow` and `cpp`, the shadow
under `cpp-shadow`) now comes through `libbitcoinkernel` instead of
`libbitcoinconsensus`, whose per-input API rebuilt a transaction's signature
hashes for every input. The kernel precomputes them once per transaction, as
Core's `CheckInputScripts` does. Script verification, one thread:

| Block | 0.7.x (`libbitcoinconsensus`) | 0.8.0 (`libbitcoinkernel`) |
|---|---|---|
| signet 227,466 (3,373 inputs), glibc / static musl | 4.57 s / 6.53 s | 0.17 s / 0.24 s |
| mainnet 974,146 (7,990 inputs), glibc / static musl | 656 ms / 773 ms | 283 ms / 303 ms |

Mempool acceptance and the signet block solution use the same path. No verdict
changes: the kernel's interpreter is Core v32.1's, `libbitcoinconsensus` was
Core 26's (removed from Core in v28). satd pins `bitcoinkernel` 0.3.2 and
`libbitcoinkernel-sys` 0.4.1.

## RPC

- **Any request `Content-Type` is accepted** (#824). The body is read as JSON whatever the header says, as in Core; other types, including Core's documented `text/plain;`, got `415`. Also in 0.7.1.
- **`getrawtransaction`'s not-found message matches the node's index** (#1066). With a complete `-txindex` it says `No such mempool or blockchain transaction`, and with an index enabled after blocks were connected (never backfilled) it says those blocks need a block hash; only without an index does it advise `-txindex`. Code -5 as before. Also in 0.7.1.
- **A package member spending one outpoint twice gets Core's answer.** Core's `IsConsistentPackage` compares inputs only across members, so `submitpackage` answers `transaction failed` with the member's `bad-txns-inputs-duplicate`, and a multi-transaction `testmempoolaccept` refuses that member with it; satd refused the whole package as `conflict-in-package`, which still covers two members spending one outpoint.
- **`testmempoolaccept` agrees with `sendrawtransaction` under an `allow` policy rule** (#999). It runs the `-policyfile` dry run and forgives the exemptable standardness failures on an `Allow` verdict, as admission does, instead of refusing first. Also in 0.7.1.
- **`getnetworkinfo` reports which networks are reachable** (#1164). `reachable` and `limited` follow `-onlynet` and the proxy (onion needs one that reaches Tor and no `-onion=0`), as Core's `g_reachable_nets`; `ipv4` and `ipv6` were always reachable. `networks` lists Core's five; `i2p` is never reachable and `cjdns` only with `-cjdnsreachable`. Also in 0.7.1.
- **`warnings` is always an array** (#956). In `getblockchaininfo`, `getnetworkinfo` and `getmininginfo` it is `[]` when empty, as in Core since v28, not `""`. `-deprecatedrpc=warnings` restores the string form; any other `-deprecatedrpc` name is warned about and ignored. Also in 0.7.1.
- **`getblockstats` reports what Core reports, in Core's units.** `minfeerate`, `maxfeerate` and `avgfeerate` are in sat/vB (they were sat/kvB, 1000x too high; `sat-tui`'s "Avg Rate" is fixed with them); size, weight and feerate statistics leave out the header and coinbase; `mediantxsize` is a median, not a mean; and `feerate_percentiles` is new. `total_out` leaves out the coinbase, `utxo_size_inc` is Core's figure from the real output and spent-coin sizes, and `utxo_increase_actual` and `utxo_size_inc_actual` are new (#1208); every statistic matches Core 32.1 on the same blocks. Fees come from undo data, which pruning keeps, though a pruned block still answers `Block data not available`; a mismatched one is refused and an unreadable one answers Core's `Can't read undo data from disk` (-1) instead of zero fees.
- **An open WebSocket no longer outlives its bearer token** (#821). Each JSON-RPC WebSocket frame re-checks its token, so a token removed from the `-authfile` (with `SIGHUP`) or expired stops working on open sockets: frames get `-32006` (`bearer token revoked or expired`) and a `subscribemempool` ends at its next event. Capability and rate-limit changes reach open sockets too. Also in 0.7.1.
- **The capability check comes before parameter checks** (#826). On a `-rpcauthbearer` listener a token without the method's capability (such as `rpc:submit`) gets `-32004` before named parameters are checked, as with Core's `-rpcwhitelist`, not `-8 Unknown named parameter`. Also in 0.7.1.
- **Initial block download is judged as Core judges it** (#1071). The node stays in IBD until its tip has `-minimumchainwork` as well as a timestamp within `-maxtipage`, and while replaying blocks at startup, and once out it does not re-enter until restart. A synced node with a stale tip used to fall back into IBD, which made mainnet `getblocktemplate` refuse, stopped Stratum work and turned off transaction relay through the fee filter.
- **`estimatesmartfee` takes Core 32.1's shape and floors every answer** (#1200). New in 0.8.0; #1254 below changed the number again.
  - Every fee surface (`estimatesmartfee`, `estimatefees`, Esplora `/fee-estimates`, Electrum `blockchain.estimatefee`, MCP, status page) floors at the rolling mempool minimum and `-minrelaytxfee`, as in Core 32; with a full mempool satd quoted rates it would not relay.
  - `options` takes Core's `fee_rate_estimator` (`block_policy`, `mempool_policy`, `auto` by default) and `verbosity` (2 adds `mempool_health_statistics`). Unlike Core, an unknown `fee_rate_estimator` means `auto` and an unknown `options` key is ignored, where Core refuses both.
  - `estimator` names the source: `block_policy`, `mempool_policy` or `floor`. Core reports it only under `auto` and has no `floor`.
  - `blocks` is the target answered, as in Core: target 1 is answered for 2, at history's lower 2-to-3-block rate, and `mempool_policy` always for 2.
  - With no fee history the answer is Core's `errors: ["Insufficient data or no feerate found"]` with `blocks: 0`, not the relay floor; `errors` appears only on an error.
- **Bitcoin Core v32.1 options and arguments** (#1203). `prevoutfetchthreads`, `rpcmaxconnections` and `txsendrate` are warned about and skipped instead of refused as typos; `privatebroadcast` is refused, since satd does not implement it and would announce transactions to every peer. The node creates `<datadir>/fees/` as Core v32 does. `converttopsbt` takes `psbt_version`, accepting only `0` (`-8` otherwise); satd still defaults to 0, where Core v32 defaults to 2.
- **`estimatesmartfee`'s `mempool_policy` is Bitcoin Core 32's mempool estimator** (#1202). New in 0.8.0. It answers, for 2 blocks, the feerate at which the next template reaches 50% of a block's weight (`conservative`) or 75%, else the floor, as Core 32.1 does on the same mempool. A health gate refuses it, with Core's error text, during the startup mempool load and while under 75% of the last six blocks' weight was in the mempool beforehand; the rows persist in `fees/mempool_health.dat` (cleared under `-persistmempool=0` or without `mempool.dat`), and `verbosity` 2 reports them with a `mempool_health` verdict (`healthy`, `insufficient_data`, `low_coverage`). The node also tracks arrival weight per feerate band; nothing answers from it yet.
- **`estimatesmartfee`'s `block_policy` reads the chain's own fee history** (#1250). New in 0.8.0. Each of the last 3,200 blocks has a hurdle, the feerate at the 10th percentile of its weight over transactions paying the relay floor. For N blocks the estimate takes past N-block windows that began in a fee market like today's and answers a high quantile of their lowest hurdles (99.9% at 1 block, 95% economical, 97.5% conservative), rbitcoin's analog-window method (`docs/mempool-fee-estimation.md` in reardencode/rbitcoin); with too few windows it uses a plain quantile, and with none the old estimator. The history is kept in `fees/fee_history.dat` (about 140 KB) and filled in the background from block and undo data for what the file lacks, so a pruned node gathers it across restarts. A damaged or wrong-network file is logged and rebuilt from the blocks, and a reorg never leaves an abandoned branch's row. In a 30,000-block mainnet backtest it covered as often as a plain quantile and overpaid much less (median 1.9× the realised hurdle at 6 blocks, against 3.3×).
- **The default fee estimate reads the mempool for the next two blocks and the chain's fee history beyond** (#1254). This completes #1200, #1202 and #1250; the old estimator remains only as a fallback while history fills.
  - Targets 1 and 2, while the health gate passes, answer Core 32's template percentile (75% of the next block, 50% under `conservative`); every other target, and all of them while the gate fails, answer from history, held at or below the 2-block answer.
  - `conservative` is never below history's estimate or `economical`, and history answers it at 97.5%, down from 99% (at 6 blocks, 91.0% coverage at 5.5× against 96.8% at 10×).
  - Used by `estimatesmartfee` `auto` (default), `unset`, `economical`, `conservative` and satd's `blend`; `historical` is the history estimate alone. `estimatefees` (default `blend`), Esplora, Electrum, MCP and the status page use the same economical numbers.
  - Unlike Core 32.1's `auto`, which takes the lower of its two estimators, satd's mempool side sets the 1- and 2-block answer even when it is dearer than history.
  - The floor is the rolling mempool minimum or `-minrelaytxfee` (0.1 sat/vB by default); #1200's 1 sat/vB floor is gone. A target history cannot answer gets the floor while the mempool side answers, where Core 32.1 errors (Esplora omits it, Electrum answers `-1`); with neither, Core's `Insufficient data or no feerate found`.
  - On mainnet, beside a Core 32.1 node: _numbers to come before release_.
- **A too-long Bech32 address names one error location** (#1204). `validateaddress` reports only the position where the string passes 90 characters, as Core v32.
- **A JSON-RPC connection from outside `-rpcallowip` is closed without a reply** (#1204), at accept, as Core v32 does, instead of `403 Forbidden`.
- **A transaction announced twice in one `inv` is processed once** (#1204), `MSG_WITNESS_TX` counted as a txid, and logged under `-debug=net` as Core v32's `got inv:` line.
- **A request for a filtered block disconnects the peer** (#1204). satd never offers `NODE_BLOOM`, and now disconnects on `MSG_FILTERED_BLOCK` as Core v32 does instead of ignoring it.
- **A `-blocksonly` node ignores compact blocks** (#1204), header included, as Core v32 does; satd could connect a block from a pushed one.
- **`invalidateblock` and `reconsiderblock` end on the best valid chain** (#1261). When activation meets an invalid block the node tries the next-best chain, as Core's `ActivateBestChain`, and succeeds; it stopped on the invalid block's parent with an error. `preciousblock` and the startup repair after a crash in `invalidateblock` share the path.
- **`addnode` refuses an empty node** with `-8 Error: Node address cannot be empty`, as in Core v32; `addnode "" add` retried it forever. Also in 0.7.2.
- **Script `asm` is Core's** (#1265). Every `asm` field follows Core's `ScriptToAsmStr`: bare hex for pushes over four bytes, numbers for short pushes and `OP_0`..`OP_16`, `OP_CHECKSEQUENCEVERIFY`/`OP_CHECKLOCKTIMEVERIFY`, `[error]` for a truncated push, and a scriptSig signature's sighash by name (`[ALL]`). It was rust-bitcoin's (`OP_PUSHBYTES_20`, `OP_PUSHNUM_1`, `OP_CSV`). Covers `decoderawtransaction`, `getrawtransaction`, `getblock` 2 and 3, `gettxout`, `decodescript` and Electrum's verbose `blockchain.transaction.get`; Esplora's `scriptsig_asm` and `scriptpubkey_asm` keep Esplora's format.
- **`desc` in every scriptPubKey, and `decodescript` in full** (#1266). Every scriptPubKey object carries Core's inferred `desc` (`decoderawtransaction`, `getrawtransaction`, `getblock` 2 and 3, Electrum's verbose transaction), not only in `gettxout`, and `decodescript` adds `desc`, `address` and Core's `segwit` object, checked against Core 32.1 on 53 scripts (`rpc_decodescript.py` now runs in the functional suite). A wrong-length v0 witness program gets `p2sh` and `segwit`, as in Core. One difference: a sane miniscript with an off-curve key is `addr(…)` in satd, `wsh(…)` in Core.
- **Integer and verbosity arguments are parsed as Core parses them** (#1267). Each integer is read as Core's `UniValue::getInt<T>` for the handler's C++ type, then range-checked as the method does, checked against Core 32.1:
  - `getblock` and `getrawtransaction` take any verbosity: 0 or below is hex, above the top level is the top level.
  - A fraction or out-of-type value is `-1 JSON integer out of range`, not `-8 Invalid value for argument ...`.
  - Range errors match Core for `getblockhash`, `getblockstats`, `getchaintxstats` (now refuses instead of clamping), `estimatesmartfee`/`estimaterawfee` (negative target, checked before the mode) and `createpsbt`; negative values in `waitforblockheight`, `waitfornewblock`, `waitforblock`, `verifychain`, `generatetoaddress`, `generatetodescriptor`, `setban`, `disconnectnode` and `sendmsgtopeer` are handled as Core handles them.
  - Also converted: `gettxout`, `pruneblockchain`, `getnetworkhashps`, `getorphantxs`, `createrawtransaction`, `createpsbt`, `converttopsbt`, `getnodeaddresses`, `getblockfrompeer`, `prioritisetransaction` and `setmocktime` (bound `4294967295`, mistyped value `-3`).

  JSON `-0` in an unsigned argument is still read as 0, where Core refuses it.
- **`getchaintxstats` defaults to one month of blocks, and takes `nblocks=0`** (#1297). With no `nblocks` the window is Core's 4320 blocks (capped at the final block's height - 1), not 30, so `window_*` and `txrate` match Core's.
- **`decodepsbt` decodes the transaction and its scripts** (#1296). `tx` is now Core's `TxToUniv` without `hex`, as `decoderawtransaction` answers, instead of only the txid, version, locktime and input and output counts. Its script objects follow Core's `ScriptToUniv`.
- **Mempool entries carry Core v31's chunk fields** (#1068). `getmempoolentry` and the verbose mempool views report `chunkweight` and `fees.chunk`, the weight and modified fees of the chunk the transaction is mined in, as Core does; Bark's `captaind` needs them. The fees are signed, as in Core.
- **`getnetworkinfo.version` is 320000** (#1068), up from 280000, so clients with a Core v29 or v31 floor (Bark, Eclair) start. No client found switches on anything else between the two.

## Electrum

- **Sparrow batches its requests against satd** (#1069). The default server name is now `satd-electrs-electrumx-compatible/<version>`, which Sparrow recognises; Cake Wallet still finds `electrs`, and BlueWallet keeps batching. Also in 0.7.1.
- **`-electrummaxbatchrequests` defaults to 345** (#1069), Fulcrum's default, so Sparrow's 250-call verification batches fit. Also in 0.7.1.
- **Notifications are skipped.** A request with no `id` is no longer run with its reply dropped, which bypassed backpressure. Also in 0.7.2.
- **The protocol version is negotiated per connection.** `server.version` agrees a version by the spec's rule, and each method is served only at its spec versions. As the spec requires, a second `server.version` answers `server.version already sent`, and one with no common version closes the connection after its error, as ElectrumX does.
- **Electrum protocol 1.6** (spesmilo/electrum-protocol `b3db795b`). satd speaks 1.4 to 1.6; Electrum 4.7+ and BDK's `electrum-client` get 1.6. At 1.6 `blockchain.block.headers` returns a `headers` list (nonzero `cp_height` still refused), `mempool.get_info` adds `mempoolminfee`, `minrelaytxfee` and `incrementalrelayfee`, and `blockchain.relayfee` is gone; the spec's `(-height, tx_hash)` mempool order is the one satd already used. At every version, as ElectrumX: `blockchain.estimatefee` takes `ECONOMICAL` or `CONSERVATIVE` (other modes get `unknown estimatefee mode: <MODE>`), and `blockchain.transaction.broadcast_package` is Core's `submitpackage` (one child and its parents, child last, so a child can pay for a parent; `verbose=true` returns its answer).

## Mining

- **A negative `prioritisetransaction` delta stays negative in block templates** (#1274). Template selection keeps the modified fee signed, as Core does, so a child no longer pulls in a deprioritised parent whose delta it does not cover, and a negative package is left out even at `-blockmintxfee=0`. Actual fees still go to the coinbase and `getblocktemplate`.

## Mempool and relay

- **Transaction versions outside 1 to 3 are non-standard** (#1070), reason `version`, as in Core's `IsStandardTx`; `-acceptnonstdtxn` lifts it on test chains. Also in 0.7.1.

## P2P

- **Blocks and headers no longer wait for the P2P loop's tick** (#1228). They were handled on a 500 ms tick, about 25 blocks a second per peer; a fresh mainnet sync from one local peer now reaches about 58,000 blocks in five minutes, up from 7,400. Also in 0.7.2.
- **Header sync fetches each header once per peer, not many times** (#1229). Overlapping `getheaders` chains made a fresh mainnet sync download 5.6 GB of `headers` for a 78 MB chain; a new request now waits for the header tip to stall 10 seconds, and a full batch asks only its sender. The same sync takes 90 MB. Also in 0.7.2.
- **Header sync runs with one peer while the node is far behind, as in Bitcoin Core.** Until the best header is less than a day old, one peer, preferably outbound, serves headers, with a hand-over when it runs out or stalls; a fresh testnet4 node took 13.0 MB of `headers` instead of 75.5 MB.
- **Headers presync** (#1132). Header sync now stores a header chain only once it has shown enough work, as Core does: below the threshold a chain is downloaded once to measure its work, then again to store it. `getpeerinfo` reports `presynced_headers`. A clock more than two hours behind the chain stops the node with a clean shutdown where Core aborts. Core's `feature_minchainwork.py` now runs in the functional set.
- **Core's checks on blocks from peers** (#1247). A block or `cmpctblock` whose header claims too little chain work is now ignored and nothing of it is stored, as Core does (`too-little-chainwork`). A block the node did not ask for is stored only if its chain has at least the tip's work, is no more than 288 blocks above the tip, and has the minimum chain work; otherwise only its header is kept.
- **A `getheaders` waits for its answer** (#1262). As Core's `MaybeSendGetHeaders`, an outstanding `getheaders` under two minutes old suppresses new ones from announcements, so a looping peer no longer draws one every 2 seconds.
- **A fresh initial sync runs without RocksDB's write-ahead log, as intended.** The 10,000-block catch-up test now measures to the best header, not a fresh node's first header batch.
- **The coin cache counts what it holds.** A coin created and spent between flushes is erased, as Core's `SpendCoin` erases a FRESH coin, and the flush threshold counts entries and buffered index rows; the cache had flushed at a third of its budget. With Core's indexes (`-txindex`, `-addressindex=0`) a mainnet sync reached about 240,000 blocks in five minutes (Core 29.3: 246,700).
- **The coin cache flushes when it is full, as Bitcoin Core's does**, not every 1,000 blocks or at a quarter of `-dbcache`. Blocks below `-assumevalid` no longer start verification threads, and storing a block no longer walks the index. Peak IBD memory rises by up to the `-dbcache` budget, and a crash replays up to a few thousand stored blocks; a prune flushes first, so none is lost.
- **Initial sync syncs the block files once per batch, not once per block.** Index entries wait for one fsync per 64 blocks or 100 ms, never reaching the database ahead of their bytes; a crash re-downloads only the waiting blocks, as in Core. Height 100,000 now takes about 70 seconds instead of 7 minutes; blocks at the tip still sync before they connect.
- **Disconnect log lines give the right reason** (#1152). The line is `Disconnecting peer`, with `reason="rpc_request"` only for `disconnectnode` and `reason="internal"` otherwise. Also in 0.7.1.
- **Onion peers are logged by their onion address** (#1165), not `0.0.0.0:<port>`. Also in 0.7.1.
- **A pruned node prunes during initial sync** (#1154). Blocks are fetched in height order within `-maxahead` of the tip, as in Core, not at random up to the header tip; a block `inv` during IBD gets `getheaders` only, and an unrequested block above the window is not stored. Blocks stored above the window by 0.7.0 stay until the tip reaches them. Also in 0.7.1.
- **Peer handling no longer stops while a block connects during initial sync** (#875). IBD blocks are stored on their own thread (up to 128 MiB queued) instead of the peer task, which waited out long connects and then dropped peers as stalled.
- **A `headers` message no longer stops peer handling while a block connects** (#1187). Header batches are accepted on their own thread, in order; block-relay messages and pings behind a batch still wait for it, as in Core.
- **Onion seeds for every network** (#1162). Tor v3 fixed seeds from Core v31.2, kept where they answered: 138 mainnet, 41 testnet3, 49 testnet4, 48 signet. testnet4 and testnet3 had none. Also in 0.7.1.
- **Automatic dials draw from the whole address book** (#1148), with Core's odds for recent and failed attempts, not only 256 `peers.dat` entries plus gossip. As in Core, candidates without the needed services or on another service's well-known port are skipped before dialling. `-connect` still turns automatic dials off.
- **Onion addresses are in the address book** (#1157). Tor v3 onions are kept in `peers.dat` with the rest, as Core keeps BIP 155 networks, instead of an in-memory list. Their network group is Core's (first four bits of the key), one source holds at most 64 in the new table, they are dialled only with a Tor proxy and without `-onion=0`, at most 16 a pass, onions named by `-connect`, `-addnode` or `-seednode` stay out, and `getnodeaddresses`, `getaddrmaninfo`, `getrawaddrman` and `addpeeraddress` handle them as in Core. `-asmap` groups IP addresses only.
- **Feeler connections** (#1149). With its outbound slots full the node opens a short feeler to a new-table address about every two minutes, and tests a contested tried slot first, as Core does (since #1127 the next full-relay dial did that). Not under `-connect`.
- **Two block-relay-only outbound peers** (#1225). Once its eight full-relay peers are up the node opens Core's two block-relay-only peers, capped by `-maxconnections` (one at 9, none at 8 or fewer). A block-relay-only `addconnection` no longer takes a full-relay slot. satd's IBD full-relay target is 64, so they open after IBD.
- **Block-relay-only peers survive a restart: `anchors.dat`** (#1150). A clean stop writes them to `anchors.dat`, byte-compatible with Core's; the next start deletes it and dials them first, skipping unsuitable ones as Core does. Not under `-connect`. `peers.dat` stays satd's own format. Core's `feature_anchors.py` now runs in the functional set.
- **`addconnection` opens onion connections** (#1150) through the proxy, with the requested type and `v2transport`, as Core does.
- **An outbound peer on every reachable network** (#1156). As in Core, a node with its eight full-relay peers and none on a reachable network (IPv4, IPv6, onion) dials an extra peer there about every five minutes; eviction never drops a network's only peer. Not below eight slots, during IBD or under `-connect`.
- **An extra block-relay-only peer every few minutes** (#1155). After IBD, as Core does, the node opens one about every five minutes, then drops the youngest of its block-relay-only peers unless it gave a block more recently than the second-youngest, which goes instead. Needs a spare slot (none at `-maxconnections` 10 or below); not under `-connect`. A peer is not dropped in its first 30 seconds or while blocks download from it.
- **One source cannot fill the address book** (#1264). Each source's network group holds at most 1,024 new entries, a sixteenth of the book, as Core's bucketing limits one source; one peer could fill an empty book. An older `peers.dat` loads only the first 1,024 per source.
- **The onion address no longer reaches peers that can see the node's IP** (#1209). With `-listenonion` it goes only to peers on the onion listener or through the proxy, without `-externalip` beside it; `addr_from` is Core's dummy address, and `getaddr` replies never carry the node's own addresses. A deliberate difference from Core, listed in `CORE_DIFFERENCES.md`.
- **200 connections, and half the inbound slots for transaction relay** (#1263). As in Core v32, `-maxconnections` defaults to 200, and transaction-relaying inbound peers are capped at `-inboundrelaypercent` (default 50, SIGHUP-reloadable) of the inbound slots (94 of 189 by default), evicting by Core's inbound eviction rules, which protect `noban` peers among others. Outbound and manual connections are unaffected.
- **`-maxconnections` is capped at 2000** (#1295), with Core v32.1's warning (bitcoin/bitcoin#35919); the inbound slots follow the capped value. A value too large for an integer reads as 2147483647, as in Core.
- **File-descriptor budget** (#1294). As Core does, satd raises its soft descriptor limit at startup and fits `-maxconnections` to it, or refuses to start with Core's error when its hard minimum (the fixed needs, every cap the operator set, and a floor of 64 per cap left at its default) does not fit. Caps left at their defaults then shrink to fit what is left, one log line each; the manual's packaging chapter has the formula.
- **`-discover`, off by default** (#1209). Honoured instead of skipped: each outbound clearnet peer is told the address it reports seeing. Unlike Core it defaults off, as it lists the node's IP with crawlers, and adds no interface or `-bind` addresses. Never sent through the proxy; kept out of `getaddr` replies, so a peer that reports another node's IP on the same port gets that address withheld too. SIGHUP-reloadable.
- **A `getheaders` with an empty locator gets one header, or none** (#1298): the header `hashStop` names, and only for a block Core's `BlockRequestAllowed` admits; satd answered with headers from height 1, even for a block it had only as a header.
- **A block is not announced back to a peer that has it** (#1299). Core's `PeerHasHeader` decides: no `inv`, `headers` or `cmpctblock` goes to a peer that announced the block or one built on it; satd skipped only a peer whose last known block was that very block.
- **A full node makes room for a new inbound peer** (#1293). With every inbound slot taken, a new inbound peer evicts one chosen by Core's eviction rules and is dropped only if every one is protected; satd refused every newcomer. Inbound slots are `-maxconnections` less 11, as in Core, not less 8.
- **An empty `getblocktxn` disconnects the peer**, as in Core v32; 33 bytes could make the node upload up to 4 MB. Also in 0.7.2.
- **A `cmpctblock` needs `sendcmpct` first** (#1275). One from a peer that never sent `sendcmpct` version 2 is ignored, header included, as in Core v32.
- **A new block is announced only after its transaction rules pass.** The compact announcement waits for the BIP 34 height and finality checks, as Core waits for `ContextualCheckBlock`. Also in 0.7.2.
- **Tor replies and the saved onion key are checked before use**, as in Core's next release: a malformed key or service ID from Tor is refused, a malformed saved key is refused with a warning naming the file, and over-long control-port lines are refused. An unquoted saved key could inject command arguments. Also in 0.7.2.
- **A peer is not penalised for the transactions it relays**, as in Bitcoin Core since v30, which removed `MaybePunishNodeForTx`. satd charged a peer 10 misbehaviour points for a transaction failing its scripts under the consensus flags or spending more than its inputs, and 1 for an orphan over the standard weight, so ten invalid transactions disconnected the peer and banned its address. Such a transaction is still refused.

## HTTP surfaces

- **A client that stops reading gives its slot back** (#823). A write that makes no progress closes the connection after `-rpcservertimeout` on JSON-RPC, as in Core, or 60 s on Esplora, streamws and with `-rpcservertimeout=0`. Also in 0.7.1.
- **Shutdown closes WebSockets and SSE streams** (#822): `/ws` gets `1001 Going Away`, and SSE responses on streamws and Esplora end. Also in 0.7.1.
- **Timeouts too large for the clock are clamped** (#826). `-rpcservertimeout` or `-esplorarequesttimeout` over a year is a year; a huge value made every connection panic. Also in 0.7.1.
- **`-esplorarequesttimeout=0` leaves TLS working** (#826). The TLS handshake gets 30 s instead of none. Also in 0.7.1.
- **The plain metrics listener has a connection cap and a header timeout** (#826): 64 connections and 30 s for the request head. Metrics and MCP close a write stalled for 60 s. Still loopback by default. Also in 0.7.1.
- **Esplora no longer copies the whole mempool on every request.** `GET /`, `/mempool`, `/mempool/txids`, `/mempool/recent` and `/tx/:txid/outspends`, all unauthenticated, read it in place. Also in 0.7.2.

## Operator

- **`reindex` and `reindexchainstate` in `bitcoin.conf` are honoured** (#840), hyphenated too, and rebuild on every start until removed, as in Core. Also in 0.7.1.
- **`conf.d/local.conf` overrides what the stack writes** (#843). Its top-level lines now come first, so first-value-wins no longer ignores them. Also in 0.7.1.
- **The core runtime has at least two worker threads** (#1144), so one blocking call on a 1-CPU host cannot stall RPC and P2P. Also in 0.7.1.
- **The shadow verification queue is bounded by memory** (#1145). New `-shadowqueuemb` (default 128 MiB) caps the bytes queued for the shadow engine besides `-shadowqueuesize`; on few cores the queue could grow to gigabytes in IBD. `-shadowqueuemb=0` restores the entry bound alone. Dropped work is logged; the primary engine still verifies every script. Also in 0.7.1.
- **Floodable warnings are budgeted per listener** (#825). TLS handshake timeouts and accept errors are rate-limited per listener, each Stratum listener has its own at-capacity budget, and the Electrum, Stratum and plain metrics accept loops back off 50 ms after an error. Also in 0.7.1.
- **`-dbcache=auto` respects the node's memory limit** (#1272). It sizes from the tighter of host memory and the process's cgroup limit (v2 `memory.max`/`memory.high`, or v1), so a node under systemd `MemoryMax=`, Docker `--memory` or an Umbrel or StartOS limit is not OOM-killed in IBD. Without readable cgroup files the host figures apply; nothing changes off Linux. Core's `-dbcache` is static.
- **A datadir from another network is refused** (#1270) with Core's "Incorrect or no genesis block found. Wrong datadir for network?", before `-reindex-chainstate` or `-upgradechainstate` clears anything and before the cookie is written. It cannot tell signets apart (#1271).
- **A custom signet has a data directory of its own** (#1271). As in Core's next release (bitcoin/bitcoin#34566), a custom signet keeps its data, its blocks under `-blocksdir` and its cookie in `signet_<message start>`; an empty `-signetchallenge=` is a custom signet. Unlike Core, which starts afresh, satd refuses to start when `signet/` holds this signet's chain and prints the `mv` commands, moving nothing itself. `sat-cli` takes `-signetchallenge`, `sat-tui` `--signetchallenge` and `--testnet4`, and the docker-compose `satd-init` points `rpc-cookie` at the new directory.
- **A custom signet's block files carry its own message start** (#1283). satd framed a custom signet's `blk*.dat` records with the default signet's message start, which Bitcoin Core refuses (`ReadRawBlock`, "Block magic mismatch"); it now writes the custom signet's own, and tags `dumptxoutset` snapshots with it, as Core does. satd still reads records with either start, so an older directory keeps working.
- **AssumeUTXO background validation retries a failed connect** (#557) every second instead of stopping, with `assumeutxo.connect_retry` every tenth attempt and the `assumeutxo_catchup_stalled` alert after 30. An invalid or unconnectable block stops it with `reason=invalid_block` or `reason=cannot_connect`, leaving the snapshot unvalidated. Also in 0.7.1.
- **AssumeUTXO conditions are alerts on every surface** (#557): `assumeutxo_catchup_stalled`, `assumeutxo_handoff_failing` and `assumeutxo_validation_failed` reach `status`, `alertfile` webhooks and `satd_alert_active`. Also in 0.7.1.
- **AssumeUTXO gauges** (#557): `satd_assumeutxo_background_attached`, `satd_assumeutxo_snapshot_rejected`, and while a snapshot is loaded `satd_assumeutxo_background_tip_height` and `satd_assumeutxo_snapshot_height`. Also in 0.7.1.
- **A fresh testnet4 sync gets past block 51,540** (#1216), where 0.7.0 and 0.7.1 tripped the stall watchdog on every start. testnet4 and testnet3 ship Core's default `-assumevalid`, and the watchdog counts script inputs verified on the connect path as progress (mempool admission, prefetch and the shadow engine do not count). Also in 0.7.2.
- **The default `-assumevalid` and minimum chain work are Bitcoin Core v32.1's** (#1217). The default assumevalid block moves from 840,000 to 966,143 on mainnet, 4,842,348 to 5,128,859 on testnet3, 123,613 to 151,604 on testnet4, and on signet from a block satd picked, 218,000, to Core's 321,295. The conditions for skipping scripts are unchanged.

## sat-cli

- **Arguments are converted the way `bitcoin-cli` converts them** (#1268). `sat-cli` parses an argument as JSON only when Core v32.1's `vRPCConvertParams` table lists it for the method, by position or name, `-named` included, so text such as `123` or `true` is sent as text; a listed argument that is not JSON is refused with `error: Error parsing JSON: <arg>`. satd's own RPCs are in the table: `estimatefees` (`targets`), `getmempoolhistory` and `getreorghistory` (`since_secs`), `getmempoolsummary` (`top_n`), `getsilentpaymentblockdata` (`verbosity`, `dust_limit`), `listquarantine` (`count`, `skip`), `stripopreturns` (`threshold`), `getaddressbalance`, `getaddresshistory` and `getaddressutxos` (`address`, JSON when it parses), and `allowquarantined=` on `sendrawtransaction`; unknown methods keep the old guess.
- **`-stdinrpcpass`** reads the RPC password from the first line of stdin, as in `bitcoin-cli`, and `-stdin` keeps empty lines as empty arguments, as Core does.

## Storage

- **Block reads no longer wait behind each stored block's fsync** (#547); the fsync runs after the block-file lock is released. Also in 0.7.1.
- **A block file never grows past its size cap** (#547), even when the next file already exists after pruning. Also in 0.7.1.
- **A re-fetched block frees its download slot during initial sync** (#547). Also in 0.7.1.

## Release tooling

- **`sign-tarballs.sh` keeps its downloads across a failed run** (#903) in `${SATD_SIGN_DIR:-${XDG_CACHE_HOME:-~/.cache}/satd-sign/<tag>}` (mode 0700, ownership checked), reusing only files whose hashes still match and signatures that still verify, and removes it after a successful upload or `--dry-run`; `--images` is unchanged. Also in 0.7.1.

## SDKs

- **A resilient watch re-anchors after a drop before its first confirmed event** (#777). `Subscribe` and `Watch` responses carry a `satd-head-cursor` header, and the Go and Rust SDKs resume from it when they have no cursor of their own (no `FromCursor` / `from_cursor`, empty store), so an event in flight at an early drop is no longer lost. Also in 0.7.1.

## Packaging

- **The Nix build of `satd` is reproducible across x86_64 CPUs** (#321). The flake pins jemalloc's address width, page size and hugepage size, which it read from the build CPU. Also in 0.7.1.
- **`flake.lock` is committed** (#321), so every build of a commit evaluates the same Nix inputs. Also in 0.7.1.
- **The x86_64 Linux release tarballs no longer depend on the build runner's CPU** (#321); `release.yml` pins the same jemalloc values. Also in 0.7.1.

## Upgrade notes

These changes, also in 0.7.1, need attention when upgrading from 0.7.0:

- A client that reads `warnings` from `getblockchaininfo`, `getnetworkinfo` or `getmininginfo` as a string gets `[]` on a node with no warnings. It already got an array whenever a warning was active, and Core has returned an array since v28. Start the node with `-deprecatedrpc=warnings` to keep the string form for now.
- A `bitcoin.conf` carrying `reindex=1` or `reindexchainstate=1` now rebuilds on start. Remove the line if the rebuild is not wanted.
- In the docker-compose stack, a `conf.d/local.conf` line for a key `satd-init` writes now takes effect. Check that file for stale lines before upgrading.
- A node whose shadow queue held more than 128 MiB now drops shadow work past that and logs it. Raise `-shadowqueuemb` to keep more.
- Log consumers that matched `Disconnecting peer on request` should match `Disconnecting peer` with `reason="rpc_request"` instead.
- The Electrum server reports a new default name, `satd-electrs-electrumx-compatible/<version>`. A client or monitor that matched the old `satd-electrs-compatible` name exactly should match the new one, or set `electrumservername` to keep the old name. `-electrummaxbatchrequests` now defaults to 345; an operator who wants the old limit can set it to 100, but Sparrow then fails to verify a wallet with more than 100 transactions.
- A custom signet (`-signetchallenge`) whose blocks do not follow the standard retarget schedule, such as one run by a modified bitcoind with a shorter block interval, no longer syncs. Bitcoin Core refuses it too.
- A JSON-RPC client that pauses mid-response, reading nothing for longer than `-rpcservertimeout` while the server has more to send, is now disconnected. Raise `-rpcservertimeout` if a client legitimately does that.
- The AssumeUTXO warnings have new `getwarnings` ids: `assumeutxo-validation-failed` is now `alert.assumeutxo_validation_failed`, `assumeutxo.catchup_halted` is now `alert.assumeutxo_catchup_stalled`, and `assumeutxo.handoff_failing` is now `alert.assumeutxo_handoff_failing`. A `status` consumer sees three new kinds (proto values 8 to 10); the Rust and Go SDKs in this release name them, and an older SDK reports them as unknown kinds with their severity and message intact.

New in 0.8.0:

- `-consensus` defaults to `cpp-shadow`, so the Rust engine decides and Core's interpreter checks it. A node that set no `consensus` now runs that way; set `consensus=rust-shadow` to keep Core's interpreter deciding. A node that already sets `consensus` is unaffected.
- A node run with `-dbcache=auto` under a memory cgroup limit lower than host memory (#1272) starts with a smaller cache and keeps it within that limit. Set a number, `-dbcache=<MB>`, to size it by hand.
- A custom signet (`-signetchallenge`) now keeps its data in `<datadir>/signet_<message start>`, as Bitcoin Core does from its next release (#1271). A node that ran a custom signet in `<datadir>/signet/` refuses to start after the upgrade and prints the move to make, for example `mv ~/.bitcoin/signet ~/.bitcoin/signet_54d26fbd`, plus a second `mv` for `<blocksdir>/signet` when `-blocksdir` is set. Stop anything else using the directory, run the printed commands, and start again; nothing is synced again. Scripts and tools that read `signet/.cookie` on such a node read `signet_<message start>/.cookie` instead, or pass `-signetchallenge` to `sat-cli` or `sat-tui`. The default signet is unaffected.
- `-maxconnections` defaults to 200, up from 125 (#1263). A listening node can hold up to 72 more inbound peers, each with a socket and its buffers, so it uses more file descriptors and some more memory. The packaged systemd units already allow 65,536 descriptors; a node started by hand under a shell limit of 1,024 should raise it or set `maxconnections`. Transaction-relaying inbound peers are now capped at `-inboundrelaypercent` (default 50) of the inbound slots, including on a node that sets `maxconnections`. `maxconnections=128` with `inboundrelaypercent=100` keeps 0.7's 117 inbound slots, all free to relay transactions (#1293).
- A node takes 3 fewer inbound peers for the same `-maxconnections` (#1293): the inbound slots are `maxconnections` less 11, as in Core, where 0.7 used less 8 (189 at the default 200; 114 instead of 117 at 125). The value is the one left after the 2000 cap and the file-descriptor fit. Add 3 to `maxconnections` to keep the old count. Once the slots are full, a new inbound peer evicts an existing one instead of being refused.
- `peers.dat` is written in format version 3, which can hold onion addresses (#1157). A 0.7 or earlier `peers.dat` loads. An older satd refuses a version 3 file and starts with an empty address book, so a node downgraded from 0.8.0 rebuilds its peers from the DNS and fixed seeds.
- `-maxconnections` above 2000 is lowered to 2000, with a warning (#1295).
- satd checks its file-descriptor limit at startup (#1294). Under a low limit a default node shrinks `maxopenfiles` and Esplora's socket cap to fit (under 1,024: 288 and 172); a node whose explicitly set caps do not fit refuses to start.
- A custom-signet blocks directory written before 0.8.0 holds records framed with the default signet's message start (#1283). satd reads them, but Bitcoin Core does not, so sync such a directory again from scratch before pointing Core at it.
- The default `-assumevalid` block is higher on every network (#1217). A node still in initial sync, or started fresh, skips script verification up to the new block (126,143 more blocks on mainnet); set `-assumevalid=<hash>` to keep the old one or `-assumevalid=0` to verify every script. With the higher minimum chain work, a syncing node skips scripts only once its best header has that much work.

- Electrum: a client that offers protocol 1.6, such as Electrum 4.7 and later or BDK's `electrum-client`, now gets 1.6: `blockchain.block.headers` answers with a `headers` list instead of one `hex` string, and `blockchain.relayfee` is gone in favour of `mempool.get_info`'s `minrelaytxfee`. A client that offers 1.6 must read the 1.6 shapes, as the spec requires; one that cannot should offer 1.4 only. `blockchain.transaction.broadcast_package` now takes `submitpackage`'s shape at every version: a package that is not one child with its direct parents, sorted with the child last, is refused, where satd used to submit the members one by one in any order.
- Electrum: a client whose `server.version` names no version satd speaks now gets its error and then the connection closes; it used to stay open. A second `server.version` on one connection is refused with `server.version already sent`. A connection that never sends `server.version` is served as before.

- `getblockstats`' `minfeerate`, `maxfeerate` and `avgfeerate` are in sat/vB, a thousandth of what 0.7 reported for the same block, and `total_size`, `total_weight`, `avgtxsize`, `mintxsize`, `maxtxsize`, `mediantxsize` and `avgfeerate` leave out the header and coinbase, as in Core. A dashboard or script that divided satd's feerates by 1000, or read `total_size` as the block's size, should drop the division or read `size` from `getblock` instead. `total_out` no longer includes the block reward, and `utxo_size_inc` is Core's figure rather than 0.7's estimate (#1208). Clients written for Core need no change.
- Integer arguments (#1267): a value that does not fit an argument is now `-1 JSON integer out of range`, as in Core, where satd answered `-8 Invalid value for argument ...`. `getchaintxstats` refuses an `nblocks` that reaches the final block's height instead of shrinking it to fit, and `setmocktime` refuses a time past `4294967295`.
- A synced node no longer drops back into initial block download when its tip goes stale (#1071). A monitor that read `initialblockdownload: true` as the sign of a stalled node should watch the tip's age instead, as the `tip_stall` alert does. A `-minimumchainwork` set above the chain the node can reach now keeps it in IBD, as in Core.
- `sat-cli` sends an argument as JSON only when Bitcoin Core's conversion table lists it, as `bitcoin-cli` does (#1268). A script that relied on the old guess, passing a number, boolean, `null`, array or object to an argument Core treats as a string, now sends the text; one that passed text to a listed argument, such as `getblock <hash> verbose`, is refused with `Error parsing JSON`. A command line that works with `bitcoin-cli` works the same way with `sat-cli`.
- `getnetworkinfo.version` is 320000 (#1068). A client that checks it against an exact list of Core versions (`corepc`'s v28 client) no longer matches.
- `decodepsbt`'s `tx.vin` and `tx.vout` are arrays, not counts (#1296). A client that read the counts should take the arrays' lengths, or `inputs` and `outputs`.
- `getchaintxstats` with no `nblocks` measures one month of blocks (4320), not 30 (#1297). A client that wanted the recent rate should pass `nblocks` itself.
- A peer that relays invalid transactions is no longer disconnected or banned for it, as in Core v30 and later. An operator who relied on satd banning such peers can ban them with `setban`.

- Fee estimates (#1200, #1254): the default on `estimatesmartfee`, `estimatefees`, Esplora, Electrum, MCP and the status page comes from the new estimators, and is lower than 0.7's in a calm market. `estimatefees` in `blend` mode no longer answers from the mempool simulator; ask for `mempool` mode to keep it. A node with no fee history and no mempool side yet (the first six blocks after a cold start) has `estimatesmartfee` return Core's `errors` answer instead of a feerate; a client must read `feerate` as optional, as it must with Core. `estimatefees` (and the MCP fee tool) leaves out `economy_feerate` when it would be 0, which only a zero relay floor allows. Target 1 is answered for 2 blocks and `blocks` says so. `errors` is absent from a successful answer. Each answer carries a new `estimator` field.
- Every RPC `asm` field is now in Core's format (#1265). A script that parsed satd's `OP_PUSHBYTES_<n>`, `OP_0`, `OP_PUSHNUM_<n>`, `OP_CSV` or `OP_CLTV` tokens must read Core's instead; one written for Core needs no change.

- **Building from source** now also needs **cmake** and the **Boost headers,
  1.74 or later** (`apt install libboost-dev`, `brew install boost`; header-only,
  nothing is linked). `libbitcoinkernel-sys` builds Bitcoin Core's kernel with
  them. A static musl build through cargo-zigbuild must also point that cmake
  build at zig and pass `-UNDEBUG`, since zig defines `NDEBUG` at `-O2` and Core
  refuses to build without assertions; `release.yml` shows how.
