# satd 0.7.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.7.0 is the next minor release on the 0.x line. Fixes for 0.6.0 ship as
0.6.x patch releases from the `release/0.6` branch.

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- **Bitcoin Core's ZMQ notifications.** `-zmqpubhashblock`, `-zmqpubhashtx`,
  `-zmqpubrawblock`, `-zmqpubrawtx` and `-zmqpubsequence` publish Core's
  messages byte for byte, so LND's `bitcoind` backend, Umbrel's Bitcoin apps
  and other ZMQ consumers can run against satd unchanged
  ([details](#bitcoin-core-zmq-notifications)).
- **Package CPFP in `submitpackage`.** A child can pay for a parent below
  the relay floor or the rolling minimum fee, as in Core, so a Lightning
  commitment transaction signed at a feerate the mempool has since passed
  can still be closed on chain through satd
  ([details](#mempool-policy)).
- **TRUC (version 3) transactions.** satd enforces BIP 431's
  topology and size limits, with sibling eviction, as Core does. Lightning
  channels that use TRUC commitments rely on them to stop a counterparty
  pinning a force close ([details](#mempool-policy)).

## Bitcoin Core ZMQ notifications

satd now publishes Bitcoin Core's ZMQ topics. Until now it skipped the
`-zmqpub*` options with a warning and offered only its own event envelope,
which left out every application written against Core's ZMQ: LND in
`bitcoind` mode, which needs `rawblock` and `rawtx`; Umbrel apps that take
Core's ZMQ ports; pool software waiting on `hashblock`; mempool visualisers
built on `sequence`.

**Configuration** is Core's. The five address options are multi-valued and
each value is a notifier; topics on the same address share a socket;
`unix:<path>` binds a Unix socket (and satd also takes `ipc://<path>`);
`-zmqpub<topic>hwm` sets the high-water mark (default 1000, 0 for no limit).
`getzmqnotifications` lists the notifiers in Core's shape, and `help` shows
Core's `== Zmq ==` category. `-debug=zmq` turns on the publisher's debug
logging. All ten options take effect at restart.

**What is the same as Core.** Every message is Core's, byte for byte: the
topic, the body (a hash in display order, a transaction or block in its
witness serialization, or a `sequence` record) and the notifier's sequence
number. Each event publishes Core's messages in Core's order: a connected
block's transactions on `hashtx`/`rawtx` and `sequence C`, then `hashblock`
and `rawblock` for a new tip outside initial block download; a disconnected
block's transactions and `sequence D`; a mempool admission's `hashtx`,
`rawtx` and `sequence A`; any other mempool removal's `sequence R`. `A` and
`R` carry the mempool sequence number `getrawmempool(false, true)` reports,
so a consumer can line the stream up with a snapshot. A reorg announces each
block from the first one with more work than the old tip, as Core does;
`invalidateblock` announces none. As on Core, an address that
cannot be bound turns ZMQ off without stopping the node, and an address with
an invalid port stops it at startup with Core's message.

**What is different.** satd publishes block-derived messages in chain order
and mempool-derived ones in the mempool's order, but promises no order
between the two groups; Core puts all of them in one order. Applications that
open one socket per topic, as LND and Umbrel's apps do, cannot tell: two
sockets have no order between them on Core either. An application that
rebuilds a mempool from `sequence` alone should use the streaming API, which
remains satd's recommended interface for anything new. Blocks connected
during initial block download or `-reindex` publish nothing, a subscriber
also loses messages past 256 MiB queued, and a few address forms are not
supported. The [Operator Manual](https://epochbtc.github.io/satd/streaming.html#bitcoin-core-zmq-compatibility)
states the guarantee and `CORE_DIFFERENCES.md` lists every difference.

The messages travel over a ZMTP 3.0 publisher built into satd, tested
against libzmq (pyzmq) and LND's own ZMQ client. The ZMQ library behind
`-eventszmqbind` was not usable for this: it delivers the last part of a
large message only with the next message to the same subscriber, so LND
would have seen each block one block late.

A new PR-gating canary runs LND in `bitcoind` mode against satd, with
`rawblock` and `rawtx` on separate ports as Umbrel lays them out. LND checks
`getzmqnotifications` at startup and refuses to run without both topics; the
canary then checks that LND sees a payment made outside it while it is
still unconfirmed, and confirms it after exactly one more block. Of the
seven sub-tests in Core's own `interface_zmq.py`, five pass against satd;
the other two stop where they assert the order between a reorg's blocks and
the transactions it returns to the mempool.

`/metrics` gains `satd_zmq_messages_total{topic}`, `satd_zmq_subscribers`,
`satd_zmq_subscriber_drops_total`, `satd_zmq_events_lagged_total`,
`satd_zmq_rawtx_unavailable_total` and `satd_zmq_block_read_failures_total`,
exported while the publisher runs.

`-eventszmqbind` is unchanged. Its `hashtx` and `hashblock` topics keep
Core's wire format but not Core's per-event content; use `-zmqpub*` for Core
semantics.

## Streaming Consumption API

- **No events lost in a deep reorg.** A reorg sends its whole run of events
  at once: a marker, every disconnected block and every connected block. The
  chain-event channel held 64, so a reorg of more than about 30 blocks could
  overflow it before the event bus read it, and streaming subscribers missed
  blocks with nothing to show for it. It now holds 1024.
- **A package's parent is announced before its child.** A zero-fee parent
  admitted by `submitpackage` on the strength of a child that sweeps its dust
  output had its `Enter` emitted after the child's, so a subscriber saw a
  transaction spend one it had not been told about yet. The parent's `Enter`
  now comes first, as Core announces a package, on the mempool stream and on
  ZMQ alike. It still carries the sequence number it took, and a parent that
  is removed again because its child was refused is still never announced.

## Block validation

- **A custom signet syncs past height 50,000.** Every signet shares the
  default signet's genesis block, and satd applied the default signet's
  built-in checkpoints to a custom signet (`-signetchallenge`) as well. The
  custom chain's block at height 50,000 failed as a checkpoint mismatch, and
  the node stopped there; the only way past was `-checkpoints=0`. A custom
  signet now has no built-in checkpoints, and no default assumevalid block
  either, as in Core, where only the default signet has one. The default
  signet keeps both.
- **Contextual header rules on every path.** A header's timestamp must be
  above its parent's median time past and at most two hours ahead of the
  node's clock, and its version must meet the BIP 34/66/65 minimums. satd
  checked these only for a block arriving through `submitblock` or a `block`
  message. Headers from a `headers` message, and blocks stored during initial
  block download, skipped them. Like Core's `AcceptBlockHeader`, satd now
  checks them before a header enters the block index, before a block is
  stored, and again when a block is connected, which also covers blocks
  indexed by a reindex or by an earlier satd. A header refused only for
  being ahead of the clock no longer counts against the peer that sent it,
  as in Core.
- **Transaction rules before a block is stored.** Every transaction's
  context-free checks, locktime finality (`bad-txns-nonfinal`) and the BIP 34
  coinbase height (`bad-cb-height`) used to be checked only when the block
  was connected. A side-chain block that broke them was written to disk, and
  `submitblock` answered `inconclusive`. They are now checked before the
  block is written, as in Core's `AcceptBlock`: the block is refused with
  Core's reason, and a header announced for it is marked invalid, so the
  node stops asking peers for the block.
- **`-assumevalid` skips scripts only under Core's conditions.** satd skipped
  script verification for any block at or below the assumevalid block's
  height. It now skips a block only when it is an ancestor of the assumevalid
  block, on the best-header chain, under a best header with at least the
  minimum chain work, and more than two weeks of proof of work deep, as Core's
  `ConnectBlock` does. Side-chain blocks below the assumevalid height, and the
  last two weeks before the best header, are verified in full. The log
  reports each change in the decision with Core's "Enabling/Disabling script
  verification" line. When the best header is on a branch without the
  assumevalid block, satd verifies every block, which is stricter than Core.
- **`-minimumchainwork` takes effect.** It was accepted and ignored. It now
  replaces the network's minimum chain work, which gates the `-assumevalid`
  skip and header announcements. A value Core refuses stops the node with
  Core's message.
- **BIP 30 as Core checks it.** satd skipped the BIP 30 duplicate-coinbase
  check for every block above the BIP 34 height on mainnet and testnet3. Core
  skips it only on a chain whose block at the BIP 34 height is the known one,
  and checks it again from height 1,983,702, where coinbases from before
  BIP 34 start to carry valid heights. satd now does both. Testnet3 is past
  that height, so a testnet3 node now runs the check on every block, as Core
  does. Mainnet is unaffected until that height.
- **A failed `invalidateblock` leaves the node on a valid tip** (#977).
  `invalidateblock` on a block of the active chain disconnected the branch
  and reconnected a competing one as a single reorg. If a block of the
  competing branch failed, the reorg was rolled back to where it started: the
  tip the node had just marked invalid. The node then stood on it, and
  refused every block extending the real best chain until a restart. As in
  Core's `InvalidateBlock`, satd now first disconnects down to the
  invalidated block's parent. A competing branch that fails to connect then
  leaves the node on the parent, with the failing block and its descendants
  marked invalid.

## Peers

- **A peer that sends an invalid block is disconnected.** A block refused
  outside initial block download was logged with no penalty for the peer that
  sent it. A block stored during initial block download that failed when it
  connected was marked invalid, but its sender was never identified. Both are
  now charged as Core's `MaybePunishNodeForBlock` charges them: the peer is
  disconnected and banned, except that a `noban` or manual peer is kept and
  a local one is only disconnected, as for any other misbehaviour. A block
  rebuilt from a compact block, one refused only for a timestamp ahead of the
  node's clock, and one this node could not store are not charged (#544).
- **A peer stalling initial block download is disconnected** (#972). When a
  peer held blocks for 15 seconds without delivering one, satd took them back
  but left the peer connected and eligible, so it could be handed the same
  blocks again at once. Blocks it was still sending arrived unrequested, and
  the stall erased the record that kept it away from heights it had failed
  on. As in Core, the peer is now disconnected. Each disconnect doubles the
  timeout for the next peer, up to 64 seconds, and connected blocks bring it
  back to 15, so a node whose own connection is slow does not drop its peers
  one after another. A block handed to another peer is now timed from that
  peer's request, so the new peer is not charged for the previous one's
  delay. A peer is judged stalling, or charged for a block it was slow to
  deliver, only while another peer has delivered a block within the
  timeout: when none has, the silence is more likely the node's own link,
  and a Wi-Fi drop of a minute or so used to disconnect every peer, leaving
  the node to redial from scratch. Core's stall detection likewise needs
  another peer waiting on the staller. A peer that delivers nothing for ten
  minutes is disconnected even then, as by Core's block download timeout,
  so a node whose peers are all dead does not keep them.
- **A node with a stale address book seeds itself** (#974). DNS and fixed
  seeds were tried only at startup, and only when the address book had
  nothing reachable. A node back after a long time offline, whose
  `peers.dat` held only dead addresses, never seeded and could stay at zero
  outbound peers until someone restarted it with `-forcednsseed`. As in
  Core, the node now tries its book first and queries the DNS seeds if it
  has fewer than two full-relay outbound peers 11 seconds in (5 minutes with
  a book of 1,000 or more addresses). The fixed seeds follow a minute in if
  the book still has nothing reachable. Core queries the DNS seeds three at
  a time; satd queries them together.

## Block relay

- **The tip is announced after a catch-up.** When satd falls far enough
  behind its peers' headers, it catches up through its parallel block
  download, and the blocks connected that way were never announced. A peer
  that hears of blocks only from satd and does not poll for headers, which
  is how Core behaves, stayed at the height it had when the catch-up began
  until another block was found. A burst of blocks mined faster than satd
  could relay them one by one was enough to start it. satd now announces the
  tip when the catch-up ends, as Core announces each new tip.

## Privacy

- **`-onlynet` takes effect.** It was parsed and never applied, although the
  manual said it restricted networks. With `-onlynet=onion` and no Tor
  proxy, a node dialled clearnet peers from the operator's own address. It
  now restricts automatic outbound connections, and the gossiped addresses
  the node keeps, to the named networks, as in Core. Inbound and manual
  connections are not affected. As in Core, startup refuses `-onlynet=onion`
  without a Tor proxy (`-proxy` or `-onion`; satd, unlike Core, cannot reach
  Tor through `-listenonion` alone) or with `-onion=0`,
  `-onlynet=cjdns` without `-cjdnsreachable`, and an unknown network name.
  DNS seeding is off when `-onlynet` leaves out IPv4 and IPv6, and an
  explicit `-dnsseed=1` with such an `-onlynet` is refused. satd has no I2P
  transport, so `-onlynet=i2p` is refused as Core refuses it without
  `-i2psam`.
- **`-proxy` turns listening off by default**, as in Core: "to protect
  privacy, do not listen by default if a default proxy server is specified".
  A node behind a Tor proxy was reachable on clearnet. A `-bind` or an
  explicit `-listen=1` keeps it listening, and `-listen=0` also turns off
  `-listenonion` unless that is set too.
- **`-proxy=0` and `-onion=0` mean what they mean in Core**: no proxy, and
  never reach `.onion`, not even a manual peer through `-proxy`. satd used the
  value `0` as a proxy address.
- With `-proxy` and an `-onlynet` that leaves out onion, satd's built-in
  bootstrap seeds (all `.onion` under a proxy) are unusable; the node warns
  at startup and needs `-seednode` or `-addnode` peers.

- **The onion address survives a restart** (#973). satd created its hidden
  service with Tor's `DiscardPK` flag, so Tor never handed back the key and
  every start made a new service at a new address. Peers kept gossiping the
  dead one, and an operator could not publish a stable address. As in Core,
  the key is now saved to `onion_v3_private_key` in the network's data
  directory, readable only by the node's user, and given back to Tor at the
  next start. A node upgrading gets one more new address, then keeps it.
- **Files satd creates are readable by its own user only.** Core sets
  `umask(077)` at startup; satd did not. The data directory was created
  0755, and `mempool.dat`, `peers.dat` and the ban list 0644, readable by
  every account on the machine. `mempool.dat` marks the node's own
  transactions as unbroadcast, and `peers.dat` holds its peers. New
  directories are now 0700 and new files 0600. The RPC cookie still follows
  `-rpccookieperms`. Existing files keep their modes until rewritten.
- **`-externalip` takes an onion address** (#973). Core's manual
  hidden-service setup configures the service in `torrc`, and tells the
  node its address with `-externalip=<address>.onion`. satd refused that at
  startup. It now accepts a v3 onion address, with or without a port, and
  advertises it when the node has not created a hidden service of its own.
- **The hidden service comes back after Tor restarts** (#973). Tor removes a
  service when the control connection that added it closes. satd connected
  to the control port once, at startup: a Tor that was not up yet, or that
  restarted later, left the node without a hidden service until satd was
  restarted, and the node went on advertising the dead address to peers and
  in `getnetworkinfo`. As in Core, satd now withdraws the address when the
  connection closes and reconnects, waiting 1 second and then half as long
  again each time, up to 10 minutes, and adds the service again with its
  saved key, at the same address. An onion `-externalip` is advertised
  while the node's own service is down. Unlike Core, satd also retries when
  authentication or `ADD_ONION` fails.

## Health and readiness

- **Unknown soft forks are reported** (#976). Core warns when the network
  activates a version-bits soft fork the node does not know about. That is
  how an operator running old software learns that the network has moved
  on. satd never did. It now runs Core's check after each new tip outside
  initial block download, on every version bit, with Core's thresholds (90%
  of a 2016-block period on mainnet, 75% on the test chains) and its
  starting heights. A bit that is locked in is logged. An active one adds
  "Unknown new rules activated (versionbit N)" to the `warnings` of
  `getblockchaininfo`, `getmininginfo` and `getnetworkinfo`, and fires
  `-alertnotify`.

- **`/readyz` notices a node that has lost its peers** (#979). Readiness
  checked only that the block connector had not given up and that the tip
  was within six blocks of the best header. A node with no peers hears of no
  new headers, so it showed no lag and answered 200 while its tip aged, and a
  load balancer kept sending it clients. `/readyz` is now also 503 while the
  `tip_stall` detector (no block for `-alerttipstallseconds`, an hour by
  default) or the `peer_floor` detector (fewer than `-alertpeerfloor` peers,
  three by default, held for a minute) is raised. The 503 body names which.
  Both thresholds are `0` on regtest; set either to `0` to leave it out of
  readiness.

## Address relay

- **`getaddr` is answered as Core answers it.** satd answered every peer's
  `getaddr`, outbound peers' included and as often as they asked, with its
  live connection list, inbound and onion peers included and stamped with
  their connect time, and with its own addresses. Any peer could map the
  node's connections, and link its onion and clearnet addresses. It now
  answers only inbound peers, once per connection, with a random sample of
  at most 23% of its address book (at most 1,000), cached for about a day
  per listening socket, so the onion and clearnet listeners' answers differ
  and repeated requests learn nothing new. A peer with the `addr` permission
  gets a fresh sample. `-externalip` addresses, which used to ride only in
  those replies, are announced to outbound peers on the same IP family when
  the connection opens, as Core announces its local address.

## Block serving

- **A pruned node no longer claims to be a full node.** satd advertised
  `NODE_NETWORK` with `-prune` set, so peers syncing from it asked for blocks
  it had deleted. Like Core, a pruned node (either `-prune` form) and a node
  still downloading history behind an AssumeUTXO snapshot now advertise
  `NODE_NETWORK_LIMITED` without `NODE_NETWORK`. Every node sets
  `NODE_NETWORK_LIMITED`, as Core does, so `getnetworkinfo` on an unpruned
  node reports `localservices` `0000000000000409` (with `NODE_P2P_V2` and
  `NODE_COMPACT_FILTERS` when those are on), and the node's own address goes
  out with the same flags.
- **Blocks are served as Core serves them.** satd answered a `getdata` for
  any block it held. A peer could ask for side-branch and invalidated blocks
  to learn which ones a node had seen, and could ask a pruned node for older
  and older blocks to find how far back it kept them, either of which tells
  one node from another. A block off the active chain is now served only if
  the node validated it and it is less than 30 days older than the best
  header, by timestamp and by the proof of work on top of it, and a request
  for any other is ignored, as in Core's `BlockRequestAllowed`. A pruned node
  disconnects a peer that asks for a block more than 290 below its tip,
  unless the peer has the `noban` permission, and its `getblocks` answer
  stops 282 blocks below the tip, as in Core.

## Mempool policy

- **`submitpackage` does package CPFP** (#984). A parent below the relay
  floor or the rolling minimum fee was refused even when its child paid
  enough for both, unless it was a zero-fee parent with one ephemeral dust
  output. That broke Lightning's force close: a commitment transaction's
  feerate is fixed when it is signed, and once mempool fees rise past it
  only an anchor spend paying for both can get it mined. As in Core's
  `AcceptPackage`, a member refused on its own only for its feerate is now
  judged with the child that pays for it, by the package's combined
  feerate. The members share one `effective-feerate` and list each other in
  `effective-includes`. A package whose combined feerate is short is
  refused on the child, with Core's `min relay fee not met` or
  `mempool min fee not met` and the package's numbers. Each parent keeps
  the reason it was refused for on its own. Also as in Core:
  - nothing is evaluated together once any member is refused for a reason
    no feerate changes;
  - the members go in without making room for each other, and the pool is
    trimmed once the whole package is in. A member the trim takes is
    reported as `mempool full`;
  - eviction ranks a transaction by its descendant score, the higher of its
    own feerate and that of it with its descendants, so a parent leaves
    with the child that pays for it rather than ahead of it;
  - an ephemeral dust parent's child now pays for both at the floors, where
    satd asked it to pay only for itself.

  Not as in Core: a parent below the floors that would replace a mempool
  transaction is refused (Core's package RBF), and the parent is not
  relayed to satd peers as a package (Core's 1-parent-1-child relay). Core
  peers fetch it from satd as the parent of the child they were sent.

  Core's `mempool_limit.py` now runs unmodified in the functional-test
  harness.

- **TRUC (BIP 431) policy for version 3 transactions** (#1020). satd took
  version 3 as a standard version and applied none of BIP 431's rules to it,
  so it accepted, relayed and mined version 3 transactions that Core refuses.
  Lightning's TRUC commitment transactions rely on those rules: a
  counterparty can attach only one small child to a shared transaction, so
  it cannot pin a force close behind a large, low-feerate descendant. As in
  Core's `policy/truc_policy.cpp`, an unconfirmed version 3 transaction now:
  - has at most one unconfirmed parent and one unconfirmed child, so no
    grandchildren and no second child;
  - is at most 10,000 vbytes, and at most 1,000 vbytes when it has an
    unconfirmed parent, both sigop-adjusted;
  - spends only unconfirmed version 3 outputs. A transaction of any other
    version may not spend an unconfirmed version 3 output;
  - is replaceable whether or not it signals BIP 125.

  A second child of a version 3 parent may instead evict the first, with no
  input in common, if it pays for the replacement under the usual RBF rules
  (sibling eviction). A refusal on those grounds says
  `insufficient fee (including sibling eviction)`. Everything else is
  refused with `TRUC-violation` and Core's detail. The rules apply to
  `sendrawtransaction`, `testmempoolaccept`, transactions from peers and
  `submitpackage`. In a package, a member tried on its own may evict a
  sibling. Members judged together may not, and a violation among them is
  reported in `package_msg`, as Core reports it. Transactions a reorg
  returns to the mempool are not held to the rules, since the block they
  left may have broken them, and `mempool.dat` reloads are. Moving the
  replacement checks after the fee floor, in Core's order, also means a
  replacement below the floor is now refused for its fee rather than by the
  replacement rules.

  Core's `mempool_truc.py` passes in full and is in the harness's run set,
  with the package `testmempoolaccept`, cluster limits and RBF changes
  below.

- **Cluster limits** (Core v31's `-limitclustercount` and
  `-limitclustersize`). A transaction is refused as `too-large-cluster` when
  the unconfirmed transactions connected to it through spends, in either
  direction and itself included, would number more than
  `-limitclustercount` (default and maximum 64) or come to more than
  `-limitclustersize` kvB (default 101, sigop-adjusted). satd counted only
  the transaction's ancestors and left out the transaction itself. So a
  parent could gain any number of children, and a chain of 65 got in at the
  default of 64. `-limitclustersize` was an unknown option, which refused to
  start. It also moves the `-maxmempool` floor, as in Core: room for 40
  clusters of that size. A replacement is counted without what it evicts.
  Transactions a reorg returns to the mempool are not held to the limits:
  Core admits them and trims oversized clusters afterwards, and satd does
  not trim, so it keeps them.

- **Replacements in larger clusters.** satd built RBF feerate diagrams only
  for a conflict with at most one in-mempool parent or child. Anything
  larger, such as one of several children of a cheap parent, or a conflict
  in a longer chain, fell back to a per-conflict rule. That rule weighed the
  replacement with its unconfirmed ancestors but each conflict on its own.
  It refused bumps Core accepts: replacing one child of a cheap parent with
  two children improves the parent's cluster, but against the child alone
  the replacement and its parent looked worse. It also accepted
  replacements that evict a conflict's high-feerate child, which Core
  refuses. satd now compares the diagrams of every cluster the replacement
  touches, before and after, as Core v31 does. As in Core, a replacement
  that would take its cluster past the cluster limits is refused as
  `replacement-failed, cluster size limit exceeded`.

  This is not only a fix: it changes outcomes in both directions. Bumps
  Core accepts now pass, and some replacements satd used to accept are now
  refused, such as one that evicts a well-paying child. Wallets that bump
  a transaction with unconfirmed descendants may see a refusal where they
  did not before; the same replacement is refused by Core v31.

  The order within each cluster is an approximation of Core's. satd
  linearizes greedily by ancestor-set feerate, then merges that order with
  the cluster's existing one, so a replacement's diagram is never worse
  than either. Core searches for an optimal order. The two agree on small
  clusters, but on large or tangled clusters satd and Core can still
  disagree about a replacement at the margin (see
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md)).

- **A multi-transaction `testmempoolaccept` is evaluated as a package.**
  satd checked each transaction against the mempool alone. A transaction
  spending an earlier one in the same call was refused as `missing-inputs`,
  the TRUC package checks never ran, and one transaction's failure did not
  stop the rest being judged. As in Core's `AcceptMultipleTransactions`:
  - each transaction is checked in order, and may spend an earlier one;
  - replacing a mempool transaction is refused as
    `bip125-replacement-disallowed`, and TRUC sibling eviction is off;
  - a TRUC violation or `too-large-cluster` over the set is every
    transaction's `package-error`;
  - a child must spend all of its parents' ephemeral dust;
  - the first refusal ends the evaluation, and the transactions after it
    are returned with only their ids.

  Each transaction is still judged by its own feerate, as in Core.
  `txn-already-known` now also carries `reject-details`, as Core gives for
  every refusal but `missing-inputs`. Core's `mempool_truc.py` and
  `mempool_package_limits.py` now pass and are in the harness's run set.

- **Core's script policy.** satd verified a transaction's scripts under the
  block's consensus flags only, and had none of Core's checks on what a
  transaction spends. It accepted, relayed and put in block templates spends
  that Core holds out of its mempool:
  - spends of soft-fork upgrade hooks: unknown witness versions, unknown
    taproot leaf versions, `OP_SUCCESS` opcodes, upgradable `OP_NOP`s and
    unknown tapscript public key types. A soft fork that gives one of these a
    meaning can make such a spend invalid, and a node that mines it then
    mines an invalid block;
  - scripts that break Core's other policy flags: high-S or non-strict
    signatures, non-minimal pushes and `IF` arguments, a dirty stack, a
    non-null failing signature, an uncompressed key in segwit v0;
  - spends of outputs of no type Core recognises, P2SH redeem scripts with
    more than 15 signature checks, and transactions whose inputs hold more
    than BIP 54's 2500 legacy signature checks, which are expensive to
    validate;
  - bloated witnesses: a P2WSH script over 3600 bytes, more than 100 stack
    items or one over 80 bytes, a taproot annex, a tapscript stack item over
    80 bytes, or any witness on a pay-to-anchor or non-witness spend;
  - transactions with a sigop cost above 16000, a fifth of a block's.

  The mempool now runs Core's `PolicyScriptChecks` under Core's
  `STANDARD_SCRIPT_VERIFY_FLAGS` on satd's Rust script engine, whichever
  engine `-consensus` selects (the C++ library takes consensus flags only),
  after the configured engine has checked the scripts under the block's
  flags. It refuses what Core refuses with Core's reject reasons:
  `mempool-script-verify-flag-failed (...)`, `bad-txns-nonstandard-inputs`,
  `bad-witness-nonstandard` and `bad-txns-too-many-sigops`.
  `testmempoolaccept`, `submitpackage` and a reloaded `mempool.dat` apply the
  same checks. As in Core, `-acceptnonstdtxn` lifts the checks on what is
  spent and how, and not the script flags or the sigop cap. A peer that
  relays a transaction refused only by policy is not penalised, as before.
- **`-bytespersigop` takes effect, and sigops are priced.** satd priced a
  transaction at its vsize alone. Core prices it at the larger of its vsize
  and its sigop cost times `-bytespersigop` (default 20 bytes), so a
  transaction dense in signature checks pays for the share of a block's
  80000 sigop budget it takes, not only for its bytes. A few hundred bytes
  can carry thousands of signature checks: a 134-vbyte spend with 3941
  sigops is 19705 vbytes to Core. satd asked such a transaction for a small
  fraction of Core's fee at the relay floor, for RBF and for eviction, and
  its block template ranked it ahead of transactions paying more for the
  block space they take. satd now uses Core's sigop-adjusted size for every
  mempool feerate, for the `vsize` that `getmempoolentry`,
  `getrawmempool`, `testmempoolaccept` and `submitpackage` report, and for
  the block template's ranking, as Core does. `weight` and a block's weight
  limit are unchanged. `-bytespersigop`, accepted and ignored before, sets
  the factor at startup.
- **Package parents are checked for standardness.** A zero-fee parent with
  an ephemeral dust output, admitted by `submitpackage` on its child's fee,
  skipped satd's output standardness checks. It no longer does.
- **A `prioritisetransaction` delta set ahead of its transaction survives a
  restart** (#981). `mempool.dat` kept the deltas of transactions in the
  pool and dropped the ones waiting for a transaction that had not arrived.
  As in Core, they are now written after the transactions and restored on
  load. The file's version does not change: an older satd reads the new
  file and ignores the deltas.
- **That zero-fee package parent takes its entry time from the node's
  clock** (#981), which follows `setmocktime`, as every other transaction's
  does. It read the system clock, so under a mock time its `time` and its
  expiry were wrong.

## Transaction relay

- **An announced transaction is downloaded once, not once per announcer.**
  satd answered every transaction `inv` with an immediate `getdata` to the
  peer that sent it, and kept no record of what it had already asked for.
  A transaction announced by several peers before it arrived was
  downloaded from each of them, so transaction bandwidth grew with the
  number of peers. satd now schedules downloads as Core's
  `TxRequestTracker` does:
  - each announcement is recorded per peer, and only one request for a
    transaction is outstanding at a time;
  - an outbound peer (or one with `noban`) is asked at once; an inbound
    peer after 2 seconds; an announcement by txid waits a further 2
    seconds while any peer relays by wtxid; a peer with 100 requests
    already outstanding waits 2 seconds more. Among peers whose wait is
    over, outbound ones are always chosen first, and otherwise the choice
    is random, so an attacker cannot arrange to be asked;
  - a request not answered within 60 seconds, answered with `notfound`, or
    left open by a peer that disconnects passes to the next announcer. A
    peer is never asked twice for the same transaction;
  - each peer may have at most 5000 announcements tracked; more are
    ignored, unless the peer holds the `relay` permission;
  - receiving the transaction (accepted, refused or kept as an orphan), or
    seeing it confirmed, forgets every other announcement of it.

  An orphan's missing parents go through the same scheduler, asked of the
  orphan's sender and of every peer that announced the orphan, one at a
  time, rather than requested at once from the sender alone. As in Core
  they wait 2 seconds (fetched by txid) while wtxid peers are connected.
  The waits run on the node clock, so `setmocktime` moves them.

- **A refused transaction is not fetched again.** satd kept no record of the
  transactions its mempool refused, so every peer that announced one got a
  `getdata`, and each copy was validated again, scripts included and with
  the mempool locked. A transaction that fails late and expensively could
  be fed to the node over and over, once per peer and announcement. Like
  Core, satd now remembers the last 120000 refusals until the tip moves,
  does not request or validate them again, and drops an orphan whose parent
  it refused. A refusal for the fee alone is remembered separately, as
  Core's reconsiderable filter, so it is not fetched on its own again but
  can still enter with a child that pays for it. As in Core, a refusal is
  recorded by wtxid, so a peer can still offer the same transaction with a
  valid witness, except where no witness can help (a spend of a
  non-standard output, or of a refused parent).

## RPC

- **`getblock` and `getrawtransaction` answer as Core v31's do** (#978).
  - `getblock` has `strippedsize`, the block's size without witness data,
    and Core v31's `coinbase_tx`: the coinbase's version, locktime,
    sequence, scriptSig and witness reserved value.
  - At `getblock` verbosity 2 each transaction has its `fee`, and at
    verbosity 3 each input its `prevout`. satd rendered verbosity 2 and 3
    alike, with neither. Both come from the block's undo data, as in Core,
    so they are there without `-txindex`.
  - `getrawtransaction` verbosity 2 takes `fee` and `prevout` from undo
    data too. satd looked the spent coins up in the UTXO set and then the
    transaction index, so a node without `-txindex` left both out once the
    coins were spent.
  - A coinbase input shows its `txinwitness`, as in Core.

## Electrum and Esplora

- **A scripthash's history is capped by the work it costs, not only by the
  size of the answer.** Electrum `blockchain.scripthash.get_history` already
  refused a history over 200,000 transactions with `history too large`, but
  it read and resolved the scripthash's entire history first, and
  `get_balance`, `listunspent`, the `subscribe` status and the Esplora
  address stats and UTXO list read it with no cap at all. One request for a
  busy mainnet scripthash, with millions of rows, cost hundreds of MB to
  several GB and millions of point reads; a few in an Electrum batch, or a
  few concurrent Esplora requests, could run the node out of memory, and a
  request timeout did not stop the work.
  - Each of these now counts the history's transactions first, from the
    raw index rows, and stops at the first one past the cap. A history over
    200,000 transactions is refused after reading at most that many
    transactions' rows, however long it is.
  - Electrum: `get_history`, `get_balance`, `listunspent` and `subscribe`
    answer code `2`, `history too large (cap = 200000 entries)`, the error
    `get_history` already used, as ElectrumX and Fulcrum refuse the same
    methods above their `max_history`. A refused `subscribe` is not kept,
    and a subscribed scripthash whose history grows past the cap gets no
    further status notifications.
  - `get_first_use` reads only the scripthash's first block instead of its
    whole history, and is not capped.
  - Esplora: `GET /address/:addr` and `/scripthash/:hash` (the stats) and
    their `/utxo` and `/sse` routes answer 400 `Too many history entries
    (more than 200000 transactions)`, as mempool.space's electrs does above
    its history limit. An `/sse` stream for such a script would never carry
    an event, since its status is no longer recomputed (that recompute read
    the whole history on every block). The paged `/txs` routes were already
    bounded and are unchanged.
  - Under the cap every answer is unchanged, row for row.

## Shutdown

- **Shutdown waits for the RPC calls still running** (#983). The JSON-RPC
  listeners stopped accepting at the shutdown signal, but a call already
  running went on while the node flushed the chainstate, wrote the
  clean-shutdown marker and dumped the mempool. A `sendrawtransaction`
  admitted then was missing from `mempool.dat`, and a `generatetoaddress`
  went on connecting blocks: in one test run the marker recorded height 390
  while mining continued to 2312, the call was never answered, and the node
  exited with its chainstate still open. As in Core's `Shutdown()`, the node
  now waits for those calls before it persists anything, with a quarter of
  what is left of `-maxshutdownsecs`; a call still running at the end of
  that share costs the clean-shutdown marker, not the flush.
  `generatetoaddress` and `generatetodescriptor` (RPC and the MCP tool) stop
  before the next block and return the blocks mined so far; `waitfornewblock`,
  `waitforblock` and `waitforblockheight` return the current tip; a
  long-polling `getblocktemplate` fails with `-9 "Shutting down"`. All as in
  Core.

## Mining

- **`getblocktemplate`'s `mintime` takes the BIP 94 floor at a retarget
  height.** At the first block of a difficulty period, Core's
  `GetMinimumTime` raises `mintime` to 600 seconds before the parent when
  that is above the median time past plus one, and Core applies the same
  floor to `curtime`, on every network. satd advertised the median time past
  plus one as `mintime` and applied the floor to `curtime` only on testnet4.
  On testnet4, which enforces BIP 94, a block stamped at the advertised
  `mintime` at a retarget height failed as a timewarp. `mintime` and
  `curtime` now match Core on every network. The Stratum servers use the same
  value, so a share stamped below the floor is refused as a bad time, and a
  declared Job Declaration job whose `min_ntime` is below it is refused.

## Configuration

- **List options take both sources** (#995). For a repeatable option given
  both on the command line and in `bitcoin.conf`, satd used the command
  line's values *instead of* the config file's. Core merges them, command
  line first, so a wrapper that adds one `-addnode` or `-bind` keeps the
  config file's. satd now does the same for every Core list option: `bind`,
  `whitebind`, `connect`, `addnode`, `seednode`, `rpcbind`, `rpcallowip`,
  `rpcauth`, `whitelist`, `externalip`, `onlynet`, `signetseednode`,
  `signetchallenge`, `debug`, `debugexclude` and `loglevel`. A negation that
  ends the command line (`-noconnect`, `-norpcauth`) still drops the config
  file's values. satd's own list options keep their behaviour: the command
  line's list replaces the config file's.
- **The `getaddr` answer cache follows `setmocktime`**, as Core's does. Its
  expiry was on a clock the mock time does not move.
- **`-maxmempool` below 5 MB is refused at startup** with Core's message,
  `-maxmempool must be at least 5 MB`. Core's floor is room for 40 of its
  largest clusters (101 kvB each), since a smaller pool would trim away a
  package it had just admitted. `0` is still allowed, as in Core.

## Upgrade notes

- **The mempool bounds each transaction's whole cluster** (see Mempool
  policy). A transaction joining a cluster of 64 is now refused as
  `too-large-cluster`, however its relatives are arranged; before, only its
  ancestors counted. Software that hangs many children off one unconfirmed
  parent, as a batch payout spending its own change can, sees the 64th
  refused, as on Core v31.
- **Some replacements satd used to accept are now refused** (see Mempool
  policy, "Replacements in larger clusters"). A replacement that evicts a
  conflict's high-feerate descendants must now improve the whole cluster,
  as on Core v31. The cluster order satd uses is an approximation of
  Core's, so on large clusters the two can differ at the margin.
- **`getblock`, `getrawtransaction` and `decoderawtransaction` drop the
  fields Core does not have** (see RPC). Software reading them must change:
  - `getrawtransaction` no longer has `blockheight`; read the height from
    `getblockheader <blockhash>`.
  - A mempool transaction no longer has `"confirmations": 0`: the field
    is absent, as in Core.
  - At verbosity 2, a mempool transaction has no `fee` or `prevout`, as in
    Core; `getmempoolentry` has its fees.
  - Transactions inside `getblock` no longer carry `blockhash`,
    `blockheight`, `confirmations`, `time` or `blocktime`.
  - `decoderawtransaction` no longer echoes the transaction's `hex`.

- **A node with `-proxy` and no explicit `-listen` stops accepting inbound
  connections**, and without an explicit `-listenonion` it stops publishing
  its hidden service. To keep either, set `listen=1` (and `listenonion=1`).
- **Configs with `-onlynet` may now refuse to start**, with Core's message,
  where they combine options Core refuses (see Privacy).
- **A `-maxmempool` between 1 and 4 now stops the node from starting** (see
  Configuration). Raise it to at least 5.
- **Sigop-dense transactions cost more to relay.** A transaction whose sigop
  cost times 20 exceeds its weight now needs a fee for that larger size, and
  its reported `vsize` grows to match.
- **The mempool refuses non-standard scripts.** A transaction Core's
  mempool would refuse for its scripts or what it spends is now refused by
  satd's too, including one loaded from an existing `mempool.dat`. Software
  that relied on satd relaying such spends must send them to a miner
  directly.
- **A pruned node advertises `NODE_NETWORK_LIMITED` instead of
  `NODE_NETWORK`.** Peers that need the whole chain stop syncing from it, and
  a peer asking it for a block more than 290 below its tip is disconnected.
- **A list option set in both `bitcoin.conf` and on the command line now
  takes both** (see Configuration). Check a command line that repeats a
  `bind`, `rpcbind`, `connect` or `addnode` from the config file: the node now
  gets the union, and a duplicate `bind` or `whitebind` stops startup.
- **New files in the data directory are 0600, and new directories 0700**,
  as in Core (see Privacy). If another account reads satd's files, grant it
  access explicitly. For the RPC cookie, use `-rpccookieperms=group` or
  `all`.
- **Electrum and Esplora refuse scripthashes with more than 200,000
  transactions** for the requests whose cost follows the whole history (see
  Electrum and Esplora): Electrum `get_balance`, `listunspent` and
  `subscribe` (as `get_history` already did), Esplora address stats,
  `/utxo` and `/sse`. A client that queried such a scripthash through those requests
  now gets an error; Esplora's `/txs/chain` pages still serve its history.
- **`-zmqpub*` options now take effect.** A `bitcoin.conf` or command line
  carried over from Bitcoin Core with `zmqpub*` lines was accepted with a
  warning and the lines ignored. They now bind those addresses at startup.
  If a Bitcoin Core node on the same machine still holds them, satd logs the
  bind failure and runs with ZMQ off, as Core would; remove the lines if you
  do not want satd publishing.
