# satd 0.7.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.7.0 is the next minor release on the 0.x line. Fixes for 0.6.0 ship as
0.6.x patch releases from the `release/0.6` branch.

This file accumulates entries as changes land; it is not yet a cut release.

## Highlights

- **Bitcoin Core's ZMQ notifications.** `-zmqpubhashblock`, `-zmqpubhashtx`,
  `-zmqpubrawblock`, `-zmqpubrawtx` and `-zmqpubsequence` publish Core's
  messages byte for byte, so LND's `bitcoind` backend, Umbrel's Bitcoin apps
  and other ZMQ consumers can run against satd unchanged
  ([details](#bitcoin-core-zmq-notifications)).

## Bitcoin Core ZMQ notifications

satd now publishes Bitcoin Core's ZMQ topics. Until now it skipped the
`-zmqpub*` options with a warning and offered only its own event envelope,
which left out every application written against Core's ZMQ: LND in
`bitcoind` mode, which needs `rawblock` and `rawtx`; Umbrel apps that take
Core's ZMQ ports; pool software waiting on `hashblock`; mempool visualisers
built on `sequence`.

**Configuration** is Core's. The five address options are multi-valued and
each value is a notifier; topics on the same address share a socket;
`unix:<path>` binds a Unix socket (and satd also takes `ipc://<path>`);
`-zmqpub<topic>hwm` sets the high-water mark (default 1000, 0 for no limit).
`getzmqnotifications` lists the notifiers in Core's shape, and `help` shows
Core's `== Zmq ==` category. `-debug=zmq` turns on the publisher's debug
logging. All ten options take effect at restart.

**What is the same as Core.** Every message is Core's, byte for byte: the
topic, the body (a hash in display order, a transaction or block in its
witness serialization, or a `sequence` record) and the notifier's sequence
number. Each event publishes Core's messages in Core's order: a connected
block's transactions on `hashtx`/`rawtx` and `sequence C`, then `hashblock`
and `rawblock` for a new tip outside initial block download; a disconnected
block's transactions and `sequence D`; a mempool admission's `hashtx`,
`rawtx` and `sequence A`; any other mempool removal's `sequence R`. `A` and
`R` carry the mempool sequence number `getrawmempool(false, true)` reports,
so a consumer can line the stream up with a snapshot. A reorg announces each
block from the first one with more work than the old tip, as Core does;
`invalidateblock` announces none. As on Core, an address that
cannot be bound turns ZMQ off without stopping the node, and an address with
an invalid port stops it at startup with Core's message.

**What is different.** satd publishes block-derived messages in chain order
and mempool-derived ones in the mempool's order, but promises no order
between the two groups; Core puts all of them in one order. Applications that
open one socket per topic, as LND and Umbrel's apps do, cannot tell: two
sockets have no order between them on Core either. An application that
rebuilds a mempool from `sequence` alone should use the streaming API, which
remains satd's recommended interface for anything new. Blocks connected
during initial block download or `-reindex` publish nothing, a subscriber
also loses messages past 256 MiB queued, and a few address forms are not
supported. The [Operator Manual](https://epochbtc.github.io/satd/streaming.html#bitcoin-core-zmq-compatibility)
states the guarantee and `CORE_DIFFERENCES.md` lists every difference.

The messages travel over a ZMTP 3.0 publisher built into satd, tested
against libzmq (pyzmq) and LND's own ZMQ client. The ZMQ library behind
`-eventszmqbind` was not usable for this: it delivers the last part of a
large message only with the next message to the same subscriber, so LND
would have seen each block one block late.

A new PR-gating canary runs LND in `bitcoind` mode against satd, with
`rawblock` and `rawtx` on separate ports as Umbrel lays them out. LND checks
`getzmqnotifications` at startup and refuses to run without both topics; the
canary then checks that LND sees a payment made outside it while it is
still unconfirmed, and confirms it after exactly one more block. Of the
seven sub-tests in Core's own `interface_zmq.py`, five pass against satd;
the other two stop where they assert the order between a reorg's blocks and
the transactions it returns to the mempool.

`/metrics` gains `satd_zmq_messages_total{topic}`, `satd_zmq_subscribers`,
`satd_zmq_subscriber_drops_total`, `satd_zmq_events_lagged_total`,
`satd_zmq_rawtx_unavailable_total` and `satd_zmq_block_read_failures_total`,
exported while the publisher runs.

`-eventszmqbind` is unchanged. Its `hashtx` and `hashblock` topics keep
Core's wire format but not Core's per-event content; use `-zmqpub*` for Core
semantics.

## Streaming Consumption API

- **No events lost in a deep reorg.** A reorg sends its whole run of events
  at once: a marker, every disconnected block and every connected block. The
  chain-event channel held 64, so a reorg of more than about 30 blocks could
  overflow it before the event bus read it, and streaming subscribers missed
  blocks with nothing to show for it. It now holds 1024.
- **A package's parent is announced before its child.** A zero-fee parent
  admitted by `submitpackage` on the strength of a child that sweeps its dust
  output had its `Enter` emitted after the child's, so a subscriber saw a
  transaction spend one it had not been told about yet. The parent's `Enter`
  now comes first, as Core announces a package, on the mempool stream and on
  ZMQ alike. It still carries the sequence number it took, and a parent that
  is removed again because its child was refused is still never announced.

## Upgrade notes

- **`-zmqpub*` options now take effect.** A `bitcoin.conf` or command line
  carried over from Bitcoin Core with `zmqpub*` lines was accepted with a
  warning and the lines ignored. They now bind those addresses at startup.
  If a Bitcoin Core node on the same machine still holds them, satd logs the
  bind failure and runs with ZMQ off, as Core would; remove the lines if you
  do not want satd publishing.

## About this release

satd is free software under the [MIT License](../../LICENSE).

- **Stability & compatibility** — Tier 1 surfaces (Bitcoin Core-compatible
  JSON-RPC wire shape, CLI flag names/defaults, `bitcoin.conf` keys, on-disk
  layout, Electrum/Esplora surfaces) are governed by
  [`STABILITY_POLICY.md`](../../STABILITY_POLICY.md). satd follows
  [semantic versioning](https://semver.org/spec/v2.0.0.html); while in the
  `0.x` pre-1.0 line, deprecations may be accelerated (see the policy).
- **Security & disclosure** — report vulnerabilities per
  [`SECURITY.md`](../../SECURITY.md). Consensus-affecting bugs are treated as
  P0 with same-day acknowledgement.
- **Verifying this release** — tarballs are signed with minisign, container
  images with cosign (keyless OIDC), and git tags with SSH signatures (no GPG).
  The key matrix and verification steps are in
  [`SECURITY.md`](../../SECURITY.md).
- **Intentional differences from Bitcoin Core** — catalogued in
  [`CORE_DIFFERENCES.md`](../../CORE_DIFFERENCES.md).
- **Operating satd** — observability, the full flag matrix, tuning, and the
  downstream packaging contract live in the
  [Operator Manual](https://epochbtc.github.io/satd/).
