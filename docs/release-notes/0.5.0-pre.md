# satd 0.5.0

> Pre-release — in progress · [Changelog](../../CHANGELOG.md)

satd 0.5.0 is the wallet-backend release (Theme A), headlined by **BIP 352
silent payments**: a node-side tweak index and two ways to consume it — stream
per-block tweaks and scan client-side (the scan key never leaves the device),
or register a scan key and let the node match for you. The index is opt-in
(`silentpaymentindex=1`, default off); nothing changes for a node that does not
enable it.

This file accumulates entries as the feature stack lands; it is not yet a cut
release.

## Highlights

- **Silent payments (BIP 352) — foundation.** A shared BIP 352 kernel now backs
  both the tweak index and the scan-key matcher, so a tweak the node stores and
  a tweak a wallet recomputes are identical by construction. Validated against
  the BIP 352 v1.1.0 test vectors.
- **[A first-party Go SDK](#go-sdk-satdevents)** — `satdevents`, at
  `clients/go/`, in full parity with `satd-events-client` and held there by a
  differential harness that diffs both clients' view of the same node, event for
  event, on every PR.
- **[Three BIP 141 witness rules brought to exact Core parity](#the-bip-141-witness-rules-now-match-core-exactly)**
  — satd accepted blocks Bitcoin Core rejects. Not reachable through honest
  mining, but each was a chain split with satd on the losing side.
- **[The chain tip can no longer stand on blocks that were never
  connected](#the-tip-can-no-longer-stand-on-blocks-that-were-never-connected)**
  — a synced mainnet node served a UTXO set missing eight blocks' worth of
  outputs for five and a half hours while reporting a healthy tip. satd now
  refuses to connect onto a parent it never connected, and refuses to start on
  a tip that stands on a hole.
- **[A reorg and the block connector could destroy each other's
  work](#a-reorg-and-the-block-connector-could-destroy-each-others-work)** — an
  `invalidateblock` on a synced mainnet node and the connector connected the
  same blocks at the same time; the reorg lost, rolled back, and took eight
  blocks the connector had already committed with it. The connector now holds
  the same lock every other chain mutator does.
- **[Median-time-past could be taken from a branch a reorg had already
  displaced](#median-time-past-could-come-from-a-branch-that-had-already-lost)**
  — MTP gates BIP 113 locktimes and BIP 68 sequence locks, so the blocks a reorg
  decides were validated against a median that can accept or reject a
  transaction Bitcoin Core would not. Both reorg paths and the pipelined connect
  path are affected.
- **[A durability hole between block data and the index that references it is
  closed](#a-crash-could-strand-a-blocks-index-entry-over-block-bytes-that-never-landed)**,
  and [`getblockfrompeer`](#getblockfrompeer-repair-a-lost-block-without-a-resync)
  can now repair a datadir that already has one — previously a single lost
  block body meant a full resync.
- **[Bitcoin Core v28+ obfuscated block files are now readable](#storage--core-compatibility)**
  — the documented "reuse a Core `blocks/` directory" migration works against
  modern Core datadirs with no configuration.

## Silent Payments

The kernel lives in a new workspace-internal crate, `node-sp-index`, alongside
the schema codec, backfill-cursor, read trait, and config that the rest of the
stack builds on. It has no daemon wiring yet — enabling the index, serving it,
and matching against it arrive in the following changes.

- **BIP 352 kernel.** Input eligibility and public-key extraction (P2TR with
  NUMS exclusion, P2WPKH, P2SH-P2WPKH, P2PKH including malleated scriptSigs;
  uncompressed keys and future-SegWit spends correctly skipped), the public
  tweak `T = input_hash · A`, and the scan loop (labels, `K_max = 2323` bound).
  The only cryptographic dependency is `bitcoin::secp256k1`, already in the
  tree. Correctness is measured as parity with the official BIP 352 vectors,
  not self-consistency.
- **`sp_tweaks` row format.** One row per block from taproot activation upward,
  present even when empty so row-presence distinguishes "indexed, no eligible
  txs" from "not indexed". Each row embeds the hash of the block it describes,
  making it self-authenticating — readers verify identity without consulting
  the height→hash index.
- **Index write path.** `silentpaymentindex=1` (default off, always compiled —
  no cargo feature) makes `connect_block` stamp one tweak row per block
  at/above taproot activation, in the same atomic RocksDB batch as the
  chainstate, so a served row can never describe a partially-committed block.
  Reorg disconnects remove the row by height; `-reindex-chainstate` rebuilds
  the index from genesis via the normal connect path. Two Prometheus counters
  (`satd_spindex_rows_total`, `satd_spindex_row_removes_total`) report committed
  rows.
- **Deferred backfill.** Turning the index on for an existing datadir does not
  silently leave the pre-flag history unindexed: the node reports the index as
  *not synced* (a `sp_index.complete` marker, cleared atomically whenever a block
  connects with the index off), and `backfillindex silentpayment` walks every
  block from taproot activation to the tip to fill it. The walk reconstructs
  spent prev-output scripts from undo data (no temp column family), anchors to
  the chain tip captured at start, aborts cleanly and cleans up its stale rows if
  a reorg invalidates that anchor, and resumes from its last 1000-block
  checkpoint across a restart or `kill -9`. `pauseindex` / `resumeindex` /
  `cancelindex silentpayment` drive it; `getindexinfo` grows a `silentpayments`
  section (enabled + synced flags, live backfill state, cursor/snapshot
  heights, ETA), and
  a `satd_spindex_backfill_progress_ratio` gauge tracks progress. Both the gauge
  and the ETA measure against the span the walk actually covers — taproot
  activation to the snapshot, not genesis to the snapshot — which on mainnet is
  about a quarter of the chain, so a just-started backfill reads 0.0 and climbs
  from there. The ETA is reported only while a backfill is running: a paused or
  failed cursor has frozen progress, and extrapolating from it produces a
  confident, badly wrong number. Note that `0.0` on the gauge does not mean the
  index is incomplete — an index built inline from a genesis sync needs no
  backfill and stays at `0.0`. Never alert on that gauge alone — the
  `satd_spindex_enabled` / `_synced` / `_backfill_state` gauges added later in
  this release are what tell those cases apart; see
  [Three conditions that used to fail quietly](#three-conditions-that-used-to-fail-quietly).
  A
  from-genesis sync with the flag on needs no backfill — it is complete by
  construction. The serving surfaces (streaming `tweaks` category + JSON-RPC
  `getsilentpaymentblockdata`) land in a later change.
- **What it costs, measured.** The index is bigger than the original design
  estimate, and the manual now carries measurements rather than estimates. A
  full taproot-era index on mainnet (heights 709,632 to 962,151, 252,520 blocks
  holding 187,015,795 tweak entries) is about **13 GB** of row content, not the
  ~4 GB the disk-footprint chapter previously quoted. The reason is that
  eligibility is common, not rare: a transaction qualifies when it pays a
  taproot output and has an input whose public key the protocol can recover, so
  the era averages ~740 eligible transactions per block and a mean row of
  ~54 KB. Recent blocks run nearer 260, which is about **1 GB/year** of growth
  at current usage; the era mean is inflated by the 2023-2024 inscription
  period. Backfilling the whole era took **6 h 46 m** (~10 blocks/s) on a node
  that stayed at the tip and kept serving its other surfaces. That walk is
  bound by CPU, not disk — it does an EC multiply per eligible transaction, and
  ~70% of the elapsed time is per-transaction work. One related correction:
  `tweak_dust_limit` filters far less than the chapter claimed — nothing
  measurable at 330 sat (the taproot dust threshold), about 10% at 546 sat, and
  about two thirds at 0.001 BTC. It is a bandwidth control for subscriptions,
  not a way to shrink the index.
- **The rest of the footprint table was stale too.** While measuring the
  silent-payment row it became clear the neighbouring estimates had drifted
  badly, so the whole table is now measured from one fully-indexed mainnet
  node: `addr_spending_v2` ~256 GB (was ~140), `outpoint_spend` ~186 GB (was
  ~100), `tx_index` ~79 GB (was ~140), and two that were wrong by orders of
  magnitude — `undo` ~74 GB (was "small (rolling)"; satd keeps disconnect data
  for every block, it is not a rolling window) and `coins` ~10 GB (was "~tens
  of MB"). The BIP 158 filter row remains an estimate; the measured node does
  not run `blockfilterindex`.
- **Streaming wire schema.** The Streaming Consumption API schema
  (`satd-events-proto`) gains the messages both silent-payment consumption modes
  ride on. Tier 1 (client-side scan, zero custody) adds a `tweaks` firehose
  category — **bit 8, and deliberately not part of the `categories=0` "all"
  default**, so a pre-existing subscriber never starts receiving tweak volume
  after an upgrade — carrying a per-block `BlockTweaks` body (`TweakEntry` =
  33-byte tweak + optional txid/max-value), plus `tweak_dust_limit` and
  `tweaks_only` subscription knobs for server-side dust filtering and compact
  entries. Tier 2 (scan-key watch, the convenience mode) adds a scan-key watch
  kind — `AddSilentPayments` / `RemoveSilentPayments` control messages, a
  `SetWatchSet.silent_payments` field for atomic whole-set replace, and a
  `SilentPaymentMatched` event that carries the tweak + output counter so the
  client derives the output key offline. The scan secret is a watch credential,
  never a spending key. All of it is additive: the schema version does not bump,
  and a node or client that ignores these surfaces is byte-identical to before.
  Live emit, index-backed replay, the server-side matcher, and the SDK typed
  events and examples arrive in the changes that follow.
- **Tier 1 serving — stream your tweaks.** The `tweaks` firehose is now live on
  the gRPC `Subscribe` stream. On each connected block the node emits a
  `BlockTweaks` (only while a tweak subscriber is attached, so an idle index
  costs nothing on the bus), and a `from_cursor` resume replays the missing
  blocks straight from the index. A **tweaks-only** subscription cold-syncs from
  taproot activation in a single subscription: because every row embeds the hash
  of the block it describes and the fast path is gated on the index being
  complete, that replay is exempt from the 10,000-block replay clamp — a phone
  can catch up ~240k mainnet blocks of tweak data without a height→hash round
  trip. A **mixed-category** subscription keeps the clamp so cursors stay
  ordered. Per-subscription `tweak_dust_limit` (drop entries below a value floor)
  and `tweaks_only` (33-byte tweak alone, no txid/max-value) filter both live and
  replayed events. Asking for `tweaks` on a node with the index off, or
  requesting replay while it is still backfilling, is refused in-band rather than
  served with holes. A read-only JSON-RPC fallback,
  `getsilentpaymentblockdata "blockhash" ( verbosity dust_limit )`, serves the
  same bytes for scripts and integrators not yet on an SDK. The WS/SSE carrier
  and the typed SDK helpers follow in later changes; the server-side scan-key
  matcher (Tier 2) does too.

- **Tier 2 scan-key watch — server-side matching (confirmed path).** A
  constrained client that would rather not scan every block itself can register
  a scan credential and let the node do the ECDH. On the `Watch` stream,
  `AddSilentPayments` (or an atomic `SetWatchSet.silent_payments` replace)
  registers up to 16 targets per connection — each a `(b_scan, B_spend)` pair
  plus optional labels — and the node emits a `SilentPaymentMatched` for every
  output paying one of them as blocks connect. The event carries the output's
  key, value, and the public tweak `T` with its BIP 352 counter `k`, so the
  wallet re-derives the full output key (and hence its spending key) **offline**
  from its own `b_scan` — the node never holds spend authority. Matching
  recomputes from the block and its undo data via the same kernel the index uses,
  so it works with `silentpaymentindex` off, and it does zero extra work on any
  block when no target is registered. The scan secret is disclosed to the node to
  run ECDH — the operator (or anyone who compromises the node) learns *which*
  outputs are yours but can never spend them — so it is held in-memory per
  connection only, wrapped in a zeroize-on-drop buffer, and never persisted or
  logged. The same messages are mirrored on the WS/SSE JSON surface. The typed
  SDK helpers follow in a later change.

- **Tier 2 scan-key watch — mempool (unconfirmed) matching.** A registered scan
  credential now matches payments the moment their transaction is accepted into
  the mempool, not only when it confirms: the node emits a `SilentPaymentMatched`
  with `confirmed = false` on acceptance, and re-emits the same match with
  `confirmed = true` when the transaction lands in a block — exactly the two-phase
  shape the `ScriptMatched` watch already uses. The obstacle was data, not math:
  the default mempool event path keeps only a scripthash and value per prevout,
  which cannot classify input types or extract pubkeys. Rather than make silent
  payments silently depend on an operator raising `streamprevoutmeta` to `full`,
  the node retains the resolved prevout `scriptPubKey`s on each mempool entry
  **only while at least one silent-payment watch is live** — the matcher and the
  mempool share a single lock-free gate counter, so with no scan key registered
  nothing extra is retained and the mempool path is byte-for-byte what it was
  without silent payments. Matching is best-effort, like every mempool watch: a
  scan key registered after a transaction was already admitted matches it only
  once it confirms (the confirmed path and `RescanBlocks` cover the gap), and an
  RBF-replaced or evicted transaction simply never reaches the `confirmed = true`
  re-emit. An unconfirmed match carries no resume cursor — it is not a durable
  chain position — so a reconnecting client resumes from the last confirmed
  event. Mirrored on the WS/SSE surface.

- **Tier 2 scan-key watch — index-accelerated rescan.** Registering a scan key
  and then running a bounded historical `RescanBlocks` is how a fresh wallet
  cold-syncs its silent-payment history. When the tweak index is enabled and
  complete, that rescan now reads each block's tweaks straight from the index
  instead of reconstructing them from undo data and re-running the per-tx
  elliptic-curve math — the same acceleration the `tweaks` firehose replay
  already enjoys. It is gated block by block on the stored row's embedded block
  hash matching the block being scanned; any row that is absent, mismatched, or
  from a still-incomplete index falls back to recomputing that block from undo.
  Because both paths run the identical matching kernel, the fast path can only
  ever change *how fast* a rescan finds payments, never *which* payments — a
  reorg-heavy history rescanned with acceleration on and off yields identical
  matches. With the index off, rescans recompute exactly as before.

- **Tier 1.5 — mempool-time tweak firehose.** The `tweaks` firehose emits one
  `BlockTweaks` per *connected block*; a zero-custody client therefore learns of
  a payment only at confirmation. Tier 1.5 closes that latency gap without giving
  up custody: the node computes the same BIP 352 public tweak `T = input_hash·A`
  at **mempool admission** and emits it as a `MempoolTweak` the instant a
  transaction is accepted, so the client runs its local ECDH against unconfirmed
  transactions too — the scan key still never leaves the device. It is opt-in per
  subscription (`mempool_tweaks`, and like the block firehose it requires the
  `TWEAKS` category bit — never part of the `categories=0` default), and the tweak
  is computed only while a firehose subscriber is attached, so an idle node does
  no extra work and the mempool path stays byte-identical to before. Because a
  mempool tweak is public data with no custody dimension, it is emitted
  best-effort and **ephemeral**: no resume cursor and no index replay (a
  reconnecting client resumes from the last confirmed `BlockTweaks`), and no
  retraction if the transaction is replaced by fee-bump or evicted — the
  block-connect `BlockTweaks` remains the authoritative, durable record. Delivered
  by the SDK as `SubscribeOptions::mempool_tweaks` and typed `Event::MempoolTweak`;
  `sp_light_scan.rs` scans block and mempool tweaks through one shared code path.

- **Tweak events can carry the transaction's taproot outputs.** Each
  `TweakEntry` gains `taproot_outputs` — the transaction's taproot outputs
  (`vout`, 32-byte x-only key, value), the scan candidates a client checks its
  derived `P_k` against. A `MempoolTweak` **always** carries them: an unconfirmed
  transaction has no block to fall back to, so a `getrawtransaction` to recover
  the outputs races eviction/replacement (you can get the signal and then find
  the transaction already gone). Carrying them makes a mempool tweak
  self-sufficient — the client confirms the match in the event itself, with the
  scan key never leaving the device. For `BlockTweaks` the outputs are opt-in per
  subscription (`tweak_outputs`), since the confirmed firehose is meant to stay
  lean and a client scanning confirmed transactions can fall back to the block;
  the node re-derives them at serve time so the on-disk index does not grow and
  no reindex is needed. The outputs are public the moment a transaction reaches
  the mempool, so this discloses nothing new. Delivered by the SDK as
  `TweakEntry::taproot_outputs` and `SubscribeOptions::tweak_outputs`.

- **Rust SDK — both silent-payment modes, typed.** The published
  `satd-events-client` SDK now covers silent payments end to end. Tier 1 (the
  recommended zero-custody mode): a `Categories::TWEAKS` subscription with
  optional `tweak_dust_limit` / `tweaks_only`, delivered as typed
  `Event::BlockTweaks`, plus a runnable `sp_light_scan.rs` example that does the
  client-side ECDH locally — the scan key never leaves the process. Tier 2 (the
  convenience mode): `add_silent_payments` / `remove_silent_payments` on both the
  raw `WatchHandle` and the reconnect-resilient `ResilientWatch` / `WatchSetBuilder`
  (which re-register scan keys automatically after a drop), delivered as typed
  `Event::SilentPaymentMatched`, plus an `sp_wallet.rs` example that re-derives
  each payment's spending key offline from the tweak and counter. The scan-key
  helpers use the crate's default `bitcoin` feature to derive a target's removal
  identity.

### The dashboard shows the tweak index

`sat-tui`'s services row carried `addr-idx`, `esplora` and `electrum`. It now
carries `sp-idx` too, so an operator watching a multi-hour silent-payment
backfill can see it:

```
addr-idx synced   sp-idx backfill 62.4% (835,200/962,151)  ETA 2h 41m   esplora 127.0.0.1:3002   electrum 127.0.0.1:50001
```

Steady state reads `synced` or `syncing`. The backfill is a **single** pass over
the taproot era, unlike the address index's two, so there is no pass counter and
the percentage is a plain cursor/snapshot ratio.

The column is rendered only when the index is enabled, so a node that does not
use silent payments keeps the previous three-column row rather than gaining a
permanently empty placeholder. Making that decision correctly required a new
field: `getindexinfo.silentpayments` now reports **`enabled`** separately from
`synced`. Both are false when the index is off, so `synced` on its own could not
distinguish "index disabled" from "index on but not caught up" — a consumer had
to guess, and guessing wrong labels a disabled index as perpetually syncing. The
flag was already computed internally; it simply was not being emitted.

A satd too old to report `enabled` is treated as "off" and shows no column,
except while a backfill is actually running — a backfill in flight is itself
proof the index is on.

## Index backfills

### The ETA now measures working time, not wall-clock

`getindexinfo` reports an `estimated_remaining_seconds` for each deferred
backfill. It was computed as `(now - started_at) * (1 - r) / r`, where
`started_at` is stamped once when the backfill is first started and then copied
forward across every pause, resume and daemon restart. So "elapsed" was
wall-clock since the job first began rather than time it spent working, and
every idle hour was extrapolated as though the walk had been grinding through
it:

| Scenario | Reported | Actually remaining |
|---|---|---|
| Paused 48h at 10%, then `resumeindex` | 20.25 days | ~54 hours |
| Daemon down a week at 10% | 65 days | ~54 hours |
| Resumed 1h into a mainnet-shaped walk | 45 days | hours |

The estimate is now measured over the current **stint** — the uninterrupted
span since the running backfill last started walking blocks. A stint is
anchored when a runner begins its walk, re-anchored when it returns from a
pause, and dropped when it pauses or exits, so idle time cannot be extrapolated
as work. This is deliberately in-memory state: a persisted counter has to be
flushed periodically or a `kill -9` loses it, and a persisted anchor goes stale
across exactly the crash-and-restart case the fix exists for. The on-disk
cursor format is unchanged, and the fix applies to all three backfills
(`address`, `basic block filter index`, `silentpayments`) through one shared
estimator.

One visible consequence: the field reads `0` for the first few seconds after a
start, a resume, or a daemon restart, while the new stint measures something.
`0` has always meant "no estimate available" here rather than "nearly done" —
`state` and `cursor_height` are the fields to watch during that window.

### Every DB-backed index now tells Prometheus whether it will serve

The silent-payment index gained `enabled` / `synced` / `backfill_state`
gauges mid-cycle; the other two DB-backed indexes were worse off
([#558](https://github.com/epochbtc/satd/issues/558)): the block-filter index
exported no metric of any kind, and the address index exported only an
`enabled` bit and row counters. A failed address backfill takes the Electrum
and Esplora address surfaces offline with **no** Prometheus signal at all; a
failed filter backfill silently takes down BIP 157 serving and
`getblockfilter`.

Both families now export the same readiness shape as the silent-payment
index: `satd_addrindex_synced` and `satd_addrindex_backfill_state{state="…"}`
for the address index, and `satd_filterindex_enabled` / `_synced` /
`_backfill_state{state="…"}` for the filter index. Each `synced` matches the
corresponding `getindexinfo` predicate — it is the serving answer, not the
raw on-disk marker — and every state series is always present, so an alert
on `state="failed"` can be written before it has ever fired. The Operator
Manual's alerting recipes now apply to all three families by prefix
substitution.

### The filter backfill resumes across a restart again

The block-filter backfill persisted its cursor correctly, but the layer every
production read goes through — the coin cache wrapping the store — did not
forward the three filter-cursor read/write methods to the backing store, so
the trait defaults answered instead
([#555](https://github.com/epochbtc/satd/issues/555)). Three consequences:

- A **paused or interrupted filter backfill never resumed** after a restart:
  the persisted `paused` cursor read back as `idle`, the auto-resume check
  never fired, and neither did the "cursor is active but `blockfilterindex=0`"
  warning. Re-running `backfillindex` re-walked from genesis.
- A filter backfill's **failure reason was never persisted** — the write
  landed in a default that returns an error the caller ignores.
- `getindexinfo` **never showed `last_error`** for the filter index.

The address and silent-payment families always forwarded correctly; only the
filter trio was missing. It went unnoticed because the in-memory test store
implements the methods itself, so every test exercised a path production
never takes. The new tests read the cursor through the cache layer — the
path that was broken.

## Alerting & node health

Every body on the streaming API so far described the *chain* or the *mempool*.
None of them described the **node**, so an operator who wanted to know that their
daemon had stalled, filled its disk, or lost its peers had to poll
`getblockchaininfo` on a timer and diff the results themselves.

- **Node-health events are now first-class on the firehose.** A new `status`
  category carries `StatusEvent` bodies for six conditions the daemon detects
  about itself: `ibd_complete`, `tip_stall`, `disk_low`, `mempool_congested`,
  `peer_floor`, and `deep_reorg`. Each event carries a machine-readable `kind`,
  a `severity`, a human-readable `message`, and a `details` map of structured
  fields as strings — mostly decimal numbers (thresholds, counts, byte totals),
  but not exclusively: a `cleared` event can carry a `reason` token such as
  `detector_disabled`. Do not parse the map uniformly as integers.
- **Level-triggered, not edge-spammed.** A standing condition emits exactly one
  `raised` when it is entered and exactly one `cleared` when it recovers, with
  hysteresis between the two thresholds so a value hovering at the line does not
  flap a pager. Conditions with no recovered state — IBD finishing, a deep reorg
  landing — are `edge` and never produce a `cleared`.
- **Opt-in by construction.** The category is **bit 16** and, like the
  silent-payment `tweaks` category, is deliberately excluded from the
  `categories = 0` ("all") default: a subscriber written against an older node
  never begins receiving a body it has no parser for after an upgrade. Unlike
  `tweaks` there is no index prerequisite. Served on the three mask-bearing
  transports — gRPC `Subscribe`/`Watch`, WS, and SSE. It is deliberately **not**
  emitted on the ZMQ `nodeevent` topic: ZMQ has no per-subscriber category mask,
  so putting it there would push a new body shape at every existing `nodeevent`
  consumer. For health over ZMQ, use `alertfile` webhooks or `-alertnotify`.
- **`status` needs `rpc:read` on top of `stream:subscribe`.** Every other
  category describes the chain, which is public; this one describes your host —
  free disk, peer topology, mempool occupancy and `mempoolminfee`, tip height,
  IBD state. That is the content of `getblockchaininfo`, `getpeerinfo`,
  `getmempoolinfo` and `getwarnings`, and the whole point of a separate
  `stream:subscribe` capability is that you can give a wallet backend or a
  tenant a streaming token *without* node read RPC. So a token holding only
  `stream:subscribe` is refused (`PERMISSION_DENIED` / `403`) when it asks for
  bit 16, and a mid-stream category update from one has the bit stripped rather
  than honored. This narrows nothing for a node that has not enabled
  `-authfile`: with no token store the behavior is unchanged, and the operator
  principal (cookie, `rpcuser`, `rpcauth`) holds every capability already.
- **Durability is by re-evaluation, not replay.** A status event carries no
  resume cursor and is excluded from the replay ring, so a `from_cursor` resume
  never yields one. Instead the detectors re-examine every condition at startup
  and re-raise the ones still standing — which is what makes health alerting
  at-least-once across a restart. A condition that both raised and fully cleared
  while a consumer was away is stale by definition and is not reconstructed.
- Additive on the wire: the schema version does not bump, `StatusKind` is an open
  enum, and `details` is a string map, so future conditions and fields ship
  without breaking a deployed consumer.

### One detection, three surfaces

An operator should not have to pick a monitoring style to find out their node is
in trouble. Each detection is reported simultaneously as:

- a `status` event on the streaming API,
- an entry in `getwarnings` (and so in `getblockchaininfo.warnings` and the
  TUI), which also fires the Core-compatible `alertnotify` shell hook,
- a `satd_alert_active{kind="..."}` gauge on `/metrics`.

They are driven from the same state machine, so they cannot disagree: if the
gauge reads 1, the warning is present and the raise event was published.
`satd_alert_active` is pre-registered at 0 for every standing condition from the
first scrape, so a Prometheus rule can reference a series before it ever fires.

Each event carries the numbers behind it in `details` — free bytes and the
watched path, seconds since the last block and the tip height, a reorg's true
depth and fork height, the mempool's current `mempoolminfee` — so an alert is
actionable without a follow-up query. (`ChainEvent::Reorg` does not carry a
fork point, so the detector derives the true depth by counting the reorg's
disconnects rather than reporting the threshold it crossed.)

### Three conditions that used to fail quietly

The principle above — a condition the node detects should reach the operator on
every surface — turned up three places where it did not hold.

**The silent-payment backfill was not alertable.**
`satd_spindex_backfill_progress_ratio` was the only signal the index exported
about its own readiness, and `0.0` on it meant five different things: the index
is off; it was built inline from a genesis sync and is complete without a
backfill ever running; a backfill finished via the below-activation
short-circuit; one has only just started; or one *failed* at or near taproot
activation. So neither `ratio == 0` nor `ratio < 1` identified a problem — the
first alerts on every node with the index disabled, the second on every healthy
from-genesis node, forever. There was no expression over the exported set that
answered "is the backfill stuck or failed", which is the one question the gauge
exists to support.

Three gauges disambiguate all five:

```
satd_spindex_enabled                              1 if the index is on
satd_spindex_synced                               1 if complete on disk
satd_spindex_backfill_state{state="failed"}       1 if the backfill failed
```

`state` carries one series per lifecycle state (`idle`, `running`, `paused`,
`completed`, `cancelled`, `rejected`, `failed`), exactly one of them 1. All
seven are always present, for the same reason `satd_alert_active` pre-registers
at 0: a family that publishes only its active label leaves `state="failed"`
*absent* rather than `0` when healthy, and an alert on an absent series either
needs `absent()` gymnastics or never fires at all.

**AssumeUTXO background validation could stop, silently and permanently.**
Two ways, both fixed.

A connect error ended the catch-up thread for the process while the snapshot
stayed attached and `getchainstates` went on reporting `assumeutxo_rejected:
false` — one log line was the entire trace. It now raises a standing warning,
so it reaches `getwarnings`, the TUI and `-alertnotify`.

The second was quieter and needed no failure at all on the connect path. The
handoff — the UTXO-set hash comparison at the snapshot height — runs only after
a *successful connect*. So if the handoff itself failed on I/O (it flushes coins
and hashes the whole set; either can hit a full disk), the background tip was
already at the snapshot height, no further connect was possible, and nothing
could ever call the handoff again. The loop's own comment said it would "wait
and re-check"; nothing did. It now genuinely retries, and reports the condition
if the retries keep failing.

Neither path marks the snapshot rejected. That marker is a durable "this
snapshot is invalid" verdict, and only the handoff comparison proves it — what
otherwise reaches these paths is storage I/O failure, and a full disk must not
condemn a good snapshot. A snapshot that *is* proven invalid is marked and
reported by the handoff itself, so the new warning stands aside for it rather
than describing it, less accurately, a second time.

**A reader could straddle a cursor write.** The silent-payment, filter and
address backfill cursors were each read with independent per-key lookups while
the runner writes state, cursor height and snapshot height in a single batch.
Harmless mid-run, where only adjacent heights mix — but across a restart it
could pair the previous run's `cursor_height` with the new `snapshot_height`,
reporting a backfill that had just started at zero as 75% complete. The reads
now take a RocksDB snapshot, so every key comes from one sequence number.

The silent-payment cursor is the one a Prometheus scrape reads, so it is where
this was observable; the filter and address cursors are read by `getindexinfo`
and at startup and were fixed alongside it.

### Configuration

Five new thresholds, all hot-reloadable — retuning an alert should not require a
restart, since you are usually retuning it *because* it is firing. Setting one
to `0` disables that detector:

| Key | Default |
|---|---|
| `alerttipstallseconds` | `3600` (`0` on regtest) |
| `alertdiskfreemb` | `10240` |
| `alertmempoolfullpct` | `90` |
| `alertpeerfloor` | `3` (`0` on regtest; capped by the `-connect=` count) |
| `alertreorgdepth` | `3` (`10` on test networks, `0` on regtest) |

Three defaults are network-dependent, all for the same reason: an alert that
fires while the network behaves exactly as designed is one operators learn to
ignore, and that costs them the mainnet alert too.

`alerttipstallseconds` is `0` on regtest. Regtest blocks exist only when
something calls `generatetoaddress`, so an idle chain is its resting state
rather than a stall — and the alert is *critical*, so a node left running for an
hour between test runs would pin `getwarnings`, hold the error flag, and raise
the TUI's blocking modal on a chain doing exactly what it should. Every other
network keeps the hour, test networks included: unlike a shallow reorg, going an
hour without a block is not an ordinary property of thin hashrate.

`alertreorgdepth` is `3` on mainnet, where a reorg that deep costs real hashrate
and invalidates transactions merchants have begun treating as settled. On
signet, testnet and testnet4 it is `10`: those chains are not economically
secured, and reorgs a few blocks deep are an ordinary consequence of thin,
volatile hashrate rather than an incident. It is raised rather than disabled —
past the 6-confirmation convention a wallet has been told something false, and
that is worth reporting on any chain. Regtest is off entirely, since its test
suites reorg on purpose and constantly.

`alertpeerfloor` gets `0` on regtest, because a regtest node normally runs
entirely alone and a permanent critical warning is a poor greeting for a first
run. Every other network — signet included — keeps the floor, since a detector
defaulted off is indistinguishable from a healthy one on the metrics surface.
Set it to `0` explicitly on a deliberately isolated
node.

The floor is a property of the configuration as well as the network, so
`-connect=` lowers it to the number of peers configured. `-connect=` pins the
node to exactly those addresses and suppresses both DNS seeding and the fixed
seeds, so a node given one upstream can never reach a floor of `3` — the
warning would stand forever in `getblockchaininfo.warnings`, which wallet
software renders to end users. Capping rather than disabling keeps the alert
doing the one useful thing it still can here: reporting a `-connect=` node that
had all its configured peers and then lost one. An explicit `alertpeerfloor`
overrides this in either direction. A node that has never seen a peer gets a 90 s startup grace, and the hold
begins when the grace expires or the first peer arrives, whichever is sooner.

`tip_stall` is **not** suppressed during initial block download, which is worth
stating plainly because the opposite would be the obvious design.
`is_initial_block_download()` is a function of the tip's *age*, not a sync-progress
flag, so a node that is fully caught up and then stops re-enters it a day later —
exactly when you want to hear from it — and a node restarted while already wedged
never leaves it, so gating on the flag would silence the alert permanently at the
worst possible moment. Nothing is lost by not gating: a node that is genuinely
syncing connects blocks continuously, which keeps the age far below the threshold
and suppresses the alert on its own. A node that has connected nothing for the
whole threshold is stalled whether it is wedged mid-sync or wedged at the tip.

The stall clock is seeded at detector start rather than from the tip timestamp,
so restarting a node that has been down for hours does not page you for a stall
that is really a restart.

`disk_low` will not take the rest of alerting down with it. `statvfs` on a hard
NFS mount whose server has gone away does not return, and a detector that simply
awaited it would park the entire poll loop: tip stall, deep reorg, mempool and
peer checks would all stop running and every gauge would freeze at its last
value, so even an external Prometheus rule on tip age could not fire. A wedged
mount would silently switch off the whole alerting subsystem — the one condition
alerting exists for. Each poll therefore gives the outstanding probe a bounded
slice and then moves on, carrying the same probe forward rather than starting
another; a filesystem that never answers costs one stuck thread in total and
leaves `disk_low` on its last known verdict, with a log line saying so. Every
other detector keeps running normally.

`deep_reorg` figures are exact. Depth, fork height and the new tip come from
the reorg log record that `perform_reorg` writes and fsyncs, rather than being
reconstructed by counting disconnect events off the event bus. The bus ring
holds 64 entries and a reorg of depth D emits `2D + 2` events in a single
burst, so a counting implementation loses precision — or drops the reorg
entirely — at exactly the depths this alert exists for.

**`deep_reorg` pages, but does not become a standing warning.** It and
`ibd_complete` describe events, not states, so nothing would ever clear them.
They fire `alertnotify` (every occurrence — each reorg is its own event) and
emit their `status` event, but they never enter `getwarnings`. An entry nothing
clears would keep `getblockchaininfo.warnings` non-empty and the TUI's warning
modal open for the life of the process — and on signet and testnet4, where
reorgs several blocks deep are an ordinary part of the chain rather than an
incident, that would happen on the first one and never stop. A reorg's durable
record is the reorg log (`getreorghistory`); the warnings set is for conditions
that are true right now.

Two of the new gauges are worth having independently of alerting:
`satd_tip_last_connect_age_seconds` and `satd_disk_free_bytes` — the latter
omitted rather than reported as zero when the filesystem cannot be
interrogated, and sampled whatever `alertdiskfreemb` is set to, so disabling the
alert does not delete the series out from under a Prometheus rule of your own.
Disk headroom previously had no alerting or metric at all, which is how a silent
disk-fill wedged a node in May.

### Alert webhooks

Health events on the streaming API still require something to be *watching*.
`alertfile=<path>` pushes instead — a TOML file describing any number of signed
HTTP hooks, each filtered by category, kind, and severity floor:

```toml
version = 1

[[webhook]]
id = "pager"
url = "https://alerts.example/satd"
secret = "a-long-random-string"
categories = ["status"]
kinds = ["tip_stall", "disk_low"]
```

- **One wire schema, not two.** The POST body is byte-identical to the JSON a
  WebSocket subscriber receives for the same event, so a receiver parses both
  with one code path. Delivery metadata (`X-Satd-Signature`, `X-Satd-Timestamp`,
  `X-Satd-Delivery`, `X-Satd-Hook`, `X-Satd-Attempt`) rides in headers and never
  in the body — which is what keeps the signature stable across retries and
  makes `X-Satd-Delivery` usable as an idempotency key.
- **The signature covers the delivery metadata, not just the body.** The HMAC is
  taken over `"2" LF timestamp LF delivery-id LF hook-id LF body`. Signing the
  body alone would leave the idempotency key — the value the contract tells you
  to deduplicate on — both unauthenticated and predictable, so anyone holding a
  single captured delivery could replay it under the ids of alerts you have not
  received yet and have your receiver discard the real ones as duplicates. The
  signed timestamp bounds how long a captured delivery stays replayable;
  receivers should reject anything outside a 600-second window.
- **Failure behavior.** Delivery is serial and in-order per hook, with
  exponential backoff to a five-minute ceiling on transient failures. A
  permanent 4xx is counted and skipped rather than retried forever — a receiver
  answering 404 must not pin the queue and convert every later event into a
  drop. Redirects are never followed: a 3xx is a permanent drop, because chasing
  one would carry the signed body to a host the alertfile never named. A hook
  that falls far enough behind **drops events silently** — there is no in-band
  gap notice and no resume cursor, because nothing is persisted to resume from.
  Watch `satd_alertwebhook_dropped_total` if you need to know. Do not read the
  absence of a notice as the absence of a gap; if you need that guarantee, the
  Streaming Consumption API is the surface that offers it.
- **Best-effort by design.** Webhooks are the basic way to automate off chain
  and mempool events — page me, poke a script, ping a dead-man's switch. They
  are not an integration API and deliberately do not try to be one: nothing is
  persisted, a hook that was down resumes at the live head, and events dropped
  by a full queue or a lagging bus are counted in
  `satd_alertwebhook_dropped_total` and logged. Retries cover the one failure
  the surface promises to survive, a receiver that is briefly unreachable.
  Health alerts are the exception and get it for free: the detectors re-evaluate
  at startup and re-raise anything still standing, so a live problem reaches you
  across a restart without any delivery machinery. Anything needing guaranteed
  delivery, resumability, or history uses the **Streaming Consumption API**,
  which is the canonical way to integrate with satd and already does all of it
  properly — real cursors, backpressure, and a bounded `RescanBlocks`.
- **Reloadable.** Hook definitions are re-read on every SIGHUP even when no
  `bitcoin.conf` key changed, so a hook can be added, edited, or removed live.
  A parse error keeps the last-good set — alerting that silently stopped after
  a typo is the worse failure. The file must be mode 0600; it holds signing
  secrets. A reload is a handover, not a restart: a hook whose stanza you did
  not touch keeps its delivery task, so its queue and retry backoff survive.
  Editing one hook does not discard a page that another hook was still
  retrying — which matters because a status event has no replay behind it and
  the detector that raised it will not raise it twice.
- Per-hook counters are exported (`satd_alertwebhook_delivered_total`,
  `_failed_attempts_total`, `_dropped_total`, `_queue_depth`,
  `_last_success_age_seconds`), and a node with no alertfile exports none of
  them.

**`reorgwebhook=` is absorbed, not replaced.** The existing keys keep working
and their payload, headers, and retry schedule are unchanged byte for byte — `ChainEvent::Reorg` does not
carry the `depth`, `fork_height`, or disconnected/reconnected lists that a
`ReorgRecord` does, so re-shaping it would have silently broken deployed
receivers. It is now served by the new dispatcher, which also moves that
outbound HTTP off the consensus runtime, where it should never have been. It
keeps reporting `X-Satd-Webhook-Version: 1` — the body-only signature and the
absence of a delivery id are part of what deployed receivers already verify —
while alertfile hooks report `2`. New deployments should prefer an `alertfile`
hook with `categories = ["chain"]`.

> **Upgrade note for `reorgwebhook=` users.** One behavior does change:
> redirects are no longer followed. A receiver that answers `3xx` — an
> `http`→`https` reverse-proxy hop, a trailing-slash redirect — now has its
> record retried three times and then dropped with a warning in the log (the
> legacy path deliberately keeps its original retry-any-non-2xx behavior),
> where the old dispatcher would have chased up to ten hops. Point the key at
> the final
> URL. This is deliberate: following a redirect hands a signed body, and the
> node's identity with it, to a host the operator never named, and the useful
> targets for that are exactly the ones invisible from outside — a cloud
> metadata endpoint, an RFC1918 admin port, the node's own RPC.

The delivery contract is specified normatively in
[`docs/api/webhooks.md`](https://github.com/epochbtc/satd/blob/master/docs/api/webhooks.md),
with signature test vectors so a receiver can be verified offline.

A stalled endpoint provably cannot reach consensus — deliveries run on the
isolated API runtime and the fan-in never blocks. Measured on a regtest node
connecting 20 blocks: **11.23 ms** with no webhook, **11.24 ms** with every
event going to a receiver that accepts the connection and never answers.

### Fixes from the alerting review

**A changed `alertfile=` was silently ignored on SIGHUP.** The dispatcher binds
its path when it is built at startup, so editing `alertfile=` and reloading
re-read the **old** file and logged `alertfile reloaded` naming a path that was
no longer configured. That is the accept-and-ignore failure the config layer
rejects unknown keys to prevent — and worse, because it reports success.

`alertfile` now works exactly like `authfile`: the file's *contents* are
re-read on every SIGHUP (adding, editing or removing a hook stays live, which
is the point of the feature), while changing *where* the file lives is
reported as restart-required.

**The plaintext-HTTP gate waived link-local addresses.** A hook URL is
required to be HTTPS unless it is local or the operator sets
`allow_insecure_http = true`. The IPv4 arm waived link-local as well as
loopback and RFC1918 — so `http://169.254.169.254/...`, the cloud
instance-metadata address, was accepted with no opt-in. Link-local is neither
loopback nor RFC1918, the IPv6 arm never waived `fe80::`, and both the spec and
this manual describe the waiver as "loopback and RFC1918". The code now says
what the prose always did.

**`-alertnotify` is rate-limited for edge events.** Standing conditions fire
the hook once, when they become active. Edge events — currently `deep_reorg` —
fire per occurrence by design, because three reorgs are three things that
happened and collapsing them would lose information. But each message queues an
exec on an unbounded channel that the notifier drains one at a time, so "per
occurrence" with no floor meant a burst — a scripted
`invalidateblock`/`reconsiderblock` loop, or a thin-hashrate chain having a
rough patch — grew the queue without bound and pushed the hook arbitrarily far
behind real time, until you were being paged about a reorg from twenty minutes
ago.

There is now a one-minute window per event id, and **the window reports the
worst occurrence in it, not the first**. That distinction is the whole point: a
limiter that keeps whichever event arrived first would let a depth-3 reorg claim
the window and reduce a depth-200 reorg one second later to an increment, so an
exchange halting deposits on `-alertnotify` would be paged about the harmless
one and never told about the serious one. Concretely:

- The first occurrence pages immediately, as before.
- An occurrence strictly deeper than anything already paged in the window
  escalates through at once — capped at one escalation per window, so a rising
  sequence still cannot page per occurrence.
- Everything else is held rather than discarded. When the window closes, the
  worst held occurrence pages, carrying a count of the others and the window as
  actually measured: `rolled back 41 blocks [3 more in the previous 74s]`.
- A burst that simply stops is drained by the health detector's poll rather
  than waiting for a next occurrence that never comes.

The full-fidelity record is untouched: the reorg log and the `status` event on
the streaming API still carry every occurrence, unthrottled.

**The active-warnings set is capped at 256 distinct ids.** Most warning ids are
fixed strings, but a few embed an identifier — a corrupt block's warning is one
per block, and nothing clears those. A storage fault across thousands of blocks
would have put thousands of rows into `getwarnings` and `getblockchaininfo`,
fired `-alertnotify` once per row, and filled the TUI's blocking modal with a
list nobody could read. Past the cap, new ids are counted in a single
`warnings.truncated` row instead; ids that are already active keep updating, and
the node log — which is not capped — still carries every one in full.

### Writing a receiver

A receiver is an HTTP endpoint that verifies the signature and acts; where an
alert goes after that — a pager, a chat channel, a ticket — is the receiver's
business, not the node's. Two things are worth getting right, and the spec
publishes test vectors for both: verify `X-Satd-Signature` over the **raw
body**, in constant time, *before* parsing it (key order and whitespace are part
of the signed bytes, and parsing unauthenticated input is the thing to avoid),
and deduplicate on `X-Satd-Delivery`, since satd retries whenever a response is
lost after the receiver already acted. The delivery id is inside the signature,
so a forged one cannot poison the dedup window.

Acknowledge before doing slow work: the node's per-hook queue is serial, so a
receiver that answers only after its own downstream call adds that latency to
every subsequent event. A condition and its recovery share a `collapse_id`, so a
receiver surfacing alerts to a human can replace the alert with its recovery
rather than stacking a second message beneath it.

### SDK support

`satd-events-client` gains `Categories::STATUS` and a typed
`Event::Status { kind, state, severity, message, details }`. The three enums are
deliberately **open**: a condition, state, or severity a client build predates
arrives as `Unknown(i32)` rather than failing to decode, and `severity` remains
meaningful, so a generic "log it, page on critical" handler keeps working across
node upgrades. `StatusSeverity` is ordered, so a severity floor is a comparison
rather than a match. All three are `#[non_exhaustive]`: the crate is published
and the node's taxonomy grows independently of it, so without that a downstream
`match` listing every variant *including* `Unknown(_)` would be exhaustive, and
adding a condition node-side would force a breaking SDK release.

`StatusSeverity` orders by severity *rank*, not by proto value:

```text
Unspecified  <  Info  <  Warning  <  Critical  <  Unknown(_)
```

`Unknown(_)` outranking `Critical` is deliberate — a level this build cannot
name is not one to quietly filter out. `Unspecified` is the opposite case and is
a separate variant for exactly that reason: it is proto3's zero value, which is
what an *absent* field decodes to, so folding it into `Unknown` would make a
severity the producer forgot to set outrank `Critical` and page on the
documented filter. An absence of information is not a loud condition.

satd itself never emits a zero `kind`, `state`, or `severity` — the node's own
enums are closed and the encoder writes an explicit value — so this is defence
against a third-party producer, a re-encoding relay, or a future schema, not a
bug reachable against a stock node. `StatusKind` and `StatusState` gain the same
`Unspecified`/`Unknown` split, and `EvictReason` (which shipped in 0.4.0 routing
*every* unrecognized value into `Unspecified`, leaving its `Unknown` variant
unconstructible) now decodes the same way. The rule across all four: an unset
field and an unrecognized value are different facts and never share a variant.
`docs/api/streaming.md` states the ranking normatively, so a non-Rust client has
a basis to agree.

The runnable `examples/health_watch.rs` shows the shape a real integration
wants: `resilient_subscribe` rather than a plain subscription, because the node
restarting is exactly when standing conditions are re-raised and is exactly what
kills an unsupervised plain one; a **timeout on the stream**, because
subscribing to heartbeats and then ignoring them proves nothing — a wedged
publisher on a live process answers keepalives while `next()` blocks forever, and
"no output" reads as "healthy"; raise/clear pair tracking to hold what is wrong
right now (rather than counting alerts, which only ever grows); and routing by
severity so an unknown condition still reaches the right place.

One limitation is called out rather than papered over. Status has no cursor, so
it is not replayable *and* a gap is not detectable: `ResilientSubscription` hides
reconnects, and its only synthetic notice is cursor-anchored. A drop during which
one condition raised and another cleared leaves a client's picture silently
wrong. Treat the stream as the low-latency edge signal and **`getwarnings` as the
authority** — poll it on a slow timer alongside, and a missed transition
self-corrects at the next poll instead of persisting for the life of the process.
Seeding once on connect is not sufficient, because later reconnects are invisible
to the caller. The example labels its set "observed by this client" for that
reason, instead of claiming "all clear".

## Go SDK (`satdevents`)

The streaming API gains a second first-party client. `satdevents` lives in this
repository at [`clients/go/`](https://github.com/epochbtc/satd/tree/master/clients/go)
as an independently versioned Go module, and is documented in the new
[Go SDK](https://epochbtc.github.io/satd/go-sdk.html) chapter of the Operator
Manual.

```sh
go get github.com/epochbtc/satd/clients/go
```

It is **full parity** with `satd-events-client`, not a core subset: the
firehose, watches (scripts, outpoints, transaction lifecycle with auto-close,
depth alarms, descriptors, silent-payment scan keys, prefix buckets), durable
cursors with commit-on-poll semantics, reconnect with backoff, lag recovery,
mid-stream re-anchoring, bounded historical rescan, atomic watch-set replace,
watch-set loaders, in-band acks, and local prefix re-filtering.

It is also idiomatic Go rather than a transliteration. Functional options
replace the builder; the `Event` enum becomes a sealed interface consumed by a
type switch, so the compiler still bounds the variant set; `Option<T>` fields
become pointers, keeping "absent" distinct from zero; `#[non_exhaustive]`
becomes a `Known() bool` method on each open enum; and every blocking call takes
a `context.Context`. Cancel safety, which the Rust SDK implements as an explicit
state machine, falls out of the design here — the reconnect loop hands events
over an unbuffered channel, so returning on `ctx.Done()` structurally cannot
consume one.

**The published dependency graph is gRPC and protobuf, and nothing else.** A
client library that drags in a Bitcoin stack forces version bumps on
applications that already have one, so script and txid parameters are `[]byte`
and `[32]byte` with conversion helpers, and silent-payment scan-key validation
is an in-tree on-curve check rather than a curve dependency. The code
generators, the linters, the E2E suite, and the thirteen runnable examples each
live in their own nested module, so nothing they need reaches a consumer.

### How parity is verified

The Go SDK will not get the day-to-day production use the node does, so CI —
not usage — is
what stands between a green badge and a rotted client. Every satd PR runs the Go
unit tests (including a protobuf-reflection test that fails when a variant is
added to the `.proto` without a Go decoder), builds all thirteen examples, runs
the Go E2E suite against the same freshly built `satd` binary the Rust E2E suite
uses, and runs a **differential parity harness**.

The harness is the part worth describing. One node, two clients — the Rust SDK
in-process and the Go SDK as a subprocess — driven through a byte-identical
watch spec. Each renders every event it receives to canonical JSON, and the two
dumps are diffed line by line. A field one side decodes differently, an
off-by-one, a variant one side cannot decode at all: all of them surface as a
diff and fail the PR. "Parity with the Rust SDK" is otherwise a claim nobody
checks.

Writing it immediately earned its keep, turning up three API-shape divergences
between the two SDKs before it ever ran green.

Two normalizations are applied, and the cost of each is stated rather than
buried. The publisher's per-process `instance_id` is dropped, since it differs
per connection by definition. And events are sorted by their rendered content
rather than arrival order, because two connections are served by independent
tasks and the node legitimately interleaves a watch match against a chain event
differently for each — comparing arrival order would fail on server scheduling
and say nothing about the SDKs. **The harness therefore proves the two clients
see the same events with the same field values, not that they see them in the
same order.**

Sorting on content is deliberate, and the obvious alternative is wrong: keying on
the cursor looks natural but only confirmed events carry one, so every
mempool-side event inherits whichever block cursor happened to arrive before it
on that connection — and identical events land in different buckets on the two
streams. Content is the only key derived entirely from what is being compared.

### Cross-port fixes to `satd-events-client`

The Go SDK was written as a port of the Rust one, which makes a review of the
port a review of the original. Four defects found in `clients/go` were present
here too and are fixed in this release:

- **A failed cursor-store write no longer reports success on retry.** Both
  resilience layers took the armed cursor *before* attempting the write, so a
  transient failure surfaced the error and discarded the arm; the retried
  `commit()` then found nothing armed and returned `Ok(())`. The exposure is an
  idle stream — exactly the graceful-shutdown path where a caller commits
  explicitly and no further event re-arms the cursor. The process exits believing
  the cursor is durable, and the restart finds an empty store and resumes
  forward-only, losing everything that happened while it was down. That is an
  at-least-once violation, not a replay.
- **An auto-resumed lag now backs off.** Receiving the `Lagged` notice reset the
  reconnect counter (an event is progress), and the auto-resume path then
  reconnected with the counter at zero — skipping the backoff entirely and
  leaving `max_retries` unable to bound it. A consumer that is chronically too
  slow lagged, re-subscribed instantly, lagged again, and spun, each cycle
  costing the node a full confirmed-history replay.
- **Prefix watches no longer leak bits below the declared width.** The wire
  carries whole bytes, so a 12-bit bucket ships two — and those four extra bits
  were sent unmasked. The node masks to `bits` before keying, so they moved no
  bucket and bought the client nothing; they simply handed the node 16× more of
  the scripthash than the anonymity set the consumer asked for. The unmasked
  dedup also broke the documented collapse: two scripts sharing a 12-bit bucket
  but differing in bits 13–16 registered as two buckets rather than one.
  `PrefixWatcher::prefixes` now also returns a sorted, stable registration order.
- **`FileCursorStore` now fsyncs.** A rename is atomic with respect to readers,
  but atomicity is not durability: the rename could reach the disk while the
  bytes it points at had not. The temp file is synced before the rename and the
  directory after it.

The remaining findings did not port. The lag path's immediate persist is correct
in Rust and was wrong in Go, because `handle_event` runs inside `next()` here
while Go's pump reads one event ahead; the inert generation guard and the
edit-during-replay race are Go-only, since `ResilientWatch` is `&mut self` and an
edit cannot interleave with `next()`; `Debug` already redacted the bearer token.
Worth recording, because an audit that assumes the two clients are line-for-line
equivalent produces false positives in both directions.

### Examples

Thirteen runnable programs under
[`clients/go/examples/`](https://github.com/epochbtc/satd/tree/master/clients/go/examples),
one per usage shape: the twelve counterparts of the Rust set (`firehose_tail`,
`resilient_tail`, `watch_outpoints`, `descriptor_wallet`, `lifecycle_alarms`,
`resilient_watch`, `health_watch`, `prefix_privacy`, `sp_wallet`,

code most worth compiling. They all are: a renamed method cannot rot in a file
whose whole purpose is to be copied.

## Security

### A bearer token no longer travels in cleartext by accident

Both first-party SDKs would send a bearer token over an unencrypted connection
with no error and no warning, and the node accepted the configuration that makes
that a routable exposure rather than a loopback one.

Nothing caught it. gRPC-Go has a safety net for exactly this — it refuses to
attach a `PerRPCCredentials` whose `RequireTransportSecurity()` reports true to
an insecure channel — but the Go SDK attaches the token with
`metadata.AppendToOutgoingContext`, which that check never sees. The Rust SDK
attaches it as ordinary metadata for the same reason. And the one guard that did
exist (an `http://` target combined with a TLS option is refused) does not fire
when no TLS was requested at all.

It is not a contrived configuration either: a remote-bound node with
`eventsgrpcauth=1` and no TLS was supported. Both ends behaved exactly as
configured while the credential sat on the wire.

The token is a capability-scoped credential for the events surface: anyone who
captures it can subscribe to the firehose and register watches. On a Tier 2
scan-key watch (`add_silent_payments` / `AddSilentPayments`) the same plaintext
stream also carries BIP 352 **scan secrets**, which disclose which outputs
belong to a receiver.

Three changes, which have to land together — the differential parity harness
holds the two SDKs to the same behaviour, and it would correctly flag a
one-sided fix:

- **Rust SDK.** `connect()` returns the new `StreamError::InsecureCredential`
  when `bearer_token` is combined with an endpoint that will not be encrypted.
  The predicate is the URI scheme rather than the builder's TLS state, because
  tonic selects TLS from the scheme alone — *and* this crate's `tls` feature,
  because tonic gates its https handling behind its own `tls` feature. In a
  `default-features = false` build an `https://` endpoint connects in cleartext
  h2c rather than failing, so a token is refused there whatever the scheme.
  Keep the default `tls` feature if you use a token.
- **Go SDK.** `Dial` returns the new `KindInsecureCredential`
  (`errors.Is(err, ErrInsecureCredential)`) when `WithBearerToken` is combined
  with an insecure transport. Any `WithTLS*` option or an `https://` target
  satisfies it.
- **Node.** `eventsgrpcallowremote` together with `eventsgrpcauth` now requires
  `eventsgrpctlscert` and `eventsgrpctlskey`. This is the rule `mcpallowremote`
  has always enforced, applied to the surface with the same exposure; it closes
  the hole for third-party clients too, which no SDK change can reach.
  `eventsgrpcmtls` satisfies it on its own — it already requires the certificate
  and key, and it authenticates without a token.

For loopback and test harnesses, `insecure_bearer_token(token)` /
`WithInsecureBearerToken(token)` do what the old code did, with the risk named.
They are separate methods rather than a flag so the unsafe choice has to appear
at the call site, and so that switching back to the safe method cannot silently
leave the waiver behind.

`streamwsallowremote` is deliberately unchanged: that transport has no TLS of
its own, so requiring it would remove the deployment rather than secure it. A
remote streamws bind still sends its token in cleartext unless a TLS-terminating
proxy fronts it — prefer the loopback bind plus a proxy.

### The events-gRPC TLS listener now negotiates HTTP/2 (`h2`) over ALPN

A node with `eventsgrpctlscert`/`eventsgrpctlskey` set could not be reached by
any standard gRPC client — including this repo's own Rust SDK. gRPC over TLS is
HTTP/2 over TLS, and a conformant client (tonic's TLS connector among them)
offers exactly `h2` over ALPN and refuses a connection on which the server
selected no protocol.

The listener terminates TLS itself and hands tonic already-decrypted bytes, so
the server always spoke h2; the rustls acceptor simply advertised no ALPN. A
rustls server with no configured protocols does not *fail* such a handshake — it
completes it and selects nothing — so the whole failure landed on the client, as
an opaque transport error on a connection whose certificate had verified
perfectly. Nothing in the node log said anything was wrong, and the pre-existing
TLS test never offered ALPN, so it proved only that TLS terminated, not that gRPC
could traverse it.

The acceptor now advertises `h2`. A client that offers a disjoint ALPN set —
`http/1.1` only, say — is cleanly rejected at the handshake rather than left to
fail later. The HTTP/1.1 surfaces (Esplora REST and JSON-RPC) are unchanged and
still advertise no ALPN; a separate builder entry point carries the protocol
list, so those listeners cannot start offering a protocol they do not implement.

## Mempool & mining

### The mempool now refuses transactions the next block cannot include

Admission enforced no transaction finality of any kind
([#588](https://github.com/epochbtc/satd/issues/588)): no absolute-locktime
check and no BIP 68 sequence-lock check. A transaction with a locktime months
in the future was admitted, relayed, stored — and flowed straight into
`getblocktemplate`, so a miner using satd's template mined a block that every
validator rejects as `bad-txns-nonfinal`. The block's work is wasted and the
reward lost, and anyone could trigger it for the cost of one standard-fee
transaction.

Admission now applies Bitcoin Core's two policy checks with next-block
semantics, using Core's reject strings:

- **`non-final`** — absolute finality against the next height and the tip's
  MTP (Core's `CheckFinalTxAtTip`).
- **`non-BIP68-final`** — relative locktimes against each prevout's real
  confirmation height and MTP anchor, with unconfirmed parents treated as
  confirming at `tip + 1` (Core's mempool-height convention — which is what
  makes a nonzero height-based relative lock on an unconfirmed parent
  unsatisfiable, the property CPFP composition relies on).

Neither rejection penalizes the sending peer: finality is tip-relative, and a
peer one block away legitimately relays these.

### Block templates are now valid by construction

Two more ways `getblocktemplate` could hand a miner an invalid block, fixed
together ([#589](https://github.com/epochbtc/satd/issues/589)):

- **CPFP children were emitted before their parents.** Template selection
  ordered purely by effective fee rate — and a CPFP child paying a higher
  rate than the parent it funds is not an edge case, it is the point of
  CPFP. A block that spends a transaction's output before the transaction
  appears is invalid (`bad-txns-inputs-missingorspent`).
- **A child could be included without its parent** — the parent missing the
  weight cutoff, or held by an `on template` quarantine while the child was
  not.

Selection is now dependency-aware: a transaction is included only when every
input resolves against the UTXO set to a confirmed coin, or to an output of a
transaction already in the template, greedy by fee rate over that ready set.
Children land after their parents; a child whose parent never makes it in is
dropped with it — including a child orphaned by its parent's eviction
(expiry, replacement, or a conflict removed at block connect), whose prevout
exists nowhere at all. The template also re-checks absolute finality and
BIP 68 sequence locks per transaction, as Core's miner does — admission
normally guarantees both, but a reorg can lower the tip after admission, and
a mempool loaded from persistence may predate the admission check.

## Consensus

### The BIP 141 witness rules now match Core exactly

A block's hash commits to its merkle root, and the merkle root commits to
**txids** — which exclude witnesses. Every witness byte in a block therefore
sits outside everything the block hash authenticates. Bitcoin Core closes that
gap with two rules in `CheckWitnessMalleation`, and a block is subject to
exactly one of them:

- **A witness-commitment output is present**, and segwit is active at that
  height: the coinbase witness must be *exactly one 32-byte item*
  (`bad-witness-nonce-size`), and the BIP 141 commitment must verify
  (`bad-witness-merkle-match`).
- **Otherwise**: no transaction in the block may carry witness data at all —
  the coinbase included (`unexpected-witness`).

satd was laxer than Core in three ways, and in each of them the *coinbase* was
what went unchecked:

1. **No nonce-size rule.** satd took coinbase witness item 0 when it happened
   to be 32 bytes, and silently substituted an all-zero nonce otherwise. Core
   mines a zero nonce, so that fallback *is* the genuine value for essentially
   the whole chain — meaning the coinbase witness could be truncated, padded
   with junk items, or dropped entirely and the commitment would still
   recompute to the same value.
2. **The `unexpected-witness` scan skipped the coinbase.** It ran over
   `txdata[1..]`, so a block with no commitment output but witness data hung
   off its coinbase input was accepted.
3. **The commitment was only verified when some other transaction carried
   witness data.** A witness-stripped copy of a segwit block — same block hash,
   same merkle root, no witnesses left to notice — skipped the check outright.

None of these is reachable through honest mining, which is why they went
unnoticed: Core-derived miners produce well-formed blocks. But each one accepts
a block Core rejects as `BLOCK_MUTATED`, which is a chain split with satd on
the losing side, and exactly the shape that bites during an incident — a
malicious or buggy miner can partition satd nodes from the network.

All three are now enforced, gated on segwit activation exactly as Core gates
them on `DEPLOYMENT_SEGWIT`. A pre-activation block whose coinbase happens to
carry a commitment-shaped `OP_RETURN` — mainnet has these, from miners running
segwit-ready software before lock-in — is still judged by the second rule and
is not spuriously rejected.

A fourth divergence fell out of the same audit: a block carrying witness data
with no commitment output was rejected with `bad-witness-merkle-match`, where
Core says `unexpected-witness`. Both nodes rejected it, so this was a reject
*label* difference rather than a consensus one, but the hand-transcribed Core
reason in satd's static `feature_block` matrix had it wrong and satd's own
laxness happened to agree with the error. Both are corrected.

The three rules are pinned by new cases in the **live Bitcoin Core
block-acceptance differential**, which submits identical bytes to satd and a
real `bitcoind` and requires the same verdict *and* the same reject reason. All
three cases fail against the previous code with Core rejecting and satd
accepting.

### Upgrading

Two consequences worth knowing before you upgrade.

**A block already on disk could fail the new rules.** Every earlier satd
version accepted and stored the three classes above, and none of them changes
the block hash or merkle root, so such a block connects and reaches `Valid`
with nothing logged. It is not reachable through honest mining — but a peer
that wanted to plant one could, and this release closes the ingress hole that
let them (see [the mutation gate](#the-block-ingress-mutation-gate-now-matches-cores)).

If your datadir already has one, `-reindex` no longer treats it as fatal: the
replay stops at that height and the node syncs the rest from peers — see
[below](#a-reindex-that-cannot-replay-a-block-now-stops-instead-of-bricking).
The repair tool is
[`getblockfrompeer`](#getblockfrompeer-repair-a-lost-block-without-a-resync),
which in this release also replaces a stored copy that parses but is not
canonical.

**Side-chain blocks with non-canonical stored bytes are no longer indexed.**
The side-chain indexing pass logs and skips rather than failing, so this
degrades gracefully; the effect is that if such a branch later wins, satd
re-downloads it instead of reorging onto the stored copy.

**External miners** using `submitblock`: a block carrying a commitment output
with a malformed or absent coinbase witness nonce used to be accepted whenever
the block had no witness transactions, and is now rejected
`bad-witness-nonce-size`. That is Core parity, but it is a live behaviour
change for anything that built its own coinbase. See
[#548](https://github.com/epochbtc/satd/issues/548) for the related
`getblocktemplate` gap that makes the trap easier to fall into.

### Transaction finality now matches Core: the coinbase counts, and the cutoff is strict

The nightly **block-differential fuzzer** — libFuzzer mutating raw blocks,
satd's real validation in-process, a live `bitcoind` as the oracle — found an
accept/reject divergence ([#581](https://github.com/epochbtc/satd/issues/581)):
satd accepted a block whose coinbase carried a future height locktime with a
non-final sequence; Core rejects it `bad-txns-nonfinal`.

Two laxnesses in the finality check, both accepting what Core rejects:

1. **The coinbase was exempt.** Core's `ContextualCheckBlock` runs `IsFinalTx`
   over every transaction in the block — the coinbase included. A coinbase
   with an unsatisfied locktime and a non-final sequence is a consensus
   reject. satd skipped the coinbase entirely.
2. **The cutoff was non-strict.** Core requires the locktime to be *strictly*
   below the cutoff — the block's own height for height locktimes, the median
   time past for time locktimes. A transaction whose locktime equals the
   connecting height is non-final; satd accepted the equality, on both the
   height and the time branch.

Neither shape is produced by honest wallets or miners, which is why they went
unnoticed. But each one accepts a block Core rejects — a chain split with satd
on the losing side, deliverable by anyone willing to mine one block.

Auditing the same neighbourhood found a third laxness, in **BIP 68**: Core's
version gate has always compared unsigned
(`static_cast<uint32_t>(tx.nVersion) >= 2`), so a transaction whose version
has the high bit set — negative as a signed 32-bit integer — is still
subject to sequence locks. satd compared the signed value and skipped
enforcement, accepting a block Core rejects.

Core has enforced all three rules from the beginning, so no block on any
public chain violates them: tightening satd to match cannot reject a
historical block. The fixes are pinned in layers — unit tests on the fuzz
reproducer's exact shape, both equality boundaries, and the high-bit
version, and three new cases in the live Bitcoin Core block-acceptance
differential (`coinbase_nonfinal`, `locktime_equal_height`,
`bip68_high_bit_version`), each requiring the same verdict from satd and a
real `bitcoind`.

### The block-ingress mutation gate now matches Core's

A *mutated* block is one whose contents can be changed while its **block hash
stays the same**. That is why rejecting one is not enough — an honest block
sharing that hash has to remain acceptable afterwards — and why the check runs
at every ingress point rather than once, deeper in.

satd's gate covered merkle malleability (CVE-2012-2459) and 64-byte
transactions. Core's `IsBlockMutated` also runs the witness rules, and satd's
omission had a concrete cost: a witness-mutated block passed ingress and was
caught a layer later in `store_block`, worth 10 ban points instead of 100 — and
that is the path by which such a block reaches disk in the first place, which is
the precondition for the reindex hazard above. The gate now runs the same three
checks in the same order, including a merkle-root mismatch, which it previously
left for a later stage.

Two of the changes make satd *less* strict, which matters more than it sounds
on a gate that bans at 100 points: being stricter than Core here means banning
honest peers and partitioning yourself off the network.

- **A 64-byte transaction no longer makes a block mutated when it has a
  coinbase.** Core deliberately confines that rule to coinbase-less blocks —
  which are already invalid — precisely so it is not a consensus change. A
  64-byte transaction is otherwise consensus-legal today, so satd was rejecting
  an honest block at ingress and banning whoever sent it.
- **A block whose parent we do not know is no longer checked.** The witness
  rules are segwit-gated, so they need the block's height, and the parent's
  index entry is the only way to know it before accepting the block. Core skips
  the gate in that case rather than guessing an activation state; a block that
  cannot be placed cannot be connected either, so it is rejected downstream on
  its own merits.

### Compact-block reconstruction no longer duplicates a transaction on a short-ID collision

BIP 152 identifies each non-prefilled transaction in a compact block by a
6-byte *short ID*. Six bytes is small enough that two different transactions can
share one — crafted by a peer, or roughly one in 2⁴⁸ by chance. satd's
reconstruction resolved every announced short ID against the mempool
independently, so if a peer announced the same short ID for two slots (or two
mempool transactions matched one announced short ID), the same transaction was
placed in both slots. The result was a block with a duplicated transaction: its
merkle root no longer matched the header, the [mutation
gate](#the-block-ingress-mutation-gate-now-matches-cores) rejected it, and the
relaying peer — possibly honest — took the ban. The real block was never
re-requested along that path.

Reconstruction now follows Core's `PartiallyDownloadedBlock::InitData`: a short
ID that is announced more than once, or that matches more than one mempool
transaction, is treated as unresolved and its slots are fetched with
`getblocktxn`, so the peer supplies the real, distinct transactions instead of
satd guessing one. A short ID that matches exactly one mempool transaction is
still filled locally, so the common no-round-trip case is unchanged.

### A reindex that cannot replay a block now stops instead of bricking

`-reindex` rebuilds the chain database from the block files, and it clears that
database before the replay starts. So a block it could not replay used to be
unrecoverable in the worst way: the run aborted *after* the wipe, leaving no
chain at all, and every retry re-derived the same plan and died at the same
block. A recovery tool that destroys the thing it is recovering.

It now stops at that height instead. Everything below stays replayed and
durable, no index entry is written for the offending block or anything above it
— which is what lets normal sync re-fetch those heights, since a peer's copy no
longer collides with a stored entry — and the run reports what happened rather
than logging "complete". The halt is logged at error level and raised as a
standing warning, so it reaches `getwarnings`, the TUI and `-alertnotify`; a
reindex that quietly stops early and calls itself finished is its own failure
mode.

This covers both reasons a block can be unreplayable: bytes that fail
validation, and bytes that cannot be read at all.

### Unreadable block data is now reported as corruption, not silence

A `block_index` entry that is not `HeaderOnly` or `Pruned` asserts that the
block's bytes are on disk. When they are missing, truncated or malformed
anyway, that is local corruption — but every caller saw the same "no block"
answer it would get for a pruned block, and the index runners turned it into
`missing block data (pruned or corrupt?)`.

That is not a hypothetical: a mainnet node ran for weeks with one block
truncated to 2083 of 1619761 bytes behind a live entry, failing the same index
backfill on every restart, with nothing in the warnings system and no signal an
operator could act on.

The read still returns "no block" — callers are built around that — but the
condition is now reported: an error log and a standing warning, one per block,
naming the repair:

```
getblockfrompeer <blockhash> <peerid>
```

### Deliberate remaining difference

Core checks block weight
*after* the witness rules, because a weight failure can mark a block
permanently invalid and an attacker who pads the coinbase witness inflates the
weight without changing the block hash — so weighing first would let a mutated
copy poison the index against the honest block. satd never persists a verdict
from this function (a rejected block leaves no index entry; only the
`invalidateblock` RPC ever marks a hash `Invalid`), so the cheaper check stays
first.

### Median-time-past could come from a branch that had already lost

Found while auditing the reorg paths after the incident above, and unrelated to
it.

satd keeps a small cache of recent block timestamps to answer
median-time-past without touching the store. A reorg updated that cache for the
block that *triggered* it and for nothing else — the blocks the reorg
reconnected were never recorded. So at every height the reorg replaced, the
cache went on holding the **displaced** branch's timestamp, and
`get_median_time_past` returned it for as long as that height stayed inside the
eleven-block window.

MTP gates BIP 113 locktimes and BIP 68 sequence locks, so a wrong median can
accept or reject a transaction Bitcoin Core would not. That makes this a
consensus fault rather than a reporting one.

Three things were wrong and all three are fixed.

Both reorg paths now record each reconnected block's timestamp **as they
reconnect it**, not after the loop finishes. Timing is the whole point: the
next block up reads an eleven-block window that covers the block just
connected, so recording late left every reconnect from the fork point plus two
onward — and the block that becomes the tip — validated against the timestamps
of the branch being displaced. This applies to the `invalidateblock` /
`reconsiderblock` reorg as well; it had the same late ordering.

An aborted reorg rebuilds the cache from the restored tip's own ancestry,
walking parent pointers. Entries staged during a reconnect that then failed
describe a branch the node is no longer on, and the per-height dedup below has
already destroyed the ones they replaced, so they cannot be restored in place.
Simply clearing would be correct, but it routes the next eleven median lookups
through the store fallback, which resolves each height through the `height_hash`
index — the same "best known block at this height" index that is not an
active-chain oracle, and which an aborted reorg can itself pollute: a
coinbase-only block whose only output is unspendable produces no coin writes, so
its batch takes the cache's pass-through and its height row reaches disk even
though the reorg was discarded. Parent pointers cannot be polluted that way.

And the cache holds at most one entry per height: lookups resolve a height with
a first-match search, so a duplicate silently shadowed the newer value, and
whether that was ever observed depended on how quickly front-eviction happened
to remove the stale entry — timing-dependent reasoning of exactly the kind that
produced the bug.

Exposure is not narrow. The blocks a reorg reconnects are affected immediately,
during the reorg that accepts them; no subsequent blocks are needed. The
lingering-stale-entry case afterwards is the milder half.

**The pipelined connect path had the same fault from a different direction.**
The prefetcher computes each block's median-time-past when it buffers the
block, off the height→hash index at that moment, and `connect_preprocessed_block`
passed it to `connect_block` verbatim. That function already refuses to trust
anything else the prefetcher captured — it re-derives the parent, re-checks that
the block extends the tip, and reconciles the block against the index entry
authorising it, explicitly because the prefetcher may have captured that entry
before the parent connected. MTP was the one consensus input still crossing the
boundary unchecked.

The prefetcher's justification was that on the IBD path the index is
authoritative, because it is written forward as blocks connect. A connector that
deliberately advances past a height whose row named a different block — which is
exactly what the connector fix in this release does — falsifies that. Blocks
buffered while the row was poisoned keep the median they were stamped with; the
dispatcher only evicts entries *below* its cursor, so they survive; and once the
row is repaired the buffered block's hash matches and it connects. One differing
element shifts an eleven-element median.

It is now computed on the connect thread. That also closes a quieter gap: this
path *wrote* the MTP cache but never read it, so for the bulk of IBD blocks the
"median comes from the branch being connected" guarantee this section is about
was not in force at all.

## Storage / Core compatibility

### The tip can no longer stand on blocks that were never connected

On a synced mainnet node the chain tip advanced eight blocks past the last
block it had actually connected. The tip was a real canonical block. Its
ancestry matched mainnet exactly. `getblockchaininfo` was self-consistent and
`/healthz` stayed green. But every output created in those eight blocks was
absent from the UTXO set — the node's answer to `gettxout`, and to every
wallet-facing index built on it, was wrong for five and a half hours, and
nothing anywhere said so.

What finally surfaced it was luck: the next block happened to spend one of the
dropped outputs, so the connector wedged on
`bad-txns-inputs-missingorspent`. Had it spent nothing from that window, the
node would have carried on serving a truncated UTXO set indefinitely.

`BlockStatus::Valid` is written in exactly one place — block connection — and
nothing downgrades it, so the eight blocks reading `DataStored` is proof they
were never connected in that chainstate. Three changes make that state
detectable and unreachable:

**Connecting requires a connected parent.** Every connect path already
required the block's `prev_blockhash` to equal the tip. That pins the *shape*
of the chain and says nothing about whether the tip's own coins were ever
applied — every connect on the way up to the bad tip satisfied it. Both
sequential (IBD) connect paths and the steady-state `accept_block` path now
also require the parent to be a block this chainstate connected. The
steady-state path matters most: a synced node does not use the sequential
connectors, and the divergence was observed on a synced node.

The check reads through the in-memory block-index cache, so it sees writes that
are still buffered. Its coverage is therefore the first connect after a
restart, and any entry that has since been evicted — the startup audit below is
what reads the persisted state cold. Failing it raises a distinct error rather
than the generic `bad-prevblk`, so the connector does not mistake it for a
fork-blocked frontier and "recover" by handing off to the reorg path, which
would clear the operator warning on the grounds that the condition is
self-healing. This one does not heal.

**Preprocessed blocks are checked for internal consistency.** The flat-file
connect path verifies that the record it read hashes to the block it is
connecting, because a mis-recorded offset lands on another record's *start*
rather than on garbage, and a sibling at the same height with the same parent
will validate. The prefetch path had no equivalent: it committed
`tip.hash = pre.hash` without ever reconciling that hash against the block it
validated or the index entry that authorised it. Now all three must agree.

**The parent check needed a durable answer to read.** A check that refuses to
extend the chain is only as good as the status it reads, and that status was
not reliably readable. `connect_block`'s batch carries coins, so it is buffered
until the next flush; its block-index write — the upgrade that records "this
block was connected" — reaches readers only through a fixed-size LRU. Falling
through to the inner store on an LRU miss returns the *pre-connect* status that
`store_block` wrote, so a block that was connected reads as one that never was.

That is not a rare race. Every `headers` message puts up to 2000 entries into
the same LRU, so a peer can evict a recently connected parent at will, and the
consequence is the check firing on a healthy chain and refusing to extend it —
a false positive that stalls the node, not the missed detection the code
originally described. Block-index reads now consult the pending batch before
the inner store, so an unflushed write is visible whether or not the cache
still holds it.

**Startup refuses a tip standing on a hole.** satd walks the tip's ancestry at
startup and, on finding a block it never connected, reports the affected
heights and exits rather than serving. This is deliberately not a repair: the
height index is derived state that can be rewritten from the block index, but a
missing UTXO delta can only be recovered by replaying the block, so the remedy
is `-reindex-chainstate` and the job here is to refuse loudly instead of
answering wrongly.

The exit status is **3**, distinct from the `1` startup uses for ordinary
refusals like a bad config, so alerting can tell the two apart without
scraping stderr. The message names `satd-chainstate-audit` (below), which
reports what actually disagrees before you commit to a multi-hour replay. A
broken parent *pointer* — as opposed to a hole — gets its own message and its
own remedy, `-reindex`: `-reindex-chainstate` trusts the same block index and
cannot fix it. The two are not mutually exclusive — the walk can classify holes
and then hit a broken pointer below them — so both are printed when both are
present, and the remedy given is the one the stronger fault requires.

A distinct exit status only buys something if a supervisor acts on it, and the
units we ship set `Restart=always` for reasons documented in the unit file. So
they now also set `RestartPreventExitStatus=3`. Without it the node refusing to
start would restart every five seconds indefinitely, each cycle re-opening
RocksDB and re-running the startup scans, and `systemctl is-failed` would stay
false because the unit never settles — the operator gets a scrolling FATAL
instead of a stopped unit, and unit-state alerting never fires. If you maintain
your own unit file, add that line.

The audit also runs a second time after a `-reindex` or `-reindex-chainstate`,
for the same reason `-checkblockindex` does: the pre-replay run passes
trivially, because clearing the chainstate drops the tip pointer and leaves a
one-block chain to walk. Without the second run, a replay that stopped short or
rebuilt the same hole would serve for a full uptime before the next startup
caught it — the operator's remedy failing silently, which is the worst possible
moment not to say so.

On a **pruned** node every remedy above is unavailable, because they all replay
blocks from the flat files and those blocks have been deleted:
`-reindex-chainstate` refuses outright, `-reindex` would rebuild a truncated
chain, and the audit tool cannot read blocks that are gone. satd detects this
and says so, rather than sending an operator through three instructions that
each fail differently. The workable path — `getblockfrompeer` for the affected
heights, or a resync — is what it prints instead.

An AssumeUTXO node is not caught by this. Everything at or below the snapshot
base is exempt. It has to be the whole range, not just the base block:
the background chainstate re-validates genesis→base and writes its results into
the *shared* block index, so mid-validation that range reads connected up to
wherever the background has reached and unconnected above it — connected blocks
beneath unconnected ones, which is exactly the shape the rule otherwise treats
as damage. Exempting only the base would have made a healthy AssumeUTXO node
refuse to start and told its operator to discard the snapshot.

The mechanism that produced the original divergence is still under
investigation (#567); these changes bound its blast radius from "serve wrong
answers silently" to "refuse to start, and say which heights".

### `satd-chainstate-audit`: check a datadir against its own blocks

When the mainnet node above was wedged, there was no way to ask it whether its
UTXO set was right. Answering that took a throwaway RocksDB reader, written by
hand, and four separate on-disk artifacts — the fourth of which reversed the
conclusion the first three supported.

`satd-chainstate-audit` asks that question as a shipped tool, and asks it whole
instead of one column family at a time. It walks the tip's ancestry,
reads each block back from the flat files, and reports every disagreement:

```
$ satd-chainstate-audit --datadir /path/to/datadir
NOTE: this opens the chainstate read-write. It issues no writes of its own, but
RocksDB replays and truncates the WAL, may compact, and rewrites bookkeeping on
open; …  If this datadir is evidence, stop now and audit a copy instead.

auditing 2016 blocks below tip 0000…b571b0 (height 961640)
checked 2016 blocks, heights 959625..=tip
ancestors never connected: 8
  height 961632 0000…46ff24ba status DataStored
  …
coins missing: 38412
  4a5e…a33b:0
  …
INCONSISTENT: 8 ancestor(s) never connected; 38412 coin(s) missing
```

Eight mainnet blocks is tens of thousands of outputs once the unspendable ones
are excluded, and only the blocks above them in the window can spend any back —
so the count is large by nature. `--verbose` prints all of them; without it each
list is truncated.

It names the outpoint, the height and the txid. A verdict would have been worth
very little; this is what shortens the next investigation from days to minutes.

It takes the RocksDB lock, so the node must be stopped. Exit status is `0`
consistent, `1` could not run, `2` inconsistent, so it scripts cleanly.

It issues no writes of its own, but it is not non-mutating: opening the
chainstate opens RocksDB read-write, which replays and truncates the WAL, may
compact, rewrites bookkeeping, creates any missing column family, **drops the
legacy address-history column families** and stamps the schema version — after
which an older satd will no longer open that datadir. Opening the block files
creates `xor.dat` if absent. If the datadir is evidence — the case this tool
exists for — copy it and audit the copy. The tool says so on every run. It is
not in the release tarballs or the Docker image; build it from source.

Two things it deliberately does not call damage. Blocks the node **pruned** are
reported separately: they are unreadable by construction, and counting them as
faults would fail every healthy pruned node and then recommend
`-reindex-chainstate`, which a pruned node refuses outright. And on an
**AssumeUTXO** node it reads the snapshot base from the background chainstate's
own marker, so the history below the base — which that node legitimately has not
validated yet — is reported as unvalidated rather than as a hole.

A block that cannot be read still bounds what can be concluded, but only below
itself: coin checks are skipped at and below the highest such block, because its
spends are unknown, and the tool says so in its output. Above it the verdicts
are sound, since the walk runs newest-first and a coin created at height H can
only be spent at or above H.

Memory is the one cost to watch. Every output the window creates and every
outpoint it spends is held until the end, so the default window already runs to
roughly a gigabyte on mainnet and a much larger `--window` will exhaust a small
machine — on a box that, by the nature of this tool, is already having a bad
day.

It diagnoses and does not repair, deliberately. A missing coin is recoverable
only by replaying the block that created it.

### A connector that stopped short of the headers tip no longer parks until the next block

On a testnet4 node catching up after a restart, the block connector pulled a
few hundred blocks and then tore down 27 blocks short of the headers tip it
already knew. The node then sat — tip stationary, peers connected, no errors —
for thirteen minutes, until the next testnet4 block was found and its headers
announcement re-triggered the download. Liveness only, and it self-heals on
the next block. But the parked interval is bounded only by block production —
unbounded on a chain with slow or irregular blocks — and for all of it the
node serves a stale tip while knowing better headers.

The cause was that every path that (re)armed the block-download scheduler ran
inside the inbound-headers handler. A connector that exits short — a headers
batch accepted between its completion check and its teardown, or the
deliberate hand-off to the reorg path when the frontier is fork-blocked —
left no driver until a peer volunteered the *next* headers message. Worse,
blocks the scheduler had downloaded but not yet connected were unreachable in
steady state: the block-request fallback skips them because their data is
present, and a peer re-sending one is rejected as a duplicate for the same
reason.

Two changes close the family. The P2P run loop now periodically re-evaluates
the same scheduler-creation gate the headers handler uses, so re-arming is
poll-driven rather than exclusively announcement-driven. And the steady-state
block processor now drains stored-but-unconnected blocks on the best header
chain directly from disk, so a torn-down connector's already-downloaded tail
connects within seconds, without any network event. (#582)

### The connector said "giving up" and then did not

Small, and it cost real hours. When a block fails to connect repeatedly, the
connector logged `Persistent connect failure, giving up` and broke its loop. A
comment next to it claimed systemd would restart the process. Neither was true:
breaking exits the connector loop, not the process, and the run loop starts a
fresh IBD within seconds, which fails at the same block and arrives back at the
same line. An operator watching a wedged mainnet node read "giving up" every
thirty seconds for five and a half hours while the node did anything but.

The message now says what happens — that IBD will restart and retry the same
block, and that this repeats until the cause is fixed — and the node-warning
says so too.

### A consistency check that reads the blocks back

Diagnosing the incident above took four separate on-disk artifacts — `coins`,
`height_hash`, `undo` and `chain_tx` — and the fourth reversed the conclusion
the first three supported. What was missing throughout was a way to ask the
node the direct question: *does the UTXO set actually agree with the blocks you
say are on the active chain?*

`verify_chainstate` answers it. It walks the tip's ancestry by parent pointer,
reads each block back, and checks that every output those blocks created is in
the UTXO set, every output they spent is gone, every height row names the right
block, every `tx_index` row points at the block that actually contains the
transaction, and every cumulative transaction count equals its parent's plus
its own. It reports *what* disagreed — the outpoint, the height, the txid —
never a boolean.

This is expensive and is not on any hot path. It backs the reorg scenario tests
below, and it is the basis for auditing a datadir offline.

An oracle is only useful if its verdicts are trustworthy in both directions, so
three ways it could lie were closed. It does not count outputs the UTXO set
never holds — an OP_RETURN, or a script over the size limit — because
`connect_block` never writes them; every post-segwit coinbase carries a
witness-commitment OP_RETURN and unspendables run at roughly a quarter of all
outputs at height 840000, so counting them meant millions of phantom faults and
a healthy mainnet node called corrupt. Blocks the node *pruned* are reported
apart from blocks it could not read, because pruned blocks are unreadable by
construction: folding them together failed every healthy pruned node and then
recommended `-reindex-chainstate`, which a pruned node refuses outright. And
the cumulative-count check is skipped when the backfill that populates those
rows has not run — auditing a datadir copied before that happened would
otherwise report a full window of faults against a perfect UTXO set.

Absent `tx_index` rows are judged against the datadir's own record of whether
the index was ever fully built. They are the correct state on a node running
without `-txindex`, which is why they were counted rather than listed — but
excluding them from the verdict unconditionally meant a node whose txindex was
genuinely broken was reported consistent, which is the one answer a diagnostic
must never give wrongly. Judging them against the `-txindex` *setting* alone
does not work either: that is just the flag the store was opened with, and an
offline tool pointed at someone else's datadir can have it wrong in either
direction. So the verdict now takes both the setting and the persisted
completeness marker, which is maintained atomically with the batches that would
invalidate it. Rows missing from an index that was never fully built — a node
that runs no index, or one where `-txindex=1` was switched on after syncing
without it — are reported as *unchecked* rather than either clean or damaged.
The marker does not weaken the fault this exists to catch: it is cleared only by
connecting a block with the index off, never by row loss, so a
complete-but-corrupted index still fails the verdict.

A block that cannot be read still bounds what can be concluded, but only below
itself. The walk runs newest-first and a coin created at height H can only be
spent at a height at or above H, so every create above the highest unreadable
block has a complete spend set and a sound verdict. Withholding the entire
window instead — as the first version did — means a single truncated block
hides every missing coin above it. That is not hypothetical here: this node has
seen both a truncated block and an eight-block UTXO hole, and together they
would have produced "1 block unreadable", no coins named, and a clean report
once the one block was repaired. The spent-coin check needs no such bound at
all: it only ever draws on blocks that *were* read, and their spends had to
have removed those coins regardless of what any unreadable block contained.

Two reorg tests now use it: branches that re-mine the same transaction, with
and without a flush between them. Both check the whole chainstate rather than
the one row a known defect touched, and both read **cold** — flushing and then
dropping every read-through cache before checking. That detail is the point.
The in-memory caches receive each operation in per-call order and stay correct
regardless of what the batch layer persisted, so a running node answers
correctly on top of an index that is already damaged. A test that checks a hot
node cannot see this class of defect at all; checked cold, both tests fail
against the pre-fix batching code.

### A reorg and the block connector could destroy each other's work

Every part of satd that mutates the chain takes one lock, `accept_lock`, so
that only one of them writes the UTXO cache and the tip at a time — every part
except the block connector, on the reasoning that the connector *is* the single
writer on the peer-to-peer path. That is true of the peer-to-peer path and
false of the node: an `invalidateblock` from RPC is a second writer, and it
runs a reorg that walks the replacement branch block by block, connecting each
one into the same cache the connector is connecting blocks into.

On a synced mainnet node the two met. The operator invalidated a four-block
stale branch; the reorg disconnected it and started reconnecting the canonical
blocks behind it, while the connector — which had been stuck on the invalidated
branch and was now free to move — connected the same blocks from the other
side. Whichever thread reached a given block second found its inputs already
spent by the first and failed `bad-txns-inputs-missingorspent`. That failure
was the reorg's, and a failed reorg rolls back by discarding every unflushed
change in the coin cache. The rollback assumes the cache holds nothing but the
reorg's own tentative work. It held eight blocks the connector had already
committed as well, and it threw those away too: their outputs vanished from
the UTXO set, the coins the invalidated branch had spent came back as
unspendable phantoms, and the eight blocks reverted to "downloaded but never
connected" while the tip stayed above them. The node then failed to connect the
next block, for the same missing coins, once a minute for five and a half
hours, and every flush in between wrote the damage to disk.

Nothing about the reorg or the rollback was wrong in isolation; the connector
running unsynchronised alongside them was. The connector now takes
`accept_lock` for the whole of both its connect paths — the block-index and tip
checks, validation, the write batch and the tip update as one indivisible
mutation. A connect that arrives while a reorg is in progress waits for it and
then re-reads the tip, so it either continues from where the reorg left the
chain or finds its block already connected; neither can produce a second
connect of the same block.

The cost is a lock acquire and release per block, uncontended during initial
sync and reindex. It is contended exactly where it must be: a connect that
overlaps an `invalidateblock` waits for it, which on a full mainnet block index
is tens of seconds. Bitcoin Core's connector waits on `cs_main` for the same
reason. A connector blocked there is now visible as
`phase=waiting_for_accept_lock` in the stall watchdog's output rather than as
an unexplained pause.

This class of bug does not announce itself, so it is worth being precise about
what was and was not affected. A node that never runs `invalidateblock` or
`reconsiderblock`, and never has a block submitted through `submitblock` or
mined internally while it is connecting, has only one chain writer and was
never exposed. The damage, where it happened, was confined to the UTXO set and
the block index: no block data was lost, and `-reindex-chainstate` rebuilt the
node correctly from the blocks it already had.

### The reorg rollback now checks the assumption it rests on

A failed reorg rolls back by discarding every unflushed change in the coin
cache. That is only correct if the cache holds nothing but the reorg's own
work — and until the fix above, one thread could put something else there.
The discard did not check; it could not, because nothing recorded who had
written what.

It does now. The flush exclusion a reorg holds for the length of its mutation
doubles as a claim to be the only thread writing, and any write arriving from
another thread while it is held is recorded — provided the rollback could
actually destroy it. A coin-free, tip-less batch (an index backfill's rows, a
prune's status stamps, a block arrival being recorded) passes straight through
to disk, untouchable by the discard, and is deliberately exempt: a multi-hour
address backfill beside an operator `invalidateblock` is a supported
combination, and misreading it as corruption would turn a safe rollback into a
needless halt. A rollback presented with a cache that has been *discardably*
written by someone else refuses: nothing is discarded, and the node stops
without flushing. Stopping is the point. The reorg's own checkpoint flush is
the last thing that reached disk and the exclusion guarantees nothing has
landed since, so the on-disk chainstate is consistent at — or, if the flush ran
in bulk-load mode, at an SST boundary before — that checkpoint; the process
ends without running the shutdown flush that would otherwise persist the
mixed-up cache, and the node restarts onto a consistent state and redoes the
work.

This changes nothing about a healthy node. Reaching the refusal means a chain
mutator is running without `accept_lock` — a defect of the kind that has just
been fixed once, not an operating condition — and the alternative to stopping
is the silent UTXO loss that made it worth fixing.

Making the assumption checkable immediately found a second writer that was
breaking it. An AssumeUTXO node runs a background chainstate that validates
history behind the snapshot, and while its UTXO work goes to a private
database, the block-index and height rows it writes go into the *shared* block
store — which is the snapshot chainstate's coin cache. Nothing serialised those
writes against that chainstate's reorgs: the write prunes superseded entries
out of the cache's pending buffer on its way through, the same buffer a reorg
stages its tentative rows in, and two unserialised writers in the one buffer a
rollback reasons about is the #567 shape again. The background now takes
the same lock for the shared write. It holds it only for that write, not across
its own validation, so the cost is one lock acquisition per background block.

### A reorg now leaves a record of itself

Reconstructing what happened in #567 was harder than it should have been,
because on the `invalidateblock`/`reconsiderblock` path a reorg wrote almost
nothing to the log. `perform_reorg` logged each block it disconnected; the
reconnect loop logged nothing at all; and an abort — which throws away the
whole cache delta and puts the tip back — logged nothing either. A reorg that
disconnected three blocks and then died left three lines and no indication
that it had failed. The only witness was the error string the RPC caller
happened to see.

Three lines were added, all on paths that run at most a few times a day:

- The chosen reorg, before any of it is done: the branch being left, the
  branch being taken, the fork point, and how many blocks each way.
- Each block the reconnect loop connects, matching the disconnect lines and
  the equivalent line the block-triggered reorg path already had.
- The abort, at error level, naming the block it failed on, the underlying
  error, the tip being abandoned and the tip being restored.

The same loops now also count for liveness. A deep reorg holds the chain
lock end to end, which parks the connector and flattens the heartbeats the
stall watchdog reads — a multi-minute `reconsiderblock` reconnect looked
exactly like a wedge and was a SIGTERM candidate. Every disconnected and
reconnected block now bumps the connect heartbeat, so a reorg making
per-block progress reads as progress, and only a reorg that stops does not.

### `invalidateblock` says when it only half-worked

`invalidateblock` marks the branch invalid, persists that, and *then*
re-activates the best remaining chain. The order is deliberate — a crash
between the two must not leave a truncated tip whose disconnected block still
reads `Valid` — which means a failure of the second half is a partial
success, not a failure. It did not report itself that way. The operator on
the #567 node ran `invalidateblock`, got back

```
{"code":-1,"message":"bad-txns-inputs-missingorspent"}
```

and had no way to tell from it that the branch *had* been invalidated, that
the tip was now somewhere else, or that anything was wrong beyond the command
not working.

The error now says so, and names the way back:

```
block index updated, but re-activating the best chain failed:
bad-txns-inputs-missingorspent. The node will retry activation as blocks
arrive; reconsiderblock undoes the invalidation.
```

`reconsiderblock` reports the mirror case the same way, with its own remedy —
re-running it — since "undo" is meaningless once the marks are already
cleared. One class of failure keeps its identity instead of being wrapped: a
deliberate refusal with an actionable message of its own, such as the
AssumeUTXO guard that refuses to reorg below the snapshot height, still
surfaces as the bad-argument error (`-8`) it always was, now with the
partial-success context appended. The JSON-RPC error codes are otherwise
unchanged — `-5` unknown block, `-8` bad argument, `-1` everything else, as
Core does — so only the message text differs.

### `/readyz` notices a connector that cannot make progress

Readiness was decided by chain lag alone. That misses a node wedged at its own
tip, and it misses one wedged mid-sync once its peers stop offering headers it
does not have. The #567 node failed the same connect once a minute for five
and a half hours with every health surface reporting fine.

A standing `connect.persistent_failure` warning — the connector has exhausted
its retries on a block — now fails `/readyz`. The warning clears on every
path out of the wedge, not just one: the connector's own eventual success,
the fork-handoff that tears the IBD connector down and hands recovery to the
steady-state reorg path, and any successful steady-state connect thereafter.
Without those last two, a node healed by the handoff would sit at 503 until
someone restarted it — the IBD connector that owns the only other clear site
never runs again once the tip tracks the headers. `/healthz` is unchanged and
stays a plain process-is-alive probe: a restart loop is a worse answer to a
wedged connector than a node that keeps running and says it is not ready.

### `loadtxoutset` now freezes the chainstate it is loading into

The same review found a second pair of writers with nothing between them.
`loadtxoutset` requires a fresh chainstate — a tip still at genesis — and
checked that once, at the start. The check was correct at the instant it ran
and meaningless a moment later: streaming a mainnet UTXO snapshot takes
minutes, and a node loading one is by definition a fresh node with its headers
already synced, which is exactly the node whose block connector is busily
connecting blocks from genesis. Nothing stopped the connector from advancing
the tip mid-stream. From there either ending was wrong: a snapshot rejected at
the final hash check rolled back by wiping the chainstate — including every
block the connector had committed — and a snapshot that passed adopted its
base block as the tip, clobbering the tip the connector had moved.

The precondition is now a claim rather than a check. `loadtxoutset` takes
`accept_lock`, verifies the chainstate is fresh, and raises a load-in-progress
flag before it streams a single coin; every chain mutator — the connector,
`submitblock`, `invalidateblock`, `reconsiderblock` — checks that flag
immediately after acquiring the same lock and refuses with a new
`SnapshotLoadInProgress` error until the load completes or fails. The flag
drops on every exit, success and failure alike. The block connector treats the
refusal as the pause it is: it parks and retries quietly instead of counting
the refusals against the retry budget that raises the operator-facing
persistent-failure warning. Block *download* and header acceptance continue
throughout — only chain mutation waits.

### The coin cache can no longer resurrect a spent coin

A node under sustained operation wedged for 54 hours looping
`bad-txns-BIP30` after an ordinary one-block reorg: 55 outputs created by the
*disconnected* block were still answering `gettxout`, 48 of them re-mined in
the very block the node was rejecting. The measured part
([#583](https://github.com/epochbtc/satd/issues/583)): the on-disk chainstate
was never wrong — a restart cleared all 55 and the node connected straight
through. The phantoms lived only in the in-memory clean-coin LRU.

The mechanism is a small family of insert-after-invalidate races. Batch
absorption invalidates correctly — every coin write pops the clean LRU before
staging its dirty entry — but three paths insert into that LRU from data read
*outside* its lock: `get_coin`'s read-through populate, `get_coins_batch`'s
(whose window spans a whole batched store read), and the flush's promotion of
drained coins (whose window spans an entire backing-store write). A reader
that fetched a coin just before a disconnect retired it could re-insert it
just after. The stale entry sits masked behind the dirty `Spent` marker —
reads still answer correctly — until the next flush drains that marker to
disk, at which point the mask is gone and the clean LRU answers with a coin
the store deleted. Nothing evicts it: every re-read refreshes its LRU
recency, so a retry loop (BIP30 re-checks the same outpoints every ~30
seconds) keeps it alive indefinitely.

The clean LRU now carries an invalidation generation. Every coin-carrying
batch bumps it; the three insert sites snapshot it before their unlocked
read and decline the insert if it moved. A declined insert costs one warm
cache entry — the caller still gets its answer, and the next read re-fetches
through the store. Each of the three interleavings is pinned by a
deterministic test that parks the racing thread inside its window while the
spend lands.

Worth keeping from the incident: a `bad-txns-BIP30` (or
`bad-txns-inputs-missingorspent`) wedge that survives retries is **not**
proof of disk corruption. Restart first and re-measure — it is cheap, and it
discriminates cache staleness from real damage before anyone pays for a
reindex.

### A failed UTXO-cache flush no longer throws the delta away

Found while auditing the coin cache after the reorg incident, and independent
of it.

The flush builds one batch out of everything buffered — the dirty coins, the
block-index, height, undo and transaction-count rows, the pending tip — and
empties all of them *before* handing the batch to RocksDB, so that reads are
not held behind a write that can take seconds. When the write succeeds that is
exactly right. When it fails, a whole flush window's worth of UTXO changes had
just been erased from memory with nothing left to retry from, and the node
carried on as though the flush had worked. A full dbcache window is hundreds of
thousands of coins; the trigger is anything RocksDB reports an error for, a
full disk being the obvious one.

The write now hands the batch back when it fails, and the cache puts everything
where it was: coins, buffered rows, tip, counters. Reads answer as they did
before the attempt and the next flush writes the complete delta. Two details
are worth stating because they are deliberate:

- Restored coins come back marked as possibly-present in the backing store even
  if they were known-absent before. That flag is what allows a create-then-spend
  pair inside one window to skip the store entirely, and after a failed write it
  is no longer safe to assume anything was written. The conservative direction
  costs at most a redundant delete of a key that was never written, which
  RocksDB treats as a no-op.
- A write that landed while the failed flush was in flight wins over the
  restored value. Dropping the lock before the write is what allows that write
  to happen at all, so the restore has to yield to it.

Anything written since the drain is preserved, and the store trait now carries
this as an explicit contract rather than an assumption: what comes back on
failure is the *unapplied remainder* — for a single atomic store, the whole
batch untouched; for the AssumeUTXO background's split store, exactly the half
that did not land. A coins-side failure there returns the coins delta (tip
included) while the block rows that already reached the shared index stay put
and are not replayed — replaying absolute index rows later could resurrect a
status a newer writer had since retired, and the old behaviour of writing the
whole delta off as unrecoverable threw away work a retry could have saved. A
backing store that genuinely cannot describe what it applied still has to say
so, and the cache logs that case as unrecoverable instead of pretending it
retried.

### `invalidateblock` no longer strands the connector on the dead branch

The same mainnet incident began with a stall. The operator invalidated a
competing branch, satd truncated the chain back to the fork point as it should,
and then the connector logged

```
Connector stuck waiting for block data  height=961632 block_index_status=Some(Invalid) has_height_to_hash=true
```

every minute — the line is throttled per stuck height — for the next five and
a half hours. The canonical block at that height was on disk the whole time.

The connector picked its next block by asking the height→hash index for
`tip_height + 1`. That index is "best known block at this height", not a
statement about the active chain, and nothing rewrites it when a branch is
invalidated — so it kept handing back the block that had just been marked
dead. This is the same "address by height, not by chain" family as the
`accept_header` clobber and the median-time-past walk, both fixed previously.

The row is not obviously wrong, which is what made it durable: the invalidated
block's parent *is* the fork point, so it is a genuine child of the tip. Only
its status disqualifies it.

The connector now checks that the block a height row names can actually extend
the active chain, and when it cannot, selects the tip's best connectable child
directly from the block index instead. The healthy path is unchanged and still
costs one point lookup — including for a header whose block has not been
downloaded yet, which is selected exactly as before so the connector waits for
data rather than paying for a scan. The scan runs only on genuine disagreement,
and is bounded by the length of the dead branch: connecting a block rewrites
its own height row, so each damaged height is repaired once.

The healthy path costs two point lookups rather than the one the connector read
before: the height row, then its entry, because the status is the whole point.
The fallback only runs when that row cannot extend the tip, and it is
rate-limited to one scan per thirty seconds for the same stuck `(tip, height)`
— so between scans the connector still reads the row, exactly as it did before.
The scan itself filters as it goes instead of building an adjacency map of the
entire block index first; on mainnet that is the difference between a transient
allocation in the hundreds of megabytes and none, on a node that by definition
is already having a bad day. If that scan fails partway it is not treated as
"found nothing": the storage error is logged and raised as a node warning rather
than swallowed, and the connector still prefers the best candidate the scan
reached before the fault, falling back to the height row only when it reached
none. That preference is the point. Anything the scan admitted has already been
checked to be a stored child of the current tip, which is exactly what the
connector requires, so a partial candidate is connectable by construction; the
height row is the thing this whole path exists to route around. Preferring the
row would trade a transient suboptimality — a lower-work sibling, which the
ordinary reorg path corrects afterwards — for a permanent wedge, because the row
is rejected as `Duplicate`, the fork-handoff recovery tests for a different
error and never fires, and the next scan meets the same persistent fault. The
warning is cleared as soon as a scan completes, so a transient fault does not
leave a standing error pinned for the life of the process.

One more stall shared the same shape and is fixed alongside it. A height row
naming an already-connected block — a reorg displaces it and `disconnect_block`
writes no status, so the `Valid` marker sticks — was rejected by
`connect_stored_block` as `Duplicate`, which the connector treated as harmless
and retried immediately, with no sleep and no retry counter. That is a core
spinning at 100% for as long as the condition lasts, and unlike the stall above
it is silent. `Duplicate` now counts toward the retry limit like any other
connect error, so the existing fork-handoff recovery runs instead.

### `bad-txns-inputs-missingorspent` now says which outpoint

When a block fails to connect because an input's coin is not in the UTXO set,
satd logs the outpoint, the spending txid, the input index and the height. The
reject reason on the wire and in RPC errors is unchanged — it is Core's string,
verbatim.

This is usually the first visible symptom of a UTXO set that has quietly lost
coins, and without the outpoint, localising the damage is a bisection over the
whole chain. With it, one log line names the block.

### `confirmations` now distinguishes the active chain from a losing branch

`confirmations` was derived from a block's height and nothing else: if the
height was at or below the tip, the block was reported at that depth. Nothing
checked whether the block was actually *on* the active chain. A valid block from
a losing branch therefore reported the depth its height implied — a stale block
60,000 deep claimed 60,000 confirmations — where Bitcoin Core reports `-1`.

`nextblockhash` had the matching flaw: it was resolved through the height index,
so an off-chain block was handed the *active* chain's successor.

The two together had a sharper consequence than either alone. A stale block and
the canonical block at the same height became indistinguishable through satd's
own RPC — same `confirmations`, same `nextblockhash`, and (legitimately) the
same `previousblockhash`, `chainwork` and `height`, because two siblings share
all of those. An operator investigating a fork could not tell the two apart
without cross-checking against another implementation.

Both are fixed across `getblock`, `getblockheader` and `getrawtransaction`.
Note that Core's conventions differ by RPC and satd now follows each:
`getblock` and `getblockheader` report `-1` for a block that is not on the
active chain, while `getrawtransaction` reports `0` for a transaction whose
containing block is not on it.

### `mediantime` is now a median

`mediantime` returned the block's own timestamp on `getblock`,
`getblockheader`, `getblockstats` and `getblockchaininfo`. It is now the median
of the block and its ten ancestors, as Core defines it.

It is computed by walking parent pointers rather than the height index, so a
block off the active chain is measured against its own ancestry instead of
whatever the active chain holds at those heights — the same reasoning that
makes the `confirmations` fix meaningful.


### A crash could strand a block's index entry over block bytes that never landed

Block bodies live in the `blk*.dat` flat files; the `block_index` entry for a
block records the file and offset its record starts at. Those are two
independently buffered write streams, and outside bulk-load mode nothing
ordered them: RocksDB's write-ahead log carried the index entry into the page
cache without an fsync, and the flat-file append sat in the page cache too. A
kernel panic or power loss between the two could write back the pointer and
lose the payload.

`ChainState::flush_durable` has always fsync'd the flat files before the
RocksDB memtables for exactly this reason, but that ordering only binds *at a
flush*. Between flushes the window was open.

The damage is quiet. Consensus never notices, because the block's UTXO delta
was applied when it connected and is never revisited — the node stays at the
tip, fully synced, `verificationprogress` 1.0. What breaks is everything that
re-reads a body: `getblock` and `getblockstats` return `-5`, any index backfill
walking that height fails hard, and a peer's `getdata` for the block cannot be
served. On one mainnet node this surfaced 48 days after the fact, when
a silent-payment backfill died at 97.3% on a single block whose record had been
cut at a 4 KiB page boundary, 1.6 MB short of where the index said it ended.

**Fixed** by fsyncing a block's flat-file record before the index entry
referencing it can be committed. The fsync is unconditional, including during
initial block download.

An earlier revision of this fix skipped it under the bulk-load write mode used
for IBD, on the theory that disabling the write-ahead log meant an index entry
could only become durable through the periodic flush — which fsyncs the flat
files first. That reasoning was wrong, and a review caught it: disabling the
WAL does not stop RocksDB from flushing a memtable to an SST on its own.
Write buffers are per-column-family and atomic flush is enabled, so the 64 MB
`coins` buffer filling during IBD drags `block_index` to disk with it, while
the flat files are only fsync'd every ~1000 blocks. **IBD was the more exposed
path, not the safe one** — a kernel panic mid-sync could leave many holes at
once, and the node then parks waiting for block data it will never find.

The cost is one fsync per stored block. In steady state that is nothing; during
IBD it is real but bounded, and it is not optional. Amortizing it properly
means deferring `block_index` writes until the record they reference has been
synced, which is Bitcoin Core's model and a larger change than this fix.

Two smaller instances of the same failure class are closed alongside it: a new
`blk*.dat` file now has its directory entry fsync'd before it is written into,
and a write that fails partway (ENOSPC mid-record) now truncates the torn
record instead of appending past it — the sequential scanners used by
`-reindex` have no resynchronization, so a torn record would have silently
hidden every block after it in that file.

Existing datadirs are not audited or migrated on upgrade. A hole punched by an
earlier crash stays until it is repaired — see below.

### `getblockfrompeer`: repair a lost block without a resync

Until now a single unreadable block body had no recovery path short of
re-syncing the whole chain. satd now implements Bitcoin Core's
`getblockfrompeer` RPC, which asks one peer for one block:

```sh
sat-cli getblockfrompeer <blockhash>            # satd picks a NODE_NETWORK peer
sat-cli getblockfrompeer <blockhash> <peer_id>  # or name one from getpeerinfo
```

The reply is routed to a repair path rather than the normal accept path — which
would reject it as a duplicate, precisely the case that needs handling. The
block's record is rewritten and its index entry repointed, preserving status,
height, chainwork and header. Like Core, the call returns once the request is
sent; the repair happens on arrival and logs `Repaired block data from a
peer-supplied copy`.

Three differences from Core, and they are not all in the permissive direction:

- **`peer_id` is optional.** Core requires it. When omitted satd picks a
  connected `NODE_NETWORK` + `NODE_WITNESS` peer. A *malformed* peer id is an
  error, not an auto-select.
- **"Block already downloaded" means the stored bytes are the canonical
  block**, not that the index status flag is set. Core tests the flag, which
  refuses exactly the case this RPC is most useful for: an entry claiming to
  hold data whose record is gone. satd goes one step further than "do the bytes
  read back", because that is not the same question — witness bytes sit outside
  everything the block hash commits to, so a copy can deserialize and hash
  correctly while carrying a padded, truncated or stripped witness. Such a copy
  is replaced. Nothing else would ever surface it: `getblock` on it succeeds.
- **More restrictive than Core: pruned blocks are refused.** Core allows
  re-fetching them; satd will not repopulate data the prune accounting no
  longer tracks, and says so up front rather than failing after the download.

Error message strings are close to Core's but not identical, and named
arguments are not supported (a satd-wide limitation, not specific to this
method).

A block we hold only the header for is *not* repaired through this path. It is
handed to the normal block-download path instead, which applies the checkpoint
and signet block-solution checks the repair path does not — and, unlike a
repair, actually connects the block.

The supplied block is untrusted and is authenticated before anything is
written. Its hash must match a header already in our index — carrying the
proof-of-work, difficulty and checkpoint checks made when that header was
accepted — and its transactions must match the merkle root that hash commits
to, with CVE-2012-2459 mutation rejected.

The witness check is the subtle one, and it needs both of Bitcoin Core's rules
rather than just the obvious one. A block's merkle root commits only to txids,
so any witness edit leaves the merkle root and the block hash untouched. So:
when a BIP 141 commitment output is present (and segwit is active at that
height) the coinbase witness must be exactly one 32-byte item and the
commitment must verify; otherwise no transaction may carry witness data at all.
Together those pin every witness byte, so the supplied bytes can only be the
block's canonical serialization.

Getting only the first half of that right is easy, and the first revision of
this change did: it verified the commitment but inherited a witness scan that
skips the coinbase input. Since nothing commits to the coinbase witness — the
merkle root covers txids, and the coinbase wtxid is hardcoded to zero in the
witness root — a peer could append junk to it, shorten it, or drop it
altogether and still pass. Those bytes would have been persisted as our
authoritative copy: non-canonical forever, re-accepted by a later `-reindex`,
and grounds for every Core peer to ban us the moment we served that block. An
independent review of this PR caught it before release.

A peer whose reply fails these checks is banned. Peers that cannot serve
witness data are excluded from selection up front rather than punished for
answering as best they can.

The height those witness rules are gated on is taken from the block's own
parent link, not from the index entry, and the two must agree. The link is
inside the 80 bytes the block hash commits to; `entry.height` is state
belonging to the very index this RPC exists to repair. A disagreement refuses
the repair — and deliberately not as a validation error, so an honest peer is
not banned for our damaged index.

Pruned and invalidated blocks are refused. Both states are deliberate operator
or consensus decisions, and repopulating them would contradict the decision
that produced them (and, for pruned blocks, desynchronize the prune
accounting).

`getblockfrompeer` is classified as a control-plane method: it is rejected on
the read-only listener and requires `rpc:write` under capability-scoped bearer
tokens.

### A reorg could delete the height and txindex rows the replacement block had just written

`getblockhash` answered `-8: Block height out of range` for two heights in the
middle of a healthy active chain on a synced mainnet node — neighbouring
heights intact, the blocks themselves fine, only the reverse height→hash entry
missing. It turned out to be a batching defect that also affects the
transaction index, where the consequences are worse.

The chainstate cache buffers non-coin index operations into a single pending
`StoreBatch` while coin writes are outstanding, and flushes them together. A
reorg feeds that buffer twice: disconnecting the displaced block emits a remove
for height H, and connecting the replacement emits a put for height H, in two
separate `write_batch` calls with no durable flush between them. Both land in
one batch. A `StoreBatch` is applied as every put followed by every remove, so
the remove ran second and annihilated a row that should have survived — the put
was the later operation.

The address, filter, outpoint-spend and silent-payment indexes were already
deduplicated by key when batches merge, for exactly this sequence. The height
index and the txindex were not; they were plain-appended, so a put and a remove
for the same key could coexist in one batch and resolve by apply order rather
than by which operation came last.

What made it hard to notice is that the in-memory caches are correct. They
receive each operation in per-call order, so a *running* node answers from
cache no matter what persisted.

How long that hides the damage differs sharply between the two indexes, and
the difference matters for anyone deciding whether their node is affected. The
height cache is a fixed two million entries — enough to cover the whole chain
— so a missing height row genuinely stays invisible until a restart, possibly
weeks after the reorg. The txindex cache is sized from `-dbcache` (5% of it, at
64 bytes per entry: roughly 350,000 entries at the default), which at mainnet
transaction rates is on the order of a day's blocks. Once the row is evicted the
lookup falls through to the empty on-disk entry. **A long-running node is not
protected from the txindex symptom** — it surfaces on its own, without a
restart, and looks exactly like a transaction that was never mined.

The txindex exposure is the more serious of the two and the likelier to be hit.
Its trigger is the ordinary behaviour of a reorg: the displaced block's txids
are removed and the replacement chain re-mines the same transactions, colliding
put and remove on the same txid. The result is `getrawtransaction` reporting a
transaction that *is* in the chain as unknown, silently, with no other symptom.

A missing height row is not purely cosmetic. `median_time_past` resolves the
eleven-block window through the height index on the connect path, and MTP gates
BIP 113 locktimes and BIP 68 time-based sequence locks — so a dropped row
inside that window shifts the median and turns a consensus decision on data the
node does not have. Reaching it takes a narrow coincidence: the reorg has to be
followed by a restart while the affected height is still within eleven blocks
of the tip, since until the restart the warm cache answers correctly. Narrow,
but not cosmetic, and it is the reason this is worth an out-of-band note rather
than a changelog line.

A chainstate reindex is not exposed — it resolves MTP through the replay plan
specifically because the height index is derived state that cannot be trusted
mid-replay. Index backfills are not exposed either: they walk parent pointers
rather than the height index, which is why a silent-payment backfill ran
straight past both damaged heights without noticing them.

**Fixed** by giving both indexes the same last-writer-wins merge the other
indexes have, so a merged batch's puts and removes are disjoint by key and the
apply order stops mattering.

The fix stops new rows from being lost. For the height index, the startup audit
described next also cleans up rows already gone; for the txindex, `-reindex`
remains the repair.

### The height index is now audited and rebuilt at startup

A missing height→hash row never needed a reindex to fix. The height index is
derived state: for every height at or below the tip there must be exactly one
row, and the active chain is the tip's ancestry by definition. So satd now
checks it on every start and rebuilds what is missing by walking parent
pointers down from the tip.

The check is one sequential scan of the index — the cheap direction, versus a
point lookup per height. On a clean node it allocates a presence map, finds
nothing and writes nothing, which is the only outcome almost every node will
ever see. On a mainnet-sized index the scan costs roughly 0.4 s, and it runs
before the node serves RPC or connects to peers so that nothing can observe a
damaged index.

Deriving from the tip's ancestry rather than from neighbouring index rows is
the load-bearing choice. An earlier revision of this work anchored each gap on
the row one height above it and read that block's parent pointer, which is
wrong in two ways that a review caught: it consults rows this very pass
declares untrustworthy, so a fork block whose divergence point was the gap
itself satisfied every corroborating check and got written; and across a run of
consecutive gaps only the bottom of the run was checked, so the pass could
queue several rows, discover the branch was wrong, and persist them anyway.
Walking the tip's ancestry removes the entire class — there is no anchor to be
wrong about.

What it deliberately will not do:

- **It only adds rows for heights that have none.** A row that is present but
  points at the wrong block is never overwritten. Correcting one means
  adjudicating between competing blocks by chainwork, and silently replacing a
  row the node believes in would be a worse failure than the gap. Rows the walk
  passes that disagree with the tip's ancestry are logged, so the condition is
  visible rather than silent.
- **It refuses what it cannot derive.** A broken parent chain, or a block whose
  index entry misreports its own height, stops the walk rather than being
  guessed past. Everything below stays a gap and is reported.
- **It separates "not yet validated" from damage.** Heights whose blocks this
  chainstate has not connected — the ordinary state of an AssumeUTXO snapshot's
  history while background validation works through it — are reported as
  pending, not as faults. Blocks that were connected and later pruned keep
  their header and are still repairable, so pruned nodes are covered too.
- **It declines a rebuild.** Past half the range being absent — and past a
  floor under which small counts always repair — the pass reports and does
  nothing, rather than building from scratch an index it exists to repair.

Gaps it cannot rederive are logged at error level with the heights involved.
Those still need a `-reindex`.

#### The en-masse threshold is a share, not a count

That last point shipped as an absolute number — a thousand gaps — and the
number was wrong in a way worth writing down, because it looked like a safety
guard and was not one.

It did not bound cost. The walk costs one block-index read per height between
the tip and the *lowest* gap, so what it is paying for is how far down the
damage reaches, not how much of it there is. A thousand gaps packed under the
tip is a cheaper repair than a single gap near genesis, and a count-based
threshold waved the expensive one through while stopping the cheap one.

It did not bound risk either. The pass writes a row only for a block it reached
by walking the tip's own ancestry *and* whose status is `Valid` or `Pruned`.
That check is per height and unconditional, so a chainstate that has not
validated its history — the case the threshold named — writes nothing whatever
the threshold is set to. Removing the count removed no protection.

What it did do was decline real repairs and then explain them wrongly. A node
on a chain that reorgs frequently accumulated a few thousand missing rows in
its recent history, all of them derivable, the whole walk under a second. Every
restart it declined, and logged that an AssumeUTXO snapshot's history was still
being validated — on a node that had never loaded a snapshot. Any node on a
reorg-heavy chain reaches that count eventually and silently stops self-healing
from then on.

The threshold is now a share of the heights at or below the tip, with a floor
under which a small gap count is always repaired — a tip-at-genesis chain
whose one row is lost is "100% absent" yet costs nothing to fix, and a short
regtest chain with most rows gone is a trivial walk; the floor only ever
*permits* repairs, so it cannot recreate the old ceiling's defect. Damage in
the percent range is repaired however many rows it spans; only an index that
is mostly absent — which is a rebuild, and a reindex's job — is declined.

When the pass does decline, the log now says only what it can actually see.
With an AssumeUTXO background validator attached, wholesale absence is the
expected shape of not-yet-validated history and the message says so at info
level — it does not advise a `-reindex` that would cost the operator the
snapshot's entire benefit. Without one, the same condition is real damage and
is reported as such, at warn, with the reindex advice attached.

One cost is accepted knowingly: a snapshot node whose background validation
has crossed the halfway mark now runs the ancestry walk at each restart —
reads only, nothing written, every unvalidated height reported as pending —
where the old count guard happened to skip it. The walk shrinks as validation
advances and disappears when it completes.

### Core v28+ XOR-obfuscated block files (`blocksxor`)

Bitcoin Core v28.0 (October 2024) started XOR-obfuscating the `blocks/*.dat`
payloads on disk by default, keyed by a random 8 bytes persisted in
`blocks/xor.dat`. satd previously read block files raw, so the migration path
in `CORE_DIFFERENCES.md` — keep Core's `blocks/` dir, `-reindex-chainstate`
into satd — silently failed against any datadir created by Core v28.0 or
later.

satd now speaks the same on-disk dialect:

- **An existing `blocks/xor.dat` key is honored automatically** on every
  read and write path (block fetch, `-reindex`, `-reindex-chainstate`,
  the block-file audit, `satd-chainstate-repair`). Pointing satd at a
  default modern Core `blocks/` directory needs no configuration.
- **Plaintext stays satd's native format**: a freshly initialized blocks
  dir gets the all-zero key (recorded in `xor.dat` for Core
  interoperability), and existing satd datadirs are untouched — the zero
  key short-circuits the XOR entirely, so the plaintext path costs
  nothing. This deliberately diverges from Core's default of obfuscating
  new dirs; set `blocksxor=1` to opt into a random key on a brand-new
  blocks dir.
- **`blocksxor` is now a real option** (previously recognized-but-ignored):
  unset honors whatever the dir carries; `1` matches Core's default
  behavior for fresh dirs; `0` demands plaintext and refuses to start on a
  dir whose stored key is nonzero (Core-parity fail-closed, since silently
  ignoring the key would corrupt every subsequent write).
- Reindex scans also terminate cleanly on Core's zero-preallocated file
  tails under a nonzero key, and a block read under a mismatched key fails
  with a clear error instead of returning garbage.

Restart-required; not hot-reloadable via SIGHUP.

### `-reindex` now picks the most-work branch at a fork

`-reindex` rebuilds the block index and UTXO set by replaying the `blk*.dat`
files. Those files are a block *tree*, not a chain: Core and satd both persist
every block they fully receive, including ones a later reorg orphaned, so any
datadir that has been live through a reorg has fork points on disk — one parent
with two children.

The replay walked that tree breadth-first and connected **every** block
reachable from genesis as if it extended the tip, with no chainwork comparison.
At the first fork that produced one of two outcomes:

- **Loud.** If the two branches spent a coin in common, the losing block
  connected first, the winning block was then handed an already-spent input, and
  the reindex aborted with `bad-txns-inputs-missingorspent` — potentially days
  into a mainnet rebuild.
- **Silent, and worse.** If the branches did not conflict, the losing block
  connected *successfully*: its coinbase and spends were applied on top of the
  winning chain, and the reindex ran to completion reporting success over a UTXO
  set that no longer matched consensus.

This was most likely to bite exactly where `CORE_DIFFERENCES.md` points
operators: migrating a Bitcoin Core datadir into satd. A Core node that finished
IBD and then ran live accumulates orphaned blocks from that point on, so the
first fork tends to sit at the height where the node went live — far enough into
the replay to have cost hours or days first.

The replay now selects the branch with the most cumulative chainwork (not the
greatest depth — depth agrees on mainnet but is the wrong metric across a
difficulty transition) and connects only that branch, matching what
`ActivateBestChain` does on the live path. Blocks off the winning branch are
written to the block index as `DataStored` and left unconnected, so
`getblockheader` on an orphaned hash keeps working across a reindex and the
branch stays available should it later be extended. Duplicate records for the
same block are collapsed to the first copy on disk.

No configuration change, and nothing to do beyond running the fixed binary: a
reindex that previously aborted now completes, and one that previously
"completed" should be re-run.

### `-reindex-chainstate` selects by chainwork instead of trusting the height index

`-reindex-chainstate` keeps the block index and replays the chain to rebuild the
UTXO set. It used to decide *which* chain by walking the height→hash index —
height 1, 2, 3, and so on.

That index is derived state. It names the active chain, and it has been observed
polluted with a fork block in production (the `bad-cb-height` reindex loop).
Given such an index the replay connected the fork block, carried on with the main
chain on top of it, and **reported a successful reindex** over a UTXO set
assembled from two branches — the same silent corruption as the `-reindex` bug
above, reached through a different door.

The replay now derives its chain from the block index itself, which is
self-authenticating in the way that matters: every entry carries the block
header, and a header names its parent by hash. Selection picks the most-work
fully-connectable branch, **recomputing** cumulative chainwork and height from
those headers rather than trusting the index's own `chainwork` and `height`
fields, so a damaged index cannot misdirect the replay through them either. A
polluted height→hash entry is now simply irrelevant — it is not read, and the
replay rewrites it on the way past.

Selection also honors block status, so an `invalidateblock` still holds across a
chainstate reindex (an invalid block and everything descending from it is
excluded), and a branch with a header-only hole in its ancestry is passed over
in favor of one that can actually be replayed.

Branch selection also validates proof of work before trusting a header's
`nBits`. An 80-byte header always deserializes — every field is a fixed-width
integer — so one flipped bit in an exponent yields a well-formed header claiming
an astronomical target. Since block connection checks no PoW either, such a
record would have out-scored the honest chain, been connected, and left the node
pinned on a branch it could never reorg away from while holding all the honest
block data on disk.

Two further changes fall out of this:

- **The replay must reach the height the chainstate was already at.** Selection
  admits only data-carrying blocks and requires every ancestor to qualify, so one
  ineligible block low in the chain truncates the plan — or empties it. A pruned
  datadir hits this every time. `-reindex-chainstate` now records the tip height
  before clearing the chainstate and fails closed if the block index cannot
  reach it, naming the shortfall, instead of reporting a completed reindex over
  a truncated or empty UTXO set.
- **An exact chainwork tie keeps the chain the node was already on**, matching
  the consensus first-seen rule rather than resolving by block hash.
- **A partial chainstate on a different branch is not resumed.**
- **All reindex paths now verify each block extends the chain being replayed** —
  the invariant `connect_stored_block` has always enforced on the IBD path. This
  sits behind the selection fixes as a belt-and-braces check: `connect_block`
  applies a UTXO delta computed against the *current* set, so a future bug in
  either picker fails loudly instead of committing a spliced chainstate.

### A reindex now validates the blocks it replays, and the index it reads them through

Two classes of trust remained after the selection work above, both in the same
place: the replay believed things about a block without deriving them from the
block.

**The block bytes were never re-checked.** Flat-file records carry no checksum —
the framing is a magic number and a length — and the 80-byte header is only 80
bytes of a record that can be megabytes. A bit flipped inside a transaction
payload therefore left the header hashing correctly, passed the PoW re-check,
matched the hash the plan asked for, and was connected: the corrupted UTXO delta
landed and the reindex reported success. Every replay path now runs full
context-free validation (merkle root, witness commitment, duplicate
transactions, weight) on the bytes it read, which is what Bitcoin Core's
`CheckBlock` does at the same point. On the chainstate-reindex path this runs on
the prefetch workers, off the connect thread.

**Median time past came from the height→hash index.** MTP gates BIP113 locktimes
and, evaluated at a spent coin's height, BIP68 time-based sequence locks — so it
is a consensus input, and it was being resolved through the one structure a
reindex exists to distrust. It is now resolved through the branch being
replayed. The coin-height lookup matters most: a coin spent near the tip can
have been created at any height in history, so unlike the block's own MTP it is
not confined to a window near the connect cursor.

Alongside that, the header stored in the block index must now match the header
in the block file before either replay path will use its parent link, its
`nBits` or its timestamp — the index keys entries by block hash, but nothing
constrained the stored header to be the one that hashes to that key.

That check is what makes the replay's verification **inductive**: every block it
connects is reconciled with the block files before anything reads the entry, so
each parent link, chainwork value and MTP timestamp it consumes is backed by the
files. The induction needs the run to start at genesis, so **a partially-replayed
chainstate is no longer resumed** — the replay starts at genesis or refuses.
Nothing changes in practice, because satd already cleared the UTXO set before
every `-reindex-chainstate`; a crashed replay was restarted, never resumed. What
changes is that it is now the rule rather than a property of the caller. Starting
above genesis would validate the blocks above the resume point against index
entries below it that nothing reconciled, and BIP68 makes that hole unbounded: it
evaluates a spent coin's MTP at the coin's *creation* height, which can be
anywhere in history, so no fixed window of verification covers it. Genesis
itself — the one header the replay consumes but never connects — is compared
against the network constant.

## Logging

Two operator-facing log-hygiene changes; no configuration and no format change
to the structured (JSON) log:

- **Per-transaction mempool acceptance is now `debug`, not `info`.** Under
  normal load the node accepts a transaction per mempool entry, so the
  "Transaction accepted to mempool" / "RBF replacement accepted to mempool"
  lines dominated the default-level log. They now sit at `debug`; raise
  verbosity to see them.
- **ANSI color is auto-detected.** The text log colorized unconditionally, so
  escape sequences leaked into `journald` and any piped or redirected log.
  Color is now emitted only when stdout is a terminal and `NO_COLOR`
  (<https://no-color.org>) is unset, so captured logs stay clean. A real
  terminal is unchanged.

## Upgrade notes

**A remote events-gRPC bind with bearer auth now requires TLS.** If you run
`eventsgrpcallowremote=1` with `eventsgrpcauth=1` and no certificate, the node
will refuse to start on this release. Either set `eventsgrpctlscert` and
`eventsgrpctlskey`, or switch to `eventsgrpcmtls=1`, or bind loopback behind a
TLS-terminating proxy and drop `eventsgrpcallowremote`. This is a deliberate
break: the previous configuration put a bearer token — and any BIP 352 scan key
registered over the stream — on the wire in the clear. Loopback binds and mTLS
deployments are unaffected.

**SDK callers pairing a bearer token with a plaintext endpoint now get an
error** rather than a silent cleartext send. Use TLS — an `https://` endpoint
plus `tls()`/`tls_ca_pem()` on the Rust SDK (the `tls` feature is default-on;
a `default-features = false` build cannot encrypt anything and refuses a token
on every endpoint), any `WithTLS*` option or an `https://` target on the Go
SDK — or `insecure_bearer_token` / `WithInsecureBearerToken` for loopback and
tests.

Otherwise no action required — the silent-payment index is off by default; with
the flag unset, a node's defaults and on-disk behavior are byte-identical to
0.4.0.

The `blocksxor` support is likewise a drop-in: existing satd datadirs remain
plaintext; the only on-disk change is a new 8-byte `blocks/xor.dat` file
(all-zero for existing dirs) written on first start, which Core v28+ also
understands. Note that a blocks dir *created* with `blocksxor=1` is not
readable by satd 0.4.x or earlier.

**Block writes are now fsync'd.** A block's flat-file record is made durable
before the index entry referencing it is committed, on every write path
including initial block download. This is a correctness fix, not a tunable, and
it costs one fsync per stored block; expect some IBD throughput cost against
0.4.0 on slower storage.

**Existing datadirs are not audited on upgrade.** If an earlier crash left an
index entry pointing at block data that never reached disk, that hole persists
until it is repaired with `getblockfrompeer` — see
[Repairing lost block data](https://epochbtc.github.io/satd/disk-footprint.html#repairing-lost-block-data).
The symptom is a single block returning `-5 Block data not available` on a node
that is not pruning, usually surfacing as an index backfill that fails at one
height.

**A webhook URL of `http://169.254.x.x/...` now fails at startup.** The
plaintext-HTTP gate no longer waives IPv4 link-local (see *Alerting & node
health*), and a bad `alertfile` is fatal at startup by design — a node that
came up "successfully" with alerting silently off is the failure an operator
notices last. If you have a link-local hook URL, either move it to `https://`
or add `allow_insecure_http = true` to that `[[webhook]]` stanza **before**
upgrading. The startup error names the webhook id and both options. No other
address range changed: loopback, RFC1918 and IPv6 unique-local are waived as
before.

If you ran `-reindex` on 0.4.x or earlier against a datadir that had been live
through a reorg, re-run it on this release. A reindex that aborted with
`bad-txns-inputs-missingorspent` left nothing usable; one that completed may
have a UTXO set that silently disagrees with consensus. The same applies to a
`-reindex-chainstate` run over a datadir that had previously logged
`bad-cb-height` or any other sign of a damaged block index — on this release
that run is no longer misdirected by the damaged index, so re-running it is the
fix.
