# Changelog

A terse index of satd releases. **Full, explanatory release notes live in
[`docs/release-notes/`](docs/release-notes/)** — one file per release; this
file points there for detail and keeps only a short list of unreleased changes.

Format is loosely based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/);
satd follows [semantic versioning](https://semver.org/spec/v2.0.0.html) for its
Tier 1 public surfaces (RPC method shape, CLI flags, `bitcoin.conf` syntax, file
layout) per [`STABILITY_POLICY.md`](STABILITY_POLICY.md).

## [Unreleased]

Bound for **0.6.0**, a minor release on the 0.x line. This is an index: every
item below is (or will be) written up in full in the in-development
[`docs/release-notes/0.6.0-pre.md`](docs/release-notes/0.6.0-pre.md).

### Changed

- `satd-init` (the reference stack, Umbrel and StartOS) writes `upgradechainstate=1` for a satd that has the flag, so an app-store node rebuilds its chainstate from the block files by itself on the first start after a release that changes the format, and restarts a rebuild a power cut interrupted.
- sat-tui draws the mempool size and UTXO age histograms as log-scaled bar charts, four rows tall with each bucket's count on its bar, instead of one-row linear sparklines that showed the largest bucket and flattened the rest. Both tails of each distribution are now visible. The age chart marks its young buckets as estimates while the node is still building its exact counts.
- **Storage: every index is keyed on a dense transaction ordinal instead of a 32-byte txid.** Four schema steps, 3 → 7, and **one** `-reindex-chainstate` for all of them; the block files are untouched and nothing is re-downloaded. A fully indexed mainnet chainstate is projected to drop from ~826 GB to ~449 GB. Pruned datadirs must resync. The four bullets below are the individual steps.
- **Chainstate schema 4.** The transaction index is keyed on dense chain-order transaction ordinals (`tx_loc`, `txseq_txid`, `txseq_block`) instead of `txid -> block_hash`, replacing the `tx_index` column family. An ordinal carries the transaction's position within its block as well as the block, so `getrawtransaction` indexes into the block instead of scanning it for a matching txid. Existing datadirs need one `-reindex-chainstate`; pruned datadirs must resync. A node that runs neither `-txindex` nor `-addressindex` writes no more than before.
- **Chainstate schema 5.** Coins record the ordinal of the transaction that created them, and the confirmed-side spend index (`spent`) is keyed on it: 16 bytes per row instead of the 76 `outpoint_spend` took, with both 32-byte identifiers recovered through the ordinal map. Esplora's `/tx/:txid/outspends` now answers from one prefix scan rather than one point read per output. The AssumeUTXO caveat is unchanged and now enforced: a snapshot load marks the address and spend indexes incomplete, so those surfaces refuse rather than answering "unspent" for history the node does not have yet — that was previously reported as complete.
- **Chainstate schema 6.** Address funding rows key on the creating transaction's ordinal: 32 bytes a row instead of 64, on the largest-but-one family in a fully indexed chainstate. The documented iteration order is unchanged — the store resolves and sorts before a row leaves it — so Electrum's `listunspent`, `get_balance` and `get_history`, and Esplora's address endpoints, answer byte-for-byte as before.
- **Chainstate schema 7.** Address spending rows key on the spending transaction's ordinal and name the output they consumed by the funding transaction's: 32 bytes a row instead of 92, on the largest family in a fully indexed chainstate — it carried two 32-byte transaction identifiers. Spend-by-address stays a single prefix scan, and `getaddresshistory` still emits `prev_txid` and `prev_vout` on the wire.
- A missing cumulative transaction count for a block's parent is now a hard error at connect time instead of silently restarting the count at zero. It also fixes a long-standing defect: `-reindex-chainstate` dropped genesis' own row and never re-seeded it, so every `getchaintxstats` total after a chainstate rebuild was one short for the life of the datadir.
- `gettxoutsetinfo`'s `utxo_age_distribution` counts the `<1h`, `<1d`, `<1w` and `<1mo` buckets exactly, from a per-height window of the most recent 4320 heights kept beside the coins, and gains an `exact` field. Before, each 1000-block chunk went into one bucket by its midpoint, so `<1d` was always empty or held a whole chunk. The window is an additive metadata key: no schema step and no reindex; an existing datadir builds it with one background scan at startup, reporting `exact: false` until it lands.
- Esplora `POST /tx` needs `rpc:submit` (or `rpc:write`) on a bearer token, on top of `esplora:read`. `esplora:read` alone could broadcast before, which made "read" a misnomer once `rpc:submit` became the broadcast capability elsewhere. Operator credentials and the loopback default are unaffected.

### Added

- `-upgradechainstate=1` rebuilds the UTXO set from the block files by itself when the datadir's chainstate schema is older than the binary's, or a previous rebuild did not finish, and does nothing otherwise. Off by default; it never downgrades and refuses a pruned node. The app-store packages will turn it on, which is how an app-store node crosses the schema 3 → 7 change without a shell (#839).
- Every block template is checked before it is used, as Core's `CreateNewBlock` checks its own. A structural check (every consensus rule but script execution) runs on each template: `getblocktemplate` and the `generate` RPCs answer a failing one with `TestBlockValidity failed: <reason>`, and the Stratum server replaces it with a coinbase-only job. A full check through the node's own script verifier follows in the background on each new tip; a failure there switches every Stratum job to coinbase-only until a template passes again. A failure is logged with the reject reason and the offending transaction, counted in `satd_template_checks_total`, and raised as the new critical `template_invalid` alert (a new `status` kind on the streaming API, the webhook dispatcher and `-alertnotify`).
- `getstoragefootprint` and `sat-cli debug storage-footprint` report per-column-family SST bytes, live key estimates, bytes per key and pending compaction, so operators can see where a chainstate's disk goes without an offline `ldb` dump against a stopped node. The `chain_tx` column family was missing from the existing per-CF diagnostics and is now reported.
- `getmempoolsummary [top_n]`, a bounded aggregate view of the mempool: a vsize histogram over every transaction plus the `top_n` by ancestor feerate. Replaces `getrawmempool verbose` for callers that only render an aggregate — on a mainnet-sized mempool that reply is ~85 MiB and ~4 s of node CPU, against ~9 KB here.
- `-prune=1` is Bitcoin Core's spelling for *manual* pruning, and satd now implements it: prune mode with no budget, where the new `pruneblockchain` RPC is the only thing that ever deletes. `getblockchaininfo` reports such a node as pruned with `automatic_pruning: false` and no `prune_target_size`. satd refused the flag at startup before.
- `-fastprune`, Core's 64 KiB block-file size. Pruning deletes whole files, so a short test chain never crossed the 128 MiB boundary and a prune could delete nothing.
- A bearer-token capability for mempool submission, `rpc:submit`: `sendrawtransaction`, `submitpackage`, and the other methods the read-only listener classes as mempool-submit. A broadcaster's token can hold `rpc:read` + `rpc:submit` and never `stop` or `addnode`. `rpc:write` implies it, so existing tokens are unaffected.
- The metrics and health endpoints can be served over TLS on a second port (`-metricstlsbind`), with optional client certificates (`-metricsmtls`), so Prometheus can scrape a node across a network without a reverse proxy (#752).
- The appliance images are published as release assets, alongside the
  tarballs and signed with the same minisign key. They fit GitHub's 2 GiB
  per-asset limit — `qemu-img` compresses them during the build — so there is
  no separate download host and nothing to reassemble (#742).
- Appliance images for **arm64** as well as amd64, for Apple Silicon and
  arm64 servers. The arm64 desktop carries Sparrow only, since Electrum and
  Liana publish no arm64 build; its welcome page names what is installed
  (#742).
- Operator Manual: a new **Installing satd** chapter covering the Umbrel community store (`epochbtc/umbrel-apps`), the StartOS package (`epochbtc/satd-startos`), the appliance images, the container image and the tarballs; the README's quick start points at it.
- A status page on the metrics listener, `statuspage=1`: a single-page, self-refreshing `sat-tui` for a browser, with connection strings from `statusadvertise`. Off by default (#749).
- Streaming API: `Subscribe`/`Watch` responses carry `satd-version` and `satd-events-schema` gRPC headers; `STABILITY_POLICY.md` now states the SDK ↔ node compatibility rule.
- Rust SDK: warns when the node is one minor version behind, refuses two or more (`StreamError::NodeTooOld`, override `allow_old_node()`) and any schema mismatch (`StreamError::SchemaMismatch`); `StreamClient::node_version()`.
- Go SDK: the same check (`ErrNodeTooOld`, `WithAllowOldNode`, `ErrSchemaMismatch`, `WithLogger`, `Client.NodeVersion`); `Watch` now waits for response headers; the module is versioned with the node (`satdevents.Version`), next tag `clients/go/v0.6.0`.
- The Umbrel and StartOS packages open onto the status page, and the appliance turns it on; Umbrel publishes Esplora over TLS on 8431; the reference stack and the appliance serve metrics and the status page over native TLS on 9336 (#750).
- **Stratum V1 solo-mining server** (`--stratum=1`): miners connect to the node directly; the username is the payout address. Loopback by default, TLS/mTLS listener, refused on signet (#746).
- **Stratum V2** on the same server (`--stratumv2bind`): Noise NX transport, standard and extended channels, and an authority key persisted at `<datadir>/stratum_v2.key` so miners that pin it survive a restart (#748).
- Compact block reconstruction is observable: one `compact block reconstructed` log line per block (transactions prefilled, from the mempool, from the extra pool, requested; whether a round trip was needed) and `satd_net_compact_block_*` metrics. `-blockreconstructionextratxn` now works: replaced and policy-refused transactions are kept (default 100) so blocks containing them reconstruct without a round trip (#765).
- BIP 152 high-bandwidth compact block relay: satd selects up to three high-bandwidth peers, announces new blocks — including blocks found through the Stratum server — as `cmpctblock` before connecting them, and serves `MSG_CMPCT_BLOCK` and `getblocktxn` from a tip cache. Core's `p2p_compactblocks_hb.py` joins the functional run-set (#770).
- PSBT version 2 (BIP 370) on every PSBT method, carrying the BIP 375 silent payment fields losslessly. Core rejects any PSBT above version 0. `decodepsbt` gains a version 2 shape; `combinepsbt` refuses a conflicting value rather than picking one; `joinpsbts` refuses a silent payment PSBT that has committed to its input set.
- `createpsbt` accepts a silent payment address (`sp1…`) as an output key, with a new trailing `psbt_version=2`. `decodepsbt` and `analyzepsbt` spell the recipient back as its address. `createrawtransaction` refuses an `sp1…` key and says why a raw transaction cannot pay one.
- `sat-cli signpsbtwithkey` is a BIP 375 Signer: it computes the ECDH shares for the inputs it holds, proves them (BIP 374), derives the silent payment output scripts once every eligible input is covered, freezes the transaction, and only then signs. A partial run reports which inputs still owe a share and exits 2. `sat-cli signpsbtwithsigner` passes a version 2 PSBT to an external signer and verifies the reply. The node holds no keys.
- Send-side silent payments (BIP 375): `analyzepsbt` verifies the BIP 374 DLEQ proofs, binds each input's public key to the output it spends, cross-checks previous outputs against the UTXO set, recomputes every silent payment output script, and reports a per-output status; `finalizepsbt` refuses to extract a transaction whose silent payment outputs do not verify, with no override. The node stays keyless.
- Opt-in `cmpctblock` prefill (`-cmpctblockprefill`, `-cmpctblockprefillbytes`, default off / 8192 bytes): new blocks are announced with the transactions this node lacked prefilled, following Core's proposal #35558 (#772).
- `getmininginfo` reports `bits`, `target`, `blockmintxfee` and the next block's `height`/`bits`/`difficulty`/`target`; `getblock`, `getblockheader`, `getblockchaininfo` and `getchainstates` report `target`; on signet `getblockchaininfo` and `getmininginfo` report `signet_challenge`; `getprioritisedtransactions` reports `modified_fee`; `getmempoolentry` reports `wtxid`.
- **Stratum V2 Job Declaration** (`--stratumv2jd=1`), solo semantics: a miner declares its own transaction set from this node's mempool. New `getstratuminfo` RPC (#751).
- `getstratuminfo` lists each connected miner (device, difficulty, share counts, best share, last share, estimated hashrate) and a node-wide hashrate; the metrics endpoint exports `satd_stratum_*` connections, miners, shares by result, blocks found and hashrate.
- `-debug=stratum`: the Stratum server's per-miner debug lines (device, version-rolling mask, every share with the difficulty it achieved, a five-minute status line with estimated hashrate). Always logged: a disconnect summary per miner, and every refused share with its reason.
- A block found through the Stratum server is saved to `<datadir>/stratum/found/<height>-<hash>.hex` before it is submitted, so a block the node refuses, or a submission that panics, can still be sent to another node with `submitblock`.

### Fixed

- A pruned node in initial sync could stop for good. Pruning deleted a block file once the active-chain blocks in it were below the cut, but blocks are stored as they download, far ahead of the tip, so the file often also held blocks not yet connected; they went with it, and the node retried the next one's missing record forever (`failed to read stored block`). A file now goes only when every block stored in it is at or below the cut, as in Core.
- A stored block whose record was gone was retried forever, by the initial-sync connector and by the one that connects stored blocks at the tip: the index said the data was there, so nothing downloaded it again, and `getblockfrompeer`, the remedy the node logged, refuses a block above the tip in prune mode. The node now asks a peer for the block itself (at most every 10 s, a random peer each time), repairs the record through the `getblockfrompeer` route, and connects it. The error names the missing record instead of reporting a failed read as `block file write failed`.
- An interrupted `-reindex-chainstate` or `-reindex` no longer starts on the next run with a truncated UTXO set and indexes stamped complete, stuck at the height it reached. A marker written before the wipe makes a plain start refuse and name the flag that finishes the job (#839). Opening for a rebuild no longer drops the previous schema's column families before the rebuild starts, so a rebuild refused at startup leaves a datadir the previous release can still read.
- The metrics listener answers while the node starts, including through a `-reindex-chainstate` or `-reindex` rebuild that runs for hours on mainnet. It used to come up only after the chain state was loaded, so a scrape was refused, `/readyz` was connection-refused rather than 503, and the status page an app store opens onto was a closed port. Now `/healthz` is 200, `/readyz` is 503 `not ready: starting: <what the node is doing>`, `/metrics` carries `satd_build_info` and `satd_startup_*` gauges, and with `statuspage=1` the page shows **starting** or **rebuilding chainstate** with the rebuild's progress and ETA. The running node's listener takes the bound port over before the full RPC answers, so the port never closes in between. A metrics TLS certificate or bind problem now stops satd before the rebuild instead of after it (#841).
- `-blockmaxweight` is applied (#836). It was parsed and read nowhere, so every template filled to 4,000,000 WU. It now follows Bitcoin Core: a value above the consensus maximum stops the node with Core's message, one below the 8,000 WU coinbase reserve is raised to it, a package that would *reach* the cap is left out (`>=`, where satd refused only one that went past it), and a malformed value in `bitcoin.conf` stops the node instead of becoming the default. Selection gives up on a near-full block at Core v30's 4,000 WU margin rather than v29's reserve-sized one.
- **Consensus (signet):** default-signet block solutions are verified (#767). They never were, so a node on the default signet followed any block whose proof of work met signet's trivial target. Custom signets signed with Bitcoin Core's tooling verify too now: satd's BIP 325 `to_spend` transaction lacked the leading `OP_0`, so only solutions satd had signed itself ever passed (#837).
- **Consensus:** BIP 34 accepted a coinbase that pushed the right block height in a non-minimal encoding (padded, an unneeded sign byte, `OP_PUSHDATA1`, a data push for heights 1–16). Bitcoin Core requires the scriptSig to start with exactly `CScript() << height` and rejects those blocks as `bad-cb-height`, so satd would have followed a block the network rejects. The check now compares bytes, as Core does; Stratum Job Declaration applies the same rule to a declared coinbase.
- Block templates ranked each transaction by its own fee rate, so a child paying for a cheap parent (CPFP, a Lightning anchor, a zero-fee ephemeral-dust parent) waited behind the parent and was left out once middling transactions filled the block — on `getblocktemplate`, `generatetoaddress` and the Stratum server alike. Templates now use Bitcoin Core's ancestor-score package selection: a transaction is ranked by the fee rate of itself plus its unconfirmed ancestors, and the whole package goes in together.
- Block templates kept to the block weight limit but not the sigop limit, so a mempool dense in sigops (bare multisig outputs count 20 each) produced a template `connect_block` refuses as `bad-blk-sigops` — on `getblocktemplate`, `generatetoaddress` and the Stratum server alike, so a miner who found that block found nothing. Templates now reserve 400 sigop cost for the coinbase and leave out a transaction that would bring the total to 80,000, as Core does; `getblocktemplate` reports each transaction's `sigops`; and a Stratum V2 Job Declaration, or a custom job whose own coinbase outputs add sigops, is refused when the block it yields could exceed the limit.
- Esplora (plain and TLS) and `streamws` bounded nothing at the socket level and never closed an idle keep-alive connection: `-esploramaxconns` and `-streamwsmaxconns` are taken per request or inside the handlers, and `axum::serve` builds hyper without a timer, so a client that opened connections and never closed them was limited only by the process's file-descriptor table — the same failure the TLS RPC listener had (#813). Both surfaces now run the capped accept loop the RPC listeners use: a permit per socket taken at accept (`-esploramaxsockets`, `--streamws-max-sockets`, default 1024), an idle budget on keep-alive connections (`-esplorarequesttimeout` for Esplora, 30 s for streamws), and the TLS handshake on the connection's own task instead of inline in Esplora's accept loop, where one slow client stalled every other connection for the handshake budget; `-esploramaxsockets` is one cap shared by the plain and TLS listeners. The permit now travels with the socket, so an open WebSocket keeps its slot until it closes — on streamws and on the JSON-RPC listeners, which serve WebSocket too and released the slot at the upgrade. Every socket and connection cap is clamped to 100,000, so a mistyped value no longer panics satd at boot.
- A client that connected to a JSON-RPC listener and never sent a byte, or sent one byte of the HTTP/2 preface, held its connection slot forever, `-rpcservertimeout` notwithstanding: hyper's header timer is armed only once the protocol version has been sniffed from the first bytes, and such a socket never got that far; a client that started HTTP/2 unasked got a connection with no idle timeout at all. The JSON-RPC, Esplora and streamws listeners now serve HTTP/1.1 only, so the header timer covers a request head from its first byte. **Upgrade note:** a client using HTTP/2 prior knowledge against them must use HTTP/1.1; none of them offered HTTP/2 over TLS.
- A JSON-RPC batch, and a WebSocket on the JSON-RPC listener, are charged against a bearer token's `rate_limit` per call. The HTTP layer charged one unit per request before it could see the body, so a `1/s` token could carry any number of calls in one batch, or over one socket after the upgrade. A call over budget is answered in-band with `-32005` and `retry_after_secs`.
- The TLS RPC listener's connection cap (100, the same as the plain listener) counted in-flight handshakes only: the permit taken before the handshake was released as soon as the connection began serving, so established idle connections were uncounted and a keepalive flood could exhaust file descriptors and wedge the listener. The permit is now held until the connection closes, as the plain listener already did (#813). Follow-up: the cap and the `-rpcservertimeout=0` lockout trade-off are documented; a peer outside `-rpcallowip` no longer takes a connection slot — the allowlist is checked before the cap, and the peer is answered `403` and closed from a separate pool of 16 — so outsiders can no longer lock allowlisted clients out; an IPv4 client of a dual-stack `[::]` bind is matched as IPv4, where it missed every IPv4 entry and the loopback exemption; the TLS listeners (`-rpctlsbind`, `-rpcreadonlytlsbind`) enforce their allowlist (`-rpcallowip`, `-rpcreadonlyallowip`) at all, which they never did — a configured allowlist now drops a non-listed peer at accept, before the handshake and before it takes a connection slot, while an empty allowlist leaves a TLS bind reachable as before; and every listener that sheds at capacity logs the first five refusals a minute plus a suppressed count, instead of one warning per refused socket.
- A node could wedge behind its only peer instead of syncing. A peer in BIP 152 high-bandwidth mode announces new blocks with `cmpctblock` rather than `headers`, and that path did not record that the announcing peer held the block it announced. The node learned the headers, raised its download target, and then asked nobody for the data: the parallel download scheduler will not assign a peer heights above what it believes the peer has (Core's `UpdateBlockAvailability`; #770).
- The TUI's mempool panels showed stale data indefinitely against a mainnet-sized mempool. They were fed by `getrawmempool verbose`, whose reply exceeds the node's 20 MiB response cap at roughly 17,000 transactions, and the steady-state poll loop discarded RPC errors without surfacing them. The panels now read `getmempoolsummary`, and any method whose poll fails is named in the title bar (`rpc failing: <method>`) instead of silently leaving its panel frozen.
- JSON-RPC replies are no longer bound by the request-body cap. One 20 MiB constant governed both directions, so a reply whose size is set by the chain or the mempool — `getrawmempool verbose` crosses it at roughly 17,000 mempool transactions — was answered `-32008 Response is too big` where Bitcoin Core, which caps requests only, answers the call. The request cap is unchanged; responses are bounded separately at 256 MiB, derived from the default `-maxmempool` (#723).
- Compact block receive path hardened: a `cmpctblock`'s header is validated before the block is reconstructed, pending reconstructions and the record of which blocks were asked of a peer are bounded per peer and expire, a block being reconstructed is not also downloaded in full, and a merkle mismatch after reconstruction falls back to fetching the full block instead of penalising the peer (Core parity; #763).
- The Stratum server no longer drops a miner that is still hashing. Every connection used to be closed after 120 s without a message, and a miner sends nothing but shares, so even a miner at vardiff's 30 s target was dropped about every half hour, a miner with rarer shares far more often, and each one restarted at its lowest difficulty. An authorized miner may now go quiet for twenty expected share intervals (within 2 min to 1 day; a day before its rate is known). Connections that have not authorized still get 120 s. A Stratum V2 miner pointed at the V1 port is now named as such in the disconnect reason.
- Stratum vardiff no longer chases chance. It rescaled the difficulty every 90 s on about three expected shares, by up to ×4, so a miner on target wandered across a factor of 17 within an hour; it now moves only when the shares since the last change are significantly off target (with a looser test once 40 shares were expected, and a looser one still before a miner's first share), leaves a rate within 15% alone, and steps by at most ×8. In simulation 95% of settled miners hold within ×2 with at most two changes in five hours, where the old rule changed about 170 times across a median ×17. Slow "lottery" miners (ESP32-class, ~1 MH/s) at the default difficulty were closed by the idle limit before vardiff could lower them and restarted at 10,000, so they never submitted; they now reach difficulty 1 in about twelve minutes and are not dropped. The idle limit is no longer shortened by vardiff lowering a quiet miner's difficulty.
- Stratum work follows a tip the node reached through block download. Those blocks connect without a chain event, so work stayed on the old tip for up to 30 seconds after a node caught up — long enough for a Job Declaration client to be refused (#763).
- The `tip_stall` alert no longer fires during a long initial sync. Its clock was advanced only by chain events, and the block-download path connects without emitting any, so it measured time since process start: every mainnet IBD raised a critical alert an hour in and held it for the rest of the sync, on a node connecting blocks as fast as it could. The clock now follows the polled tip as well. A node wedged mid-sync still pages (#814).
- `preciousblock` was a stub that acknowledged the call and did nothing. It now works as Core's does, and equal-work tips are ordered by the order their data became connectable (Core's `nSequenceId`) rather than by block hash.

- A rejected script now says *which* script rule it broke, as Bitcoin Core does: `mempool-script-verify-flag-failed (Non-canonical DER signature)` rather than a generic `ERR_SCRIPT`, and `testmempoolaccept`'s `reject-details` names the input it failed on. A block that fails to connect logs Core's `Block validation error: <reason>` line.

- A `pong` now answers for everything the peer sent ahead of the `ping`, as Bitcoin Core's does. satd answered `ping` on the peer's socket task while `block` and `tx` travelled a queue to the manager and on to the block processor, so a peer that used `send_and_ping(block)` — the standard way to wait for a block, and what Core's own test framework does — got the pong before the block was connected.

- `-maxtipage` is honoured: a tip older than it keeps the node in initial block download. It was parsed and ignored.
- With no `-rpcbind`, the RPC server listens on `::1` as well as `127.0.0.1`, as Core does; a malformed `-rpcbind` port, an empty or malformed `-rpcauth`, and a cookie file that cannot be written stop startup with Core's messages; `-norpcauth`, `-norpccookiefile`, bracketed IPv6 in `-rpcallowip`, `-cjdnsreachable`'s allowlist rule and Core's `-noX=0` double negative are accepted.
- An expired mempool transaction now takes its descendants with it, and `-mempoolexpiry` is applied whenever a transaction is accepted, as in Core, rather than on a 30-second timer; a child of an expired parent used to stay in the pool.
- `generatetoaddress`, `generatetodescriptor` and `generateblock` work on every chain, as in Core, instead of only regtest.
- Blocks mined by the node's RPCs always carry the witness commitment, as Core's do; an empty block on a custom signet was rejected `bad-signet-blksig` for lack of it.
- `-rpcservertimeout` in `bitcoin.conf` was ignored (the command-line flag worked), so every RPC connection used the 30-second default and a client idle longer than that was disconnected.
- `-peertimeout` is implemented: a handshake that does not finish within it is dropped with Core's reason, on the node clock. satd bounded each handshake step by `-timeout`, Core's socket-connect budget.
- `getblocktemplate` honours `longpollid`: the call waits for a new tip or a mempool change instead of returning at once.
- Core's handshake rules: an outbound peer lacking the desired service flags is dropped, as is a connection to ourselves; pre-handshake messages are logged. New log lines for connections, bans, RPC dispatch, mutated blocks and transaction rejections.
- A peer that announces headers the node cannot connect yet is no longer ban-scored, as in Core. A node syncing from a peer that was still mining could reach the ban threshold in half a second and disconnect its only block source, stopping the sync dead.
- The P2P loop no longer waits out its 500 ms tick when the peer-message queue is still full, which had capped every inbound path — initial block download most of all — at 64 messages per tick.
- `invalidateblock` now moves the node's header tip off the invalidated branch, as Core's `RecalculateBestHeader` does, and `reconsiderblock` lets it back. `reconsiderblock` also clears the marks *below* the block it is given, as Core does: reconsidering the tip of an invalidated branch used to leave the path back to the fork still marked, so the branch could never reconnect. `getblockchaininfo` reported a `headers` height on the refused branch — one the node would never reach, growing with every block mined on it (#778).
- A full mempool raises a rolling minimum fee (Core's `mempool min fee not met`), reported as `getmempoolinfo.mempoolminfee` and advertised to peers in `feefilter`; `sendrawtransaction` and `testmempoolaccept` rejections use Core's `reason, detail` message; `getrawmempool` accepts `mempool_sequence=true`.
- P2P follows Core's rules for v2 transport detection and `addnode v2transport`, `feefilter` sending, protocol-violation disconnects (`-blocksonly`, block-relay-only, BIP 37 filters, unpermitted `mempool`), ping timing on the node clock, per-message byte counts for the version handshake, and Core's message log lines; a 4 MB message over v2 is no longer refused, and IBD asks a peer only for blocks it has announced.
- A signet block with an invalid solution is rejected as `bad-signet-blksig` (Core's reason) rather than `bad-signet-solution`; `-signetchallenge` given twice is refused, and a non-hex value is reported in Core's words.
- A node that mined its own chain, and so had never been sent a header by a peer, counted itself as still in initial block download and ignored every transaction its peers announced. It now takes them (#759).
- `verificationprogress` in `getblockchaininfo` and `getchainstates` is Bitcoin Core's transaction-count estimate, equal to Core's; it was the tip's timestamp over the current time and read 0.69 at genesis (#744).
- An appliance image can be built around a published release. The
  `--satd-source release` path asked for
  `satd-<version>-x86_64-linux-gnu.tar.gz`, a target triple and compression
  format the release has never used, so it always 404'd; released images now
  carry the signed release binary rather than a rebuild (#742).
- The appliance boot test waits for satd to finish starting instead of asking
  `systemctl is-active` once. The single call raced the unit and failed a
  release build with a diagnostic that showed the service running (#742).
- The Umbrel package takes its own host ports (8430, 8433, 8436, 8439, 50012), so it installs beside Bitcoin Node, Fulcrum and Ride The Lightning, and its backups leave the chain out (#743).
- The StartOS package's backups skip the AssumeUTXO background chainstate, and its sync check no longer reports `verificationprogress`, which read about 69% at genesis (#743).
- `getblocktemplate` now carries the retargeted difficulty at a retarget boundary (and after a testnet 20-minute gap) instead of the tip's bits, and reports `mintime` as median time past + 1 instead of `curtime` (#746).
